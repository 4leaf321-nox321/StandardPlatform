# 작업 워커 설계 — 파일을 올리고 받는 일을 요청 밖으로

> 작성 2026-09-20 · 결정 셋(작업 파일은 DB · 가져오기는 늘 작업 · 사람 확정은 그대로)은 사용자와 합의한 것.

## 1. 왜

파일을 올려 바꾸는 것이 이 플랫폼의 **일반적인 쓰임**이 된다. 지금은 올린 파일을 요청 안에서 처리한다 —
객체 1만 1천 개 미리 보기가 44초였고(계획 문서의 리허설), 브라우저 · MCP 클라이언트는 1–2분에서 끊는다.
그래서 5,000행 상한(`bulk.MAX_ROWS`)이 있고, 계획과 적용에 **같은 파일을 두 번** 올려야 하며, 앱을
재시작하면 하던 일이 어디까지 됐는지 아무 데도 안 남는다.

```
브라우저 · MCP ──POST /api/jobs──▶ jobs 표 ◀──집는다── <slug>-worker (A 와 B 각 한 대)
                ◀─GET /api/jobs/{id}─┘                    │
                                                           ├─ 진행률을 표에 쓴다(다른 연결)
                                                           └─ 결과 파일을 표에 넣는다
```

## 2. 원칙

1. **요청은 짧게, 일은 표에.** 오래 걸리는 일은 `jobs` 행 하나가 되고 요청은 `job_id` 만 돌려준다(202).
2. **파일은 한 번만 올린다.** 계획도 적용도 같은 `job_files` 행을 읽는다. 두 번 올리게 하면 두 파일이
   다를 수 있고 그 차이는 아무 데도 안 뜬다.
3. **미리 보기 → 사람 확정 → 적용은 그대로.** 워커는 사람 단계를 빼는 게 아니라 기다리는 자리를 옮긴다.
   적용은 계획의 **지문**이 같을 때만 — 미리 본 뒤 다른 사람이 무엇을 바꿨으면 거절하고 다시 보게 한다.
4. **한 작업은 전부 아니면 무.** 진행률은 보이되 반만 들어간 상태는 없다 — 본 트랜잭션은 하나고,
   진행률은 **다른 연결**로 쓴다.
5. **가져오기는 늘 작업이다.** 작은 파일은 바로, 큰 파일만 뒤에서 — 그런 두 길은 두지 않는다. 길이
   둘이면 고장도 두 가지로 나고 화면 동작이 어느 길로 갔느냐에 따라 달라진다. 작은 파일은 어차피
   1초 안에 끝난다.

## 3. 결정 — 작업 파일은 DB 에 둔다

서버가 A · B 두 대다. 올린 파일이 A 의 디스크에 놓이면 B 의 워커가 못 읽는다. 공용 폴더(설치 때 묻는
「공용 스토리지 폴더」)는 아직 없고, 있어도 다른 사업장이라 느리다. 작업 파일은 **7일 뒤 지우는
임시물**이라 `job_files.data`(bytea)에 넣으면 스트리밍 복제로 따라가고 어느 대가 집어도 된다.
상한 `JOB_FILE_MAX_BYTES`(기본 100MB). 첨부(`attachments`)는 그대로 filestore 다 — 그것은 영구물이고
공용 폴더의 몫이다. 저장 계층은 `jobs/files.py` 하나라 공용 폴더가 생기면 거기만 바꾼다.

## 5. 워커

`python -m app.worker` — 앱과 같은 SIF · 같은 `.env`. systemd `<slug>-worker.service`, A · B 에 하나씩.

- **집기**: `SELECT … FROM jobs WHERE status='queued' ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1`.
  두 대가 같은 행을 두 번 안 집는다. 자문 잠금은 안 쓴다 — 그건 「한 대만」 이고 이건 「나눠서」 다.
- **심장박동**: 30초마다 `worker_heartbeats.last_seen` 과 `jobs.heartbeat_at`. `running` 인데 심장박동이
  `WORKER_STALE_SECONDS`(300) 넘게 없으면 다른 워커가 `queued` 로 되돌린다(`attempts+1`, 3번까지, 그 뒤 `failed`).
- **진행률**: 처리 200행마다 다른 세션으로 `progress` 를 쓴다. 본 트랜잭션은 열려 있다.
- **취소**: `cancel_requested` 를 단계 사이에서 본다. 트랜잭션 중간이면 롤백.
- **오류**: `AppError` 는 문구 그대로 `error` 에, 그 밖의 예외는 로그에 스택 · `error` 에는 한 줄.
- 한 워커는 한 번에 하나(`WORKER_CONCURRENCY`, 기본 1). 폴링 간격 2초, 비어 있으면 5초까지 늘린다.

## 6. API

| | |
| --- | --- |
| `POST /api/jobs` (multipart `kind` · `params`(JSON) · `file`) | 202 + 작업. 파일이 필요한 종류인데 없으면 422 |
| `GET /api/jobs` · `GET /api/jobs/{id}` | 내 것 · 내 부서 것. 시스템 관리자는 전부 |
| `POST /api/jobs/{id}/apply` | 계획 작업 → 적용 작업(같은 파일 · 같은 지문 · `parent_id`) |
| `POST /api/jobs/{id}/cancel` | `queued` 면 바로 `cancelled`, `running` 이면 `cancel_requested` |
| `GET /api/jobs/{id}/download` | 결과 파일 |

`POST /api/objects/{type}/import` · `…/relations/import` 는 위의 얇은 껍데기 — 작업을 만들고 202 로 돌려준다.
`import-rows`(JSON 행, MCP)는 5,000행 상한을 둔 채 동기로 남긴다 — MCP 도구를 작업으로 옮기는 것은 4단계.

## 7. 순서

1. **함** (09-20) — 표 · 워커 뼈대(집기 · 심장박동 · 복구 · 진행률) · `objects_import` · `relations_import` ·
   API · 「작업」 화면 · 가져오기 대화상자의 진행 막대 · systemd 유닛. 화면에서 **계획을 펼쳐 읽고
   적용**한다 — 대화상자를 닫아도 계속된다고 해 놓고 돌아와 적용할 자리가 없으면 그 말은 절반만
   참이다(계획 표는 대화상자와 **같은 것**을 쓴다 — `objects/ImportPlanTable.tsx`).
2. **함** (09-20) — `bundle_import` · 내보내기(`objects_export` · `relations_export` · `bundle_export`,
   결과 파일은 `job_files` 에 두고 `download` 로). 행 상한 10만. 정제 도구는 202 를 받아 기다린다.
3. **함** (09-20) — `<slug>-sync.timer` 는 `datasource_sync` 작업을 넣기만 하고 워커가 돈다(시킨 사람
   없는 작업 — `allow_system`). 아직 안 끝난 같은 작업이 있으면 안 넣는다. 화면 · MCP 의 「동기화」 도 작업.
4. **함** (09-20) — MCP: `objects_import` · `relations_import` · `bundle_import` 가 계획 작업을 돌려주고
   (작은 것은 그 호출 안에 끝난다), `job_status` · `job_apply` · `jobs_list`. **AI 의 적용은 `job_apply`
   로만** — 도구에서 `apply=true` 를 없앴다. 쓰기 방어가 한 겹 더 두꺼워졌다.
5. **한 대 안에서 함** (09-20, 아래 「리허설에서 본 것」) — 워커 둘이 나눠 집는지, `kill -9` 뒤
   되살아나는지. **남은 것은 두 서버**: A 에 올린 파일을 B 의 워커가 집는지(파일이 DB 에 있으니
   돼야 한다), `update` 중 하던 작업이 어떻게 되는지.

### 리허설에서 본 것 (2026-09-20, 시험 DB · 진짜 워커 프로세스)

| 해 본 것 | 결과 |
| --- | --- |
| 워커 **둘**을 띄우고 500행짜리 작업 6개 | **3 : 3 으로 나눠 집었다.** 같은 작업을 두 번 집은 것 없음(`attempts` 전부 1), 전부 `done`, 진행률 500/500 까지 남음. 미리 보기라 객체는 0개 — 아무것도 안 남았다 |
| 2만 행 작업을 돌리던 워커를 **`kill -9`** | 그 작업은 `running` 인 채로 남는다(18,000/20,000 에서 멎음). 다른 워커가 심장박동이 멎은 것을 보고 `queued` 로 되돌렸고(`attempts` 2), 2만 행을 **처음부터 다시** 돌려 `done`. 시작부터 끝까지 81초 |

되돌릴 때 **처음부터 다시 돈다** — 이어서 하지 않는다. 계획은 원래 매번 새로 세우고(그 사이에 남이
바꿨을 수 있다), 적용은 한 트랜잭션이라 반쯤 들어간 상태가 없기 때문이다.

`WORKER_STALE_SECONDS` 를 10초로 낮춰 확인했다. 운영 기본값은 300초다 — 짧으면 잠깐 느린 워커의
작업을 남이 뺏는다.

### 지문은 쓰기 전에 본다 — 실측

`apply_objects` 는 끝에서 스스로 커밋한다. 처음엔 적용 뒤에 지문을 견줬고, 시험이 잡았다 — 거절은
됐는데 값은 이미 들어가 있었다. 그래서 `before_apply`(파일) · `before_commit`(묶음) 훅을 두어 **새 계획을
쓰기 전에** 본다.

## 7b. 쌓이는 것과 알리는 것 (2026-09-21)

- **기록도 치운다.** 워커가 한 시간마다 파일(7일)과 **끝난 작업 기록**(30일, `JOB_TTL_DAYS`)을
  지운다. 도는 것은 안 지운다 — 멎은 작업은 워커가 되살릴 몫이고, 지우면 그 일이 있었다는
  사실까지 사라진다. 타이머가 소스마다 5분에 한 줄이라 **하루 288행**이 쌓인다.
- **목록은 기본이 「내가 시킨 것만」.** 종류 · 상태로도 거른다. 안 그러면 사람이 올린 작업 한 줄이
  타이머의 288줄 사이에 파묻힌다.
- **오래 걸린 것만 알린다**(`JOB_NOTIFY_AFTER_SECONDS`, 기본 20초). 1초에 끝난 것까지 알리면
  그때 사람은 아직 그 화면을 보고 있었고, 본 것을 한 번 더 말하는 종은 잡음이 된다. 타이머가
  넣은 작업은 시킨 사람이 없어 저절로 빠진다.

### 홈이 말한다 (2026-09-21)

「작업」 화면을 열어야만 아는 것은 **아무도 제때 모른다** — 그 화면은 평소에 안 연다. 그래서
홈의 「남은 일」(`register_maintenance`)에 셋을 올렸다:

| 줄 | 누구에게 | 왜 |
| --- | --- | --- |
| 읽고 적용하기를 기다리는 계획 | 시킨 사람 | 알림을 놓치면 며칠 뒤 「그때 그거 안 들어갔네」 가 된다 |
| 실패한 내 작업 | 시킨 사람 | 실패는 조용하다 |
| 작업 워커가 살아 있지 않습니다 | 시스템 관리자(기다리는 작업이 있을 때만) | 워커가 죽으면 **가져오기도 웹훅도** 멎는다 |

계획 작업의 `applied` 는 영영 거짓이다(적용은 **새 작업**이다) — 그것만 보면 적용하고 나서도
홈이 계속 조른다. 그래서 **적용 작업이 걸린 계획은 빼고** 센다.

서버 화면의 「쌓인 것」 에는 작업 수 · 살아 있는 워커 수 · 작업 파일(개수와 MB)을 올렸다.
작업 파일은 DB 에 들어 있어서, 안 보여 주면 덤프가 왜 커졌는지 물을 자리가 없다.

### 웹훅도 워커가 보낸다 (2026-09-21)

전에는 앱 프로세스 안의 데몬 스레드가 보내고 `threading.Timer` 로 재시도했다. **새는 것은
없었지만** 셋이 아쉬웠다:

1. 앱을 재시작하면 보내던 것과 재시도 타이머가 함께 사라진다 — 밀린 것이 **다음 이벤트가 올
   때까지** 안 나갔다.
2. uvicorn 워커 넷이 각자 스레드를 띄우고 자문 잠금으로 셋이 물러난다.
3. 「지금 뭐가 도는가」 가 웹훅 화면에만 있다.

이제 `on_events` 는 보낼 기록을 남기고 **작업 한 줄**(`webhook_dispatch`)을 넣는다 — 이미
기다리는 작업이 있으면 안 넣는다(백 건을 고친 날 작업이 백 줄이 되면 안 된다). 재시도는 워커가
`RETRY_AFTER_SECONDS` 마다 남은 pending 을 보고 작업을 다시 넣는다 — 표에 남으니 재시작해도
살아난다.

**대가**: 워커가 없으면 웹훅도 안 나간다. 전에는 앱만 살아 있으면 나갔다. 그래서 워커는
「있으면 좋은 것」 이 아니라 앱과 함께 떠 있어야 하는 것이 됐다(`deploy.sh` 가 함께 깐다).

## 8. 남은 것

- 공용 폴더가 생기면 `job_files.data` 를 거기로(3장).
