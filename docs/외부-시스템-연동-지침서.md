# 외부 시스템 ↔ Standard Platform 연동 지침서 (초안)

**읽는 사람:** 상대 시스템(MatNexus · TestScope · ReportArchive · Standard Platform 쌍둥이)을
만드는 개발자. 이 문서 하나만 보고 양방향 연동을 만들 수 있게 적었다 — Standard Platform(이하
**SP**)의 코드를 보지 않아도 된다.

**초안이다.** 「정해야 할 것」 절에 아직 안 정한 것을 모아 두었다. 그 답을 받으면 확정본이 된다.

---

## 0. 30초 요약

| 방향 | 무엇을 | 누가 만드나 |
| --- | --- | --- |
| 그쪽 → SP | SP 가 **주기적으로 읽어 간다** | 그쪽이 읽기 API 하나(§3) |
| SP → 그쪽 | 그쪽이 **주기적으로 읽어 간다** | SP 는 이미 있다. 그쪽은 받는 코드만(§4) |
| SP → 그쪽 (즉시) | 바뀐 순간 알림 | 그쪽이 수신구 하나(§4.4). 선택 |
| 그쪽 → SP (밀어넣기) | 그쪽이 SP 에 직접 넣는다 | SP 는 이미 있다. 선택(§5) |

**형식은 하나다.** SP 가 쓰는 묶음 형식(`sp-bundle/1`, §6) 을 양쪽이 그대로 쓴다. 시스템마다
형식을 만들고 어댑터로 잇기 시작하면, 어댑터는 n² 로 늘고 **둘 중 하나만 고쳐진 날** 조용히
틀린 데이터가 흐른다.

## 1. 말 맞추기

| 말 | 뜻 | 예 |
| --- | --- | --- |
| **타입**(type) | 표 하나. `slug` 로 부른다 | `supplier`, `material` |
| **속성**(property) | 타입의 칸. `key` 로 부른다 | `grade`, `melting_point` |
| **관계 종류**(relation type) | 객체 사이의 선. `slug` 로 부른다 | `supplied_by` |
| **객체**(object) | 타입의 한 행 | 「ACME」 공급사 |
| **식별자**(key) | 객체를 가리키는 **안 바뀌는 문자열** | `ACME-001` |
| **별칭**(alias) | 같은 것을 부르는 다른 이름 | 「앤시스」 ↔ 「Ansys」 |
| **묶음**(bundle) | 정의 + 객체 + 관계를 담은 JSON 하나 | §6 |
| **작업**(job) | 오래 걸리는 일. 넣고(202) 나중에 결과를 받는다 | §4.2 |

---

## 2. 원칙 다섯

1. **형식은 하나** — `sp-bundle/1`. 그쪽 내부 모델이 달라도 **경계에서만** 이 모양으로 낸다.
2. **식별자는 그쪽이 정하고, 절대 바꾸지 않는다.** 바뀌는 순간 SP 는 그것을 「새것」 으로 보고
   하나를 둘로 만든다. 자동 증가 정수여도 좋고 UUID 여도 좋다 — **안 바뀌기만 하면 된다.**
3. **지우지 말고 사용 중지로 보낸다**(`status: "deprecated"`). 받는 쪽에는 그것을 가리키는
   참조가 이미 있고, 행이 사라지면 그 참조는 빈 칸이 된다.
4. **시각은 ISO-8601 UTC** — `2026-09-22T01:23:45Z`. 로컬 시각·오프셋 없는 문자열은 받지 않는다.
5. **미리 보기 → 적용.** 넣는 길에는 언제나 「무엇이 바뀌는지 먼저 보는」 단계가 있다. 자동
   연동이라도 처음 몇 번은 사람이 그 표를 본 뒤 켠다.

## 3. 그쪽이 만들 것 ① — SP 가 읽어 갈 API

SP 에는 **데이터 소스**라는 장치가 있다. 주기마다 바깥 JSON 을 읽어 우리 타입의 행으로 바꾸고,
칸 대응·값 대응·다시 찾기·미리 보기까지 SP 가 한다. **그쪽이 만들 것은 읽기 엔드포인트 하나뿐이다.**

### 3.1 모양

```
GET  {base_url}/{path}?page=1&page_size=500
Authorization: Bearer {토큰}
Accept: application/json
```

응답:

```json
{
  "items": [
    {
      "id": "ACME-001",
      "name": "ACME 정밀",
      "country": "KR",
      "grade_code": "A",
      "is_active": true,
      "updated_at": "2026-09-22T01:23:45Z"
    }
  ],
  "total": 1234,
  "page": 1,
  "page_size": 500
}
```

### 3.2 규칙

| 규칙 | 왜 |
| --- | --- |
| 항목은 **평평한 객체**(중첩 금지, 값은 문자열·숫자·불리언·null) | 중첩을 펴는 규칙을 양쪽이 따로 만들면 갈린다. 중첩이 꼭 필요하면 그쪽에서 `owner_name` 처럼 펴서 낸다 |
| 항목마다 **안 바뀌는 식별자**를 한 칸에 | §2-2 |
| 항목마다 `updated_at` (ISO-8601 UTC) | 언제 것인지 모르면 되돌릴 수도, 늦은 것을 버릴 수도 없다 |
| 지운 것은 **행을 빼지 말고** `is_active: false` 또는 `deleted: true` 로 | §2-3 |
| 열 이름은 안 바꾼다. 늘리는 것은 자유 | SP 의 칸 대응이 열 이름에 물려 있다 |
| 같은 요청은 같은 답 (정렬 고정) | 쪽 넘김 중에 순서가 바뀌면 행이 빠지거나 겹친다 |
| 목록은 **전량**을 낼 수 있어야 한다 | 첫 연동과 정합성 점검은 전량 대조로 한다 |

### 3.3 쪽 넘김 — 셋 중 하나만 고르면 된다

| 방식 | 요청 | 끝나는 조건 |
| --- | --- | --- |
| `page` | `?page=1&page_size=500` | 받은 행이 `page_size` 보다 적으면 끝 |
| `offset` | `?offset=0&limit=500` | 같음 |
| `cursor` | `?cursor=xxx&page_size=500` | 응답의 `next` 가 비면 끝 |

SP 는 셋 다 읽는다. 파라미터 이름이 다르면(예: `perPage`) **그쪽 이름을 알려 주기만 하면 된다** —
SP 쪽 설정에 적는다. 고칠 코드는 없다.

### 3.4 인증

넷 중 하나. **SP 는 비밀을 화면에 다시 보여 주지 않는다.**

| 방식 | 보내는 것 |
| --- | --- |
| `bearer` | `Authorization: Bearer {토큰}` |
| `basic` | `Authorization: Basic {base64}` |
| `header` | 임의 헤더 — 예 `X-API-Key: {값}` |
| `none` | 폐쇄망 안에서만 |

토큰은 **읽기 전용**으로 발급해 준다. 연동이 쓰기를 할 일은 이 방향에 없다.

### 3.5 OData · 파일도 된다

그쪽이 이미 OData v2/v4 를 내고 있으면 그대로 붙는다(엔티티 셋·`$filter`·`$select`·쪽 넘김을
SP 가 안다). CSV · Excel · JSON 파일을 공유 폴더나 URL 로 떨구는 방식도 된다. **새로 만들 때만**
§3.1 을 쓰면 된다.

### 3.6 SP 쪽에서 하는 일 (참고)

그쪽이 보낸 열을 SP 의 칸에 잇는 것은 SP 화면에서 한다:

```
id          → key
name        → label
grade_code  → properties.grade   값 대응: {"A": "1등급", "B": "2등급"}
country     → properties.country
```

표에 없는 코드가 오면 **그 행은 오류**로 세워 둔다(조용히 통과시키면 고를 값이 오염된다). 그래서
**코드 목록이 늘면 미리 알려 줘야 한다** — §12.

## 4. 그쪽이 만들 것 ② — SP 에서 받아 가기

SP 는 **이미 다 있다.** 그쪽은 받는 코드만 쓰면 된다. 셋 중 필요한 것만 고른다.

### 4.1 토큰 받기

SP 관리자가 그쪽에 **개인 접근 토큰(PAT)** 을 발급한다. 모든 요청에 붙인다:

```
Authorization: Bearer standardplatform_pat_xxxxxxxxxxxx
```

범위(scope)는 셋이다. **받아만 가면 `read` 하나면 된다** — 내보내기도 읽기로 친다.

| 범위 | 할 수 있는 일 |
| --- | --- |
| `read` | 읽기 전부 + 내보내기 |
| `objects:write` | 객체·관계 넣기·고치기 |
| `ontology:write` | 정의(타입·속성·관계 종류) 바꾸기 |

### 4.2 길 ① 타입 하나를 쪽 단위로 (가장 간단)

```
GET /api/objects/{type_slug}?limit=200&offset=0
```

```json
{
  "items": [
    {
      "id": "0f2c...",
      "type_slug": "supplier",
      "key": "ACME-001",
      "label": "ACME 정밀",
      "description": "",
      "properties": { "grade": "1등급", "country": "KR" },
      "ref_labels": { "3a1e...": "탄소강" },
      "aliases": ["앤시스"],
      "external_ids": { "erp": "V-100" },
      "status": "active",
      "owner_workspace_slug": "hq",
      "owner_workspace_name": "본사",
      "valid_from_year": null,
      "valid_to_year": null,
      "created_at": "2026-01-02T03:04:05Z",
      "updated_at": "2026-09-01T00:00:00Z"
    }
  ],
  "total": 1234, "limit": 200, "offset": 0
}
```

주의 두 가지:

- **참조 칸의 값은 UUID 다.** 사람이 읽을 이름은 같은 응답의 `ref_labels` 에 `{UUID: 이름}` 으로
  따로 온다. 그쪽이 이름을 저장할 것이면 여기서 꺼낸다.
- `total` 을 믿고 `offset` 을 끝까지 돌린다. 한 쪽의 상한은 서버가 강제한다 — 기본 50, 최대 200.

### 4.3 길 ② 파일로 통째 (큰 타입)

큰 타입은 쪽을 돌리지 말고 파일로 받는다. **작업**이라 세 걸음이다.

```bash
# 1) 넣는다 — 202 와 작업 id
curl -sX POST "$SP/api/objects/supplier/export?format=json" -H "Authorization: Bearer $TOKEN"
# {"id":"9d1f...","status":"queued",...}

# 2) 될 때까지 본다 — status 가 done 이 될 때까지 몇 초 간격으로
curl -s "$SP/api/jobs/9d1f..." -H "Authorization: Bearer $TOKEN"

# 3) 받는다
curl -s "$SP/api/jobs/9d1f.../download" -H "Authorization: Bearer $TOKEN" -o supplier.json
```

- `status` 는 `queued` · `running` · `done` · `failed` · `cancelled`.
- `failed` 면 `error` 에 이유가 한 줄로 온다.
- 목록과 **같은 거르개**를 쿼리로 붙일 수 있다 — `?status=active&p.grade=1등급`.
- 관계는 `POST /api/objects/{type_slug}/relations/export?format=json`.

### 4.4 길 ③ 정의까지 통째 (쌍둥이용)

SP 쌍둥이처럼 **같은 구조를 그대로 받는** 경우에는 묶음을 받는다.

```bash
curl -sX POST "$SP/api/bundles/export" -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' -d '{"group":"plm"}'
# → 작업. 4.3 과 같은 방식으로 받는다. 받은 JSON 이 §6 의 묶음이다.
```

받은 묶음을 그대로 자기 SP 에 넣으면 정의·객체·관계가 한 번에 선다(§5).

> 정의까지 받으려면 시스템 관리자 토큰이 필요하다 — 부서를 가리지 않고 전부 나가기 때문이다.

### 4.5 즉시 알림이 필요하면 — 웹훅 수신구 (선택)

주기 폴링으로 충분하면 안 만들어도 된다. 「바뀐 순간」 이 필요하면 엔드포인트 하나를 연다.

```
POST {그쪽 주소}
Content-Type: application/json; charset=utf-8
X-Event: object.changed
X-Delivery-Id: 6b2f...
X-Signature-256: sha256=9f86d0...
User-Agent: standard-platform-webhook
```

```json
{
  "id": "6b2f...",
  "event": "object.changed",
  "at": "2026-09-22T01:23:45Z",
  "actor": { "label": "홍길동", "client": "web", "token": null },
  "target": { "table": "object_instances", "id": "0f2c...", "label": "ACME 정밀", "type_slug": "supplier" },
  "workspace_id": "1a2b..."
}
```

받는 쪽 규칙:

1. **서명을 확인한다** — `X-Signature-256` 은 `"sha256=" + HMAC-SHA256(secret, 원문 바이트)`.
   비교는 상수 시간 비교 함수로. 서명이 다르면 401 로 돌려보낸다.
2. **2xx 를 빨리 돌려준다.** 본문은 안 봐도 된다. 느리면 SP 쪽 재시도가 쌓인다.
3. **같은 것이 두 번 올 수 있다.** `X-Delivery-Id` 를 저장해 두고 이미 본 것은 버린다.
4. **이 알림에는 값이 없다.** 「무엇이 바뀌었다」 만 온다 — 받으면 §4.2/4.3 으로 끌어가 확인한다.
   값을 실어 보내면 받는 쪽마다 다른 시점의 값을 갖게 된다.
5. 실패하면 SP 가 세 번까지 다시 보낸다. 그 뒤에는 SP 화면에서 사람이 다시 보낸다.

## 5. 그쪽이 SP 로 밀어 넣기 (선택)

읽어 가는 쪽으로 충분하면 안 해도 된다. 그쪽이 「내가 보낼 때 보내겠다」 면 이 길이다.

```bash
# 1) 미리 보기 — 아무것도 저장하지 않는다
curl -sX POST "$SP/api/bundles/import" -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' \
     -d '{"source":"matnexus","apply":false,"objects":[{"type_slug":"supplier","rows":[...]}]}'
# → 202, 작업 id

# 2) 계획을 본다 — 행마다 create · update · unchanged · error
curl -s "$SP/api/jobs/{id}" -H "Authorization: Bearer $TOKEN"

# 3) 넣는다 — 같은 파일, 같은 지문
curl -sX POST "$SP/api/jobs/{id}/apply" -H "Authorization: Bearer $TOKEN"
```

- `apply: true` 로 한 번에 보내도 된다. 그때도 **전부 아니면 무**다 — 한 행이 오류면 아무것도 안 들어간다.
- `source` 는 그쪽 시스템 이름(소문자·숫자·`-`·`_`, 40자 이내). 이것이 있어야 「그쪽이 관리하는
  것」 으로 표시되고, SP 화면에서 사람이 손대는 것을 막는다 — 안 막으면 다음 동기화가 그 수정을
  말없이 덮어쓴다.
- 정의(`ontology`)가 든 묶음은 `ontology:write` 범위가 더 필요하다.

## 6. 묶음 형식 — `sp-bundle/1`

```json
{
  "format": "sp-bundle/1",
  "group": "plm",
  "exported_at": "2026-09-22T01:23:45Z",
  "ontology": { "groups": [...], "types": [...], "relation_types": [...] },
  "objects":  [ { "type_slug": "supplier", "workspace_slug": null, "rows": [ ... ] } ],
  "relations":[ { "type_slug": "part", "rows": [ ... ] } ],
  "counts": { "types": 4, "objects": 1200, "relations": 300 },
  "warnings": []
}
```

넣을 때는 `ontology` · `objects` · `relations` · `source` · `apply` 만 쓴다. 나머지는 무시된다.
**셋 중 하나만 보내도 된다** — 객체만 보내려면 `ontology` 를 아예 빼면 된다.

### 6.1 정의 (`ontology`)

| 자리 | 필수 칸 | 자주 쓰는 칸 |
| --- | --- | --- |
| `groups[]` | `slug`, `label` | `icon`, `sort_order`, `is_active` |
| `types[]` | `slug`, `label` | `nav_group_slug`, `parent_slug`, `key_policy`, `description`, `properties[]` |
| `types[].properties[]` | `key`, `label`, `data_type` | `required`, `multi`, `unit`, `enum_options`, `ref_type_slug`, `help`, `default_value`, `unique` |
| `relation_types[]` | `slug`, `label`, `src_type_slugs`, `dst_type_slugs` | `inverse_label`, `directed`, `cardinality` |

`data_type` 은 열 중 하나: `text` · `text_long` · `number` · `date` · `datetime` · `bool` ·
`enum` · `url` · `object_ref` · `file`.
`enum` 이면 `enum_options` 가, `object_ref` 면 `ref_type_slug` 가 있어야 한다.
파일 칸(`file`)은 **묶음으로 오가지 않는다.**

**보낸 칸만 바뀐다.** 안 적은 칸은 그대로 둔다 — 그래서 일부만 보내도 안전하다.

### 6.2 객체 행 (`objects[].rows[]`)

고정 칸 + 속성 키를 **한 평면**에 적는다.

```json
{
  "key": "ACME-001",
  "label": "ACME 정밀",
  "description": "",
  "aliases": "앤시스;ANSYS",
  "status": "active",
  "valid_from_year": 2024,
  "valid_to_year": null,
  "grade": "1등급",
  "material": "SS400"
}
```

| 칸 | 규칙 |
| --- | --- |
| `key` | 있으면 이것으로 찾아 **고친다**(upsert). 없으면 `label` 로 찾는다 |
| `label` | 필수. 사람이 읽는 이름 |
| `status` | `active` · `deprecated`. **지우지 말고 `deprecated`** |
| `aliases` | 여러 개는 `;` 로 |
| 속성 | 속성 `key` 를 열 이름으로. 여러 값도 `;` 로 |
| 참조 속성 | **상대 객체의 `key`**(없으면 이름)를 적는다. UUID 를 적지 않는다 |
| 값 비우기 | 빈 문자열은 「안 보냄」 이다. **지우려면 `\null`** 을 적는다 |
| 한 덩이 | 한 배치 5,000행. 넘으면 배치를 나눠 적는다 |

`objects` 는 **적은 차례대로** 들어간다. 다른 타입을 참조하는 타입은 그 뒤에 둔다.

### 6.3 관계 행 (`relations[].rows[]`)

```json
{ "src": "PART-1", "relation": "supplied_by", "dst": "ACME-001", "evidence_note": "계약서 3.2" }
```

- `type_slug` 는 **출발 타입**이다. `src` 는 그 타입의 객체여야 한다.
- `src` · `dst` 는 상대의 `key`(없으면 이름·별칭). 이름이 여럿에 맞으면 그 행은 오류다.
- 관계에 붙은 속성은 이 형식으로 오가지 않는다.

---

## 7. 공통 규약

| 것 | 규약 |
| --- | --- |
| 시각 | ISO-8601 UTC, `Z` 붙임. `2026-09-22T01:23:45Z` |
| 날짜 | `2026-09-22` |
| 불리언 | JSON `true`/`false`. 문자열이면 `true/1/y/yes/예/참/o` 를 참으로 읽는다 |
| 숫자 | JSON 숫자. 단위는 값에 섞지 않는다(`"12 mm"` ✗, `12` ✓ — 단위는 정의에 있다) |
| 빈 값 | `null` 또는 생략 = 「안 보냄」. **지우기는 `\null`** |
| 여러 값 | `;` 로 이어 적는다 |
| 인코딩 | UTF-8. CSV 로 주고받을 일이 있으면 BOM 없이 |
| 대소문자 | `slug` · `key` 는 **그대로** 비교한다 |

## 8. 오류

SP 의 오류는 언제나 같은 봉투다.

```json
{ "error": { "code": "APP-OBJECTS-0046", "message": "「ACME」 식별자가 2개 타입에 있습니다.",
             "request_id": "3f2c...", "details": {} } }
```

- **`message` 를 그대로 사람에게 보여 준다.** 우리말 한 줄로 「무엇이 왜 막혔나」 가 들어 있다.
- `request_id` 를 로그에 남긴다 — SP 쪽 로그와 맞대 볼 때 이것으로 찾는다.
- 재시도: `5xx` 와 네트워크 오류만. `4xx` 는 다시 보내도 같다(`429` 는 예외 — 기다렸다 한 번 더).
- `401` · `403` 이면 토큰이나 범위 문제다. 내보내기가 403 이면 §4.1 의 범위를 확인한다.

## 9. curl 자가 점검

그쪽이 만든 것이 맞는지 **SP 없이** 확인하는 순서다.

```bash
BASE=https://your-system.example.com
TOKEN=...

# 1) 인증 없이 부르면 막히나 (막혀야 한다)
curl -si "$BASE/api/suppliers?page=1&page_size=2" | head -1        # → 401

# 2) 첫 쪽이 오나
curl -s "$BASE/api/suppliers?page=1&page_size=2" -H "Authorization: Bearer $TOKEN" | jq .

# 3) 행이 있는 자리가 언제나 같나 (items 든 data 든 하나로 고정)
curl -s ... | jq '.items | length'

# 4) 식별자가 비어 있지 않나
curl -s ... | jq '[.items[] | select(.id == null or .id == "")] | length'   # → 0

# 5) 두 번 부르면 같은 순서인가
diff <(curl -s "...page=1" | jq -r '.items[].id') \
     <(curl -s "...page=1" | jq -r '.items[].id')                    # → 차이 없음

# 6) 마지막 쪽이 덜 차나 (끝을 알 수 있나)
curl -s "...page=999" | jq '.items | length'                          # → 0

# 7) 지운 것이 행으로 남아 있나
curl -s "..." | jq '[.items[] | select(.is_active == false)] | length' # → 0 이 아니어야 정상
```

SP 쪽으로 받아 가는 것은 §4.3 의 세 줄을 그대로 돌려 보면 된다.

## 10. 자주 틀리는 것

1. **식별자를 바꾼다** — 시스템 개편 때 코드 체계를 갈아엎으면 SP 에 같은 것이 둘 생긴다. 바꿔야
   하면 **먼저 알려 주고**, 옛 식별자를 별칭으로 남긴다.
2. **지운 행을 목록에서 뺀다** — SP 는 「안 온 것」 과 「지운 것」 을 구별할 수 없다. §2-3.
3. **참조를 UUID 로 적는다** — 묶음에서는 상대의 `key` 를 적는다. UUID 는 설치마다 다르다.
4. **빈 문자열로 지우려 한다** — 빈 값은 「안 보냄」 이다. 지우기는 `\null`.
5. **쪽 넘김 중에 정렬이 바뀐다** — 행이 빠지거나 두 번 온다. 정렬을 식별자로 고정한다.
6. **시각에 타임존이 없다** — 「어제 것」 인지 「오늘 것」 인지 못 정한다.
7. **새 코드값을 말없이 늘린다** — SP 의 고를 값에 없는 코드는 그 행을 오류로 만든다. §12.
8. **웹훅 본문의 값을 그대로 저장한다** — 알림은 「바뀌었다」 는 신호다. 값은 끌어가서 확인한다.
9. **웹훅을 동기로 오래 처리한다** — 큐에 넣고 2xx 를 먼저 돌려준다.
10. **쓰기 토큰으로 읽기만 한다** — 받아만 가면 `read` 로 충분하다. 넓은 토큰은 사고의 크기를 키운다.

## 11. 체크리스트

**그쪽 → SP (§3)**

- [ ] 읽기 엔드포인트 하나 (JSON, 평평한 항목)
- [ ] 안 바뀌는 식별자 · `updated_at` · 사용 중지 표시
- [ ] 쪽 넘김 한 가지 + 마지막 쪽을 알 수 있음
- [ ] 읽기 전용 토큰 발급
- [ ] §9 의 7가지 점검 통과
- [ ] 열 이름 목록과 코드값 목록을 문서로 전달

**SP → 그쪽 (§4)**

- [ ] SP 관리자에게 `read` 토큰 받기
- [ ] 타입별로 §4.2 또는 §4.3 중 하나 구현
- [ ] `total` 을 끝까지 도는 반복문 (또는 작업 폴링)
- [ ] 오류 봉투의 `message` · `request_id` 로그
- [ ] (선택) 웹훅 수신구 + 서명 확인 + 멱등 처리

## 12. 정해야 할 것 (초안이라 비워 둔 자리)

| # | 물음 | 기본안 |
| --- | --- | --- |
| 1 | 어느 타입을 주고받나 | 시스템마다 목록을 표로 확정 |
| 2 | 주기는 | 하루 1회 야간. 즉시성이 필요한 타입만 웹훅 |
| 3 | 충돌하면 누가 이기나 | **보내는 쪽이 이긴다.** 받는 쪽은 그 타입을 화면에서 잠근다 |
| 4 | 코드값 목록이 늘 때 | 늘리는 쪽이 **먼저** 알린다. 절차를 정한다 |
| 5 | 증분 | SP 목록 API 에는 아직 `changed_since` 가 없다. 지금은 전량 스냅샷 + 웹훅 신호. **SP 쪽 할 일로 잡혀 있다** |
| 6 | 첫 적재 | 전량 한 번 → 대조 → 주기 켜기 |
| 7 | 연락 | 양쪽 담당자와, 막혔을 때 볼 로그 자리 |
