### 1.1 뼈대 — 대상 × 수단 = 연계, 연계마다 축

    부문(sector)   시뮬레이션 · 검증 자동화 · 설계 자동화 · 디지털 스레드 · 모니터링 · 공장 최적화
      대상(subject)  시험 항목 (부문마다 다르다 — 설계 업무 · 공정 · 연계 구간 …)
      수단(agent)    시뮬레이션 (부문마다 다르다 — 자동화 수단 · 수집 수단 …)
        연계(pair)   대상 × 수단
          평가        연계 × 축 한 줄 = 칸(rung) 또는 값(value) + 근거 + 근거 등급 + 이력

**한 엔진, 부문별 척도 세트.** 부문을 더하는 일이 「부문 한 줄 + 척도 한 벌」 로 끝나야
한다는 것이 원본 설계의 요점이다. 부문마다 코드를 가르면 전사 요약에서 숫자가 두 번
만들어진다.

### 1.2 시뮬레이션 부문의 축 다섯 (1차 이식 대상)

| 축 | 종류 | 무엇을 받나 |
| --- | --- | --- |
| 정확도 | **값**(%) | 시험과의 일치 수준. **칸은 사람이 안 고른다** — 값이 문턱을 넘으면 올라간다 |
| 자동화 | **묶음** | 전처리 · 실행 · 후처리 · 보고 · 파이프라인을 따로 켠다. 서열은 켠 개수 |
| 모델링 수준 | **표** | 불량 유형 × 재현 수준 |
| 적용 범위 | **칸** | 어디까지 적용됐나 |
| 시험 대체 | **묶음** | 시험을 얼마나 대신하나 |

축의 종류가 다섯이다(`rung` · `value` · `set` · `matrix` · `step`/`lever`). **이 다섯을
지키는 것이 이식의 핵심**이다 — 「단계 하나 고르기」 로 단순화하면 정확도가 값과 칸으로
갈려 둘이 되고, 자동화는 선후 없는 항목에 억지 서열이 생긴다.

### 1.3 기반 조사 — 역량을 떠받치는 조건

축은 전부 **결과**를 잰다. 조건이 안 보이면 낮은 수준이 「못한다」 로만 읽히고, 사업부는
자료를 방어적으로 적는다. 그래서 옆에 세운다.

- **사람(FTE)** — 한 사람은 1.0 이고 여러 줄에 나오면 각 줄이 1/n 이다. **투입률을 사람이
  적지 않는다**(퍼센트를 받으면 합이 사람 수를 넘는다). 셈은 코드가 한다.
- **S/W** — 툴별 라이선스 카피 수, 전사 공유 여부(공유는 전사 합에서 한 번만 센다).
- **H/W** — 자원별 CPU·RAM·GPU. **물성 데이터** — 종수 하나.
- **이름은 화면에 안 나간다** — 가명(담당 A·B)이 기본이고, 실명은 사무국과 그 사업부를
  고칠 수 있는 사람에게만. 보고본 스냅샷에는 아예 안 들어간다.

### 1.4 「가상 검증률」 은 여기가 아니다 — 갈래가 둘이다

말이 섞이기 쉬운 자리라 먼저 못박는다.

| | 역량 축 (`dev_dt_maturity`) | DX KPI (`dx_kpi_management`) |
| --- | --- | --- |
| 재는 것 | 이 시험 × 이 시뮬레이션이 **어디까지 왔나** | 사업부가 보고하는 **지표 값** |
| 예 | 정확도 · 자동화 · 적용 범위 | **가상 검증률** · One Time Pass율 · 시험 Lead Time |
| 정본 | 이 시스템(평가 이력) | **사업부 엑셀** — 시스템은 옮겨 담는 자리 |

원본은 둘을 **일부러 안 잇는다**(정의 파일에 「DX KPI 와 무관하다. 가상 검증률을 읽지도
쓰지도 않는다」 가 적혀 있다). 같은 「정확도」 라는 말을 쓰지만 계산이 다르기 때문이다 —
이으면 언젠가 누가 이 표를 보고 KPI 를 고친다. **이식도 갈래를 유지한다**(§9-3).

## 4. 자료를 어디에 두나 — 온톨로지와 전용 표를 가른다

이 플랫폼에는 이미 **온톨로지**(정의를 바꾸는 일이 배포가 아니다)와 **전용 표**(아플 때
내려가는 길, `docs/승격-경로.md`)가 있다. 둘을 이렇게 가른다.

| 것 | 어디 | 왜 |
| --- | --- | --- |
| **대상**(시험 항목 · 설계 업무 · 공정) | **온톨로지 타입** | 별칭 · 외부 식별자 · 부서 소유 · 일괄 입력 · 내보내기 · **코어 공개**(형제 플랫폼이 가져간다)가 이미 있다. 전용 표로 두면 이 여섯을 다시 만든다 |
| **수단**(시뮬레이션 · 자동화 수단) | **온톨로지 타입** | 같다. 이미 개발 설치에 `sim_tool` 이 있다 |
| **연계 · 평가 · 이력 · 근거** | **확장 전용 표** | 모양이 고정이고(축 정의는 코드), 유일성(연계×축)과 이력이 DB 보장을 요구한다. JSONB 로 두면 집계 질의가 전부 JSONB 를 탄다 |
| **라운드 · 스냅샷 · 검토 · 제안** | 확장 전용 표 | 보고 회차의 동결이라 값이 바뀌면 안 된다 |
| **기반 조사(사람 · S/W · H/W)** | 확장 전용 표 | 사람 줄은 실명이 있어 노출 규칙이 따로다 — 온톨로지에 두면 일반 목록 화면에 실린다 |
| **부문 · 축 · 척도 · 문턱** | **코드 상수** | 정의가 두 곳이면 둘이 갈린다. 문구만 나중에 설정으로 뺀다 |

**어느 타입을 대상·수단으로 쓸지는 설정으로 고른다.** 확장이 타입 slug 를 코드에 박으면
설치마다 다른 이름을 쓸 수 없고(형제 플랫폼마다 다르다), 온톨로지를 고치는 순간 확장이
깨진다. 그래서 확장 설정에 「대상 타입 · 수단 타입」 을 지정하는 칸을 둔다.

**객체가 병합되면 평가가 따라간다.** 평가는 객체 uuid 를 들고, 객체가 다른 것에 병합되면
(`merged_into`) 이긴 쪽으로 옮긴다 — 코어 API 가 이미 같은 규칙을 쓴다. 안 옮기면 평가가
사라진 객체를 가리키고, 그 손실은 **집계 숫자에서만** 드러난다.

## 5. 단계 — 쓸 수 있는 것이 매 단계 끝에 선다

| 단계 | 산출물 | 판단 기준(다음으로 가는 조건) |
| --- | --- | --- |
| **0. 범위 합의** | 첫 부문(시뮬레이션) · 축 다섯 문구 확정 · 대상·수단 타입 설계 · 원본 자료 표본 확보 | 사업부 한 곳의 실제 시험 20건으로 화면 없이 표를 채울 수 있나 |
| **1. 뼈대** | 확장 `dtwin` · 그룹 「디지털 트윈」 · 정의 상수 · 연계·평가 표 · 평가 화면 하나 · 감사 | 시험 × 시뮬레이션 하나에 축 다섯을 매기고 이력이 남나 |
| **2. 읽는 화면** | 사업부 현황(부문 × 부서 타일) · 축별 분포 · **커버리지** 집계 · 값 축의 문턱 환산 | 사업부 담당이 자기 화면에서 「무엇이 안 채워졌나」 를 아나 |
| **3. 기반 조사** | 사람(FTE 1/n 셈) · S/W · H/W · 물성 · 가명 규칙 · 실명 열람 권한 | 전사 FTE 합이 사람 수를 넘지 않나(공유 자원 중복 제거 포함) |
| **4. 보고 회차** | 라운드 · 스냅샷(동결) · 사무국 검토(표본) · 수정 제안 | 지난 회차 숫자가 지금 자료를 고쳐도 안 바뀌나 |
| **5. 자료 이식** | 원본 → 매핑표 → 일괄 입력 · 전용 가져오기 · 대조 보고 | 원본 건수 · 축별 분포가 옮긴 뒤와 같나 |
| **6. 넓히기** | 둘째 부문(검증 자동화 또는 디지털 스레드) · 코어 공개 · 필요하면 KPI 갈래 | 부문 추가가 「부문 한 줄 + 척도 한 벌」 로 끝났나 |

**1~2단계가 이 이식의 값어치 대부분이다.** 3단계부터는 원본에서도 나중에 붙은 층이라,
쓰면서 정하는 편이 낫다.

## 7. 자료 이식 (5단계 상세)

1. **원본에서 뽑는다** — 포털 DB 에서 대상 · 수단 · 연계 · 평가 · 이력 · 기반 조사를 JSON
   으로. 포털에 내보내기 API 가 있으면 그것을 쓰고, 없으면 읽기 전용 접속으로 한 번 뽑는다.
2. **매핑표를 만든다** — 포털의 `division_id`(정수) → 이 플랫폼의 부서 slug, `user_id`
   (정수) → 계정 email. **계정이 없는 사람이 많다**(협력사 · 타 법인) — 이름으로 맞추고,
   못 맞춘 줄은 「계정 없음」 으로 남긴다. 조용히 버리면 FTE 가 줄어든다.
3. **넣는다** — 대상 · 수단은 온톨로지 일괄 입력(식별자 = 포털 uuid 를 외부 식별자로 보존).
   연계 · 평가 · 기반은 확장의 전용 가져오기(미리 보기 → 적용).
4. **대조한다** — 건수 · 축별 분포 · 부서별 커버리지를 원본과 맞댄다. **먼저 대조하고
   주기를 켠다** — 대조 전에 켜면 틀린 대응이 이력에 쌓인다.

## 8. 위험

| 위험 | 어떻게 막나 |
| --- | --- |
| 축을 단순화하고 싶어진다 | 값 축과 칸이 갈리면 정확도가 둘이 된다. **다섯 종류를 그대로 옮긴다** |
| 실명이 화면에 실린다 | 기본은 가명. 실명은 사무국 · 그 부서 편집 권한자만. 스냅샷에는 없음 |
| FTE 합이 사람 수를 넘는다 | 투입률을 받지 않는다. 1/n 은 코드가 셈한다. 공유 자원은 전사 합에서 한 번 |
| 객체 병합 · 사용 중지로 평가가 뜬다 | `merged_into` 를 따라 옮기고, 사용 중지된 객체의 평가는 목록에서 흐리게 둔다(지우지 않는다) |
| 원본이 계속 자란다 | 이식은 **한 방향 한 번**이다. 옮긴 뒤에는 이쪽이 정본 — 양쪽을 동기화하면 둘 다 정본이 아니게 된다 |
| 범위가 부문 여섯으로 번진다 | 1차는 시뮬레이션 하나. 둘째 부문은 6단계에서, 첫 부문이 실제로 쓰인 뒤에 |

## 9. 정해야 할 것

1. **첫 부문** — 시뮬레이션으로 시작하는 데 동의하나(원본도 그것만 완성했다).
2. **부서 구분** — 포털의 사업부(MX · VD · DA · NW · 의료기기 …)를 이 플랫폼의 부서로
   그대로 옮기나, 아니면 다른 조직 기준인가.
3. **DX KPI 갈래** — 가상 검증률 같은 사업부 지표도 이 확장에 담나, 아니면 역량 축만 먼저
   하나(권함: 역량 축 먼저. §1.4 의 이유로 표를 섞지 않는다).
4. **대상·수단 타입** — 이미 있는 `sim_tool` 을 수단으로 쓰나, 새로 만드나. 대상(시험 항목)
   은 어느 이름으로 두나.
5. **원본 자료 접근** — 포털 DB 를 직접 읽을 수 있나, 아니면 엑셀 내보내기만 받나.
   (`디지털트윈 대시보드.xlsx` 같은 파일이 원본 폴더에 있다)
6. **이름** — 확장 이름 `dtwin` · 그룹 「디지털 트윈」 으로 가나.
