# 이중화 배포 설계 — 서버 두 대 · HTTPS · 자동 전환

> 작성 2026-09-16 · 결정은 사용자와 합의한 것, 「남은 것」 은 아직 미정.

## 1. 목표 구성

```
사용자 / 포탈 ──HTTPS──▶ 웹 VIP 10.252.39.140 (keepalived)
                             │  VIP 를 가진 서버의 nginx 가 받는다
             ┌───────────────┴───────────────┐
       서버 A 10.252.39.146            서버 B 10.252.39.138
       keepalived  MASTER              keepalived  BACKUP
       nginx :443 (TLS 종단) ──┬──── nginx :443 (TLS 종단)      설정 동일, 양쪽 앱으로 분배
       앱 :8040 · MCP :8042    │      앱 :8040 · MCP :8042      둘 다 활성
       PostgreSQL 16 주 ── 복제 ──▶  PostgreSQL 16 대기          로컬 디스크, 스트리밍 복제
       DB VIP (미정, 예 .141) ─┘                                 keepalived 가 주를 따라 옮긴다
             └──────── /data/<공통폴더>/<slug>/ ────────┘       다른 사업장(느림): 첨부 · 백업 · 인증서 · 공유 설정
```

- **앱은 활성-활성.** 로드밸런서(nginx)가 나눠 주고, 한 대가 죽으면 나머지가 다 받는다. 세션 고정은
  필요 없다(로그인은 JWT + DB 의 리프레시 토큰).
- **DB 는 쓰는 곳 하나.** 두 앱 모두 DB VIP 로 주에 쓴다. 동시 편집은 지금(워커 4개)과 같이 DB
  트랜잭션이 세운다 — 앱끼리의 조정은 없다.
- **DB 는 로컬, 백업만 `/data`.** `/data` 는 다른 사업장에 있어 느리므로 DB 원본을 두지 않는다. 대기
  DB 가 B 에 실시간 복제본으로 있고, 매일 덤프를 `/data/…/backup/` 에 보낸다(사업장 재해 대비).
- **여러 플랫폼이 같은 호스트명**(`hwax.sec.samsung.net`)에 **경로로** 붙는다 —
  `https://hwax.sec.samsung.net/<slug>/`. 플랫폼 이름(`APP_SLUG`)이 곧 경로 · 설치 폴더 · 유닛 이름 ·
  DB 이름이다.

## 5. 전환과 원복 (요약)

- **장애 전환(자동)**: keepalived 감시가 A 의 주 DB 접속 실패를 N 회 확인 → B 승격(`db-promote`) →
  DB VIP 를 B 로. 앱은 VIP 만 보므로 설정 변경 없음. 마지막 몇 초 유실 가능.
- **원복(사람)**: ① A 를 B 의 대기로 재구성(`db-standby --from B`) — 중단 없음, 여기서 멈춰도 된다
  (주가 B 인 채로 운영). ② 굳이 A 를 주로 되돌리려면 계획 전환 — B `db-demote` → A `db-promote` →
  B `db-standby --from A` — 수십 초 중단, 유실 0.
- **스플릿 브레인 방지**: 승격 시 「주는 B」 표시를 남기고, A 는 부팅해도 주로 못 뜬다(6번).
