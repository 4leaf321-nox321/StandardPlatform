# 데이터 온톨로지화 계획 — 원천 데이터를 AI 로 정제해 넣는 길

사내 한 그룹이 하는 일의 데이터를 **객체 · 속성 · 관계**로 구조화해 이 플랫폼에 넣고, 플랫폼을
복사해 그룹 · 조직마다 같은 방식으로 온톨로지화하려 한다. 이 문서는 그 일을 위해 **무엇을
만들어야 하는지**의 목록과 순서다. 아직 계획이다 — 만든 것은 [설계 문서](온톨로지-메타모델-설계.md)
에, 쓰는 법은 [사용자 안내서](사용자-안내서.md) 에 옮겨 적는다.

> 작성 2026-09-13 · 기준 릴리스 v0.1.2

## 1. 왜 원천을 MCP 로 바로 넣지 않나

원천 데이터를 AI 가 곧바로 MCP 도구로 넣으면 **그룹마다 AI 가 매번 다른 판단을 한다.**

- 같은 것이 **다른 타입 · 다른 이름 · 다른 식별자**로 들어간다. 그러면 복사본끼리 연결하거나
  합칠 수 없다.
- 다시 넣을 때마다 식별자가 흔들려 **같은 것이 둘씩 생긴다.**
- 무엇이 왜 그렇게 들어갔는지 **근거가 남지 않아**, 틀린 것을 찾아도 어디서 틀렸는지 모른다.

그래서 **「규칙 → 중간 결과물 → 검증 → 적재」** 를 한 벌로 만들어 두고, AI 는 그 틀 안에서만
일하게 한다. AI 가 하는 일은 제안과 추출이고, **확정은 사람이, 적재는 플랫폼의 계획 → 적용이**
한다.

```
원천(파일·시스템·문서)
  │  ⑤ 인벤토리 · ⑥ 파싱(결정적 코드)
  ▼
정규화된 조각
  │  ⑦ 스키마 제안(AI, 규약·코어 참조) → ⑧ 사람 확인 → 정의 적용
  │  ⑨ 인스턴스 추출(AI+코드) · ⑩ 개체 해소(동의어 사전)
  ▼
중간 결과물 묶음 (정의 · 객체 행 · 관계 행 · 출처 · 미해결)
  │  ⑪ 넣기 전 검증 · ⑬ 한 번에 미리 보기
  ▼
⑫ 플랫폼 적재 (계획 → 적용)  →  품질 점검
```

## 2. 이미 있는 것 — 파이프라인의 끝단으로 쓴다

새로 만들지 않는다. 아래는 이미 플랫폼에 있고, 파이프라인이 **마지막에 부르는 자리**다.

| 필요한 일 | 플랫폼에 있는 것 |
| --- | --- |
| 정의 넣기 | 온톨로지 가져오기 — 계획과 **조용히 잃는 것(경고)** 을 먼저 보이고 적용, 되돌릴 이력(스냅샷) |
| 표에서 정의 초안 | 표에서 타입 만들기(`ontology/inference.py`) — 열을 보고 종류를 **보수적으로** 추론(애매하면 글자) |
| 객체 · 관계 대량 적재 | 파일로 넣기 — 같은 식별자면 고침(upsert), **한 행이라도 오류면 전부 안 들어감**, 한 번에 5000행 |
| 같은 것을 다르게 부름 | 별칭(사람이 붙인 이름 + 바깥 시스템 식별자 `source:<slug>`), 객체 합치기 |
| 적재 후 점검 | 데이터 품질 — 필수값 빈 것 · 고아 · 끊긴 참조 · 이름 중복 |
| 시스템 원천 주기 동기화 | 데이터 소스 — OData · REST · 파일, 칸 대응, 사라진 것은 사용 중지 |
| 정의 고치기 | 고를 값 이름 바꾸기, 고를 값 → 참조 타입 승격 |
| AI 연결 | MCP 도구 18개 + 서버가 쥔 사용 가이드(`get_guide`) |
| 사람 입력 · 되돌리기 | 화면 입력, 변경 이력과 그 시점으로 되돌리기, 여럿 고치기와 묶음 되돌리기 |

**빠진 것은 그 앞단 전부다.** 무엇을 타입으로 할지 정하는 규칙, AI 가 만든 결과를 담아 검증할
형식, 그 결과가 맞는지 재는 기준.

## 3. 만들 것

### 3.1 공통 기반 — 모든 복사본이 함께 쓴다

**① 모델링 규약 문서.** AI 와 사람이 같은 기준으로 판단하게 한다. 지금 MCP 가이드는
**도구를 어떻게 부르나**만 말하고, **무엇을 무엇으로 만드나**는 말하지 않는다.

- 타입 · 속성 · 관계를 가르는 기준 — 「고를 값」 과 「다른 타입 참조」 와 「관계」 는 언제 무엇인가
- 식별자 규칙 — 원천의 식별자를 쓰나, 만들어 붙이나. **다시 돌려도 같은 값이 나오는 규칙**
- 이름 규칙(slug · 표시 이름), 여러 값 칸과 관계 중 무엇을 쓰나
- 연도 · 유효기간 정책(`temporal_kind`), 부서 소유 원칙
- 플랫폼의 제약 — 조건 · 통계는 **한 걸음**까지만 이어진 것을 본다. 두 걸음 물음이 자주 나오면
  칸이 하나 빠진 것이다

**② 공통 코어 온톨로지.** 모든 그룹이 공유하는 상위 타입과 관계 종류 — 과제 · 문서 · 설비 ·
제품, 사람 · 부서 연결, 「담당」 「사용」 「산출」 같은 관계. 그룹마다 따로 만들면 나중에 조직을
가로질러 잇거나 합칠 수 없다. **그룹은 코어를 확장만 한다** — 코어의 slug 를 바꾸지 않는다.

**③ 중간 결과물 형식.** AI 가 만든 결과를 플랫폼에 넣기 전에 담는 파일 묶음이다.

- **새 형식을 만들지 않는다.** 이미 있는 가져오기 형식 — 정의 JSON(`ontology_import`), 객체 행
  (`objects_import`), 관계 행(`relations_import`) — 을 그대로 쓴다. 따로 만들면 변환기가 하나 더
  생기고, 둘은 언젠가 갈린다.
- 여기에 둘을 덧붙인다: **출처**(원본 파일 · 행 · 페이지, 추출 근거, 확신도)와 **미해결 목록**
  (AI 가 확신하지 못한 것).
- 사람 검토 · 재실행 비교 · 감사가 전부 이 묶음 위에서 이뤄진다.

**④ 평가 세트(골든 셋).** 파일럿 그룹의 데이터 일부를 **사람이 직접** 구조화한 정답. 규약이나
프롬프트를 바꿀 때마다 AI 결과를 여기에 대어 **나빠졌는지** 본다. 이것 없이는 「AI 가 잘
만들었나」 를 판단할 방법이 없다.

### 3.2 전처리 파이프라인 — AI 가 따라가는 단계

| 단계 | 누가 | 무엇 |
| --- | --- | --- |
| ⑤ 인벤토리 | 사람 + 스크립트 | 어떤 파일 · 시스템 · 문서가 있나, 형식 · 소유자 · 갱신 주기 |
| ⑥ 파싱 · 정규화 | **결정적 코드** | Excel · CSV · 문서 · PDF → 표 · 텍스트 조각. 같은 입력이면 늘 같은 출력이어야 뒤 단계를 비교할 수 있다 |
| ⑦ 스키마 제안 | AI | 원천 샘플 + 규약(①) + 코어(②) → 「코어의 어디에 붙이고 무엇을 새로 만드나」. 표면 플랫폼의 열 추론을 먼저 돌려 초안으로 |
| ⑧ 정의 확정 | 사람 | 온톨로지 가져오기 계획의 경고를 보고 판단 → 적용 |
| ⑨ 인스턴스 추출 | AI + 코드 | 원천 → 객체 · 속성 · 관계 행. **식별자를 매번 같게 만드는 규칙**이 핵심 |
| ⑩ 개체 해소 | AI + 사람 | 「Ansys」 「ANSYS Inc.」 「앤시스」 → 식별자 하나 + 별칭들. **동의어 사전**은 그룹이 키워 가는 자산이다 |
| ⑪ 넣기 전 검증 | 코드 | 정의에 맞나 · 참조가 풀리나 · 필수값 · 미해결 목록이 비었나 |
| ⑫ 적재 · 점검 | 플랫폼 | 계획 → 적용(관계에는 근거), 데이터 품질로 고아 · 중복 확인 |

### 3.3 플랫폼 보강 — 틀에 더할 것

| | 무엇 | 왜 |
| --- | --- | --- |
| ⑬ | **정의 · 객체 · 관계 한 번에 미리 보기** | 지금은 정의를 **적용해야** 객체 계획을 볼 수 있다. 중간 결과물 묶음 전체를 넣지 않고 「넣으면 어떻게 되나」 를 한 번에 — 검토 단계의 핵심 |
| ⑭ | **출처를 담을 자리** | 관계에는 근거 칸(`evidence_note`)이 있지만 객체에는 「원본 어디서 왔나」 의 표준 자리가 없다. 공통 속성 규약으로 할지 플랫폼 칸으로 할지 정한다 |
| ⑮ | **사람이 고친 값 보호** | 파일로 넣기는 같은 식별자면 **덮어쓴다.** 원천을 다시 정제해 넣으면 사람이 화면에서 고친 값이 사라진다 — 덮지 않거나 충돌로 따로 보인다 |
| ⑯ | **복사본 찍어내기 자동화** | [새 플랫폼 만들기](새-플랫폼-만들기.md) 는 지금 손으로 한다(이름 · slug · 포트 · DB). 그룹이 여럿이면 slug 와 이름만 넣어 만든다 |
| ⑰ | **코어 온톨로지 전파** | 코어가 바뀌면 모든 복사본에 같은 정의를 계획 → 적용하는 절차 |
| ⑱ | **MCP 가이드 「모델링」 주제** | ①~③ 을 AI 가 `get_guide(topic="modeling")` 로 읽는다 — 가이드는 서버가 쥐므로 복사본마다 최신이다 |

### 3.4 이후 갱신 — 경로를 셋으로 가른다

| 경로 | 상태 | 필요한 것 |
| --- | --- | --- |
| **사람이 직접 입력** | 있다 | 화면 · 변경 이력 · 되돌리기 |
| **시스템 원천** | 있다 | 데이터 소스 동기화로 잇는다 |
| **모인 문서 · 파일** | 만든다 | 같은 파이프라인을 **다시 돌려 식별자 기준으로 고치거나 더한다.** 필요한 것: **증분 처리**(바뀐 원천만), **변경분 검토**(새로 · 바뀜 · 사라짐을 보고 적용), 사라진 것 처리 규칙(데이터 소스의 사용 중지와 같게), 사람이 고친 값 보호(⑮) |

**스키마 변경도 흐름이 있어야 한다.** 새 데이터가 기존 정의에 안 맞으면 억지로 끼워 넣지 않고,
정의 변경을 제안 → 사람 확인 → 가져오기. 끼워 넣은 데이터는 조용히 뜻을 잃는다.

### 3.5 먼저 정할 사내 조건

- **AI 사용 정책** — 사내 데이터를 어떤 모델로 처리해도 되나(외부 API 가능 여부 · 사내 모델),
  민감정보를 가리는 단계가 필요한가. **이것이 파이프라인의 모양 자체를 정한다.**
- **그룹별 역할** — 정의를 확정하는 사람(온톨로지 담당)과 데이터를 검토하는 사람. 플랫폼 기능이
  아니라 **절차**로 둔다 — 승인 흐름 기능은 만들지 않기로 했다.

## 4. 순서

1. **파일럿 그룹 하나**를 정하고 ① 규약 · ② 코어 초안 · ④ 골든 셋(소량)을 만든다. 이것 없이
   뒤를 만들면 맞게 만들었는지 판단할 수 없다.
2. ③ 중간 결과물 형식 + ⑬ 한 번에 미리 보기로 **「AI 결과 → 검토 → 적재」 한 바퀴**를 돈다.
3. ⑤~⑫ 파이프라인을 파일럿 데이터로 다듬고, 골든 셋으로 정확도를 본다.
4. ⑮ 사람이 고친 값 보호 · 모인 문서 재적재로 **갱신 경로를 닫는다.**
5. 두 번째 그룹부터 ⑯ 찍어내기 · ⑰ 코어 전파를 쓴다.

## 5. 열린 질문

- 파일럿 그룹의 원천은 무엇이 많은가 — 엑셀 · 사내 시스템 · 문서/PDF. 파싱(⑥)과 추출(⑨)의
  무게가 여기서 갈린다.
- 사내 데이터에 쓸 수 있는 AI 는 무엇인가(3.5).
- 출처(⑭)를 공통 속성 규약으로 둘까, 플랫폼 칸으로 만들까.
- 코어 온톨로지의 첫 범위 — 어느 타입까지를 「모든 그룹 공통」 으로 볼까.
