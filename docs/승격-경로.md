# 승격 경로 — JSONB 로 커진 타입을 전용 표로 내리기

온톨로지의 객체는 `objects.properties` JSONB 에 산다. 그래서 **정의를 바꾸는 일이
배포가 아니다** — 이것이 [ADR 0005](adr/0005-온톨로지-메타모델.md)의 요점이다. 대가도
거기 적혀 있다: JSONB 에는 유니크·FK·CHECK 를 못 걸고, 목록 질의가 JSONB 를 탄다.
검증은 서비스 레이어가 하고 인덱스는 표현식으로 건다. **대부분의 타입은 그것으로
충분하다.**

이 문서는 충분하지 않게 된 타입을 위한 것이다. 이 길이 설계 안에 있는 것이 ADR 0005
결정 8 의 조건이다 — **없으면 모든 것이 영원히 JSONB 에 남고, 그 상태는 몇 년 뒤에
드러난다.**

## 언제 승격하나

아래 중 하나가 **실제로** 아프기 시작했을 때. 미리 하지 않는다 — 승격은 배포를 요구하고,
그 순간 그 타입은 「정의를 바꾸면 화면이 생기는」 길에서 빠진다.

| 신호 | 왜 JSONB 로는 안 되나 |
| --- | --- |
| 유일성·참조 무결성을 **DB 가** 지켜야 한다 | 서비스 레이어의 검사는 경쟁 조건에 뚫린다. 돈·재고·법적 기록이면 그 한 번이 사고다 |
| 행이 수십만을 넘고 목록이 느리다 | GIN 인덱스는 「있는가」 에 강하고 범위·정렬에 약하다. 표현식 인덱스를 열마다 걸면 그것이 이미 표다 |
| 도메인 로직이 타입 전용으로 자란다 | 「이 타입만의 규칙」 이 `validate_properties` 에 분기로 쌓이면, 그 자리는 전용 서비스가 맞다 |
| 다른 시스템이 이 표를 직접 읽어야 한다 | 외부 조인·ETL 은 열이 있는 표를 원한다 |

**아프지 않으면 하지 않는다.** 승격한 타입은 속성을 더할 때마다 마이그레이션이 필요하다.

## 원칙 — 온톨로지에서는 아무것도 안 바뀐 것처럼

승격 뒤에도 그 타입은 **같은 slug, 같은 id** 로 온톨로지에 남는다. 다만
`kind_class='system'` 이 되고 `system_source` 가 전용 표를 가리킨다. 목록·상세·참조
풀이·관계가 전부 [`shared/system_sources.py`](../backend/app/shared/system_sources.py)
에 등록한 `SystemSource` 를 통해 전용 표에서 나온다. 부서·계정이 처음부터 이 길로
온톨로지에 보이므로, **승격은 새 길이 아니라 이미 있는 길로 옮겨 타는 것**이다.

그래서 지켜야 할 것이 하나다:

> **id 를 보존한다.** 다른 타입의 `object_ref` 칸에는 이 타입 객체의 uuid 가 그대로
> 들어 있다. 전용 표가 새 id 를 쓰면 그 칸이 전부 「(지워짐)」 이 되고, 그 손실은
> **다른 타입의 화면**에서만 드러난다.

## 절차

예로 `supplier`(공급사) 타입을 전용 표 `suppliers` 로 내린다.

### 1. 전용 표와 모델 — id 는 `objects.id` 와 같다

```python
# app/modules/suppliers/models.py
class Supplier(Base):
    __tablename__ = "suppliers"
    id: Mapped[uuid.UUID] = mapped_column(PgUUID(as_uuid=True), primary_key=True)
    """**objects.id 를 그대로 물려받는다.** 새로 만들지 않는다."""
    code: Mapped[str] = mapped_column(String(40), unique=True)
    name: Mapped[str] = mapped_column(String(200), index=True)
    country: Mapped[str] = mapped_column(String(2))
    score: Mapped[int | None] = mapped_column(Integer, CheckConstraint("score BETWEEN 0 AND 100"))
    owner_workspace_id: Mapped[uuid.UUID | None] = ...   # 객체와 같은 소유 규칙
    is_active: Mapped[bool] = ...
    deleted_at: ...
```

[`all_models.py`](../backend/app/all_models.py) 에 한 줄 더하고, 마이그레이션을 만들어
**그 자리에서 개발 DB 에 올린다**(`alembic upgrade head`). 유니크·FK·CHECK 가 여기서
비로소 생긴다 — 승격의 이유가 이 줄들이다.

### 2. 데이터를 옮긴다 — 같은 id 로

한 번 도는 스크립트(`scripts/migrate_suppliers.py`)를 쓴다. 마이그레이션 안에 넣지
않는다 — 시험은 모델로 표를 만들어 그 행을 못 받고, 실패했을 때 되돌릴 자리도 없다.

```python
for row in db.scalars(select(ObjectInstance).where(ObjectInstance.type_id == supplier_type.id,
                                                    ObjectInstance.deleted_at.is_(None))):
    p = row.properties or {}
    db.add(Supplier(id=row.id, code=row.key, name=row.label, country=p.get("country"),
                    score=p.get("score"), owner_workspace_id=row.owner_workspace_id))
db.commit()
```

값이 전용 표의 제약에 안 맞는 행(점수 120, 나라 코드 없음)은 **여기서 걸린다.** 그것이
승격이 드러내는 첫 번째 것이다 — 고치고 다시 돈다. 반쯤 옮긴 상태로 다음 단계로 가지
않는다.

### 3. `SystemSource` 를 등록한다

```python
# app/modules/suppliers/services.py
SYSTEM_SOURCE = system_sources.SystemSource(
    key="supplier",
    label="공급사",
    search=_search,      # (db, viewer, q, limit, offset) -> (rows, total) — 소유 규칙을 여기서 지킨다
    lookup=_lookup,      # (db, ids) -> {id: SystemRef} — 지워진 것은 안 준다
    list_all=_list_all,  # 파일의 식별자·이름을 id 로 풀 때
)
```

```python
# app/main.py — _register_extensions()
system_sources.register_system_source(suppliers_services.SYSTEM_SOURCE)
```

`SystemRef.key` 가 **파일과 MCP 가 적는 식별자**다(부서면 slug, 공급사면 code). 부서·계정
쪽 구현([workspaces/services.py](../backend/app/modules/workspaces/services.py) 끝,
[accounts/services.py](../backend/app/modules/accounts/services.py) 끝)이 본보기다.

### 4. 관계를 옮기고 타입을 돌린다 — 스크립트가 한다

```bash
cd backend
.venv/bin/python scripts/promote_type.py --type supplier --source supplier            # 계획
.venv/bin/python scripts/promote_type.py --type supplier --source supplier --apply --actor admin
```

[`promote_type.py`](../backend/scripts/promote_type.py) 가 하는 일
([`ontology/promotion.py`](../backend/app/modules/ontology/promotion.py)):

1. 전용 표가 **모든 살아 있는 객체 id** 로 답하는지 확인한다 — 하나라도 빠지면 아무것도
   안 하고 그 id 를 찍는다
2. 이 타입에 걸린 `object_relations` 를 `object_links` 로 옮긴다 — **id 그대로**(감사
   기록의 relation id 가 계속 맞는다)
3. `objects` 행을 `deleted_at` 으로 지운다 — 참조는 원 표에서 풀리므로 끊기지 않는다
4. 타입을 `kind_class='system'` · `system_source='supplier'` 로 돌린다

전부 한 트랜잭션이다. 운영에서는 컨테이너 안에서 돌린다(스크립트 머리말에 명령이 있다).

### 5. 화면·MCP 는 그대로다 — 확인만

- `/o/supplier` 목록이 전용 표에서 뜬다(찾기만 있고 만들기·파일·조건은 없다)
- 「공급사」 칸이 있던 타입의 상세에서 그 이름이 그대로 보인다
- 공급사와 이었던 관계가 「관련 객체」 에 그대로 있다
- MCP `objects_list("supplier")` 가 같은 모양으로 답한다
- 홈 「남은 일」 의 품질 지표에서 그 타입이 빠진다(투영은 검사 대상이 아니다)

### 6. 전용 화면 — 필요하면

만들기·고치기는 이제 온톨로지 화면에 없다. 전용 모듈의 화면(`frontend/src/modules/suppliers/`)
을 [새-플랫폼-만들기.md](새-플랫폼-만들기.md) 5단계대로 만든다. 서두르지 않아도 된다 —
읽기·참조·관계는 이미 되고, 쓰기는 파일 대신 그 표의 API 로 간다.

## 승격하면 잃는 것

정직하게 적어 둔다. 이것들이 아까우면 아직 승격할 때가 아니다.

| 잃는 것 | 대신 |
| --- | --- |
| 속성을 화면에서 더하기 | 열 하나에 마이그레이션 하나 |
| `objects_import` · 파일로 넣기 | 그 표의 API 또는 전용 가져오기 |
| 변경 이력·되돌리기(객체별) | 감사 로그는 남지만 시점 값 재구성은 전용 표가 직접 해야 한다 |
| 조건 거르기·저장된 뷰 | 전용 화면이 자기 거르기를 갖는다 |
| 지식 그래프에서 보이기 | 그래프는 `objects` 만 걷는다 — 링크는 「관련 객체」 에서만 |
| 코드표 승격·합치기 | 전용 표의 몫 |

## 되돌리기

`--apply` 전이면 아무것도 안 바뀌었다. 뒤라면: 타입을 `record` 로 되돌리고, `objects` 의
`deleted_at` 을 비우고, `object_links` 를 `object_relations` 로 옮긴다 — `promotion.apply`
의 정확한 역순이고, 스냅샷은 없다. **그래서 계획 단계에서 멈춰 보고, 시험 DB 에서 한 번
돌려 본 뒤에 운영에서 돌린다.**
