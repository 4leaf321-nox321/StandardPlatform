# 온톨로지 메타모델 — 설계와 할 일

결정의 배경은 [ADR 0005](adr/0005-온톨로지-메타모델.md) 가 정본이다. **여기는
무엇을 어떻게 만드는지**와 **무엇을 반드시 끝내야 하는지**를 적는다.

> 이 문서의 §9 체크리스트가 진행의 정본이다. 「나중에」 로 미룬 것과 「안 하기로
> 한 것」 은 다르다 — 미룬 것은 체크리스트에 **반드시**로 남는다. 안 적으면
> 미룬 것은 잊히고, 잊힌 것은 그것이 필요해진 날에 발견된다.

---

## 1. 한 줄

    그룹을 정의하면 사이드바에 묶음이 생기고,
    타입을 정의하면 그 묶음 안에 목록·프로필 화면이 생기고,
    속성·관계를 정의하면 그 화면의 폼과 관계 편집기가 생긴다.

도메인을 얹는 일이 **코드를 쓰는 일에서 데이터를 채우는 일로** 바뀐다.

## 2. 화면에서 무엇이 보이나

```
사이드바                         타입 정의가 만드는 것
──────────                      ────────────────────
홈                              (정적 — navigation.ts)
▼ 도메인          ← nav_group    /o/part        목록   ← object_type
    부품          ← object_type  /o/part/{id}   프로필
    과제
▼ 내 활동                        (정적)
    알림
▼ 관리
    온톨로지      ← 메타모델 편집 /admin/ontology
```

**정적 화면의 정본은 여전히 `navigation.ts` 다.** 동적 그룹은 그 아래 합류한다.
라우트는 둘(`/o/:typeSlug`, `/o/:typeSlug/:id`)만 늘어나므로
`routes/router.test.tsx` 의 어긋남 검사가 그대로 유효하다.

## 3. 데이터 모델

### 3.1 `nav_groups` — 표시

| 칸 | 뜻 |
| --- | --- |
| `slug` `label` `icon` `sort_order` | 사이드바 묶음 |
| `audience` | `everyone` \| `manager` \| `system_admin` — **표시일 뿐 권한이 아니다** |
| `is_active` | 지우지 않는다 |

**의미(타입)와 나눈 이유**: 한 표로 두면 「이 타입을 두 그룹에」 「그룹을 부서마다
다르게」 가 반드시 오고, 그때는 데이터가 이미 쌓여 있다.

### 3.2 `object_types` — 의미 (= 축)

| 칸 | 뜻 |
| --- | --- |
| `slug` | **바뀌면 안 되는 식별자.** 관계·URL·MCP 도구 이름이 여기 물린다 |
| `label` `icon` `sort_order` `description` | 표시 |
| `nav_group_id` | 어느 묶음에 설 것인가. NULL 이면 사이드바에 안 선다 |
| `kind_class` | `reference` \| `record` \| `system` (§3.6) |
| `entry_policy` | `open` = picker 에서 즉석 추가 가능, `closed` = 관리자만 |
| `key_policy` | `none` \| `optional` \| `required` (§4.1) |
| `key_scope` | `global` \| `workspace` — `key` 의 유니크 범위 |
| `temporal_kind` | `evergreen` \| `lifecycle` \| `yearly` \| `derived` (§4.3) |
| `list_view` | JSONB — 목록 화면의 모양 (§3.7) |
| `is_active` | 지우지 않는다 |

**타입은 전역이다**(`owner_workspace_id` 를 두지 않는다). 타입까지 부서별로 열면
같은 개념이 부서마다 갈리고, 연결하려고 만든 것이 칸막이가 된다.

### 3.3 `property_defs` — 속성 정의 (폴리모픽)

| 칸 | 뜻 |
| --- | --- |
| `owner_kind` | `type` \| `relation` — **관계에도 속성이 붙는다** |
| `owner_id` | 그 타입 또는 관계 타입 |
| `key` | `properties` JSONB 의 키. 바뀌면 안 된다 |
| `label` `unit` `sort_order` `help` | 표시 |
| `data_type` | 일곱 중 하나 (§4.2) |
| `required` `multi` | 검증과 폼 위젯 |
| `enum_options` | `data_type='enum'` 일 때 |
| `ref_type_slug` | `data_type='object_ref'` 일 때 가리키는 타입 |

폴리모픽인 이유: 타입의 속성 폼과 관계의 속성 폼이 **같은 컴포넌트**여야 한다.
두 벌로 만들면 위젯이 갈리고, 갈린 것은 한쪽만 고쳐진다.

### 3.4 `relation_types` — 관계 종류

| 칸 | 뜻 |
| --- | --- |
| `slug` `label` `inverse_label` | `part_of` ↔ 「포함」 — 화면이 양방향을 말한다 |
| `directed` | 방향이 있나 |
| `transitive` | **재귀 펼침 대상인가.** 트리·롤업이 이것으로 갈린다 |
| `acyclic` | 순환 금지 — 추가할 때 가드가 붙는다 |
| `src_type_slugs[]` `dst_type_slugs[]` | 허용 출발/도착 타입. NULL = 제약 없음 |

**메타가 데이터에 있어야 하는 이유**: 코드에 암묵이면 화면도 MCP 도 그 의미를 알
방법이 없다. ReportArchive 가 `p55` 에서 뒤늦게 깨달은 자리다.

### 3.5 `objects` · `object_relations` · `object_links`

```
objects            type_id, key, label, properties(JSONB), status,
                   owner_workspace_id(NULL=전역), valid_from_year, valid_to_year,
                   created_by, deleted_at
object_relations   src_object_id, dst_object_id, relation, properties(JSONB),
                   evidence_note, created_by, created_at
object_links       src_type, src_id, dst_type, dst_id, relation, properties
                   (한쪽 끝이 objects 밖일 때만 — system 객체)
object_years       object_id, year          (temporal_kind='yearly')
```

- **트리는 `part_of` 로 만든다.** `parent_id` 칸을 두지 않는다 — 두면 트리 관계와
  일반 관계가 두 벌이 되고 트래버설도 두 벌이 된다.
- `status` 는 `active` \| `deprecated`. **지우지 않는다** — deprecated 는 picker 에서
  숨되 이미 걸린 관계는 그대로 남는다.
- 인스턴스는 **부서 소유**다. `visible_owner_clause` · `resolve_owner_workspace` ·
  `require_owner_edit` 가 그대로 붙는다.

### 3.6 `kind_class` — 셋을 처음부터

```
reference   어휘/enum. 속성 거의 없음, picker 선택용 (불량 종류·개발 단계)
record      속성을 가진 인스턴스 객체 (부품·과제·공급사)
system      이미 있는 1급 표의 투영 (부서·계정·공지)
```

**`system` 이 핵심이다.** 부서를 온톨로지에 넣겠다고 `objects` 에 행을 복제하면
두 벌이 되고 **반드시 갈린다.** 행을 만들지 않고 `ObjectRef` 해석기가 원 표에서
라벨을 읽는다. 그 끝단의 관계는 `object_links` 에 담는다.

### 3.7 `list_view` — 화면이 자동 생성되면 반드시 필요한 것

```jsonc
{
  "columns": ["key", "label", "properties.vendor", "properties.status"],
  "sort":    { "field": "label", "dir": "asc" },
  "filters": ["properties.status", "owner_workspace"],
  "search":  ["label", "key", "properties.alias"],
  "group_by": null
}
```

**없으면 모든 목록이 똑같아지고, 똑같으면 아무도 안 쓴다.** 부품 목록과 과제
목록은 보여야 할 열이 다르다. ReportArchive 에서 「레코드+멀티뷰 엔진」 이 아직
미착수로 남아 있는 것이 이 무게의 증거다.

## 4. 확정된 셋

### 4.1 인스턴스 식별자 — `key` + 타입별 정책

사람이 정하는 `key`(부품번호·과제코드)를 두되 **타입마다 정책**을 갖는다.

| `key_policy` | 뜻 |
| --- | --- |
| `none` | `key` 를 안 쓴다. `label` 만으로 산다 (어휘 축) |
| `optional` | 있으면 유니크, 없어도 된다 |
| `required` | 반드시 있고 유니크 |

유니크 범위는 `key_scope` 가 정한다 — `global`(전사 유일) 또는 `workspace`(부서
안에서 유일). **외부 시스템과 맞물리는 축은 `global`** 이어야 한다. 부서마다
같은 부품번호가 다른 것을 가리키면, 그 데이터로는 아무 질문에도 답할 수 없다.

### 4.2 속성 타입 — 일곱

| `data_type` | 저장 | 폼 위젯 |
| --- | --- | --- |
| `text` | 문자열 | 한 줄 / 여러 줄 |
| `number` | 숫자 | 숫자 + `unit` 표기 |
| `date` | ISO 날짜 문자열 | 날짜 선택 |
| `bool` | 참/거짓 | 체크 |
| `enum` | 문자열(옵션 중 하나) | 선택 — 스물 넘으면 `SearchablePicker` |
| `object_ref` | 객체 id | 객체 picker (`ref_type_slug` 로 범위 한정) |
| `file` | — (§4.2.1) | 첨부 올리기·목록 |

`multi=true` 면 배열이 된다.

#### 4.2.1 `file` 은 첨부 모듈을 재사용한다 — `owner_field` 한 칸을 더한다

첨부는 이미 `owner_table` + `owner_id` 로 느슨하게 가리킨다. 객체에 붙이는 것은
그대로 되지만, **어느 속성의 첨부인지**를 가릴 자리가 없다.

두 길이 있고, **`attachments.owner_field`(nullable) 한 칸을 더하는 쪽**을 쓴다.

| | JSONB 에 첨부 id 를 넣는다 | `owner_field` 칸을 더한다 ← |
| --- | --- | --- |
| 삭제 정합 | 첨부를 지우면 JSONB 에 **유령 id 가 남는다** | 목록이 자연히 반영된다 |
| 질의 | JSONB 를 풀어야 한다 | `WHERE owner_table='objects' AND owner_field='drawing'` |
| 비용 | 0 | 공통 표에 칼럼 하나 (nullable, 기존 행 무영향) |

유령 id 는 **화면에서 깨진 링크로만** 드러난다. 그 대가가 칼럼 하나보다 크다.

### 4.3 시간 차원 — 처음부터 넣는다

**칼럼만 잡고 미루지 않는다.** 미루면 나중에 **모든 타입**을 건드리게 되고, 그때는
데이터가 이미 쌓여 있다. (§9 의 2단계에 **반드시**로 박혀 있다.)

| `temporal_kind` | 연도 필터 `year=Y` 가 걸렸을 때 |
| --- | --- |
| `evergreen` | 연도 무관, 항상 보인다. 필터를 무시한다 (기본값) |
| `lifecycle` | `valid_from_year` ~ `valid_to_year` 에 Y 가 들면 보인다. NULL 끝 = 진행 중 |
| `yearly` | `object_years` 에 Y 가 배정돼 있으면 보인다 (불연속 가능) |
| `derived` | **도메인이 답한다** — §4.3.1 |

#### 4.3.1 `derived` 는 레지스트리로 뺀다

`derived` 는 「그 객체가 쓰인 기록의 연도」 에서 추론한다. 그런데 **공통 틀에는
「기록」 이 없다.** 그것은 도메인의 것이다. 그래서 확장 지점을 하나 더 둔다:

```python
extensions.register_temporal_source(provider)   # 객체 id -> 쓰인 연도들
```

등록하지 않으면 `derived` 축은 **연도 필터를 무시한다**(= `evergreen` 처럼 군다).
조용히 빈 목록을 주지 않는다 — 빈 목록은 「데이터가 없다」 로 읽히기 때문이다.

## 5. 권한

| 무엇 | 볼 수 있는 사람 | 고칠 수 있는 사람 |
| --- | --- | --- |
| 그룹·타입·속성·관계 종류 | 로그인한 누구나 | **시스템 관리자만** |
| 인스턴스 | `visible_owner_clause` (전역 + 내 부서) | `require_owner_edit` |
| 관계 | 양끝 중 하나라도 보이면 | 양끝 다 고칠 수 있어야 |

판정은 `shared/permissions.py` 한 곳에서 한다. **화면의 역할 판정은 표시일 뿐**
이고 권한은 서버가 정한다.

## 6. API

```
GET    /api/ontology/schema                       전체 스키마 — MCP 의 입력
GET    /api/ontology/nav                          동적 사이드바
       /api/ontology/groups                       CRUD (시스템 관리자)
       /api/ontology/types                        CRUD
       /api/ontology/types/{slug}/properties      CRUD
       /api/ontology/relation-types               CRUD
       /api/ontology/relation-types/{slug}/properties  CRUD

GET    /api/objects/{typeSlug}                    목록 (필터·정렬·페이지네이션)
POST   /api/objects/{typeSlug}
GET    /api/objects/{typeSlug}/{id}               프로필 (속성+관계+첨부)
PATCH  /api/objects/{typeSlug}/{id}               **부분 수정** — §6.1
DELETE /api/objects/{typeSlug}/{id}               soft
GET    /api/objects/{typeSlug}/{id}/graph         트래버설 (depth 상한)

POST   /api/object-relations                      PATCH · DELETE
```

- 성공은 리소스 그대로, 오류만 엔벨로프. 오류 코드는 `errors.code("ONTOLOGY", n)` ·
  `errors.code("OBJECTS", n)` 로 만든다 — **손으로 잇지 않는다.**
- 목록은 `shared/pagination.py` 의 상한을 받는다.
- 스키마가 바뀌면 `export_openapi.py` 와 `npm run api:types` 를 함께 돌린다.

### 6.1 부분 수정에서 「안 보낸 것」 과 「비운 것」

`properties` 는 JSONB 한 칸이라 통째로 덮기 쉽다. **덮으면 이름 하나 바꿀 때마다
다른 속성이 함께 날아가고, 그 손실은 저장한 사람 눈에 안 보인다.** PATCH 는
보낸 키만 병합하고, 지우려면 `null` 을 명시한다.

## 7. 프론트

```
shared/ontology/          useSchema()  — 스키마를 한 번 받아 캐시
                          PropertyFields — data_type 별 위젯 (타입·관계 공용)
                          ObjectPicker  — SearchablePicker 위에 얹는다
modules/ontology/         메타모델 편집 (그룹·타입·속성·관계 종류)
modules/objects/          ObjectListPage · ObjectProfilePage
shared/layout/            navigation.ts 에 동적 그룹을 합류
```

- 스타일은 Tailwind 유틸리티. 전역 CSS 클래스를 새로 만들지 않는다.
- 상태의 말과 색은 `StatusBadge` 가 정한다.
- **빈 목록은 이유를 말한다**(`EmptyState`) — 데이터가 없는 것인지, 거르기가 좁은
  것인지, 권한이 없는 것인지.
- **되돌릴 수 없는 일은 무엇이 사라지는지 적는다**(`ConfirmDialog`). 속성 정의를
  지우는 창은 **그 값이 몇 개 있는지**를 말해야 한다.
- 고를 것이 스물을 넘으면 `<Select>` 를 쓰지 않는다 — `SearchablePicker`.
- 목록에는 `Pagination` 을 붙인다.

## 8. 트래버설

`modules/objects/graph.py` 한 모듈. 공개 함수만 밖에서 쓴다.

```python
neighbors(db, object_id, *, relations=None, direction="both", depth=1)
descendants(db, object_id, *, relation)      # transitive 인 관계만 재귀
ancestors(db, object_id, *, relation)
```

내부는 **재귀 CTE**로 시작한다. 그래프 엔진으로 갈 일이 생기면 이 모듈 안만
바뀐다. `depth` 에는 서버가 상한을 강제한다 — 없으면 관계가 촘촘해지는 날
목록 하나가 DB 를 통째로 훑는다.

## 9. 할 일

> **`[필수]` 는 그 단계를 끝냈다고 말하기 전에 반드시 끝나야 하는 것이다.**
> 미룰 수는 있어도 지울 수는 없다.

## 10. 검증

고칠 때마다 [AGENTS.md](../AGENTS.md) 의 넷을 돌린다. 이 설계에서 특히 걸리는 것:

- **`alembic check`** — 메타모델은 표가 많고 인덱스가 많다. 모델과 마이그레이션이
  어긋나면 **배포하고 나서 500 으로** 드러난다.
- **구조 시험** — `shared` 가 이 모듈을 import 하면 방향이 거꾸로 선다.
- **JSONB 인덱스** — 목록이 `properties` 를 타므로, `list_view` 가 거르는 키에는
  표현식 인덱스를 건다. 안 걸면 행이 몇만을 넘는 순간 목록이 느려지고, **느려진
  이유는 화면 어디에도 안 적힌다.**
