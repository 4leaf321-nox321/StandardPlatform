# 온톨로지 메타모델 — 설계와 할 일

결정의 배경은 [ADR 0005](adr/0005-온톨로지-메타모델.md) 가 정본이다. **여기는
무엇을 어떻게 만드는지**와 **무엇을 반드시 끝내야 하는지**를 적는다.

> 이 문서의 §9 체크리스트가 진행의 정본이다. 「나중에」 로 미룬 것과 「안 하기로
> 한 것」 은 다르다 — 미룬 것은 체크리스트에 **반드시**로 남는다. 안 적으면
> 미룬 것은 잊히고, 잊힌 것은 그것이 필요해진 날에 발견된다.

---

## 1. 한 줄

    그룹을 정의하면 사이드바에 묶음이 생기고,
    타입을 정의하면 그 묶음 안에 목록·프로필 화면이 생기고,
    속성·관계를 정의하면 그 화면의 폼과 관계 편집기가 생긴다.

도메인을 얹는 일이 **코드를 쓰는 일에서 데이터를 채우는 일로** 바뀐다.

## 2. 화면에서 무엇이 보이나

```
사이드바                         타입 정의가 만드는 것
──────────                      ────────────────────
홈                              (정적 — navigation.ts)
▼ 도메인          ← nav_group    /o/part        목록   ← object_type
    부품          ← object_type  /o/part/{id}   프로필
    과제
▼ 내 활동                        (정적)
    알림
▼ 관리
    온톨로지      ← 메타모델 편집 /admin/ontology
```

**정적 화면의 정본은 여전히 `navigation.ts` 다.** 동적 그룹은 그 아래 합류한다.
라우트는 둘(`/o/:typeSlug`, `/o/:typeSlug/:id`)만 늘어나므로
`routes/router.test.tsx` 의 어긋남 검사가 그대로 유효하다.

## 3. 데이터 모델

### 3.1 `nav_groups` — 표시

| 칸 | 뜻 |
| --- | --- |
| `slug` `label` `icon` `sort_order` | 사이드바 묶음 |
| `audience` | `everyone` \| `manager` \| `system_admin` — **표시일 뿐 권한이 아니다** |
| `is_active` | 지우지 않는다 |

**의미(타입)와 나눈 이유**: 한 표로 두면 「이 타입을 두 그룹에」 「그룹을 부서마다
다르게」 가 반드시 오고, 그때는 데이터가 이미 쌓여 있다.

### 3.2 `object_types` — 의미 (= 축)

| 칸 | 뜻 |
| --- | --- |
| `slug` | **바뀌면 안 되는 식별자.** 관계·URL·MCP 도구 이름이 여기 물린다 |
| `label` `icon` `sort_order` `description` | 표시 |
| `nav_group_id` | 어느 묶음에 설 것인가. NULL 이면 사이드바에 안 선다 |
| `kind_class` | `reference` \| `record` \| `system` (§3.6) |
| `entry_policy` | `open` = picker 에서 즉석 추가 가능, `closed` = 관리자만 |
| `key_policy` | `none` \| `optional` \| `required` (§4.1) |
| `key_scope` | `global` \| `workspace` — `key` 의 유니크 범위 |
| `temporal_kind` | `evergreen` \| `lifecycle` \| `yearly` \| `derived` (§4.3) |
| `list_view` | JSONB — 목록 화면의 모양 (§3.7) |
| `is_active` | 지우지 않는다 |

**타입은 전역이다**(`owner_workspace_id` 를 두지 않는다). 타입까지 부서별로 열면
같은 개념이 부서마다 갈리고, 연결하려고 만든 것이 칸막이가 된다.

### 3.3 `property_defs` — 속성 정의 (폴리모픽)

| 칸 | 뜻 |
| --- | --- |
| `owner_kind` | `type` \| `relation` — **관계에도 속성이 붙는다** |
| `owner_id` | 그 타입 또는 관계 타입 |
| `key` | `properties` JSONB 의 키. 바뀌면 안 된다 |
| `label` `unit` `sort_order` `help` | 표시 |
| `data_type` | 일곱 중 하나 (§4.2) |
| `required` `multi` | 검증과 폼 위젯 |
| `enum_options` | `data_type='enum'` 일 때 |
| `ref_type_slug` | `data_type='object_ref'` 일 때 가리키는 타입 |

폴리모픽인 이유: 타입의 속성 폼과 관계의 속성 폼이 **같은 컴포넌트**여야 한다.
두 벌로 만들면 위젯이 갈리고, 갈린 것은 한쪽만 고쳐진다.

### 3.4 `relation_types` — 관계 종류

| 칸 | 뜻 |
| --- | --- |
| `slug` `label` `inverse_label` | `part_of` ↔ 「포함」 — 화면이 양방향을 말한다 |
| `directed` | 방향이 있나 |
| `transitive` | **재귀 펼침 대상인가.** 트리·롤업이 이것으로 갈린다. 롤업은 `list_view.rollups` (`{property, fn, label}`) — 트리 아래 전부의 숫자 속성을 볼 때마다 모은다(`objects/rollup.py`, `GET …/rollup`). 저장하지 않고, 빈 것의 수를 함께 준다 |
| `acyclic` | 순환 금지 — 추가할 때 가드가 붙는다 |
| `src_type_slugs[]` `dst_type_slugs[]` | 허용 출발/도착 타입. NULL = 제약 없음 |

**메타가 데이터에 있어야 하는 이유**: 코드에 암묵이면 화면도 MCP 도 그 의미를 알
방법이 없다. ReportArchive 가 `p55` 에서 뒤늦게 깨달은 자리다.

### 3.5 `objects` · `object_relations` · `object_links`

```
objects            type_id, key, label, properties(JSONB), status,
                   owner_workspace_id(NULL=전역), valid_from_year, valid_to_year,
                   created_by, deleted_at
object_relations   src_object_id, dst_object_id, relation, properties(JSONB),
                   evidence_note, created_by, created_at
object_links       src_type, src_id, dst_type, dst_id, relation, properties,
                   evidence_note (한쪽 끝이 objects 밖일 때만 — system 객체. FK 없음)
object_years       object_id, year          (temporal_kind='yearly')
```

- **트리는 `part_of` 로 만든다.** `parent_id` 칸을 두지 않는다 — 두면 트리 관계와
  일반 관계가 두 벌이 되고 트래버설도 두 벌이 된다.
- `status` 는 `active` \| `deprecated`. **지우지 않는다** — deprecated 는 picker 에서
  숨되 이미 걸린 관계는 그대로 남는다.
- 객체는 **부서 소유**다. `visible_owner_clause` · `resolve_owner_workspace` ·
  `require_owner_edit` 가 그대로 붙는다.

### 3.6 `kind_class` — 셋을 처음부터

```
reference   어휘/enum. 속성 거의 없음, picker 선택용 (불량 종류·개발 단계)
record      속성을 가진 객체 객체 (부품·과제·공급사)
system      이미 있는 1급 표의 투영 (부서·계정·공지)
```

**`system` 이 핵심이다.** 부서를 온톨로지에 넣겠다고 `objects` 에 행을 복제하면
두 벌이 되고 **반드시 갈린다.** 행을 만들지 않고 `ObjectRef` 해석기가 원 표에서
라벨을 읽는다. 그 끝단의 관계는 `object_links` 에 담는다. 원 표는 타입의
`system_source` 가 가리키고(`workspace` · `user` · 승격한 표), 그 표는
`shared/system_sources.py` 에 등록돼 있어야 한다 — 승격 절차는 [승격-경로.md](승격-경로.md).

### 3.7 `list_view` — 화면이 자동 생성되면 반드시 필요한 것

```jsonc
{
  "columns": ["key", "label", "properties.vendor", "properties.status"],
  "sort":    { "field": "label", "dir": "asc" },
  "filters": ["properties.status", "owner_workspace"],
  "search":  ["label", "key", "properties.alias"],
  "group_by": null
}
```

**없으면 모든 목록이 똑같아지고, 똑같으면 아무도 안 쓴다.** 부품 목록과 과제
목록은 보여야 할 열이 다르다. ReportArchive 에서 「레코드+멀티뷰 엔진」 이 아직
미착수로 남아 있는 것이 이 무게의 증거다.

편집은 **타입 모달의 「목록 화면」 탭**이 한다. API 로만 넣을 수 있게 두면 속성을
정의해도 목록이 안 바뀌고, 그러면 「정의가 곧 화면」 이라는 말이 반만 참이 된다.

지금 못 하는 둘 — **없는 것을 있는 척하지 않는다:**

- `file` 속성은 열로 못 세운다. 값이 아니라 첨부라 `properties` 에 아무것도 없고,
  빈 열은 「값이 없다」 로 읽힌다.
- 거르기·검색은 **문자열 비교만** 한다(글·선택). 숫자 범위·날짜 구간은 없다.

`object_ref` 열은 된다. 값에는 id 만 있으므로 **서버가 이름을 한 번에 모아
실어 준다**(`ObjectOut.ref_labels`) — 행마다 물으면 목록 한 쪽에 질의가 수십 개
붙고, 안 실으면 목록에 UUID 가 떠서 그 열이 아무것도 말해 주지 못한다.

## 4. 확정된 셋

### 4.1 객체 식별자 — `key` + 타입별 정책

사람이 정하는 `key`(부품번호·과제코드)를 두되 **타입마다 정책**을 갖는다.

| `key_policy` | 뜻 |
| --- | --- |
| `none` | `key` 를 안 쓴다. `label` 만으로 산다 (어휘 축) |
| `optional` | 있으면 유니크, 없어도 된다 |
| `required` | 반드시 있고 유니크 |

유니크 범위는 `key_scope` 가 정한다 — `global`(전사 유일) 또는 `workspace`(부서
안에서 유일). **외부 시스템과 맞물리는 축은 `global`** 이어야 한다. 부서마다
같은 부품번호가 다른 것을 가리키면, 그 데이터로는 아무 질문에도 답할 수 없다.

### 4.2 속성 타입 — 일곱

| `data_type` | 저장 | 폼 위젯 |
| --- | --- | --- |
| `text` | 문자열 | 한 줄 (모양 규칙 가능) |
| `text_long` | 문자열 | 여러 줄 — **한 줄 칸에 넣으면 자기가 쓴 것을 못 본다** |
| `number` | 숫자 | 숫자 + `unit` 표기 |
| `date` | ISO 날짜 문자열 | 날짜 선택 |
| `datetime` | ISO 날짜·시각 | 날짜와 시각 — 측정·기록 시각 |
| `bool` | 참/거짓 | 체크 |
| `enum` | 문자열(옵션 중 하나) | 선택 — 스물 넘으면 `SearchablePicker` |
| `url` | 문자열(http/https) | 링크로 열린다 |
| `object_ref` | 객체 id | 객체 picker (`ref_type_slug` 로 범위 한정) |
| `file` | — (§4.2.1) | 첨부 올리기·목록 |

`multi=true` 면 배열이 된다.

**검증 규칙**(3-a): `min_value` · `max_value` · `decimals` · `pattern` ·
`default_value` · `unique`.

- 소수 자릿수를 넘으면 **반올림하지 않고 거절한다** — 조용히 바꾸면 사람이 넣은
  값과 저장된 값이 달라지고, 그 차이는 아무 데도 안 뜬다.
- **기본값은 만들 때만** 채운다. 고칠 때도 채우면 방금 지운 값이 되살아난다.
- `unique` 의 범위는 타입의 `key_scope` 를 따른다 — **두 벌의 규칙을 만들지 않는다.**
- 정규식이 깨져 있으면 「식이 잘못됐다」 와 「값이 안 맞는다」 를 **갈라 말한다**:
  고칠 곳이 다르다.

#### 4.2.1 `file` 은 첨부 모듈을 재사용한다 — `owner_field` 한 칸을 더한다

첨부는 이미 `owner_table` + `owner_id` 로 느슨하게 가리킨다. 객체에 붙이는 것은
그대로 되지만, **어느 속성의 첨부인지**를 가릴 자리가 없다.

두 길이 있고, **`attachments.owner_field`(nullable) 한 칸을 더하는 쪽**을 쓴다.

| | JSONB 에 첨부 id 를 넣는다 | `owner_field` 칸을 더한다 ← |
| --- | --- | --- |
| 삭제 정합 | 첨부를 지우면 JSONB 에 **유령 id 가 남는다** | 목록이 자연히 반영된다 |
| 질의 | JSONB 를 풀어야 한다 | `WHERE owner_table='objects' AND owner_field='drawing'` |
| 비용 | 0 | 공통 표에 칼럼 하나 (nullable, 기존 행 무영향) |

유령 id 는 **화면에서 깨진 링크로만** 드러난다. 그 대가가 칼럼 하나보다 크다.

### 4.3 시간 차원 — 처음부터 넣는다

**칼럼만 잡고 미루지 않는다.** 미루면 나중에 **모든 타입**을 건드리게 되고, 그때는
데이터가 이미 쌓여 있다. (§9 의 2단계에 **반드시**로 박혀 있다.)

| `temporal_kind` | 연도 필터 `year=Y` 가 걸렸을 때 |
| --- | --- |
| `evergreen` | 연도 무관, 항상 보인다. 필터를 무시한다 (기본값) |
| `lifecycle` | `valid_from_year` ~ `valid_to_year` 에 Y 가 들면 보인다. NULL 끝 = 진행 중 |
| `yearly` | `object_years` 에 Y 가 배정돼 있으면 보인다 (불연속 가능) |
| `derived` | **도메인이 답한다** — §4.3.1 |

#### 4.3.1 `derived` 는 레지스트리로 뺀다

`derived` 는 「그 객체가 쓰인 기록의 연도」 에서 추론한다. 그런데 **공통 틀에는
「기록」 이 없다.** 그것은 도메인의 것이다. 그래서 확장 지점을 하나 더 둔다:

```python
extensions.register_temporal_source(provider)   # 객체 id -> 쓰인 연도들
```

등록하지 않으면 `derived` 축은 **연도 필터를 무시한다**(= `evergreen` 처럼 군다).
조용히 빈 목록을 주지 않는다 — 빈 목록은 「데이터가 없다」 로 읽히기 때문이다.

## 5. 권한

| 무엇 | 볼 수 있는 사람 | 고칠 수 있는 사람 |
| --- | --- | --- |
| 그룹·타입·속성·관계 종류 | 로그인한 누구나 | **시스템 관리자만** |
| 객체 | `visible_owner_clause` (전역 + 내 부서) | `require_owner_edit` |
| 관계 | 양끝 중 하나라도 보이면 | 양끝 다 고칠 수 있어야 |

판정은 `shared/permissions.py` 한 곳에서 한다. **화면의 역할 판정은 표시일 뿐**
이고 권한은 서버가 정한다.

## 6. API

```
GET    /api/ontology/schema                       전체 스키마 — MCP 의 입력
GET    /api/ontology/nav                          동적 사이드바
       /api/ontology/groups                       CRUD (시스템 관리자)
       /api/ontology/types                        CRUD
       /api/ontology/types/{slug}/properties      CRUD
       /api/ontology/relation-types               CRUD
       /api/ontology/relation-types/{slug}/properties  CRUD

GET    /api/objects/{typeSlug}                    목록 (필터·정렬·페이지네이션)
POST   /api/objects/{typeSlug}
GET    /api/objects/{typeSlug}/{id}               프로필 (속성+관계+첨부)
PATCH  /api/objects/{typeSlug}/{id}               **부분 수정** — §6.1
DELETE /api/objects/{typeSlug}/{id}               soft
GET    /api/objects/{typeSlug}/{id}/graph         트래버설 (depth 상한)

POST   /api/object-relations                      PATCH · DELETE

GET    /api/objects/{typeSlug}/template           빈 CSV — 헤더가 무엇을 채울지 말한다
GET    /api/objects/{typeSlug}/export             거른 목록 그대로 CSV/JSON (쪽 상한 없음)
POST   /api/objects/{typeSlug}/import             파일로 넣기 — apply=false 면 계획만, 한 행이라도 오류면 무
POST   /api/objects/{typeSlug}/import-rows        같은 것을 JSON 행으로 (MCP)
GET    /api/objects/{typeSlug}/relations/export   이 타입에서 출발하는 관계 — src,relation,dst,evidence_note
POST   /api/objects/{typeSlug}/relations/import   (+ import-rows) 두 번 올려도 두 겹 안 됨
GET    /api/objects/{typeSlug}/{id}/references     이 객체를 가리키는 것 — 지우기 전에. 남의 부서 것은 수만

GET    /api/objects/{typeSlug}/{id}/history        이력 — 값 기록마다 그 시점 값 전체(지금 값에서 거꾸로 재구성)

GET    /api/objects/{typeSlug}?f.<칸>.<연산>=<값>   조건 거르기 — 칸 안 OR(in), 칸끼리 AND. export 도 같은 것
       /api/objects/{typeSlug}/views                 저장된 뷰 CRUD — 내 것 + 부서 공유(부서 관리자가 만듦)
POST   /api/ontology/types/{slug}/properties/{key}/rename-option   고를 값 이름 바꾸기 — 저장값도 함께
POST   /api/ontology/types/{slug}/properties/{key}/promote         enum → 코드표(참조 타입) 승격 — 계획 먼저, 스냅샷
GET    /api/objects/quality/report                 품질 — 필수값 빈 것·고아·깨진 참조·이름 같은 것. 홈 「남은 일」 이 같은 것을 읽는다

GET    /api/graph/overview                        정의 그래프 — 타입이 노드, 관계 종류가 선(실제 수로 굵기)
GET    /api/graph/search?q=                       타입 가리지 않는 시작점 찾기
GET    /api/graph/neighborhood?focus=&depth=      이웃 — depth·fanout·limit 상한을 서버가 강제, 잘리면 말한다
GET    /api/graph/subgraph?types=&offset=         한 타입의 인스턴스 전부 — 쪽 단위, 「N개 중 M개」
```

- 성공은 리소스 그대로, 오류만 엔벨로프. 오류 코드는 `errors.code("ONTOLOGY", n)` ·
  `errors.code("OBJECTS", n)` 로 만든다 — **손으로 잇지 않는다.**
- 목록은 `shared/pagination.py` 의 상한을 받는다.
- 스키마가 바뀌면 `export_openapi.py` 와 `npm run api:types` 를 함께 돌린다.

### 6.1 부분 수정에서 「안 보낸 것」 과 「비운 것」

`properties` 는 JSONB 한 칸이라 통째로 덮기 쉽다. **덮으면 이름 하나 바꿀 때마다
다른 속성이 함께 날아가고, 그 손실은 저장한 사람 눈에 안 보인다.** PATCH 는
보낸 키만 병합하고, 지우려면 `null` 을 명시한다.

## 7. 프론트

```
modules/ontology/         api.ts · 메타모델 편집 (그룹·타입·속성·관계 종류)
modules/objects/          api.ts · ObjectListPage · ObjectProfilePage
                          PropertyFields — data_type 별 위젯 (타입·관계 공용)
                          ObjectPicker  — SearchablePicker 위에 얹는다
shared/layout/            navigation.ts 에 동적 그룹을 합류
```

**`PropertyFields` 와 `ObjectPicker` 는 `shared/` 에 두지 않는다.** 객체를 찾아
주는 picker 가 `modules/objects/api` 를 부르므로, `shared/` 에 두면 shared -> 모듈
방향이 거꾸로 선다 — 백엔드에서 금지한 그 방향이 프론트에서 되살아난다.

- 스타일은 Tailwind 유틸리티. 전역 CSS 클래스를 새로 만들지 않는다.
- 상태의 말과 색은 `StatusBadge` 가 정한다.
- **빈 목록은 이유를 말한다**(`EmptyState`) — 데이터가 없는 것인지, 거르기가 좁은
  것인지, 권한이 없는 것인지.
- **되돌릴 수 없는 일은 무엇이 사라지는지 적는다**(`ConfirmDialog`). 속성 정의를
  지우는 창은 **그 값이 몇 개 있는지**를 말해야 한다.
- 고를 것이 스물을 넘으면 `<Select>` 를 쓰지 않는다 — `SearchablePicker`.
- 목록에는 `Pagination` 을 붙인다.

## 8. 트래버설

`modules/objects/graph.py` 한 모듈. 공개 함수만 밖에서 쓴다.

```python
neighbors(db, object_id, *, relations=None, direction="both", depth=1)
descendants(db, object_id, *, relation)      # transitive 인 관계만 재귀
ancestors(db, object_id, *, relation)
```

내부는 **재귀 CTE**로 시작한다. 그래프 엔진으로 갈 일이 생기면 이 모듈 안만
바뀐다. `depth` 에는 서버가 상한을 강제한다 — 없으면 관계가 촘촘해지는 날
목록 하나가 DB 를 통째로 훑는다.

- **부서 홈 위젯** — 새 표를 안 만들었다. 저장된 뷰가 `summary`(묶어 보기 설정)와
  `home_order` 를 갖는다(`0018`). **부서 뷰만 홈에 오른다** — 개인 뷰를 부서 홈에 붙이면
  같은 화면을 보는 사람마다 다른 것이 뜬다. 축은 **저장할 때 검사한다**(`summary.check_group`·
  `check_metric`): 안 하면 열었을 때 그림만 안 뜨고 무엇이 잘못됐는지 말할 자리가 없다.
  `GET /objects/home?workspace=` 가 타입 이름과 아이콘까지 실어 준다 — 홈은 타입을 모른다.
  올리는 단추는 **묶어 보기 패널에** 둔다: 「이거 홈에 두고 싶다」 는 생각은 그림을 막 그려
  놓고 보는 그 자리에서 나고, 거기서 뷰 메뉴를 열어 저장하고 부서 공유를 켜고 메뉴를 다시
  열게 하면 **그 경로를 찾아낸 사람만** 이 기능을 쓴다. 저장과 올리기는 한 요청이다
  (`on_home`) — 둘로 나누면 저장은 됐는데 안 올라간 상태가 생긴다. 홈에서 출발하는 길도
  둔다(「위젯 추가」 → 타입 고르기 → `?group=1` 로 목록이 펼친 채 열림). **내리는 단추는 홈의
  위젯에** 둔다(순서 바꾸기도 같이 — 서버가 그 부서의 홈 뷰를 통째로 다시 매긴다).
  올리기만 쉽고 내리기가 어려우면 홈은 한번 올라간 것들로 곧 지저분해지고, 그러면
  아무도 안 본다. 내려도 뷰는 안 지운다.
- **개별 순위도 축이다** — 이름·식별자로 묶을 수 있다. 「그룹이 행 수만큼 나온다」 는
  이유로 막아 두면 **「점수 높은 부품 열 개」 를 그릴 방법이 아예 없고**, 사람이 실제로
  자주 보는 것이 그 그림이다. 상한(30)과 차례가 이미 있어 그대로 순위가 된다. 차례는
  `order` 로 뒤집는다 — 「가장 낮은 것」 을 찾는 물음이 따로 있다. 식별자를 안 쓰는
  타입에서는 그 축을 고르개에서 뺀다(고를 수 있다고 보여 주고 빈 그림을 주지 않는다).
- **두 축으로 쪼개기** — `split_by`. 「부서별 몇 건」 다음 물음이 거의 언제나 「그 안에서
  등급은」 이라, 그때까지는 거르기를 바꿔 가며 여섯 번 세야 했고 그러면 사람은 그 답을
  포기한다. **계열의 차례를 서버가 정한다**(`splits`) — 화면이 칸마다 나오는 대로 만들면
  첫 칸에 없던 값이 뒤에서 튀어나와 색이 밀리고, 같은 값이 그림 안에서 두 색을 갖는다.
  없는 계열은 화면이 0 으로 채운다(빈 자리는 「없음」 과 0 을 구별 못 하게 만든다). 쪼갠
  값은 열둘까지 — 색이 여덟이라 그 위로는 같은 색이 두 번 나온다. 두 축이면 히트맵
  (`LazyPlot`)과 쌓은/나란한 막대가 뜻을 갖고, 그 설정도 뷰에 담겨 위젯이 된다.
- **묶어 보기** — `objects/summary.py`, `GET /objects/{slug}/summary`. 넣은 다음의 물음
  (「그래서 부서별로 몇 건인데」)에 답한다. **목록과 같은 거르기**를 쓴다: `_filtered` 가 만든
  질의를 받아 열만 바꾼다(`with_only_columns`) — 따로 세면 「목록에는 12건인데 묶어 보면
  15건」 이 되고 어느 쪽이 맞는지 아무도 모른다. 묶는 축은 정의가 허락한 것만(긴 글·파일·
  여러 값은 거절하고 **이유를 말한다**), 날짜는 해로. 빈 값은 「(비어 있음)」 한 칸으로 남기고
  (숨기면 막대의 합이 전체와 안 맞는데 그 차이가 어디에도 안 적힌다), 서른을 넘는 그룹은
  「그 밖에」 로 접는다. 합·평균은 숫자로 안 읽히는 값을 NULL 로 두고 지나간다 — cast 는 행
  하나 때문에 질의를 통째로 죽이고, 화면에는 500 이 뜬다. 그림은 `shared/charts` 가 그린다
  (흔한 넷은 recharts, 무거운 것은 plotly — 쓸 때만 받는다).
- **세면 안 보이는 것** — `summary.points()`, `GET /objects/{slug}/points`. 평균 하나로
  접으면 「대부분 3kg 인데 둘이 40kg」 도 「고르게 20kg」 도 똑같이 20 이 되고, 그 둘을
  가르는 것이 대개 할 일이다. 그래서 **안 센 값**을 그대로 내려 주는 길을 따로 둔다
  (상자는 숫자 칸 하나, 산점도는 둘). 집계 길과 **같은 거르기**를 쓰고(`_filtered`),
  **값이 없는 행은 뺀다** — 0 으로 채우면 없는 점이 원점에 모여 그림이 거짓말을 한다.
  상한 3,000 점, 넘으면 그렇다고 적는다. 숫자가 아닌 칸을 고르면 거절하고 이유를 말한다
  (OBJECTS-57), 투영 타입은 원 표가 답할 자리가 없어 거절한다(OBJECTS-58).
- **정의를 두 모양으로** — 구조 그림에 사케이(「흐름」)를 붙였다. 그물은 「무엇이 무엇과
  이어지나」 를, 흐름은 「어디서 어디로 얼마나 가나」 를 보여 준다 — 접수 → 검토 → 승인처럼
  단계로 이어지는 구조는 그물에서 잘 안 읽힌다. **새 API 는 없다**(`/graph/overview` 가
  이미 노드와 굵기를 준다). 사케이는 한 방향으로 흐른다는 전제 위에 서 있어 순환을
  거부하므로, 굵은 것부터 넣고 **되돌아오는 선만 빼고 그 수를 화면에 적는다** — 조용히
  빼면 그림이 「그 관계는 없다」 고 거짓말한다. 굵기 0 인 관계(정의만 있는 것)는 빼고,
  이을 것이 하나도 없으면 단추를 안 낸다.
- **묶어 보기 설정은 패널 밖에** — `objects/summarySettings.ts`. 목록 화면이 축과 기본값을
  들고 있어야 하는데(뷰를 불러오면 그 축으로 열려야 하니까) 그 형이 `SummaryPanel` 안에
  있으면 목록이 패널을 **정적으로** 끌어와 `lazy()` 가 무색해진다 — 차트 라이브러리가
  목록을 열 때마다 함께 내려온다. rolldown 이 `INEFFECTIVE_DYNAMIC_IMPORT` 로 알려 주는
  그 일이다. 그림이 없는 조각만 떼어 두면 경계가 산다.
- **조용히 멎는 것을 홈이 말한다** — 동기화 실패·오래 안 돈 소스·포기한 웹훅 전송이
  `register_maintenance` 로 홈 「남은 일」 에 오르고, 시스템 관리자에게 알림이 간다.
  **상태가 바뀔 때만 알린다**(`datasources.services._announce`): 5분 타이머가 실패마다
  알리면 하루에 288개가 쌓이고, 그러면 그 종류는 통째로 안 읽힌다. 복구도 알린다.
  그 전까지 실패는 `last_status` 에만 적혔고, 그 화면은 잘 도는 동안 아무도 안 연다.
- **원 표가 사라진 타입이 홈을 멈추지 않는다** — `system.source_or_none`. 등록이 빠진 투영
  타입 하나 때문에 모든 타입을 훑는 화면이 409 를 내면 설치 전체가 멎는다. 살아 있는지 물을
  곳이 없는 참조 칸은 **품질에서 안 본다**(없는 「깨진 참조」 를 만들어 내면 사람이 멀쩡한
  값을 지우러 간다). 그 타입을 직접 여는 자리에서는 여전히 `source_of` 가 이유를 말한다.
- **조직도 트리 화면** — 부서 정보가 표에서 트리로. 끌어 놓기로 상하관계와 형제 순서를
  바꾸고(놓는 자리는 「줄 위 띠=앞 형제」·「줄 본체=막내 자식」 둘뿐), 그 한 번이 요청
  하나(`POST /workspaces/{slug}/move` 의 `position`)로 간다 — 화면이 형제 순서를 제 손으로
  다시 매겨 여러 번 저장하면 중간 실패가 트리를 반쯤 뒤섞어 놓는다. 셈은 `tree.ts` 에
  떼어 두어 시험이 잡는다(조직도가 틀어져도 **아무 오류도 안 난다**). 이름·하는 일·상위·
  공개를 한 창에서 고치고(주소는 못 바꾼다 — 다른 시스템이 그것으로 찾는다), 찾기는 맞은
  줄의 상위까지 남기고, 보관은 기본으로 숨긴다.
- **부서 통폐합(자료 옮기기)** — 다섯째 확장점 `register_workspace_content`. 도메인이
  「이 부서가 가진 것」 과 그것을 옮기는 함수를 걸고, `POST /workspaces/{slug}/reassign` 이
  고른 종류만 한 트랜잭션으로 넘긴다(객체·저장된 뷰·첨부·데이터 소스·멤버). **가리키는
  것(`references`)과 가진 것(`contents`)은 다른 물음이다** — 「담당 부서」 로 이 부서를
  가리키는 객체는 옮기는 것이 아니라 고치는 일이라 건드리지 않는다. 이 길이 없으면 FK 가
  RESTRICT 라 자료 있는 부서는 끝내 못 지우고, 쓰지 않는 부서가 목록에 영원히 남는다.

- **표에서 타입 만들기** — `ontology/inference.py`. CSV·JSON 데이터 파일의 열을 보고
  정의를 제안(보수적 — 애매하면 글자)하고, 사람이 고친 것을 `POST /ontology/infer/build` 가
  정의 스키마 + 가져올 행으로 바꾼다. 적용은 기존 두 길(`/ontology/import`,
  `/objects/{slug}/import-rows`)로 — 규칙을 새로 두지 않는다.

### 안 하기로 한 것

## 10. 검증

고칠 때마다 [AGENTS.md](../AGENTS.md) 의 넷을 돌린다. 이 설계에서 특히 걸리는 것:

- **`alembic check`** — 메타모델은 표가 많고 인덱스가 많다. 모델과 마이그레이션이
  어긋나면 **배포하고 나서 500 으로** 드러난다.
- **구조 시험** — `shared` 가 이 모듈을 import 하면 방향이 거꾸로 선다.
- **JSONB 인덱스** — 목록이 `properties` 를 타므로, `list_view` 가 거르는 키에는
  표현식 인덱스를 건다. 안 걸면 행이 몇만을 넘는 순간 목록이 느려지고, **느려진
  이유는 화면 어디에도 안 적힌다.**
