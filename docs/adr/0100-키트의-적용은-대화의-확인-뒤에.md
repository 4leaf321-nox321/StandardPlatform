# 0100. 키트의 적용은 대화의 확인 뒤에 — 미리 본 그 계획을 AI 가 넣는다

## 배경

정제 키트(로컬 MCP `sp_mcp.py`)는 처음부터 **적용 도구를 두지 않았다** — 「사람이 확인한 뒤에만 넣는다」
를 말이 아니라 도구의 모양으로 지키려고, AI 는 미리 보기 요약까지 보이고 사람이 그 플랫폼 화면 「작업」
에서 「적용」 을 누르거나 명령 창에서 `apply` 를 쳤다. 되돌리기도 같았다(`run_undo` 는 계획만, 되돌리는
것은 `undo_command`).

그런데 사람은 이미 대화에서 요약을 읽고 「좋다」 고 말한다 — 그 뒤 화면을 열어 같은 계획을 찾아 누르는
것은 확인을 한 번 더 하는 것이 아니라 손이 한 번 더 가는 것이다. 문서 올리기(ADR 0099)에서 사용자가
「대화에서 좋다 하면 AI 가 바로 쓰게」 로 정했고, 이어서 **나머지 적용도 같게**(2026-11-27 사용자 결정)
했다.

## 결정

### 1. 적용하는 도구 셋 — 미리 본 그 계획 작업만 넣는다

- **`run_apply(work, run)`** — `run_preview` 가 세운 계획 작업(`preview.json` 의 작업)을 플랫폼의
  `POST /api/jobs/{id}/apply` 로 넣는다. **화면의 「적용」 과 같은 길**이다: 같은 파일 · 같은 지문, 계획을
  세운 토큰의 주인으로(JOBS-12). 그 사이 누가 바꿔 판정이 달라졌으면 플랫폼이 거절하고(JOBS-20 — `failed`),
  화면에서 먼저 적용했으면 또 넣지 않는다(JOBS-22 — `already`, 그 적용의 결과를 싣는다). 넣는 곳은 **미리 본
  플랫폼**이다.
- **`run_undo_apply(run_id, plan_job)`** — `run_undo` 가 보인 되돌리기 계획(`plan_job`, 새로 돌려준다)을 같은
  길로 넣는다. 그 작업이 **그 판의 되돌리기 계획인지 먼저 본다**(종류 `bundle_undo` · 판 번호 · 계획 단계) —
  다른 작업 번호를 이 길로 적용하지 않는다. 번호 모양이 아니면 플랫폼에 묻지도 않는다.
- **`document_apply(work)`** — ADR 0099 그대로. 세 도구가 같은 함수(`apply_plan`)로 플랫폼에 적용을 청한다.

명령 창의 `apply` 는 그대로다(묶음을 다시 보내 넣는다 — 미리 본 지문과 파일을 대조한 뒤). 화면의 「적용」 도
그대로다. 키트의 셋은 그 옆의 세 번째 길이다.

### 2. 키트가 먼저 막는 것 — 사람이 「좋다」 해도

- 미리 본 뒤 실행 폴더의 묶음이 바뀜(지문) · 미리 보기에 오류 · 미리 본 플랫폼이 아님 · 이미 적용한 실행 ·
  닫은 실행 — `apply` 명령과 같다.
- **정의가 확정 전이거나 확정 뒤 바뀜**(`02-정의/ontology.json` 의 sha256 이 결정기록의 확정과 다름) — 화면의
  「적용」 은 작업 폴더를 모르므로 키트가 본다. 결정은 사람의 것이라(`decision_record(confirms_ontology=true)`)
  적용의 「좋다」 로 갈음하지 않는다.
- **같은 묶음(지문)을 이 작업의 다른 실행에서 이미 적용함** — 같은 원천을 다시 변환하면 실행은 새로 생기지만
  묶음은 같다. `work_status` 가 「또 넣지 않는다」 고 알리던 것을 적용이 지킨다.

적용이 거절되면(`failed`) 잠그지 않는다 — `apply_failed.json` 에 까닭을 남기고 `work_status` 가 그것을
말한다(ADR 0098 과 같다). 적용했거나 화면에서 먼저 적용했으면 `applied.json`(어디서 — `via` `kit` ·
`screen`, 적용 작업 번호).

### 3. AI 의 규칙 — 한 번의 「좋다」 는 그 계획 하나

도구 설명 · 서버 안내 · `AGENTS.md` 에 같은 말을 둔다:

- 계획을 사람에게 보이고 묻는다(어느 플랫폼 · 무엇이 바뀌나 · 끊을 선 · 사라질 것 · 되돌리기면 지움 ·
  되돌림 · 건너뜀). 사람이 **「좋다 · 적용해」**(되돌리기면 「되돌려」) 라고 한 뒤에 부른다.
- **한 번의 「좋다」 는 그 계획 하나다** — 앞선 실행 · 다른 계획의 「좋다」 로 부르지 않고, 고쳐 다시 미리
  봤으면 다시 묻는다. 여럿을 한마디로 말했으면 무엇무엇인지 목록을 보이고 확인받는다.
- 사람의 말 없이 · 짐작으로 · 오류가 있는 계획에 부르지 않는다. 「비슷한 정의」 · 「같은 칸 다른 모양」
  경고는 적용을 묻기 전에 따로 묻는다.

시험이 **적용하는 도구의 이름(`apply` 가 든 것)이 이 셋뿐인지**, 셋의 설명에 「한 뒤에만」 · 「짐작으로」
가 있는지 본다 — 새 적용 도구가 규칙 없이 끼어들지 않게.

## 대안 — 버린 것

- **화면 적용만 그대로** — 처음의 모양. 대화의 「좋다」 와 화면의 「적용」 이 같은 확인을 두 번 하게 하고,
  수십 개 실행이면 화면을 수십 번 연다. 사용자가 바꾸기로 정했다.
- **도구에 확인 문구를 인자로**(`confirmed="좋다"` 같은) — AI 가 채우는 칸이라 사람이 말했다는 증거가
  아니다. 막는 힘은 없고 모양만 생긴다. 대신 **사람이 본 그 계획 작업에만** 묶었다 — 미리 보지 않고는 부를
  것이 없고, 본 뒤 바뀐 것은 지문이 막는다.
- **명령 창의 `apply` 와 한 길로 합치기**(그것도 계획 작업을 적용하게) — 맞는 방향이지만 명령 창 · 시험 ·
  안내가 함께 바뀐다. 이번에는 키트 MCP 만 바꾸고, 명령 창은 지금 모양(파일 대조 뒤 다시 보내기)을 둔다.
- **되돌리기는 다시 계획해 곧장 넣기**(`undo?apply=true`) — 사람이 본 계획과 넣는 계획이 다를 수 있다.
  계획 작업(`plan_job`)을 적용해 지문으로 묶는다.

## 결과

- DB 마이그레이션 없음. 새 `.env` 값 없음. 플랫폼 코드 변경 없음 — 토큰의 작업 적용(범위 `objects:write`,
  정의가 든 묶음은 `ontology:write` — `needs_scope`)은 있던 길이다. 감사 기록 · 작업에 토큰으로 적용했다는
  것(`by_token`)이 남는다.
- 키트 도구 25개(`run_apply` · `run_undo_apply` 추가). `run_undo` 가 `plan_job` · `on_screen` 을 돌려준다.
  키트를 새로 받아야 쓰인다.

## 보강(2026-11-27, [ADR 0101](0101-재점검-고침-묶음.md))

- 받아들여졌는데 아직 대기 · 도는 중인 적용은 거절이 아니다 — `waiting`, `applying.json`. `work_status` 가 그 적용
  작업에 다시 물어 끝나면 「적용함」, 실패면 「적용 거절됨」. `applied.json` 은 **끝나 들어간** 적용에만 쓴다(화면에서
  적용한 것도).
- 「정의 확정 전이면 적용 안 함」 은 **실행이 싣는 정의**(실행의 `ontology.json`)를 지금 확정한 정의와 견준다.
  미리 본 뒤 작업의 넣을 곳을 바꿨으면 다시 미리 본다.
- **가벼운(백필) 미리 보기에는 지문이 없다** — 적용 때 다시 판정한다. 위의 「같은 지문 · 지문이 막는다」 는 온전한
  미리 보기의 것이다.
- 작업 · 판 번호는 uuid 꼴만 주소에 넣는다(`run_undo` 의 번호 꾸미기로 되돌리기가 들어가던 것).
