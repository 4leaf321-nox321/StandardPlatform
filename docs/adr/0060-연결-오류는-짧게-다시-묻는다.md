# 0060. 연결 오류는 짧게 다시 묻는다 — 쪽마다 세 번, 실패하면 15 → 30 → 60분 뒤

- 상태: 채택(2026-11-08 구현)
  - 받기: `datasources/retry.py` 의 `get`(OData · REST · 파일 URL · 형제 코어 · RA 의 쪽마다), HTTP 오류에
    `details.upstream_status`
  - 실행 기록: `DataSourceRun.error_kind`(마이그레이션 0098) — `retry.failure_kind`
  - 타이머: `services.connect_retry_after` · `due`, 첫 실패 알림의 본문(`FAILED_BODY`)
  - MCP `datasource_runs` 설명, 사용자 안내서
- 날짜: 2026-11-08
- 관련: [ADR 0059](0059-자료가-언제까지-들어왔나.md)(최종 수집 시각 · 수집 실패), 웹훅의 재시도(3회 · 60초)

## 배경

받기는 쪽마다 한 번 묻는다. 그 한 번이 연결 오류 · 시간 초과 · 502 를 받으면 그 실행을 닫았고, 타이머는 정기
간격(`interval_minutes`, 하루 간격 소스가 흔하다)이 지나야 다시 물었다(`due` 는 실패 여부를 보지 않았다). 사내
API 의 야간 점검 몇 초가 하루치 기록을 늦추고, 그사이 지표는 미반영 구간을 말한다(ADR 0059).

NVIDIA Auto Ontology 와 견준 조사(2026-11-07, SP 개선 목록 「다음」 — 연계 핵심)에서 나왔다. AO 는 오류를 「SQL
틀림 · 세션 잃음 · 연결 안 됨」 으로 가르고 세션을 잃었을 때만 한 번 다시 열며, 수집 전체가 실패하면 다음 24시간
차례까지 기다린다. SP 의 오류 코드는 이미 예외 단계에서 갈리지만(DATASOURCES 11 인증 · 12 HTTP · 13 연결) 실행
기록에는 글만 남았다.

## 결정

1. **쪽마다 짧게 다시 묻는다**(`retry.get`). 연결이 안 됨 · 끊김 · 시간 초과(`TimeoutException` ·
   `NetworkError` · `RemoteProtocolError`)와 HTTP 429 · 502 · 503 · 504 만, 2초 · 8초 물러나며 두 번 더 —
   쪽 하나에 세 번. `Retry-After`(초)는 따르되 30초까지. 이미 받은 쪽은 그대로라 실패한 쪽부터 잇는다. 401 ·
   403 · 그 밖의 4xx · 500 · 응답 모양 오류 · 주소 꼴 오류는 다시 묻지 않는다 — 다시 물어도 같다. 화면에서 한 번
   묻는 카탈로그 · RA 조직 트리는 그대로 둔다(사람이 기다린다).
2. **실패의 종류를 칸으로 남긴다**(`DataSourceRun.error_kind`) — `connect`(연결 못 함 13 · 형제 코어 38 · RA
   56, 그리고 다시 물은 끝에도 429/5xx 인 HTTP 오류) · `auth`(11 · 51) · `source`(주소 · 응답 오류). 대응 ·
   행 오류 · 그 밖은 비운다. HTTP 오류는 상대의 상태를 `details.upstream_status` 로 싣는다(글에서 숫자를 다시
   읽지 않게).
3. **연결 실패면 정기 간격보다 짧게 다시 넣는다**(`connect_retry_after`). 마지막 실행부터 거슬러 연달아
   연결 실패인 횟수로 15 → 30 → 60분(넘으면 60분), 정기 간격보다 길면 정기 간격. 계획만 본 실행은 건너뛰고,
   정기 실행이 아닌 소스(간격 0) · 비활성 소스는 타이머가 돌리지 않는다. 실행 기록의 오류 줄에 「약 15분 뒤 다시
   시도합니다」.
4. **첫 실패 알림을 종류마다 다르게**(알림은 상태가 바뀔 때만 — 그대로): 연결 실패는 「연결 오류입니다 — 짧게
   다시 시도합니다」, 인증 거절은 「다시 시도해도 같으므로 인증을 확인하세요」, 그 밖은 예전 문구.

## 대안 — 버린 것

- **실행 전체를 다시 돌리기(작업 재시도).** 받은 쪽을 다시 받고, 적용한 조각이 있으면 두 번 센다. 쪽 하나를
  다시 묻는 편이 싸고 정확하다.
- **오래 기다리며 여러 번(지수 물러남 1분 · 5분 …) 한 실행 안에서.** 작업 하나가 워커를 몇 분씩 붙잡는다 —
  차례(round)의 다른 소스가 밀린다. 긴 장애는 타이머의 짧은 재시도(3)가 맡는다.
- **error_kind 를 글에서 다시 읽기.** 마이그레이션이 없지만, 문구를 고치는 날 판정이 조용히 바뀐다.

## 결과

- 시험: 쪽 하나의 503 · 연결 끊김은 그 쪽만 다시 묻고 실행이 성공(받은 쪽은 한 번만), 세 번 다 실패하면
  `connect` · 15분 뒤 차례(여유 5분) · 둘째 실패는 30분 · 돌아오면 정기 간격, 인증 거절은 한 번만 묻고 정기
  간격 · 알림 문구, 간격 0 소스는 타이머가 안 돌림. 단위: 다시 묻는 것 · 안 묻는 것 · `Retry-After` 상한 ·
  실패 종류 표.
- 시험은 기다리지 않는다(`tests/conftest.py` 의 `_retry_without_waiting`).
