# 0051. 자주검증 포스트모텀 입력 프론트 — 허브의 기존 타입 위에 얹는 얇은 확장, 관리 단위는 문제점

- 상태: 제안(2026-11-04) — 1차 · 2차 구현됨(「결과」)
- 날짜: 2026-11-04
- 관련: [ADR 0005](0005-온톨로지-메타모델.md)(도메인은 데이터로), [ADR 0006](0006-인터페이스.md), [ADR 0011](0011-축과-기록.md)(축 · 기록),
  [ADR 0012](0012-이미지-첨부.md)(사진은 공통 첨부), [ADR 0027](0027-검토함.md), [ADR 0036](0036-기록은-구성원도-넣는다.md),
  [ADR 0039](0039-관계의-유효-기간과-시점-질의.md), [ADR 0042](0042-제안된-관계.md)(AI 가 뽑은 선은 제안으로),
  [ADR 0044](0044-자주검증-회의-모듈.md)(회의 표 — 같은 조직의 다른 확장), [ADR 0050](0050-뜻으로-찾기의-바탕.md),
  확장 `caegroup`(설정 한 줄로 코어 타입을 가리키는 무늬)

## 배경

자주검증 조직의 자료(포스트모텀 · 심사회 · 설명회)는 이미 허브에 **온톨로지 타입으로 정형 적재**돼 있다 — 문서 · 문제점 · 단계별
판정 · 원인 · 재발방지 · 결과요약 지표 · 장표 그림(타입 접두 `sv_pm_*`). 문서들은 같은 틀이고 분량만 다르다. 없는 것은 **사람이 쓰기
좋은 입력 · 열람 화면과 집계**다.

관리 단위는 문서가 아니라 **문제점**이다. 문제점 하나가 1급 객체이고, 부품 · 고장모드 · 메커니즘 · 발견 채널 · 단계판정 · 일정 상태 ·
범위 · 외부 이슈 번호 같은 **태그 · 속성 축**으로 추적한다. 문서는 관리되는 문제점을 **선택 · 참조해 구성**하고(재입력이 아니다), 같은
문제점이 심사회와 포스트모텀에 겹치면 하나로 참조한다. 결과요약은 자동 집계다. 쓰기는 사람과 LLM(MCP)이 함께 한다.

제약:

- 한 번들로 여러 인스턴스가 뜬다 — 확장 모듈(켜기 · 끄기)로 붙인다.
- **코어 기준정보(고장모드 · 메커니즘 · 원인)와의 매칭은 이 확장의 일이 아니다**(조회 · 참조만 — 다른 담당의 영역).
- 「자주검증 회의 표」(`jajuverify`, ADR 0044)가 이미 있다 — 다른 것과 연결은 없다. 온톨로지 연결 틀은 플랫폼 쪽이 따로 정의한다.

## 결정

### 1. 데이터 모델은 허브의 기존 타입이다 — 표도, 타입도 새로 만들지 않는다

`sv_pm_*` 가 이미 ADR 0005 의 모양(타입 · 속성 · 관계)으로 들어 있다. 확장은 그 위에 **읽는 방향이 다른 화면**만 얹는다. 쓰기는 코어
객체 API(`POST/PATCH /api/objects/<타입>`)로 간다 — 검증(`validate_properties`) · 권한(부서 소유 · 구성원이 넣는다) · 감사 · 참조
색인 · 첨부가 그대로 따라오고, 확장이 쓰기 길을 두 벌로 만들지 않는다. **마이그레이션은 설정 한 줄 표 하나뿐이다.**

### 2. 타입 slug 는 코드에 박지 않는다 — 설정 한 줄이 가리킨다(`caegroup` 무늬)

허브의 slug 를 코드에 박으면 형제 설치(다른 이름의 타입 · 아직 적재 안 된 설치)에서 깨지고, 온톨로지를 고치는 순간 확장이 멈춘다.
그래서 설정 표 `svinput_settings`(id = 1 하나) 에 **역할 → 타입 slug · 칸 키**를 적고 시스템 관리자가 화면에서 고른다:

| 역할 | 뜻 | 기본 후보 |
| --- | --- | --- |
| `spine` | **과제 · 모델 — 코어의 축.** 문서 · 집계가 이 축으로 묶인다. 확장은 가리키기만 한다(만들지도 고치지도 않는다) | `plm_project` |
| `report` | 포스트모텀 문서 한 장 — 과제(`project` → 스파인). 비이슈 장표는 `slide_image` 로 보존 | `sv_pm_report` |
| `issue` | **문제점 — 관리 단위.** 현상 · 개선대책 · 단계별 판정 흐름 · 일정 상태 · 재발방지 · 범위 · 부품 · 고장모드 · 메커니즘 · 발견 채널 · 외부 이슈 번호 · 출처 | `sv_pm_issue` |
| `stage_result` | 단계별 판정 — 이슈의 하위 기록(단계 × PASS/FAIL) | `sv_pm_stage_result` |
| `cause` | 원인 — 이슈의 하위 기록 | `sv_pm_issue_cause` |
| `prevention` | 재발방지 — 이슈의 하위 기록 | `sv_pm_prevention` |
| `kpi` | 결과요약 지표 — 문서마다 셋, `numerator` · `denominator` 가 숫자 칸 | `sv_pm_kpi` |
| `figure` | 장표 그림 — 보이는 것 · 왜 중요한지가 글로 뽑혀 있음 | `sv_pm_figure` |

역할마다 **칸 역할**도 함께 적는다 — `model`(문서 → 스파인 참조 칸) · `report_ref`(이슈 · 지표 → 문서) · `issue_ref`(하위 기록 · 그림 →
이슈) · `stage` · `result`(판정의 단계 · PASS/FAIL 칸) · `status`(이슈의 일정 상태 칸). 설정 화면이 그 타입의 속성 정의를 읽어 고르게
하고, **없는 칸을 고를 수 없게** 한다. 후보는 역할마다 갈린다 — 허브 역할은 접두 `sv_pm_` 타입, 스파인은 그 밖의 코어 타입(`hub`).
설정이 비면 화면은 「먼저 설정에서 타입을 고르세요」 를 말한다(0건을 「없다」 로 읽게 두지 않는다 — AGENTS.md). **코어 참조(부품 ·
고장모드 · 메커니즘)는 보여 주고 고르기만 한다.**

### 3. 연결은 참조 칸 또는 관계 종류 — 여럿 대 여럿

한 문제점이 심사회 · 포스트모텀 · 설명회에 함께 실린다. 참조 칸 하나(`report`)로는 한 문서에만 속한다. 그래서 `report_ref` · `issue_ref`
는 **참조 칸(여럿 값 포함) 또는 관계 종류(`rel:<slug>`)** 둘 다 받는다 — 허브의 실제 연결이 어느 쪽이든 설정으로 맞춘다. 관계면 코어
`object_relations` 를 `edges.alive`(오늘 살아 있는 선, ADR 0039)로, 방향을 가리지 않고 읽는다(`services.members` 한 함수).

### 4. 화면 — 문제점이 첫 메뉴, 문서는 문제점을 끌어와 구성

| 층 | 경로 | 내용 | 코어에서 받는 것 |
| --- | --- | --- | --- |
| 문제점 목록 | `/ext/svinput/issues` | 관리 단위 — 고르기 칸으로 거르고 횡단으로 본다. 모든 거르기 · 통계는 코어 목록(`/o/<타입>`) | `objectApi.list` · `summary` |
| 포스트모텀 목록 | `/ext/svinput/postmortems` | 스파인(과제)으로 거르기 · 과제 상세는 코어 화면으로 · 「새 포스트모텀」 | `list(report, p.<model>=…)` · `ObjectCreateDialog` |
| 문서 한 장 | `/ext/svinput/postmortems/:id` | 머리 + 문제점 수 · 판정 집계 · 지표 + 문제점 줄(하위 기록 수 · 통과/실패) · **「문제점 끌어오기」**(코어 `ObjectRefPicker` 로 고르고 연결 모양대로 잇는다) · 「새 문제점」 | 확장 API `reports/{id}` + 코어 `profile` · `update` · `addRelation` |
| 문제점 한 페이지 | `/ext/svinput/issues/:id` | 장표 한 장처럼 — 칸(속성 정의대로 `PropertyFields`, 그 자리 수정) · 사진(공통 첨부) · 하위 기록 넷의 표와 「추가」 | `profile` + `PropertyFields` + `list(child, p.<issue_ref>=…)` |
| 집계 | `/ext/svinput/dashboard` | 단계 × 판정(PASS/FAIL) 막대 · 일정 상태 원 — 결과요약 페이지를 **자동 집계로 대체** | `summary(stage_result, group_by=properties.<stage>, split_by=properties.<result>)` · `summary(issue, group_by=properties.<status>)` |
| 설정 | `/ext/svinput/setup` | 역할 → 타입 · 칸, 후보에서만, 빠진 것 배지 | 확장 API |

폼은 코어 `PropertyFields` 가 **속성 정의대로** 그린다 — 칸이 늘어도 화면 코드가 안 바뀐다. 그림은 `shared/charts` 의 `Chart`. 이름
고르기는 `SearchablePicker` · `ObjectRefPicker`. 목록에는 `Pagination`.

### 5. 확장이 코드로 하는 일 — 넷뿐

1. 설정(한 줄 표 · 상태 · 후보 제안 — 모르는 역할 · 없는 타입 · 그 타입에 없는 칸은 422).
2. 「문서 한 장의 문제점 + 하위 기록 수(판정 통과 · 실패)」 를 한 요청으로 주는 읽기 API(`GET /api/ext/svinput/reports/{id}`) — 화면이
   이슈마다 하위 목록을 세 번 묻지 않게. 코어 서비스 함수를 import 해 센다(새 질의 엔진 없음). 볼 수 있는 것만(설치의 조회 범위).
3. 집계 API 는 두지 않는다 — 코어 `summary` 가 이미 답한다. 확장 화면이 설정의 칸 키로 그 주소를 만든다.
4. 공통 화면 훅 — `profile_facts`(자기소개 · 켠 설치에서만) · `stats`(「쌓인 것」) · `maintenance`(「남은 일」 — 설정 안 됨, 시스템
   관리자에게만). PAT 범위 `svinput:write` 는 설정 변경에만 — 객체 쓰기는 `objects:write`. MCP 는 전용 도구 없이 `extensions_schema` ·
   `extension_call`(ADR 0044 결정 20) — 가이드 주제 `svinput`.

### 6. 범위 밖 — 적어 두지 않으면 「왜 없지」 가 된다

- **중복 제거 · 교차 재사용**은 코어의 것으로 — 같은 이름 · 별칭(검토함 `duplicate`) · 뜻으로 비슷한 기록(ADR 0050). 심사회 · 설명회 이슈가
  같은 모양을 따르는 것은 **인터페이스**(ADR 0006) — 정의(데이터)의 일이다.
- **심사회 · 설명회** — 설정의 역할 묶음을 종류별로(`kinds`) 두면 화면 세 층은 같고 머리의 말만 다르다. 체크리스트는 새로 만들지 않는다
  (자동 검증 결과를 데이터 소스로 **받아 붙인다**).
- **LLM 편집 경로** — 사용자별 PAT(`objects:write`) + 허브 MCP 로 되는 길이 있고, 「허브 내장 LLM 패널」 은 코어 결정이다.
- **피더**(산발 자료 → 문제점 초안 + 태그 제안 → 사람 확정)는 `pipeline/` + 묶음 + 제안된 관계(ADR 0042) · 검토함(ADR 0027)의 일이다.
- **온톨로지 연결 틀**(태깅 · 입력 시 검색 · 선택)은 플랫폼 쪽이 정의한 뒤에 맞춘다.

## 대안

- **확장 전용 표**(`jajuverify` 1단계 방식) — 이슈가 이미 타입으로 있다. 전용 표로 두면 그것을 옮기거나 두 벌이 된다.
- **코어 타입 신설** — 코어 불가침. 기존 타입으로 충분.
- **문서 단위 입력 폼**(사람이 칸을 채움) — 문서마다 재입력 · 중복, 문제점이 트래킹되지 않는다. 관리 단위가 틀렸다.
- **관계 없이 참조 칸만** — 여럿 대 여럿(대책 하나가 불량 둘을 푼다)을 못 적는다.
- **심사회 · 설명회부터** — 커버리지가 넓고 칸 · 대책 수가 많다. 포스트모텀이 좁고 판정이 이미 구조화돼 있다.
- **온톨로지 연결을 먼저** — 틀이 따로 정의된다. 프론트를 쓰기 좋게 먼저.
- **원천 시스템의 운영 UI 직접 개선** — 운영 무변경. 확장은 비침습 선행 실험장.
- **확장이 쓰기 API 를 따로 둔다**(이슈 + 판정 n줄을 한 트랜잭션에) — 1차는 코어 API 를 화면이 차례로 부른다. 필요가 실측으로 드러나면
  그때 확장 POST 하나를 더한다(검증 · 감사는 코어 것 그대로).
