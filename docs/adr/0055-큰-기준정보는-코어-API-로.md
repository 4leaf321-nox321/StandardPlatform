# 0055. 큰 기준정보는 코어 API 로 — 정의는 묶음, 행은 묶음 구독

- 상태: 채택(2026-11-06 구현 — 코어 API 의 `shape=sp`(행 `extra` · 선 `periods` · 카탈로그 `shapes`), 선의 참조 칸을
  `key` 로, 커서를 행 비교로, 형제 코어 소스의 쌍 맞춤(`_cut_leftovers`) · 옛 식별자 · `extra` 싣기, 끊긴 받기 바로
  잇기(`sync_through`), 묶음 구독(`POST /api/datasources/subscriptions` · 「묶음 구독」 창), 연동 키트 2026-11-06 판)
- 날짜: 2026-11-06
- 관련: [ADR 0039](0039-관계의-유효-기간과-시점-질의.md)(관계의 유효 기간 — 코어 API 는 오늘 유효한 선만),
  [ADR 0041](0041-파생-계보-관계와-개정-고정.md)(계보 고정), [ADR 0024](0024-지표-증분과-홈-지표.md)(시계가 앞으로만 간다),
  `docs/외부-시스템-연동-지침서.md` §4.4(어느 길로 받나)

## 배경

0.4.74 는 묶음 내보내기에 **한 봉투 50만 줄 상한**을 두었다. 봉투를 통째로 메모리에서 만들어 200만 줄이면 워커가
10GB 를 넘겨 죽었고(실측), 받는 쪽도 파일 상한(100MB)과 한 트랜잭션에 걸렸다. 쌓이기만 하는 기록은 「정의만」 묶음 +
코어 API 로 빼면 됐지만, **기준정보 자체**(부품 80만 · BOM 120만 줄)가 커지면 갈 길이 없었다 — 코어 API 는

- 오늘 유효한 선만 준다(ADR 0039). BOM 의 「3월 1일부터 A1 → A2」 에서 한쪽이 빠진다.
- 계보 고정(ADR 0041) · 객체의 설명 · 유효 연도 · 별칭의 출처와 확인 표시를 안 준다.
- 선에 붙은 참조 칸을 공개 측의 내부 id(uuid)로 내보냈다 — 받는 쪽에서 아무것도 못 가리켰다.

받는 쪽(형제 코어 데이터 소스)도 둘이 모자랐다 — 한 차례 5만 줄에서 끊고 **다음 차례는 동기화 간격만큼** 기다려,
200만 줄의 처음 받기가 40차례(간격 1시간이면 이틀 가까이)였다. 그리고 소스가 타입마다라 묶음 하나에 소스 열 개를 손으로
만들어야 했다.

처음 떠올린 길은 **묶음 쪽을 키우는 것**이었다 — 봉투를 쪽으로 흘려 쓰기(메모리 일정 · 끊긴 자리부터 이어 받기)와
바뀐 것만 보내기(증분). 그런데 그 둘이 새로 만들어야 할 것 — 쪽 · 커서, 끊긴 자리, `since` · `as_of`, 도는 적재보다 앞선
시계(`watermark`), 지운 것 · 합친 것 · 끊긴 선의 무덤, 무덤 보관 기간이 지나면 처음부터 다시 맞추기 — 가 **코어 API 와
형제 코어 소스에 이미 다 있었고, 실측으로 구멍을 몇 번 막은 코드였다.** 묶음에 같은 것을 또 만들면 같은 일을 하는 길이
둘이 되고, 둘은 갈린다(무덤에서 이미 한 번 갈렸다 — 코어 API 는 지운 것을 알렸는데 묶음은 안 보냈다).

## 결정

**정의는 묶음(「정의만」 — 사람이 미리 보고 적용, 허브 관리가 선다), 행은 코어 API(바뀐 것만 쪽씩).** 코어 API 가
기준정보를 온전히 싣게 넓히고, 받는 쪽을 그 모양에 맞추고, 묶음 하나를 한 번에 구독하게 한다. 50만 줄 이하의 묶음은
지금처럼 한 봉투로도 받는다.

### 1. 코어 API 의 SP 모양 — `shape=sp`

바깥 시스템(RA · 연동 키트)의 모양은 그대로 두고, 형제 SP 가 청할 때만 더 싣는다.

| | 기본(`core`) | `sp` |
| --- | --- | --- |
| 행 | 지금 그대로 | `extra`: 설명 · 유효 연도 · 별칭(`value` · `source` · `note` · `verified`) — 빈 것도 싣는다(받는 쪽이 거울) |
| 선 | 오늘 유효한 선, 줄마다 | **`(src, relation, dst, dst_type)` 쌍마다 그 쌍의 기간 전부**(`periods` — 기간 · 붙은 값 · 계보 고정 · 낡음 판정). 비면 다 끊겼다 |
| 선의 흐름 | 바뀜 · 끊김 · **경계일이 지남** | 바뀜 · 끊김(경계일은 일이 아니다 — 기간이 바뀐 것이 아니다) |
| 카탈로그 | `shapes: ["core", "sp"]` 가 는다 | 같다 |

- **쌍으로 보내는 까닭**: 선 하나씩 보내면 받는 쪽이 「기간을 고친 선」 과 「새 기간의 선」 을 못 가른다(선의 정체가
  기간까지다 — ADR 0039). 쌍의 지금 목록 하나를 보내면 고침 · 끊음 · 새로 이음이 다 그 목록 하나로 온다.
- 기본 모양에는 `extra` · `periods` 가 `null` 로 선다 — 봉투의 칸이 는다(키트 2026-11-06 판에 적었다). 줄일 수는
  있었다(값이 없으면 키를 빼는 직렬화) — 그러면 OpenAPI 의 모양이 흐려지고, 키트의 시험장 · 실제 응답을 견주는 시험이
  「늘 같은 칸」 을 볼 수 없다.
- **선에 붙은 참조 칸은 두 모양 모두 `key` 로** — 객체 칸의 참조와 같은 규칙(못 보는 상대는 뺀다). 버그였다.

### 2. 받는 쪽 — 쌍을 목록대로 맞춘다

- 쌍마다 기간 하나가 관계 적재의 한 줄이 된다(붙은 값 · 계보 고정을 실어 — 받는 쪽이 새로 박지 않는다).
- **넣기 전에 목록에 없는 이쪽 기간을 끊는다**(`_cut_leftovers` — 무덤과 같은 규칙, 기간째로). 다만 **기간만 바뀐 선은
  끊지 않는다** — 목록의 한 기간과만 겹치는 이쪽 선 하나는 일괄 입력이 그 기간으로 고친다(선 id · 이력이 이어진다).
  끊는 것은 어느 기간과도 안 겹치는 선과, 한 기간에 둘 이상 겹친 선(허브에서 기간을 합쳤다)이다.
- 끊는 범위는 **그 소스가 이은 선과 그 소스의 출처가 관리하는 관계 종류(허브 관리)의 선**이다. 사람이 이은 선은 안
  끊는다(처음부터 다시 받기의 정리와 같은 규칙). 허브 관리 종류는 쌍둥이에서 아무도 못 이으므로 묶음으로 받아 둔 선까지
  정리한다 — 묶음에서 구독으로 옮겨 온 설치.
- ⚠️ **미리 보기는 끊을 것을 셈만 한다.** 세이브포인트 안에서 끊어 보고 무르는 길을 먼저 짰다 — 끊기가 쌓아 둔 변경
  알림(`events`)은 세이브포인트를 물러도 안 버려져, 실행 기록을 커밋할 때 **끊지 않은 선의 웹훅이 나갔을 것이다.**
- 이쪽 관계 종류가 기간을 안 받으면 오늘 유효한 기간 하나만 넣는다(기본 모양이 하던 것과 같다).
- **옛 식별자**(`renamed_from` · `previous_keys`)를 행에 싣는다 — 형제 코어 소스는 원래 이것을 안 실어, 허브에서 품번을
  바꾸면 쌍둥이에 같은 것이 하나 더 생겼다(두 모양 모두 고쳤다).
- 상대가 `periods` 를 안 주면(0.4.74 까지) 「상대를 0.4.75 이상으로」 로 그 차례의 선을 멈춘다 — 오늘의 선만 받고
  넘어가면 지난 · 앞으로의 BOM 이 조용히 빠진다.

### 3. 끊긴 받기는 같은 작업이 끝까지 잇는다

`sync_through` — 적용에 성공했는데 끊은 자리가 남았으면 다음 간격을 기다리지 않고 바로 다음 차례를 돈다(차례마다
커밋 — 도중에 멈춰도 받은 만큼은 남고 다음 작업이 끊은 자리에서 잇는다). 같은 타입 안의 선(부품 → 부품)이 뒤 차례에
올 끝 객체를 기다리면, **기다리는 선이 줄어드는 동안** 더 돈다 — 한 차례에 하나도 안 줄면 멈춘다(끝내 안 올 끝점에
같은 일을 되풀이하지 않게). 상한 400차례(2,000만 줄). 차례 작업(타이머)도 같다 — 가리키는 쪽 소스를 다 받은 뒤 다음
소스로 간다.

### 4. 묶음 구독

**관리 › 데이터 소스 › 「묶음 구독」**(`POST /api/datasources/subscriptions`) — 형제 설치의 API 주소 · `core:read` 토큰 ·
이 설치의 사이드바 묶음을 적으면 그 묶음의 타입마다 형제 코어 소스를 만든다. 「미리 보기」(상대의 카탈로그를 읽어
맞춰 봄) → 「생성」.

- 출처 이름 = 그 타입의 허브 관리 이름(`managed_by`) — 다르면 허브 관리 타입에 아무것도 안 들어간다.
- 선 받기 · `shape=sp` · 쪽 2,000(코어 API 상한)을 켜고, 칸 대응은 대응 제안과 같은 규칙에 **식별자 key → key** 를
  더한다 — 기준정보는 허브의 식별자가 곧 이쪽 식별자다(참조 · 선의 끝점이 그것으로 풀린다). 대응 제안은 key 를 잇지
  않았고, 그래서 식별자가 필수인 기준정보 타입에는 한 행도 안 들어갔다(시험을 짜다 드러났다).
- 상대가 코어로 공개하지 않은 타입은 까닭과 함께 건너뛴다. 같은 주소 · 타입의 소스가 있으면 두 번 만들지 않는다.
- 상대 카탈로그에 `shapes` 가 없으면(0.4.74 까지) 거절한다(`DATASOURCES-0060`).

### 5. 커서를 행 비교로(실측으로 드러난 원래의 구멍)

코어 API 의 쪽 넘김 커서가 `(시각 > m) OR (시각 = m AND id > l)` 이었다. PostgreSQL 은 이 OR 를 색인 경계로 못 써서
**색인을 처음부터 훑었다** — 200만 행 타입의 150만 번째 뒤 한 쪽이 질의만 0.65초 · API 4.2초였고 깊이에 비례해 늘었다.
뜻이 같은 행 비교 `(시각, id) > (m, l)` 는 그 자리에서 시작한다(질의 1ms, API 0.34초). 선의 흐름도 같이 고쳤다.

## 대안 — 버린 것

- **묶음을 쪽으로 흘려 쓰고 증분으로**(처음 안) — 위 배경. 같은 일을 하는 길이 둘이 된다. 그리고 증분 묶음은 받는 쪽의
  「맞춤」(묶음에 없는 선을 끊는다)과 부딪쳐, 한 선만 바뀌어 그 줄만 보내면 그 객체의 나머지 선이 끊긴다.
- **한도를 올리기**(50만 → 500만) — 보내는 쪽 메모리(20만 줄 720MB, 줄 수에 비례) · 받는 쪽 파일 상한 · 한 트랜잭션이 함께
  커진다. 그리고 매일 전량을 다시 보낸다.
- **코어 API 의 기본 모양을 바꾸기**(기간 전부를 기본으로) — 바깥 시스템의 코드는 선을 `(src, relation, dst, dst_type)`
  하나로 쥔다(키트). 기본을 바꾸면 그쪽이 같은 선 여럿을 받아 덮어쓴다.
- **행도 사람이 미리 보고 적용** — 매일 수백 줄의 바뀐 행을 사람이 볼 수는 없다. 허브 관리 타입은 쌍둥이에서 고칠 수 없는
  자료라 자동이 맞다고 봤다. 구조(정의)는 여전히 「정의만」 묶음을 사람이 보고 적용한다. 자동으로 받지 않으려면 간격을
  0 으로 둔다(「동기화」 를 클릭할 때만).
