# 0023. 머무는 기간과 큰 자료 — 보증 중 대수를 정의로, 상한을 실제 셀로

- 상태: 채택(2026-10-05 구현 — 머무는 기간 · 상한, 200만 · 2,000만 건 실측. 수치는 「결과」)
- 날짜: 2026-10-05
- 관련: [ADR 0013](0013-지표.md)(지표 · 분모 · 셀 상한), [ADR 0014](0014-분석.md)(분석 · 읽기 상한),
  [ADR 0021](0021-조건-비율-전후-비교-클레임-예측.md)(전후 비교 · 클레임 예측)

## 배경

**기간 축 건수의 덫.** 개발 서버에 스마트폰 시장 서비스 합성 자료(기록 13.6만 건, 심은 신호가 있는)를 넣고
분석을 물었다. 접수월마다의 건수로 변화점을 보면 **신모델 출시 때마다 「올랐다」 가 섰고**(2024-02 · 2025-03 ·
2026-03), 심어 둔 SW 배포 사건(2025-11 ~ 12)은 「계절」 로 묻혔다 — 시장에 깔린 대수가 늘어 건수가 늘었을
뿐이다. 「보증 중 대수」(그 달에 보증 기간 안에 있는 대수 — 최근 12개월, 유럽 24개월 판매의 합)로 나눈
비율에서야 사건이 「2025-11 에 1.76배로 올라 2026-02 에 내렸다」 로 잡혔다.

그런데 보증 중 대수는 **지표 정의로 만들 수 없었다.** 판매 지표는 「그 달에 판 대수」 이고, 「최근 N달의
합」 은 바깥에서 계산해 새 타입으로 넣어야 했다(2,814줄). MCP 로 AI 가 만들려면 AI 가 수를 직접 계산해 행으로
보내야 한다 — 「계산은 플랫폼이, AI 는 해석만」 에서 벗어나고, 자료가 크면 못 한다.

**상한.** 앞으로 훨씬 많은 자료를 분석해야 한다(사용자, 2026-10-05). 지금 상한은 셋이다 — 지표 하나의 셀
200만(계획이 어림해 거절), 읽기 한 번 2만 셀(분석이 Python 으로 받는 양), 기준 여섯. 그런데 셀 어림이
`min(기준마다 값 가짓수의 곱, 기록 수)` 라 자료가 커지면 곱은 늘 커서 **어림이 기록 수가 된다** — 기록이
200만을 넘으면 실제 셀이 수십만이어도 거절한다(규모 실측에서 「셀 350만 어림」 거절을 겪었다).

## 결정

1. **머무는 기간(`stay`) — 분모의 옵션이 아니라 지표 정의의 칸.** `{"periods": N, "periods_from": <숫자 칸>}`
   을 두면 기록 하나를 그 기간부터 N기간 동안 계속 센다 — 기간 P 의 값은 최근 N기간(P-N+1 ~ P)의 합이다.
   판매 대수 지표에 두면 그 지표가 곧 보증 중 대수이고, 접수월 인입률은 그것을 분모로 「기간끼리」 짝짓는다.
   - **셀로 계산해 둔다.** 읽을 때 창 합을 내는 대신 계산 문장 안에서 펼친다 — 그러면 분모 짝짓기(파이썬 ·
     DB 안 `paired_totals`) · 분석 · 경보 · 건 보기가 **지금 길을 그대로** 쓴다. 분모 쪽에 옵션을 두면 짝짓는
     길 셋을 모두 고쳐야 했다.
   - **묶은 셀을 펼친다.** 안쪽이 (부서, 기간, 기준 값들, 머무는 기간 수)로 묶고, 셀을 0 ~ w-1 기간 뒤로
     펼친 뒤(`generate_series`) 다시 묶는다 — 기록이 아니라 셀을 펼쳐 싸고, 건수 · 합 · 값 수는 더하고 최소 ·
     최대는 다시 최소 · 최대라 집계 다섯(과 평균 · 조건 비율)이 모두 맞는다.
   - **기록마다 다른 기간 수.** `periods_from` 은 자기 숫자 칸이나 참조 너머의 숫자 칸(`ref.country.
     warranty_months`) — 비었거나 못 읽으면 `periods`, 넘으면 `periods` 로 자른다(`periods` 가 기본이자 최대).
     기준 주소와 같은 길(`JoinPlan.axis`)로 풀어 조인을 함께 쓴다.
   - **미래는 만들지 않는다.** 계산 시점(워터마크)의 기간까지 — 이번 달은 들고, 다음 달은 아직 오지 않았다.
   - **건 보기.** 기간 P 의 셀 → 기록의 시간 칸이 P-N+1 ~ P. 기록마다 기간 수가 다르면 앞쪽에 안 든 기록이
     섞여 「≈」(`partial: ["stay"]`)다.
   - **함께 못 두는 것.** 코호트(펼친 기간에서 경과가 뜻을 잃는다) · 방문(차례가 펼친 기간과 무관하다).
   - 읽기 머리에 `stay` 를 싣는다 — 화면 · AI 가 그 값을 「그 달에 생긴 수」 로 전하지 않게.
2. **상한 — 실제 셀로 막고 넓힌다.** 목표는 기록 2,000만 건/타입(규모 실측의 10배).
   - **셀 어림은 실제 조합으로.** 표본을 **id 앞자리**로 고른다(객체 id 는 uuid4 — 무작위라 `id < 문턱` 이
     고른 표본이다). 예전의 「처음 20만 행」 은 시간순으로 쌓인 자료에서 앞 기간에 쏠렸다. 그 표본을 겹친
     넷(1/8 · 1/4 · 1/2 · 전부)으로 나눠 (부서, 기간, 코호트, 기준 값들)의 **조합 수**와 표본에서 한 번 ·
     두 번 나온 조합 수(f1 · f2)를 센다. 셀 어림 = 서로 다른 값 수 어림 둘의 **큰 쪽** —
     chao1 = d + f1²/(2 f2), GEE = √(전체 줄/표본 줄) · f1 + (d − f1) — 을 위로 묶은 것: min(값 가짓수의
     곱, 펼친 줄 수, 헵스 법칙 `d = a · n^b` 로 늘린 수). 둘은 서로 다른 자리에서 모자란다(chao1 은 큰
     자료에서 0.64배, GEE 는 중간 자료에서 0.51배 — 아래 「결과」). 헵스 늘리기만 쓴 첫 판은 2,000만
     건에서 실제의 8.6배로 어림해 맞는 정의를 거절했다 — 작은 표본 안의 기울기는 아직 1 에 가깝고,
     조합은 그 뒤에 포화한다. 표본이 전부(기록 ≤ 20만)면 어림이 **실제 셀 수와 같다**(시험). 방문 기준은
     창 함수를 표본마다 돌리지 않고 가짓수를 곱한다.
   - **진짜 상한은 계산에서.** 넣은 셀이 상한을 넘으면 그 계산을 버리고 옛 값을 둔다(`METRICS-0012`, 계산
     기록에 이유). INSERT 에 `LIMIT 상한+1` 을 붙여 넘는 계산을 끝까지 쓰지 않는다. 계획의 어림은 표본이라
     틀릴 수 있다 — 그래서 거절의 근거를 계산 쪽에 둔다.
   - **읽기 상한을 둘로.** 화면 · MCP 가 **돌려받는** 읽기(표 · 추이 · 코호트)는 2만 그대로 — 응답 크기다.
     분석이 **계산하려고 받는** 읽기는 `metrics_max_frame_cells` 20만 — 셀 하나가 Python 에서 약
     400바이트, 20만이면 80MB · 1.4초(실측). `__slots__` 로는 10% 밖에 안 준다(기준 값 dict 가 대부분).
   - **숫자.** 지표 하나의 셀 1,000만(색인까지 셀당 약 390바이트 — 지표 하나 약 4GB, 다시 세는 동안 두
     벌), 기준 6 → 8(셀은 기준 수가 아니라 실제 조합으로 막는다), 이름 풀기 5천 → 5만(이름 · 지움만, 5천씩
     나눠 묻는다 — 객체 행 전체를 끌어오지 않는다).

## 대안

### 분모 옵션(`denominator.window`)

분모를 읽을 때 최근 N기간을 더한다. 정의 하나는 줄지만, 분모를 짝짓는 길이 셋(셀을 받아 Python 으로 ·
DB 안에서 `paired_totals` · 경보)이라 셋 다 창 합을 내야 하고, 기록마다 다른 기간 수(국가의 보증 기간)는
분모 셀에 남아 있지 않아 못 한다. 같은 보증 중 대수를 다른 지표가 다시 쓰지도 못한다.

### 보증 중 대수를 바깥에서 계산해 타입으로

이번 개발 서버에서 한 것. 판매 자료가 바뀔 때마다 다시 계산해 넣어야 하고, 플랫폼마다 같은 가공을 한 벌씩
둔다.

## 결과

### 머무는 기간 — 시험

- 기간마다 최근 N기간의 합 · 미래 기간 없음 · 국가 칸에서 기간 수(2 · 3), 빈 칸은 기본, 넘으면 자름 ·
  건 보기(기간 수가 같으면 정확히 그 수, 다르면 「≈」) · 접수월 인입률의 분모(기간끼리) · 정의 잘못(시간 칸
  없음 · 코호트 · 숫자 아닌 칸 · 여러 값 칸)을 계획이 말한다 — `tests/api/test_metric_stay.py`.
- 개발 서버(판매 집계 2,524줄): `stay {periods: 24, periods_from: ref.country.warranty_months}` 가 바깥에서
  계산해 넣은 보증 중 대수 2,814칸과 **모두 같다**(머무는 기간 쪽에만 이번 달 100칸이 더 있다). 계산 0.3초.

### 상한 — 시험

- 표본이 전부일 때(기록 ≤ 20만) 계획의 셀 어림이 계산의 실제 셀 수와 **같다** — 코호트 · 여러 값 기준의
  펼침 · 참조 너머 기준까지. 계산이 상한을 넘으면 실패하고 옛 실행 · 셀 수 · 값이 그대로다. 기준 여덟은
  되고 아홉은 422. 화면 읽기 상한에 잘린 지표도 분석은 20만 상한으로 끝까지 읽는다 —
  `tests/api/test_metric_limits.py`. 늘리는 식(거듭제곱 · 비례 · 포화 · 펼친 줄의 비)과 문턱의 몫 —
  `tests/unit/test_metric_estimate.py`.

### 상한 — 규모(기록 200만 건, `scale_rehearsal.py measure --only limits`)

2,000만 건 규모 DB 를 만드는 동안(같은 PC 의 부하) 잰 것이라 시간은 참고다.

| --- | --- | --- | --- | --- |
| 판매 대수(기본 모델 x 월) | 100,050 | 100,050 | 1.00 | 2.4초 |

| ① 판매월 코호트 — 기본 모델 x 증상 | 1,682,427 | 1,079,040 | 1.56 | 47초 |

- 「기본 모델 x 부품 x 월」 은 예전 어림(곱과 펼친 줄의 작은 쪽 = 350만)으로 200만 상한에서 **거절되던
  정의**다. 실제 셀은 69만이었다.
- 머무는 기간의 어림이 16배였다 — 「셀 x N」 은 이웃 기간의 펼침이 같은 셀에 겹치는 것을 못 본다. (기간
  말고 다른 값의 조합) x (기간 수 + N - 1) 로 묶는다(고친 뒤 시험: 실제 ≤ 어림 ≤ 실제 x 2).
- 예전 읽기 상한(2만)을 넘는 분석 — 부품마다 변화점 훑기(부품 300 x 기간 93) 2.4초, 기본 모델 x 부품 연관
  1.1초, 기본 모델 2,001 집단 비교 0.9초 · 증상마다 순차 검정 0.4초 · 수명 0.35초 · 클레임 예측 2.0초.
  프로세스 메모리 최고 233MB. 지표 다섯의 셀 표 1,057MB(셀당 색인까지 약 500바이트).

- **첫 판의 어림(헵스 늘리기만)은 ① 을 1,418만으로 어림해 상한 1,000만에서 거절했다** — 실제는 166만
  (8.6배). 실측 표본 통계로 어림 식을 견줬다(표본 20만 줄):

  | 경우 | 실제 셀 | 헵스 | chao1 | GEE | 큰 쪽(지금) |
  | --- | --- | --- | --- | --- | --- |
  | ① · 200만 건 | 1,079,040 | 1.56 | 1.48 | 0.51 | **1.48** |
  | 기본 모델 x 부품 · 200만 건 | 692,348 | 1.84 | 0.95 | 1.02 | **1.02** |

  여러 값 기준에서 펼침의 비를 두 번 곱하던 것도 이때 고쳤다(표본의 줄은 이미 조인 뒤에 센 펼친 줄이다).
- **계산은 기록 전부를 매번 다시 읽는다** — 셀 1.4만의 「부품 x 분기」 도 3분, 큰 지표는 5 ~ 7분이다. 이
  규모에서 큰 지표 열 개를 밤마다 다시 세면 한 시간 남짓이다. 다음 상한은 셀이 아니라 **다시 세는 시간**이고,
  답은 증분 재계산(바뀐 기간만)이다 — [ADR 0024](0024-지표-증분과-홈-지표.md) 에서 했다.
- 분석(예전 읽기 상한 2만을 넘는 것 포함)은 기록 수와 거의 무관하다 — 부품마다 변화점 훑기 4.3초, 기본
  모델 x 부품 연관 1.3초, 파레토 0.03초, 기본 모델 2,001 집단 비교 2.3초, 증상마다 순차 검정 0.43초, 수명
  0.43초, 클레임 예측 1.05초. 프로세스 메모리 최고 211MB. 셀 표 869MB(지표 다섯 · 셀 약 274만).
