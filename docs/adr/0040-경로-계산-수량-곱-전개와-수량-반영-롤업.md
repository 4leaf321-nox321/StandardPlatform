# 0040. 경로 계산 — 수량 곱 전개와 수량 반영 롤업

- 상태: 채택(2026-10-30 구현 — `objects/explode.py` · `ontology/quantity.py` · `graph.tree_links`, 마이그레이션
  `0087_relation_quantity`)
- 날짜: 2026-10-30
- 관련: [ADR 0039](0039-관계의-유효-기간과-시점-질의.md)(유효 기간 — 선을 고르는 판정 `edges.alive`),
  [ADR 0035](0035-재귀-질의.md)(재귀 질의 — 하위 전체 · 깊이 상한), [ADR 0034](0034-조회는-전원에게.md)(보이는 범위)

## 배경

ADR 0039 가 적은 넷 중 ② 이다. 관계는 지금까지 「있다 · 없다」 만 말했다 — 롤업(`list_view.rollups`)은 트리 아래
**객체 집합**에 숫자 칸을 sum · min · max · avg · count 로 모았고, 선에 「몇 개」 가 적혀 있어도 곱하지 않았다. 그래서
제품 하나에 볼트가 몇 개 드는지(어셈블리 2개 곱하기 서브 3개 곱하기 볼트 4개), 제품의 총 무게(부품 무게 곱하기 그
부품의 총수량), 직렬 신뢰도(부품마다 신뢰도를 그 수만큼 거듭제곱)를 물을 자리가 없었다.

선에는 이미 칸이 있었다 — `object_relations.properties`(JSONB), 모양은 관계 종류의 속성(`property_defs.owner_kind
='relation'`). 「어느 칸이 수량인가」 만 정해지면 된다.

## 결정

### 1. 관계 종류의 수량 칸

- `relation_types.quantity_key`(글자, 기본 `""`) — 그 종류의 **숫자 · 값 하나** 관계 속성 하나의 키. 비면 그
  종류의 선은 모두 1개다(예전과 같은 뜻).
- 검사는 `ontology/quantity.py` 한 곳: API 의 만들기 · 수정(없는 칸 · 숫자 아님 · 여러 값 → ONTOLOGY-0096),
  정의 가져오기 · 스냅샷 복원 · 묶음의 **계획**(적용이 만들 상태 그대로 — 지금 속성 위에 파일의 속성을 얹고 본다).
  수량 칸인 속성을 숫자 아닌 것 · 여러 값으로 바꾸는 정의도 같은 계획에서 거절한다(「수량 칸이라 … 먼저 비우거나
  다른 속성으로」). 바꾸게 두면 전개가 모든 선을 「수량 없음」(1개)으로 세고, 그 총수량은 틀린 수다.
- **관계 속성 하나만 삭제하는 길은 지금 없다** — 정의 가져오기는 더하고 수정만 하고, 관계 종류를 삭제하면 속성과
  수량 칸이 함께 간다. 관계 종류의 속성은 종류도 바꾸지 않는다(`importer._plan_properties`). 그래서 「쓰이는 속성
  삭제 거절」 은 지킬 길이 아직 없고, 그 길을 만들 때 삭제 계획이 함께 막아야 한다(`quantity.py` 주석).
- 정의에 실리는 곳: 관계 종류 API 응답(그 종류의 관계 속성 `properties[]` 도 함께 — 화면의 「수량 칸」 고르개가
  여기서 숫자 칸을 고른다), 정의 JSON 내보내기 · 가져오기 · 스냅샷 · 묶음(`importer.RELATION_FIELDS`), 정의 엑셀의
  관계 종류 표, 코어 API 카탈로그 `relation_kinds[].quantity_key`(선의 모양은 그대로라 판 `revision` 에 들지 않는다 —
  연동 키트는 고칠 것이 없다), RDF 정의(관계의 `skos:note` — 관계 속성은 트리플로 안 나가므로 칸 이름만).

### 2. 전개 엔진 — 선 집합을 SQL 로, 전파는 파이썬으로

`objects/explode.py`. 뿌리(또는 위로 갈 때의 시작 객체) · 트리(관계 + 부모 쪽 끝) · 기준일 · 사용자를 받는다.

1. `graph.tree_links` — 재귀 CTE 로 **닿는 선을 한 번씩** 가져온다(부모 · 자식 · 수량 칸 값). 노드를 (id, 깊이)로
   UNION 해 걷고, 깊이 `MAX_DEPTH`(20)보다 얕은 노드에서 나간 선을 모은다. 판정은 `edges.alive_sql` — 기준일의 선만.
   `graph.py` 가 전환 경계라 SQL 은 거기 두고, `explode.py` 는 받은 것을 접기만 한다.
2. 파이썬에서 **위상 순서**(Kahn)로 한 번 훑어 노드마다 총수량 = Σ(앞 노드의 총수량 곱하기 선의 수량), 경로 수,
   가장 얕은 · 깊은 단계를 접는다. 위로 갈 때도 같은 식이다(「그것 하나에 시작 객체가 몇 개」).

**왜 파이썬 전파인가.** 경로를 SQL 에서 늘어놓으면(재귀 CTE 가 경로마다 줄을 내며 곱을 끌고 내려가면) 공유 하위
조립품에서 줄이 **경로 수만큼** 는다 — 같은 서브를 10곳에서 쓰고 그 아래가 100줄이면 천 줄, 단마다 둘씩 갈라지는
20단 사다리는 선 74개에 경로 백만(실측 아래). 선 집합은 선 수에 비례하고, 파이썬의 위상 순서 한 번도 선 수에
비례한다. SQL 안에서 노드마다 합을 접으려면 재귀 CTE 가 집계를 못 해(재귀 항에 GROUP BY 불가) 경로를 펼친 뒤에야
접을 수 있다 — 바로 피하려는 일이다.

**공유 하위 조립품** — 같은 노드로 오는 경로의 몫을 **더한다**(그래서 「총수량」 이다). 「단계별」 보기만 경로마다
줄을 내고, 그것은 상한에서 멈춘다(3).

### 3. 보기 셋과 상한

| 보기 | 줄 | 칸 |
| --- | --- | --- |
| 정리(`summary`) | 보이는 객체마다 하나 — 가장 얕은 단계, 그다음 이름순 | 총수량 · 가장 얕은 / 깊은 단계 · 경로 수 · 그 객체로 오는 선 중 수량 없음 |
| 단계별(`indented`) | 경로마다 하나 — 깊이 우선, 형제는 **이름순**(트리 화면과 같은 기준) | 단계 · 그 선의 수량 · 누적 수량 |
| 어디에 쓰였나(`where_used`) | 위로 경로마다 하나 + `tops[]` | 단계 · 그 선의 수량 · 누적(「이 객체 하나에 시작 객체 몇 개」), 맨 위(부모 없는) 객체마다 총수량 |

- 줄 상한 `LINES_MAX` = 5,000(`limit` 으로 줄인다). 넘으면 `truncated` 와 **전체 줄 수**(`lines_total` — 경로 수의
  합, 위상 순서에서 이미 센 값)를 준다. 잘린 목록은 「이게 전부」 로 읽히기 때문이다.
- 응답은 뿌리 · 기준일 · 관계 · 수량 칸 키와 이름 · 줄 · `totals`(서로 다른 객체 수 · 줄 수 · 전체 줄 수 · 선 수 ·
  수량 없음 · 볼 수 없음 · 삭제됨) · `truncated`. 파일(`…/explode/export?format=csv|xlsx`)은 화면의 표와 같은 열 ·
  같은 순서(UTF-8 BOM, `sheets.file_response`), 잘렸으면 끝 줄에 그렇다고 적는다.
- 오류: 트리가 없는 타입 OBJECTS-0131, 순환 OBJECTS-0130.

### 4. 수량

- 수량 칸이 비었거나 숫자가 아니면(글자 · 참/거짓 · 목록) **1 로 치고** 「수량 없음 n개(선)」 로 말한다 — 롤업의
  「n개 값 없음」 과 같은 결이다. 0 은 0 이다(그 아래가 안 든다). 정수는 정수로 곱한다(2 곱하기 3 곱하기 4 가
  24.0000…1 로 번지지 않게), 소수의 끝자리 잡음은 응답에서 9자리로 걷는다.
- 수량 칸이 없는 종류와 **참조 칸 트리**(`refedges` — 칸에는 선의 칸이 없다)는 모두 1개이고 「수량 없음」 으로
  세지 않는다(적을 자리가 없는 것이지 빠진 것이 아니다). 화면은 참조 칸 트리에는 「BOM 전개」 를 세우지 않는다.

### 5. 보이는 범위 — 롤업 · 하위 포함과 같은 뜻

`graph.descendant_ids` 를 확인했다: 재귀가 **객체 표를 안 보고 선만** 따라가고, 맨 끝에서 지운 객체를 거른다 —
지운 어셈블리 아래의 부품도 닿는다. 롤업은 그 위에서 보이는(`visible_owner_clause`) 것만 센다. 전개도 같다:

- **지나가기는 전부** — 남의 부서 객체(조회를 부서로 좁힌 설치)와 지운 객체를 지나가며 수량을 곱한다. 그 아래의
  보이는 부품은 제 몫의 총수량을 받는다.
- **내보이는 것은 보이고 지우지 않은 것만** — 정리에는 줄로 안 나온다. 단계별 · 어디에 쓰였나에는 **가린 줄**
  (「(볼 수 없는 객체)」 · 「(삭제된 객체)」, id 없음)로 자리를 지킨다 — 빼면 그 아래 줄의 단계가 위 줄 바로
  아래처럼 읽힌다. 몇 개를 지나갔는지 `hidden` · `deleted` 로 준다.
- 「볼 수 없는 객체 n개」 는 좁힌 설치에서 「이 아래에 내가 못 보는 것이 n개 있다」 를 말한다 — 이름 · 식별자는
  안 준다(관련 객체 · 가리키는 것의 「수만 말하기」 와 같은 정도). 기본 설치(전원 조회)에서는 늘 0이다.
- 삭제는 보통 관계가 걸려 있으면 막히므로(`delete_blocking`) 지운 객체를 지나가는 일은 드물다 — 합치기 · 직접
  고친 데이터에서 생긴다.

### 6. 순환

수량을 곱하는 일은 순환이 있으면 끝이 없다. 위상 순서를 못 세우면(시작 객체로 돌아오는 선 포함) 깊이 우선으로
돌아 **순환 하나를 찾아 이름으로** 말한다 — 「트리가 순환합니다 — A → B → C → A」(못 보는 객체는 이름을 가린다).
순환 금지(`acyclic`) 종류에는 순환이 없다(유효 기간과 상관없이 막는다, ADR 0039) — 트리를 순환을 막지 않는
종류로 정한 타입에서만 만난다. 롤업은 순환이어도 예전 셈은 그대로 내고, 수량 반영 롤업만 값 없이 까닭(`note`)을
단다. 「말단만」 은 순환이 있어도 정해진다(아래 선이 없는 객체).

### 7. 수량 반영 롤업

롤업 스펙에 `weighted`(화면 「수량 반영」) · `leaves_only`(「말단만」) · 새 `fn: "product"`(「곱」). Q 는 전개의
총수량(같은 기준일, 같은 선 집합).

| fn | 수량 반영 | 아닐 때 |
| --- | --- | --- |
| sum | Σ v·Q | Σ v |
| count | Σ Q(총 개수) | 값의 수 |
| avg | Σ v·Q / Σ Q | Σ v / n |
| product | Π v^Q(직렬 신뢰도) | Π v |
| min · max | 그대로 | 그대로 |

- 「말단만」 — **그 기준일의 트리에서 아래 선이 없는 객체만** 모은다. 아래가 지운 · 안 보이는 객체여도 아래가 있는
  것이다(지나가기는 전부와 같은 뜻).
- **중간 조립품에도 값이 있으면 두 번 센다** — 어셈블리의 무게(부품 무게의 합으로 적어 둔 값)와 그 부품의 무게가
  함께 더해진다. 무게 · 원가처럼 말단에만 원값이 있는 숫자는 「말단만」 으로 모은다. 문서 · 화면 도움말에 적었다.
- 수량 반영이면 `quantity_missing`(수량이 비어 1개로 센 선 수)을 함께 준다. 둘 다 끈 롤업은 예전과 같은 값이고
  같은 질의(`descendant_ids`)를 쓴다 — 켠 롤업이 하나라도 있으면 선 집합을 한 번 가져와 모두가 그 노드 집합을 쓴다.
- 음수 값을 정수 아닌 총수량만큼 거듭제곱하는 것처럼 셀 수 없으면 그 롤업만 값 없이 까닭을 단다.

### 8. 바깥으로

- **API** — `GET /api/objects/{type}/{id}/explode?mode=&as_of=&limit=`, `…/explode/export?mode=&as_of=&format=`.
  권한 · 기준일은 롤업과 같다(뿌리는 `_visible`, 기준일은 `edges.at(as_of)`, 비우면 오늘).
- **MCP** — `object_explode(type_slug, object_id, mode, as_of, limit)`, `object_rollup` 설명에 수량 반영, `relation_add`
  가 `properties`(선의 수량)를 받는다(예전에는 맺을 때 선의 칸을 못 적어 고치기로 두 번 불러야 했다). 정의는
  `ontology_import` 의 `quantity_key` · 롤업의 새 칸. GUIDE `2026-10-30b`.
- **화면** — 객체 상세의 「BOM 전개」(관계 트리가 있는 타입, 접어 두고 펼칠 때 센다 — 정리 / 단계별 / 어디에
  쓰였나, 상세의 기준일, CSV, 「수량 없음」 · 「볼 수 없는 객체」 · 「잘림」), 관계 종류 편집의 「수량 칸」, 롤업
  편집의 「수량 반영」 · 「말단만」 · 「곱」.

## 대안

- **SQL 에서 경로를 펼쳐 곱하기**(재귀 CTE 가 누적 수량을 끌고 내려감) — 줄이 경로 수만큼(2 위). 깊이 상한이
  있어도 공유가 많으면 상한 안에서 백만 줄이 된다.
- **노드 집합만 SQL 로 받고 선은 노드마다 다시 묻기** — 왕복이 노드 수만큼.
- **총수량을 저장(구체화)** — 롤업이 값을 저장하지 않는 까닭과 같다(부품 하나를 고친 날 옛 값을 보여 주고, 그
  차이는 아무 데도 안 뜬다). 기준일마다 다른 값이기도 하다.
- **수량을 선의 고정 칸(`object_relations.quantity`)으로** — 관계 칸(JSONB)이 이미 있고 모양을 관계 종류가 정한다.
  칸을 하나 더 두면 같은 값의 자리가 둘이 된다. 수량 칸은 「어느 관계 칸이 수량인가」 만 정한다.
- **총수량이 빈 선을 0 으로** — 그 아래가 통째로 빠져 「없다」 로 읽힌다. 1 로 치고 수를 말하는 쪽이 롤업의 결과
  같다.
- **가린 줄을 빼기**(단계별) — 아래 줄의 단계가 엉뚱한 부모 아래처럼 읽힌다.

## 남은 것(빠진 것)

- **가중 최단 경로** — 「가장 짧은 길」(ADR 0035)에 선의 값(거리 · 비용 · 지연)을 더하는 것. 지금 연결 경로는 선
  수로만 잰다. 필요해지면 관계 종류에 「가중치 칸」 을 수량 칸과 같은 모양으로 두고, 양방향 BFS 를 다익스트라로.
- **병렬 · k-of-n 신뢰도** — 「곱」 은 직렬만이다. 중복 구성(둘 중 하나만 살면 됨)은 선이나 노드에 구성 방식을 적을
  자리가 있어야 한다.
- **단위 환산** — 수량은 단위 없는 수다. 「kg 당」 · 「m 당」 처럼 부모와 자식의 단위가 다른 BOM(원자재)은 수량 칸의
  `unit` 을 읽어 환산하는 일이 남는다.
- **지표에서 전개 수량 쓰기** — 지표의 분모 · 가중(「제품 판매 대수 곱하기 부품 총수량」)에 전개를 쓰려면 지표
  계산(ADR 0023)이 트리를 펼쳐 둔 표를 써야 한다 — 지금은 화면 · API · MCP 의 읽기만.
- **대체 부품** — 「A 또는 B」(같은 자리에 들 수 있는 대안)는 선 하나로 적을 수 없다. 대체 묶음을 관계 칸이나 따로
  적는 자리가 필요하다 — 전개는 그때 대안 중 하나(기본)만 곱한다.
- 관계 속성 하나를 삭제하는 길(1) — 생기면 수량 칸인지 먼저 본다.
- ③ 파생 · 계보 관계와 개정 고정 — 선을 고르는 조건이면 `edges.alive` · `alive_sql` 에, 전개가 그 선을 따라갈지는
  `graph.tree_links` 가 그 판정을 부르므로 따로 고칠 것이 없다.
