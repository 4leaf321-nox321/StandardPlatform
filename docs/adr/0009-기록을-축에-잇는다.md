# 0009. 기록을 축에 잇는다 — 표의 열을 있는 객체로 풀어 참조 칸으로

- 상태: 채택
- 날짜: 2026-10-03
- 관련: [ADR 0005](0005-온톨로지-메타모델.md)(타입 · 속성 · 관계는 데이터), [ADR 0007](0007-속성-종류-변경.md)
  (종류 변경 — 글 ↔ 참조가 그 길에 얹힌다), [ADR 0010](0010-규모-참조-색인.md)(기록 200만 건을 견딘다 — 이
  결정의 전제)

## 배경

시스템에는 「축」 과 「기록(표)」 의 구분이 없다 — 둘 다 타입이고 객체는 한 표에 같은 모양으로 든다. 축과
기록을 가르는 것은 쓰임새(가리켜지는 쪽 · 가리키는 쪽)이고, 그 연결은 **참조 칸**이 만든다.

그런데 표에서 타입을 만들 때(화면의 「표에서 타입 생성」, 정제 도구) **어느 열이 어느 있는 타입을
가리키는지 찾아 잇는 단계가 없다.** 그래서 기록은 글자로 들어간다 — QINGS(시장 서비스, 63칸)도
「모델코드」 · 「마케팅 모델명」 이 글자라 개발모델과 이어지지 않았다. 잇고 싶으면 기록마다 손으로 정의를
고치거나 개발을 했다.

개발 DB 실측(읽기만)이 두 함정을 보였다.

- **우연한 일치** — 개발모델의 `model_revision`(값 9종, `01` · `02` …)이 Northwind 공급사 식별자(1 ~ 29)와
  65% 맞았다. 짧은 숫자는 아무 데나 맞는다.
- **1:1 이 아닌 일치** — 개발모델 식별자는 `SM-S918N_KOR_01_XXX`(전체 이름)이고, 기록의 「모델코드」 꼴
  (`SM-S918N`)은 개발모델의 `base_code` 와 맞는데 3,999건에 2,294종이다 — 한 값이 여러 모델이다.

## 결정

**표의 열마다 「이 값들이 어느 타입의 객체로 풀리나」 를 일괄 입력과 같은 이름 풀이로 세어, 참조 후보로
보이고 — 확실할 때만 참조 칸으로 제안한다. 이미 넣은 기록은 글 → 참조 종류 변경으로 잇는다.**

1. **계획 = 적용.** 후보의 「하나로 풀림 · 여럿에 맞음 · 못 찾음」 은 일괄 입력이 참조 칸을 풀 때 쓰는
   판정(`bulk._Refs.classify`: 식별자 → 별칭 → 이름 → id, 이름이 여럿이면 거절)을 **그대로** 쓴다. 따로
   세면 후보는 97% 라는데 넣으면 거절된다.
2. **보수적으로 제안한다.** 하나로 풀림이 채운 줄의 90% 이상이고, 맞은 값이 3종 이상이고, 맞은 값이
   **짧은 숫자가 아닐 때만** 종류를 참조로 바꿔 제안한다. 아니면 글자 그대로 두고 후보(30% 이상, 셋까지)를
   목록으로만 보인다 — 틀린 제안은 맞는 값처럼 들어간다.
3. **1:1 이 아니면 잇지 않는다.** 여럿에 맞는 값은 「여럿에 맞음」 으로 보이고, 사람이 식별자로 적거나 그
   수준의 축(예: 기본 모델)을 먼저 만든다. 축의 **다른 칸**(`base_code`)으로 잇는 길은 두지 않는다 — 이름
   풀이가 식별자 · 별칭 · 이름만 보므로, 그 칸으로 이으면 넣을 때 다시 풀 수 없다.
4. **이미 넣은 기록은 종류 변경으로 잇는다**(ADR 0007 의 길). 글 · 긴 글 · 고를 값 → 참조는 값마다 같은
   이름 풀이로 변환하고, 못 푼 값(여럿 · 없음)은 대체 값(식별자 · 이름 · id) 또는 값 삭제를 사람이 정한다.
   참조 → 글은 상대의 식별자(없으면 이름)로 — 되돌리면 같은 객체로 다시 풀린다. 코드표 승격(고를 값 → **새**
   코드표)과 다르다: 이것은 **있는** 축에 잇는다.
5. **MCP 로도 같은 길이다** — `table_infer`(후보와 제안) → 사람 확인 → `table_build` → `ontology_import` →
   `objects_import`. 기계가 후보를 골라 확정하지 않는다. 이미 넣은 기록은 `ontology_retype(data_type=
   "object_ref", ref_type_slug=)`.
6. **기록 크기의 종류 변경은 작업이다.** 값이 있는 객체가 2만 건을 넘으면 요청 경로가 ONTOLOGY-67 로 작업
   경로(`…/retype/job`)를 가리키고, 화면 · MCP 는 알아서 그리로 간다. 계획 → 사람 확정 → 적용이고, 적용은
   계획의 **지문**(타입별 건수 · 못 푼 값 · 대체 값)이 같을 때만 쓴다. 계획은 행을 덩어리로 읽고(200만 건을
   한 목록으로 들지 않는다), 못 푼 값은 1만 종까지만 값마다 센다. 객체마다의 이력에는 **바뀐 칸만**
   남긴다(`keys`) — 속성 전체를 두 번 담으면 이력 표가 기록보다 커진다.
7. **적용은 덩어리마다 문장 하나다.** 5천 행씩 그 칸만 읽어 잠그고, 갱신 문장 하나로 그 칸만 고친다
   (`jsonb_set` · `-`). 이력도 덩어리째 넣는다. 그리고 **객체마다 바깥에 알리지 않는다** — 웹훅 ·
   지켜보기에는 정의 한 줄(`ontology.property.retype`)이 간다. 처음에는 행마다 갱신 · 기록 · 알림을
   해서, 200만 건 한 방향이 38.5분 걸리고 메모리가 4.6GB 까지 올랐다(참조 색인 트리거가 행마다 돌고,
   알림 이벤트 200만 개가 커밋까지 쌓였다). 그 알림은 커밋 뒤 지켜보기 조회에서 바인드 한도에 걸려
   통째로 빠지기까지 했다 — 지켜보기 조회도 나눠 묻는다. 덩어리로 바꾼 뒤에도 22 ~ 27분이었는데,
   쪼개 재 보니 시간의 87% 가 `properties` 통째 GIN 인덱스 갱신이었다 — 쓰는 질의가 없어 뺐다(ADR
   0010 결정 10). 지금은 **한 방향 약 9분 · 메모리 156MB**(실험 DB, 개발 PC 기본 설정).

## 대안

### 값이 비슷한 것으로 잇는다(유사도)

「SM-S918N」 과 「SM-S918N_KOR_01」 을 같다고 보면 더 많이 잇는다. 하지만 짐작으로 이은 값은 맞는 값처럼
보여 아무도 안 고친다 — 이 저장소의 해소 원칙(「모른다」 가 틀린 답보다 낫다)과 어긋난다.

### 축의 아무 칸으로나 잇는다

`base_code` 처럼 참조 대상의 다른 칸을 열쇠로 쓰게 한다. 하지만 일괄 입력 · 데이터 소스 · 묶음의 이름 풀이가
그 칸을 모르므로 다음 적재에서 다시 풀 수 없고, 그 칸은 유일하지도 않다(실측 1:1 아님).

### 행마다 AI 가 판단한다

유연하다. 하지만 같은 원천과 같은 규칙에서 늘 같은 결과가 나와야 한다 — 정제 도구의 원칙(`sp_table`)과 같다.

## 결과

- 표에서 타입을 만들 때 열마다 「개발모델 — 하나로 97% · 못 찾음 12종」 같은 후보가 보이고, 확실하면 참조
  칸으로 제안된다(화면 · MCP).
- 기록이 축을 가리키면 개발모델 상세의 「관련 객체」 · 그래프 · 참조 너머 칸 조건과 통계가 바로 쓰인다 —
  200만 건에서도(ADR 0010).
- 큰 타입도 후보로 본다 — 처음에는 20만 건 넘는 타입을 뺐다(통째로 읽게 되어서). 이제 큰 대상은 그 열의
  값만 덩어리째 묻는다(ADR 0010 결정 12). 기록 타입은 후보로 보이되 제안하지 않는다(ADR 0011).
- 개발 DB 실데이터 점검(한 트랜잭션, 끝에 되돌림 — 바뀐 표 없음): 개발모델 · 과제 식별자로 만든 400행 표에서
  「모델」(없는 값 16개 섞음) 하나로 96% → 참조 제안, 「모델명」(이름) · 「과제」 100% → 참조 제안, 「판」(`01` …)은
  Northwind 공급사와 64% 맞았지만 짧은 숫자라 후보로만. 「모델명」 을 글로 넣은 뒤 종류 변경으로 이으니 400개
  모두 변환되고, 식별자로 푼 칸과 이름으로 푼 칸이 384행 모두 같은 객체를 가리켰다.
- 기록 200만 DB 실측: 표 추론 + 참조 후보(5,000행 · 17열) 1.35초. 종류 변경 계획 작업 약 40초, 적용 약
  9분(글 → 참조 523초 · 참조 → 글 543초, 메모리 156MB). 적용하는 동안 그 칸의 기록들은 잠긴다.
