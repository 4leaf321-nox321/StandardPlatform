## 배경

운영에서 시험해 보니(2026-11-14 사용자) 뜻으로 찾기가 **관계없는 질문에도 높게** 나왔다 — CAE 업무 백서를 넣고
「회의실 예약」 을 물었는데 낮게 안 나왔고, 「PMIC」 와 「MIC」 처럼 **이름이 포함될 뿐 전혀 다른 것**이 섞였다.

까닭은 방식이다. bge-m3 은 질문과 글을 **따로** 뜻의 자리로 바꿔 거리만 잰다 — 「같은 동네」 인지는 알아도
「답이 되나」 는 모른다. 기준(0.45)의 여유도 얇았다: 개발 DB 에서 상관없는 말의 맨 위가 이미 0.41 ~ 0.43,
맞는 짝 「물에 빠짐 → 침수」 가 0.47(ADR 0052). 기준을 올리면 맞는 것이 먼저 떨어진다.

리랭커(크로스 인코더)는 질문과 글을 **한 번에 함께 읽고** 「답이 되나」 를 점수로 준다. 사용자 결정: bge-reranker-
v2-m3 을 넣는다, 운영 서버에는 GPU 가 있다 — GPU 를 기본으로(2026-11-14).

## 결정

### 1. 리랭커 — llama.cpp 서버, 서버에 하나, GPU

- **Ollama 로는 안 된다** — 리랭크 창구가 없다(박아 둔 v0.30.10 에서 `/api/rerank` 404 확인, 공식 지원도 찾지 못함).
  Ollama 의 바탕인 llama.cpp 의 `llama-server --reranking` 이 `/v1/rerank` 를 준다.
- **판 `b12024`(2026-10-31)** 의 공식 릴리스 실행 파일 — GPU 면 `ubuntu-cuda-12.8-x64` + `cudart-…`(CUDA 런타임),
  아니면 `ubuntu-x64`. 배포가 `nvidia-smi` 로 고른다. `sp-rerank.service`, 127.0.0.1:11436, 자리 넷 · 자리마다
  4,096 토큰, 리랭크는 한 글을 한 번에(`-ub`) 읽는다. 이 서버의 SP 설치들이 함께 쓴다(Ollama 와 같다).
- **모델은 원본에서 우리가 바꾼다** — `BAAI/bge-reranker-v2-m3`(Apache-2.0)의 커밋을 박아 받고(가중치 지문은 Hugging
  Face 가 밝힌 sha256 과 견준다), **같은 판 llama.cpp 의 변환 스크립트**(그 판이 밝힌 파이썬 패키지로 임시 환경)로 GGUF
  F16 을 만든다. 남이 바꾼 GGUF 는 쓰지 않는다 — 분류 머리가 빠져 점수가 다 0 근처로 나오는 변환본이 보고돼 있다.
  - **sentencepiece 는 0.2.2 로 박는다** — 그 판의 목록(`sentencepiece>=0.1.98,<0.3.0` · `protobuf>=4.21,<5`)대로
    받으면 0.2.3 이 오는데, 0.2.3 은 protobuf 7 로 생성돼(`runtime_version`) protobuf 4 에서 변환이 떨어진다(꾸러미를
    끝까지 돌려 처음 드러남). 0.2.1 · 0.2.2 는 protobuf 4 와 맞는 꼴이고 0.2.2 는 Python 3.10 ~ 3.14 판이 있다. 같은
    입력이면 같은 GGUF 가 나온다(손으로 바꾼 것과 꾸러미의 것이 바이트까지 같았다).
- **임베딩 꾸러미에서만 깐다**(폐쇄망 — `ai/rerank/`, `SHA256SUMS`). 같은 판 · 같은 모델이면 다시 풀지 않고, 꾸러미가
  없어도 깔린 것은 그대로 쓴다. 배포의 끝에 한 번 매겨 본다 — **맞는 짝이 엉뚱한 짝보다 날 점수로 5 이상 높지 않으면
  실패**로 말한다(`RERANK_CHECK_BODY` · `RERANK_CHECK_MARGIN`). 바른 모델은 13 쯤(2.09 · -10.99, GPU · CPU 같다)이고,
  분류 머리가 빠진 모델은 점수가 다 0 근처라 「앞이 조금 크다」 로는 못 잡는다. **실패해도 배포는 멈추지 않는다.**
- **꾸러미를 만들 때도 같은 짝으로 매겨 본다** — 꾸러미의 CPU 판을 잠깐 띄워서. 점수가 이상하면 꾸러미를 만들지
  않는다 — 폐쇄망 서버에 들고 간 뒤에야 알면 밖에서 다시 만들어 들고 가야 한다. 짝 · 기준은 `deploy.sh` 의 것을
  읽는다(판 번호와 같다). 그 PC 에서 llama.cpp 를 못 띄우면 `RERANK_CHECK=0`.

### 2. 찾기 — 거리로 후보를, 관련도로 거르고 차례를

1. 거리(코사인)로 후보를 받는다 — 바닥 **0.35**(기준 0.45 보다 낮게: 기준 근처의 맞는 짝까지 리랭커가 읽게), 객체마다
   한 조각 · 같은 글은 하나, **30개**(`RERANK_CANDIDATES`).
2. 후보의 글은 **뜻의 자리를 맞출 때와 같은 글**을 객체에서 다시 짓는다(`piece_texts` — 같은 재료 · 같은 함수, 저장하지
   않는다). 리랭커에는 앞 2,000자까지(자리의 길이를 넘는 글 하나가 요청 전체를 깨뜨린다).
3. 관련도(로짓 → 시그모이드, 0 ~ 1) **0.05 이상**(`RERANK_MIN_SCORE`)만, 관련도 차례로 8개.
4. **못 부르면 거리로만** — 꺼짐 · 닿지 않음 · `RERANK_SECONDS`(3초) 넘김이면 같은 목록에서 지금처럼 0.45 · 8개를
   고르고 `meaning_rerank=unavailable` 이라고 말한다. 1분은 부르지 않는다(꺼진 리랭커를 검색마다 기다리지 않게).
   검색은 멈추지 않는다.

창구: 줄마다 `relevance`, 응답에 `meaning_rerank`(ready · off · unavailable). 화면은 「관련도 85%」, 다 걸러지면 「뜻으로
찾았지만 관련 있는 것이 없습니다」, 못 불렀으면 「관계없는 것이 섞일 수 있다」. AI(GUIDE · MCP)는 ready 인데 빈 줄이면
**「관련 있는 것이 없다」 고 답하고 억지로 늘어놓지 않는다**. 글자 줄은 그 글자가 「든」 것이라 「MIC」 에 「PMIC」 도
걸린다 — 이름이 포함될 뿐 다른 것은 섞지 않는다고 안내한다.

### 3. 리랭커가 읽는 글의 꼴 — 벡터와 같은 꼴 그대로

부품의 기본 글(「부품: MIC · 마이크 · …」)을 문장(「MIC(마이크)는 … 부품이다」)으로 바꿔 넘기는 것을 재 봤다 — 이름
질문(「마이크」)은 0.82 → 0.999 로 올랐지만 「MIC」 에 서브 PMIC 가 0.069 → **0.655** 로 함께 올라 혼동이 커졌다.
꼴을 바꾸지 않는다.

## 고르지 않은 것

- **기준만 올리기**(0.45 → 0.5) — 맞는 짝(침수 0.47)이 먼저 떨어진다. 위 표의 엉뚱한 줄도 대부분 0.45 ~ 0.57 이다.
- **Ollama 로** — 리랭크 창구가 없다. 임베딩 창구로 리랭커를 돌려 크기로 어림하는 꼼수는 점수가 아니다.
- **Hugging Face TEI** — CPU 에서 묶음이 4로 묶이는 등 손이 많이 가고 컨테이너가 크다.
- **앱 안에서(onnxruntime)** — 이미지가 2GB 넘게 커지고, 검색마다 웹 프로세스가 큰 모델을 돌린다.
- **남이 바꾼 GGUF** — 위 1.
- **글자 줄에도 리랭크** — 글자 줄의 차례는 「꼭 맞는 것이 맨 위」(ADR 0065)가 정한다. 「MIC」 에 걸린 「PMIC」 는 꼭
  맞는 「MIC」 아래로 간다. 거르지 않고 안내(GUIDE)로 둔다.

## 남은 것

- 운영에서 걸린 질문으로 기준(0.05)을 다시 본다 — 가짜 자료 41개는 작다. 놓친 것은 먼저 그 객체의 글(다른 이름)을 본다.
- 운영 L40S 에서 Ollama(bge-m3)와 리랭커가 함께 도는 메모리 · 지연 — 개발 PC 에서는 리랭커가 GPU 메모리 약 1.9GB(자리
  넷 · `-ub 4096`)를 더 썼다.
