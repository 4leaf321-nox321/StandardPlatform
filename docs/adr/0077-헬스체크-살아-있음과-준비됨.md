# 0077. 헬스체크 — 살아 있음과 준비됨

- 상태: 채택(2026-11-17 구현 · 시험)
  - `app/readiness.py`(`check` · `schema_check` · `DB_SECONDS`) · `app/schema_version.py`(`known_revisions`) ·
    `app/main.py`(`GET /api/health/ready`) · `shared/access_log.py`(`_SKIP` — 기록에서 뺀다)
  - 배포: `deploy/deploy.sh`(`health_check` — install · update · restart · status 와 갱신 실패의 되돌리기) ·
    `deploy/ha.sh`(`ready_code` — LB · 메인 서버 · 상대 앱 경유)
  - 시험: `tests/api/test_health_ready.py`
- 날짜: 2026-11-17
- 관련: [ADR 0004](0004-리눅스-Apptainer-배포.md)(배포), AO 비교의 「다음」 항목(헬스체크를 살아 있음과 준비됨으로)

## 배경

`/api/health` 는 프로세스가 떠 있으면 200 이다 — DB 를 보지 않는다. 그래서 DB 가 끊겼거나 마이그레이션이 덜
올라가도 「정상」 이었고, `deploy.sh` 의 확인(install · update · restart · status)은 「응답함」 이라 말한 채 넘어갔다.
사람은 그것을 **화면의 500** 으로 먼저 만났다(새 칸을 읽는 화면 — `schema_version.py` 의 머리말이 그 일이다).
DB 판이 뒤처진 것은 서버 화면의 「스키마」 줄이 보여 주지만, 그것은 로그인한 시스템 관리자가 그 화면을 열었을
때뿐이다.

`/api/health` 는 그대로 둘 까닭이 있다 — 버전 · 이름 · 접두어 · 화면의 바탕 주소를 주는 자리이고 MCP 가 300초마다
읽는다(ADR 0058). DB 가 끊겼을 때 이것까지 실패하면 「무엇이 깔렸나」 를 물을 데가 없다.

## 결정

1. **`GET /api/health/ready` 를 더한다**(로그인 없이). 두 가지를 보고, 하나라도 아니면 **503**:
   - `db` — DB 에 한 번 왕복(`SELECT 1`, 3초 안 — `DB_SECONDS`).
   - `schema` — DB 의 마이그레이션 판(`alembic_version`)이 코드의 머리와 같나. 뒤처졌으면(코드가 아는 옛 판)
     「마이그레이션이 덜 올라갔습니다 — DB 0100_… · 코드 0101_…(sudo ./deploy.sh update 가 올립니다)」, 표가 없으면
     「빈 DB」. **코드보다 새 판은 준비됨**으로 본다 — 더 새 판을 깔았다가 되돌린 서버는 대개 그대로 돈다(마이그레이션은
     칸을 더하는 쪽이다). 그렇다고 적는다.
2. 본문은 200 이든 503 이든 **같은 모양**이다 — `{"status": "ready" | "not_ready", "version", "checks": [{name, ok,
   detail}]}`. 감시는 상태 코드를, 사람은 `checks` 를 읽는다. 오류 봉투가 아닌 까닭: 준비됐을 때와 같은 모양이어야
   둘을 견준다(무엇이 바뀌었나).
3. **DB 확인은 따로 된 스레드에서 시간 상한을 걸고 한다.** 패킷을 버리는 DB 서버면 접속이 몇 분을 기다린다(psycopg 는
   접속 시간 상한이 기본으로 없다 — 엔진에도 안 걸었다). 앞선 확인이 아직 매달려 있으면 새로 묻지 않고 그것을 함께
   기다린다 — 감시가 몇 초마다 물어도 매달린 접속이 쌓이지 않는다.
4. **DB 오류의 원문은 싣지 않는다** — 로그인 없이 묻는 자리인데 접속 오류의 원문에 DB 호스트 · 계정이 든다. 「DB 에
   닿지 않습니다 — 서버 로그(app.log)에 까닭이 있습니다」. 로그는 **상태가 바뀔 때만** 남긴다(준비됨 ↔ 준비 안 됨).
5. 요청 시간 기록 · 접근 로그에서 뺀다(`_SKIP`) — 살아 있음과 같다.
6. **`deploy.sh` 의 `health_check` 가 준비됨을 본다.** 503 이면 그 본문을 경고로 보이고, 준비됨이 없는 옛 판(되돌린 SIF
   — 404)이면 살아 있음으로 본다. install · update 는 지금처럼 이 확인으로 멈추지 않는다(`|| true` — 경고만): 마이그레이션
   실패는 그 앞에서 이미 멈추고, 그 밖의 준비 안 됨(DB 가 잠깐 안 닿음)에 설치를 되돌리면 더 큰 일이 된다. `ha.sh` 의 경유
   확인(LB · 메인 서버 · 상대 앱)도 준비됨의 코드를 보인다.

## 대안

- **`/api/health` 가 DB 까지 본다** — 버렸다. 버전 · 바탕 주소를 묻는 자리(MCP · 사람)가 DB 장애 때 함께 실패한다.
- **엔진에 접속 시간 상한(`connect_timeout`)을 건다** — 이것만으로는 버렸다. 모든 요청의 접속에 걸리는 값이라 그 크기는
  따로 정할 일이고, 준비됨은 그 값과 상관없이 3초 안에 답해야 한다. 스레드 + 시간 상한이면 둘이 섞이지 않는다.
- **준비 안 됨이면 install · update 를 실패로** — 버렸다(결정 6).
- **워커 · MCP 도 본다** — 이번에는 뺐다. 준비됨은 「이 웹 프로세스가 요청을 처리하나」 다. 워커가 멎은 것은 서버 화면 ·
  작업 화면(「가장 오래 대기」)이 말하고, `deploy.sh status` 가 유닛마다 보인다.

## 결과

- 배포 · 점검의 확인이 정직해진다 — 「마이그레이션이 덜 올라갔습니다」 가 install · update · status 의 출력에 바로
  보인다.
- nginx(이중화의 LB)는 준비됨을 주기적으로 묻지 않는다 — 장애 넘김이 이것으로 빨라지지는 않는다. 바깥 감시 도구를
  붙이면 이 주소를 묻는다(운영 env 설정 4.3).
- 시험 DB 는 모델로 표를 만들어 마이그레이션 기록이 없다 — 시험에서 준비됨은 「빈 DB」 다. 판을 보는 시험은 그 표를
  직접 세우고 지운다.
