# 0012. 이미지 첨부 — 서버가 열어 보고 정하고, 바이트는 모델을 거치지 않는다

- 상태: 채택
- 날짜: 2026-10-03
- 관련: [ADR 0001](0001-공통-틀과-도메인의-경계.md)(공통 틀은 도메인 표를 모른다),
  [ADR 0002](0002-확장-지점-레지스트리.md)(도메인이 등록하고 공통이 부른다),
  [ADR 0010](0010-규모-참조-색인.md)(쓰는 길이 많으면 표가 맞춘다 — 트리거)

## 배경

기록(시험 결과 · 시장 서비스 건)에는 사진이 같이 붙는 일이 많다. 파일 칸(`file`)으로 저장은 됐지만
**화면에서 볼 길이 없었다.**

- 내려받기는 늘 「다운로드」였다(`Content-Disposition: attachment`).
- 로그인 토큰이 메모리에만 있어서 `<img src="/api/...">` 는 401 이 났다. 프론트에 `<img>` 가 하나도
  없었다.
- 파일의 종류는 **올린 쪽이 말한 대로** 저장하고 그대로 내보냈다. `image/png` 라고 적은 HTML 이나
  SVG 를 그림으로 띄우면, 그 안의 스크립트가 앱의 주소에서 앱의 권한으로 돈다.

MCP 로 AI 가 기록을 다룰 때는 다른 문제가 있었다.

- MCP 서버는 서버에서 돈다(streamable-http). 그래서 사용자 PC 의 파일을 못 읽는다.
- 그렇다고 AI 가 파일을 base64 로 도구 인자에 실으면 1MB 가 수십만 토큰이다. 받을 때도 같다.
- 첨부 도구가 없었고, 개인 토큰(PAT)으로는 첨부를 올릴 수도 없었다(쓰기 범위 표에 없었다).

ReportArchive 가 같은 문제를 먼저 풀었다(`mcp_server/guide/GUIDE.md` 의 「바이트가 모델을 거치면
토큰을 그대로 먹는다」). 그 길을 따르고, 거기서 비어 있던 것을 채웠다.

- 매직 바이트 판별 · SVG 차단 · 응답 머리
- 한 번만 쓰는 표
- 자료의 권한에 묶인 올리기

조사하면서 이미지와 무관한 구멍도 드러났다. 사진이 붙는 순간 이 구멍들은 「사진이 사라졌다」로
보이므로 이 결정에서 함께 막는다.

- 올릴 때 객체가 있는지, 그 칸이 파일 칸인지 보지 않았다.
- 붙이고 뗀 일이 이력에 남지 않았다.
- 합치기가 첨부를 옮기지 않았다.
- 객체의 부서가 바뀌어도 첨부의 부서는 그대로였다.

## 결정

1. **새 속성 종류를 두지 않는다. 이미지도 `file` 이다.** 파일 칸을 빼는 자리 15곳 이상(묶음 ·
   코어 API · 엑셀 · 조건 · 종류 변경 …)이 그대로 맞고, 이미 붙은 사진도 바로 보인다.
   - 칸에 `accept` 를 둔다. `image` 면 「사진만 허용」다.
   - 판정은 이름 · 확장자가 아니라 서버가 열어 본 결과다.
2. **서버가 열어 보고 이미지인지 정한다**(`shared/images.py`, Pillow).
   - 이미지로 보는 것: PNG · JPEG · GIF · WebP 로 열리고, 몸통까지 훑어도(`verify`) 깨지지 않은 것만.
   - 이미지면 `content_type` 을 서버가 읽은 종류로 고치고, 가로 · 세로를 적는다(EXIF 회전 반영).
   - SVG 는 이미지가 아니다. 글로 된 문서라 스크립트를 품는다.
   - 1억 화소를 넘는 그림(압축 폭탄)은 파일로만 붙는다.
   - 칸의 판별 결과는 `attachments.media` 에 둔다: `image` · `file` · NULL. NULL 은 이 칸이 생기기
     전의 첨부다. 처음 목록에 나올 때 판별한다 — 마이그레이션은 파일을 읽지 않는다.
3. **미리보기는 서버가 만든다.** 긴 변 320px WebP 이고, filestore 에 함께 둔다(내용 주소).
   - 휴대폰 사진의 EXIF 회전을 반영해 세운다.
   - 상세 화면의 격자는 미리보기만 받고, 원본은 크게 볼 때만 받는다.
4. **파일 응답에는 머리 셋을 붙인다.**
   - `X-Content-Type-Options: nosniff`
   - `Content-Security-Policy: default-src 'none'; sandbox`
   - `Cache-Control: private, max-age=86400`
   - 앞의 둘은 누가 주소를 앱 창에서 직접 열어도 HTML · SVG 의 스크립트가 돌지 않게 한다.
   - 화면은 받아서 `blob:` 주소로 띄운다(`useBlobUrl`). 띄우는 것은 서버가 이미지로 읽은 것만이다 —
     blob 주소는 앱과 같은 출처이기 때문이다.
5. **붙일 자리는 도메인이 답한다**(`extensions.register_attachment_owner`, 여섯째 확장 지점).
   - 공통 틀(files)은 객체 표를 모른다. 대신 `objects` 를 등록한 쪽이 넷을 본다:
     - 객체가 있고 보이는가
     - 고칠 수 있는가 — 소유 부서 관리자인지, 허브 잠금은 없는지
     - 그 자리가 파일 칸인가
     - 그 칸이 무엇을 받는가
   - 첨부의 부서는 **객체의 부서**를 따른다. 올린 쪽이 고른 부서는 쓰지 않는다.
   - 붙이고 뗀 일은 객체의 이력에 `object.attachment.add` · `.remove` 로 남는다. 지켜보기 · 웹훅도
     이 기록에서 나간다.
   - 뗄 때는 자리를 묻지 않는다. 칸이 지워진 뒤에도 이미 붙은 것은 뗄 수 있어야 한다.
6. **객체의 부서가 바뀌면 첨부도 따라간다.** 트리거가 맞춘다(`objects/attachment_sync.py`,
   마이그레이션 0055 에 그날의 사본).
   - 부서가 바뀌는 길이 넷이다: 일괄 고치기 · 묶음 되돌리기 · 이력 되돌리기 · 부서 통폐합. 코드로
     맞추면 한 길이 빠지고, 그 길에서는 객체는 보이는데 사진이 404 가 된다.
   - 트리거는 `UPDATE OF owner_workspace_id` 일 때만 돈다. 그래서 값만 고치는 덩어리 갱신에는
     걸리지 않는다.
   - 합치기는 지는 쪽의 첨부를 이긴 쪽으로 옮긴다(`attachments_moved`).
7. **MCP 는 바이트를 나르지 않는다 — 한 번 쓰는 업로드 표 + `curl`.**
   - 순서:
     1. `attachment_upload_prepare` 가 백엔드에서 표를 받는다(`POST /api/attachments/tickets`).
        표는 5분짜리이고, 자리를 정해서 낸다.
     2. 도구는 `curl -T <파일> -H 'X-Upload-Ticket: …' <주소>` 명령을 돌려준다.
     3. AI 의 셸이 그 명령을 실행해 파일을 직접 올린다(`PUT /api/attachments/upload`).
   - 표 자체가 자격이다. 그래서:
     - DB 에는 해시만 둔다.
     - 표는 주소가 아니라 머리로 보낸다. 주소는 접근 로그에 남는다.
     - 한 번만 쓴다. 단, 성공했을 때만 쓴 것이 된다. 거절되면 같은 표로 다시 올린다.
     - 낼 때와 쓸 때 **두 번** 자리를 본다. 그 사이에 권한이 바뀔 수 있다.
     - 감사에는 표를 낸 토큰의 이름이 남는다.
   - 업로드 주소는 MCP 에 들어온 주소를 따른다.
     - nginx 뒤면 같은 호스트다(경로 접두어 `/<slug>` 포함).
     - MCP 포트로 바로 들어왔으면 그 -2 다. 경로 접두어(`/<slug>`)는 붙은 채로 둔다 — 앱은
       접두어가 붙어 오든 벗겨 오든 받는다(`PrefixMiddleware`).
     - 둘 다 아니면 `MCP_PUBLIC_URL` 이 정한다(표준이 아닌 포트의 프록시 뒤). 단 그 값이 MCP
       포트를 바로 적은 것(`http://<IP>:<앱+2>/mcp` — ReportArchive 가 그렇게 쓴다)이면 쓰지 않고
       위 규칙으로 만든다. 0.4.29 는 그 값에서 `/mcp` 만 떼어 업로드를 MCP 포트로 보냈다(404).
   - **base64 도구는 두지 않는다**(ReportArchive 는 256KB 상한의 최후수단으로 남겼다).
     - 있으면 모델이 그것을 고른다.
     - 셸이 없는 클라이언트는 사람에게 화면에서 올려 달라고 한다.
   - 읽을 때도 첨부는 이름 · 크기 · `is_image` · 가로세로뿐이다. 바이트를 주는 도구는 없다.
   - 개인 토큰은 `objects:write` 로 첨부를 올리고 뗀다(`/api/attachments` 의 쓰기 범위).

## 대안

### 새 속성 종류 「이미지」

정의는 분명해진다. 하지만 파일 칸을 다루는 모든 자리에 이미지 경우를 하나씩 더해야 한다. 그리고
그 하나를 빠뜨리면 그 자리에서만 사진이 사라진다. 칸의 옵션(`accept`)으로 같은 것을 얻는다.

### 서명한 주소로 `<img src>` 를 직접

브라우저 캐시를 그대로 타고 코드가 짧다. 하지만 주소 자체가 자격이 되어 복사 · 공유 · 로그로
샌다. 그리고 그 주소를 새 탭에서 열면 앱과 같은 출처의 문서가 된다. blob 으로 받는 길은 지금의
인증을 그대로 쓰고, `Cache-Control: private` 으로 같은 사진을 다시 받지 않는다.

### 로컬 MCP(`pipeline/sp_mcp.py`)에서 경로로 올리기

PC 에서 도는 정제 MCP 는 파일을 읽을 수 있고, Claude Desktop 에서도 된다. 하지만 그 MCP 의 원칙은
「넣는 것은 사람이 명령으로」다. 그리고 원격 MCP 를 쓰는 사람이 따로 깔아야 한다. 대량(수백 장)이
필요해지면 zip + 대응표를 작업으로 올리는 길을 따로 둔다.

### 브라우저가 미리보기를 만든다(의존성 없음)

MCP 로 올라온 사진에는 미리보기가 없다. 그리고 판별이 파일 머리(매직 바이트)에 그친다. Pillow 는
바이너리 휠이라 이미지 빌드에 그대로 들어간다.

## 결과

- 상세 화면의 파일 칸은 사진을 격자로 보인다. 누르면 원본을 크게 보고 앞뒤로 넘긴다. 올리기는
  여러 장 고르기 · 끌어다 놓기 · 붙여넣기(Ctrl+V)를 지원한다.
- 속성 창에 「사진만 허용」가 생겼다. 정의 파일 · 엑셀 내보내기에 `accept` 가 실린다.
- MCP 도구가 둘 늘었다(54종): `attachment_upload_prepare` · `attachment_remove`.
- 백엔드 의존성에 Pillow 가 더해졌다(`requirements.txt`).
- filestore 에 미리보기가 더해진다. 사진 한 장에 수십 KB 다.
- 남은 것:
  - 고아 파일 정리(GC)는 여전히 없다. 거절된 업로드 · 뗀 첨부의 파일은 남는다(`filestore.py`).
  - 목록 열의 썸네일 · 만들기 화면에서 바로 올리기는 하지 않았다.
  - 대량 사진(zip) 작업도 하지 않았다.
