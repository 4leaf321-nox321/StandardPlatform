# 0035. 재귀 질의 — 연결 경로 · 하위 전체 조건 · 계층 축

- 상태: 구현 중 — 1단계(연결 경로) · 2단계(하위 전체 조건) 2026-10-23 구현. 3단계(계층 축) 예정
- 날짜: 2026-10-23
- 관련: [ADR 0010](0010-규모-참조-색인.md)(참조 색인 `object_refs`), [ADR 0011](0011-축과-기록.md)(기록은 이웃으로 안
  싣는다), [ADR 0024](0024-지표-증분과-홈-지표.md)(증분이 안 되면 전량), [ADR 0031](0031-걸음-넷과-읽기-시간-상한.md)
  (걸음 넷 · 읽기 시간 상한), `objects/graph.py`(그래프 탐색의 전환 경계)

## 배경

재귀로 묻는 길은 이미 셋이 있었다. 트리 관계(이행 · 순환 금지)로 「아래 전부 · 위 전부」 를 펼치는 재귀 CTE(트리 ·
「하위 포함」 거르기 · 롤업, 깊이 20), SPARQL 의 경로 표현(`+` · `*`, 그래프를 메모리에 세워 객체 5만까지), 걸음 넷
(고정 깊이). 비어 있던 물음은 셋이다:

- **두 객체가 어떻게 이어져 있나** — 이웃 그림은 노드마다 30개(최대 500)로 잘라서, 펼쳐 이어 붙이면 잘린 곳의 길을
  「없다」 로 읽는다.
- **「이 프로젝트 아래 전부에 달린 기록」** — 트리는 타입마다 정한 관계 하나로 그 타입의 목록에서만 되고, 기록처럼
  큰 것에는 SPARQL 이 상한에 걸린다.
- **「기본 모델 계열 전체 기준」 같은 계층 단위 지표** — 계층을 펼쳐 축으로 쓰는 길이 없다.

사용자 요청(2026-10-23): 셋을 위험이 낮은 것부터 — 연결 경로 → 하위 전체 조건 → 계층 축.

## 결정

### 1단계 — 연결 경로 (구현)

1. **양 끝에서 한 층씩, 작은 쪽을 넓힌다**(`graph.shortest_paths`). 노드마다 자르지 않는다 — 대신 들른 노드
   5만 · 노드당 선 2,000 · 길이 8 의 상한을 두고, 닿으면 `truncated`. **상한에 닿아 못 찾은 것은 「없음」 이 아니라고
   말한다.** 길이 상한(`max_depth`, 기본 6)은 사람이 고른 것이라 그것으로 못 찾은 것은 `truncated` 가 아니다.
2. **선은 이웃 그림과 같은 둘**(관계 · 참조 칸, `neighbor_edges` 를 그대로 부른다) — 가시성 · 지운 것 · 기록을
   다루는 규칙이 한 곳이다. **방향은 안 본다**(「이 부품이 들어간 제품」 은 거슬러 간다). 선의 방향은 답에 실린다.
3. **기록은 `records` 일 때만 거친다** — 인기 모델은 기록 10만 건이 가리켜서, 기록을 거치면 거의 모든 것이 두 걸음
   안에 이어진다(이웃 그림의 기본과 같다). 원 표의 행(부서 · 계정)으로 가는 링크는 거치지 않는다 — 「같은 부서」 가
   모든 쌍을 두 걸음으로 잇는다.
4. **같은 길이의 길을 `limit`(기본 3, 최대 10)개까지.** 길 하나만 주면 다른 길이 「없다」 로 읽힌다.
5. 창구: `GET /api/graph/path`, MCP `graph_path`, 화면은 지식 그래프의 노드 상세 「연결 경로」(상대 검색) ·
   「시작점부터 연결 경로」, 주소 `?focus=<출발>&to=<도착>`. 화면의 말은 「연결 경로 · N단계 · 경로 해제 · 탐색 중
   상한에 도달」(용어 표).

### 2단계 — 하위 전체 조건 (구현)

1. **조건 연산 `under`** — 「그 객체이거나, 그 타입의 트리로 그 아래 전부」. 트리는 타입마다 정한 관계
   (`list_view.tree` — 트리 화면 · 목록의 「하위 포함」 과 **같은 정의**, `graph.tree_spec` 한 곳)다. 이행 관계가
   둘 이상일 수 있어 아무거나 고르지 않는다 — 트리가 없는 타입이면 거절한다(까닭과 고칠 자리를 말한다).
2. 걸리는 자리: 참조 칸(`f.part.under`) · 걸음 끝의 참조 칸(`f.ref.model.part.under`) · 관계로 이어진 것
   (`f.out.<관계>.under`) · 목록의 객체 **자신**(`f.id.under` — 목록의 「하위 포함」 을 조건으로, 그래서 통계 ·
   지표 · 저장된 뷰에도 걸린다). 나를 가리키는 것(`in.<타입>:<칸>`) 자체에는 안 건다. 값 여럿(`|`)은 어느 하나의
   아래. 조건이 쓰이는 곳(목록 · 통계 · 지표의 거르기 · 조건 비율 · 규칙 · MCP · 저장된 뷰)이 모두 같은 식을 쓴다.
3. **아래를 먼저 뽑아 `= ANY(배열)` 로 건다**(`graph.subtree_ids` · `any_of`). 재귀를 조건식 안에 넣으면
   PostgreSQL 이 재귀 CTE 의 줄 수를 어림하지 못해(늘 백여 줄) 아래가 큰데도 한 줄씩 견주는 길을 골랐다 —
   「뿌리이거나(OR) 그 아래」 로 적은 첫 판은 OR 때문에 잎 하나도 1.5초였고, 뿌리를 0단에 넣은 둘째 판은 작은
   것은 빨라졌지만 모델 1,555개 아래가 5초 · 전부가 19초였다. 배열 하나로 넘기면 개수를 알고 고른다 — 기존
   「그 중 하나」 에 같은 id 목록을 넣은 것과 같은 속도다. 자리표가 하나라 아래가 수만이어도 넘치지 않는다.
   조건은 실행마다 새로 짓는다(지표도 계산마다) — 뽑아 둔 아래가 낡지 않는다.
4. 깊이는 트리 화면과 같은 20단계. 지나가는 노드의 가시성은 트리 펼침(`descendant_ids`)과 같다 — 걸리는 것은
   가리키는 쪽의 가시성으로 가린다.
5. **지표의 증분은 트리가 바뀌면 전량으로 센다**(`incremental._tree_types` · `_tree_change`). 부품이 다른 가지로
   옮겨 가면 기록의 시각은 안 오르는데 걸리는 기록이 바뀐다 — 너머의 주소(`ref.` · `out.` · `in.`)만 보던 증분은
   자기 칸의 「하위 전체」 를 몰라 낡은 셀을 남겼다(시험으로 잡았다 — 이 확인을 끄면 실패한다). 관계 트리는
   그 관계의 선 · 끊긴 선, 참조 칸 트리는 그 타입 객체의 변경을 본다.

### 3단계 — 계층 축 (예정)

지표 · 통계의 축으로 「이행 관계의 조상(특정 타입 · 단계)」 을 쓴다. 계층이 바뀌면 지난 셀이 낡으므로, ADR 0024 의
「관계 너머의 기준인데 그 관계가 바뀜 → 전량」 규칙에 계층 관계를 묶는다.

## 결과

- **2단계 실측**(규모 DB, 기록 200만 — 개발모델 6천 개를 6갈래 임시 트리로 엮어 한 트랜잭션 안에서 재고
  되돌렸다): 「모델이 X 하위 전체」 인 기록 — 뿌리(모델 6,000 · 기록 199만) 0.91초, 1단(1,555 · 49만) 0.57초,
  3단(43 · 1.3만) 0.14초, 잎(1 · 334) 0.01초. 같은 모델 목록을 「그 중 하나」 로 직접 넣은 것: 0.91 · 0.60 ·
  0.15 · 0.00초.
- **1단계 실측**(규모 DB 200만, 기록 제외): 같은 기본 모델의 모델 둘 2단계 · 0.03초, 같은 프로젝트의 모델 둘
  4단계 · 0.02~0.05초(들른 노드 13), 6단계 안에 안 이어지는 모델 둘 — 「없음」 · 0.05~0.10초(들른 노드 ~100). 기록을
  거쳐 부품 → 모델: 4단계 · 2.8초 · 들른 노드 6,141, 부품 하나에 기록 2만 건이라 노드당 선 상한에 닿아 `truncated`
  (부품과 그 모델을 함께 가리키는 기록이 0 건이라 4단계가 맞는 답이다).
