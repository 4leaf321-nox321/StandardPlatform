# 0005. 도메인을 코드가 아니라 **데이터로** 정의한다 — 온톨로지 메타모델

- 상태: 채택
- 날짜: 2026-09-11
- 관련: [ADR 0001](0001-공통-틀과-도메인의-경계.md)(공통 틀과 도메인의 경계),
  [ADR 0002](0002-확장-지점-레지스트리.md)(확장 지점 레지스트리)

## 배경

ADR 0001 은 도메인을 이 저장소에 넣지 않기로 했다. 그 결정은 옳았지만 **값을
치른다**: 새 플랫폼마다 표를 만들고, 스키마를 쓰고, CRUD 를 쓰고, 목록 화면을
쓰고, 사이드바에 줄을 더한다. 그 일의 대부분은 도메인이 달라도 **모양이 같다.**

한편 같은 WSL 의 `ReportArchive` 는 도메인 안에서 이미 이 길을 끝까지 갔다.
보고서에 붙는 통제어휘(`entity_types` = 축, `entities` = 값)로 시작해서, 차례로:

| 마이그레이션 | 무엇을 깨달았나 |
| --- | --- |
| `p55_relation_types` | **관계의 의미가 코드에 암묵이면 AI 가 스키마를 인지할 근거가 없다** |
| `p64_ontology_property_foundation` | 어휘로는 부족하다 — 객체에 **속성**이 필요하다 (`kind_class`) |
| `p65_link_properties_evidence` | 관계 자체에도 속성과 **근거**가 필요하다 |
| `p66_record_axes_seed` | 어휘 축과 **객체 축**은 다른 것이다 |
| `p67_object_links` | 이미 있는 1급 표(부서)는 **복제가 아니라 투영**해야 한다 |

다섯 번의 additive 마이그레이션은 **처음에 몰라서 치른 값**이다. 도메인 안에서
배운 것을 공통 틀에서는 처음부터 온전한 모양으로 시작할 수 있다.

## 결정

**타입·속성·관계를 데이터로 정의하고, 화면은 그 정의를 렌더한다.**

    그룹을 정의하면      -> 사이드바에 묶음이 생기고
    타입을 정의하면      -> 그 묶음 안에 목록·프로필 화면이 생기고
    속성·관계를 정의하면 -> 그 화면의 폼과 관계 편집기가 생긴다

도메인을 얹는 일이 **코드를 쓰는 일에서 데이터를 채우는 일로** 바뀐다. 채우는
경로에는 사람(관리 화면)과 기계(MCP)가 둘 다 있다.

### 이것은 도메인이 아니다

넣는 것은 **부품·과제·시험**이 아니라 「타입이란 무엇인가」 다. ADR 0001 의 경계를
어기는 것이 아니라 **그 경계를 지키는 도구**다 — 지금은 도메인을 얹으려면 이
저장소를 포크해 코드를 써야 하지만, 이것이 있으면 포크는 **특수 기능에만** 남는다.

### 지켜야 하는 결정 열

1. **그룹은 표시, 타입은 의미 — 나눈다.** 한 표로 두면 「이 타입을 두 그룹에」
   「그룹을 부서마다 다르게」 가 반드시 오고, 그때는 데이터가 이미 쌓여 있다.
2. **동적 화면은 라우트를 늘리지 않는다.** `/o/:typeSlug`, `/o/:typeSlug/:id` 둘로
   받는다. 그러면 `navigation.ts` 가 **정적 화면의 정본**이라는 규칙이 그대로 서고
   `routes/router.test.tsx` 도 계속 유효하다. 정본이 둘이 되는 것이 아니라,
   정적 화면의 정본은 파일이고 동적 화면의 정본은 데이터다.
3. **화면이 자동 생성되면 뷰 스펙이 필요하다.** 모든 목록이 똑같으면 아무도 안
   쓴다. 부품 목록과 과제 목록은 보여야 할 열이 다르다. 타입에 `list_view` 를 둔다.
4. **`kind_class` 셋을 처음부터** — `reference`(어휘) · `record`(객체) ·
   `system`(이미 있는 1급 표의 투영). **`system` 이 핵심이다**: 부서를 온톨로지에
   넣겠다고 행을 복제하면 두 벌이 되고 **반드시 갈린다.**
5. **트리는 관계로 만든다. `parent_id` 를 두지 않는다.** 두면 트리 관계와 일반
   관계가 두 벌이 되고, 트래버설 코드도 두 벌이 된다.
6. **관계 타입의 메타를 데이터로** — 방향성·이행성·비순환·허용 타입·역방향 라벨.
   ReportArchive 가 나중에 깨달은 것이고, MCP 로 채울 계획이면 전제다.
7. **타입은 전역, 객체는 부서 소유.** 타입까지 부서별로 열면 같은 개념이
   부서마다 갈리고, **연결하려고 만든 것이 칸막이가 된다.**
8. **EAV 의 대가를 인정하고 승격 경로를 설계에 넣는다.** `properties` JSONB 는
   유니크·FK·CHECK 를 못 건다. 그래서 무거워진 타입이 **전용 표로 승격되는 길**을
   미리 그려 둔다(전용 표를 만들고 그 타입을 `system` 으로 재등록). 이 경로가
   없으면 모든 것이 영원히 JSONB 에 남고, 그 상태는 몇 년 뒤에 드러난다.
9. **스키마 API 는 자기 설명적이어야 한다.** `GET /api/ontology/schema` 하나가
   타입·속성·관계·제약을 전부 돌려주면 MCP 서버는 도메인마다 새로 짤 필요가 없다.
   쓰기는 `scopes.register_write_scope` 로 막는다.
10. **메타모델 변경도 감사·참조 확인 대상이다.** 속성 하나를 지우면 **모든
    객체의 그 값이 사라진다.** 지우기 전에 무엇이 그것을 쓰는지 보여 준다.

### RDB 가 진실, 그래프는 투영

트래버설은 재귀 CTE 로 시작하고 `graph.py` 한 모듈로 감싼다. 그래프 엔진으로 갈
일이 생기면 **그 모듈 안만** 바뀐다. 전환 트리거는 데이터 규모가 아니라
**관계 종류의 다양화 + 임의 경로 질의의 빈발 + AI 가 질의를 생성**하는 시점이다.
미리 깔면 운영 표면만 늘고 얻는 것이 없다(ReportArchive 의 같은 결론을 따른다).

## 대안

### 도메인마다 코드로 쓴다 (지금)

표·스키마·CRUD·화면·사이드바를 매번 쓴다. 자유롭고 빠르며 제약이 정확하다.
하지만 **모양이 같은 일을 매번 다시 하고**, 플랫폼이 늘수록 같은 화면의 변종이
늘어난다. 그리고 도메인 데이터를 기계가 읽으려면 플랫폼마다 MCP 서버를 새로 짠다.

### 순수 EAV — 표 하나에 전부

`(entity, attribute, value)` 세 칸. 가장 유연하고 **가장 못 쓴다.** 값의 타입이
행마다 다르므로 정렬·집계·조인이 전부 캐스팅이 되고, 목록 하나에 self-join 이
속성 수만큼 붙는다. 타입 있는 열(`properties` JSONB) + 정의(`property_defs`)로
가는 이유가 그것이다 — **유연함은 JSONB 한 칸에 가두고 나머지는 정규화한다.**

### 외부 온톨로지 도구(트리플스토어·그래프DB)를 얹는다

표현력은 확실히 높다. 하지만 **권한·감사·첨부·부서 소유가 전부 이 틀에 이미 있고**
그것을 두 번째 저장소에 다시 만들어야 한다. 그리고 폐쇄망에 엔진이 하나 더 는다.
ADR 0004 가 배포를 SIF 하나로 좁힌 것과 정면으로 어긋난다.

### 포크 후 코드 생성(스캐폴딩)

정의에서 코드를 **생성**해 커밋한다. 제약이 진짜 DB 제약이 되는 것이 장점이다.
하지만 생성물을 손으로 고치는 순간 재생성이 불가능해지고, **그 시점은 반드시
온다.** 그리고 채우는 일이 여전히 배포를 요구하므로 「기준정보를 채워 간다」 는
목적이 성립하지 않는다.

> 다만 이 길은 **버려지지 않는다.** 결정 8 의 승격 경로가 사실상 이것이다 —
> 처음부터 전부 생성하는 대신, **무거워진 타입만** 전용 표로 내린다.

## 결과

- 새 플랫폼의 1단계가 「표를 만든다」 에서 「타입을 정의한다」 로 바뀐다.
- 포크는 **특수 기능에만** 남는다. 공통 틀의 갱신을 계속 받을 수 있는 표면이 는다.
- MCP 서버 하나가 스키마를 읽어 **모든 플랫폼**에 붙는다.
- 대가: 목록 질의가 JSONB 를 탄다. 인덱스를 표현식으로 걸어야 하고, 제약은
  서비스 레이어의 몫이다. **그 대가를 감당 못 할 타입은 승격한다** — 그 길이
  설계 안에 있는 것이 이 결정의 조건이다.
- 절차와 단계별 할 일은 [온톨로지-메타모델-설계.md](../온톨로지-메타모델-설계.md)
  가 정본이다.
