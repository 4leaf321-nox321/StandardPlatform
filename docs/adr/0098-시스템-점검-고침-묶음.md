## 배경

0.4.106 을 낸 뒤 시스템 전반을 점검했다. 돌아가는 쪽은 깨끗했다 — 개발 DB 사본에 띄운 서버에서 GET API
178개 · 화면 86개에 5xx · 화면 오류가 없었고 서버 로그에 ERROR 가 없었다. 문제는 코드 쪽이었다(권한 ·
최근 변경 · 자동 작업을 나눠 읽고, 굵은 것은 재현으로 확인했다).

## 결정

### 1. 0.4.106 회귀 — 키트 · 묶음의 문서 본문

- **이름 없이 식별자만 있는 고치기 행이 미리 보기 · 적용에서 늘 막혔다.** 검사(`ask_platform`)만 플랫폼에
  물었고 미리 보기 · 적용은 묻지 않고 다시 검사했다. 셋이 같은 눈(`known_on`)을 쓴다.
- **문서 본문만 실은 묶음을 「빈 묶음」 으로 거절했다**(BUNDLES-2). 문서도 셈에 넣는다.
- **적용이 거절돼도 실행이 「적용함」 으로 잠겼다**(`applied.json`). 거절이면 `apply_failed.json` 에 남기고
  잠그지 않는다 — 고친 뒤 다시 미리 보고 적용한다. `work_status` 는 실행 하나를 못 읽어도 나머지를 낸다.
- **문서를 실은 묶음을 되돌려도 그 묶음이 만든 객체가 남았다.** 문서 단계가 객체의 「고친 때」 를 늦게
  적어 되돌리기가 「그 뒤에 남이 고쳤다」 로 봤다. 문서 단계는 객체 단계와 같은 때(트랜잭션의 `now()`)를
  적는다.
- **식별자 범위가 부서인 타입에서 문서 본문 · 원천 삭제 표식이 부서를 안 봤다** — 아무 부서의 객체나
  집었다. 문서에는 `workspace_slug` 를 받고, 여러 부서에 같은 식별자면(부서를 안 적었을 때) 줄 오류다.
  삭제 표식도 여럿이면 줄 오류다(엉뚱한 부서의 객체를 지우지 않는다).
- **같은 객체 · 칸의 본문 둘이 작업 전체를 DB 오류로 죽였다.** 둘째를 줄 오류로, 키트 검사도 막는다.
  같은 객체를 지우는 삭제 표식 두 줄은 뒤 줄을 「앞 줄이 지운다」 로 알린다(전에는 말없이 빠졌다).
- **문서 쓰기가 원천 잠금(`managed_by`)을 안 봤다** — 묶음과 화면 저장 둘 다. 다른 쓰기와 같게 막는다.
- **개인 정보 검사의 오탐** — 「18-2024-0012」(문서 번호) · 「react@18.3.1」(판 표기) · 13자리 숫자(바코드 ·
  밀리초 시각)가 오류였다. 전화는 0 · +82 로 시작하는 국내 번호, 메일은 끝이 글자 도메인, 주민등록번호는
  앞 여섯이 날짜이고 **줄표가 있거나 검증 숫자가 맞으면 오류**, 줄표 없는 날짜 모양 13자리는 경고다(국내
  바코드는 880 으로 시작해 날짜처럼 읽혀, 바코드 검증 숫자가 맞으면 경고로 둔다).
- **플랫폼 칸 키(`status` …) 검사가 옛 스냅샷 복원과 코어 구독을 통째로 막았다.** 그 둘에서는 경고로만
  둔다(`keep_reserved`) — 그 키를 이미 쓰던 정의다. 새로 만드는 정의는 그대로 막는다.

### 2. 권한

- **`objects:write` 토큰이 데이터 소스 경로로 정의를 바꿨다**(RA 보고서 기록 타입 만들기 · 코어 구독의
  적용 · 보류된 정의 승인). 그 두 자리는 `ontology:write` 다.
- **부서 자료 옮기기 계획을 `objects:write` 토큰이 적용했다.** 그 계획은 `human_only` 를 달고 적용 자리가
  토큰을 막는다(JOBS-31) — 토큰으로는 계획을 세울 길도 없는 일이다. `human_only` · `by_token` 은 작업을
  넣을 때 적을 수 없는 예약어다.
- **읽기로 연 POST 가 그 아래 주소까지 열었다** — `/api/metrics/plan` 이 slug 가 `plan` 인 지표의 재계산 ·
  경보까지. 이제 그 주소 하나만. 바깥 SPARQL 창구의 `POST /api/rdf/sparql` 은 읽기로 연다(토큰의 POST 가
  막혀 있었다).
- **부서로 좁힌 설치에서 장표가 볼 수 없는 주제 객체의 이름 · 값을 냈다.** 목록은 「(볼 수 없는 객체)」,
  한 장 · pptx 는 403(SLIDES-40), 「쓰인 장표」 는 404(SLIDES-41) — **ADR 0101 에서 빈 목록으로 바꿨다**(부서 · 계정은
  `objects` 에 행이 없어 늘 404 였다).
- 검토함 「전부 작업으로」 가 토큰 출처를 작업에 넘기지 않았다 — 지금은 사람만 정하는 종류가 그 길에 실리지
  않지만, 실리게 되면 우회된다. 계획 · 적용 작업 모두 `by_token` 을 싣는다(적용을 토큰이 시켜도).

### 3. 드문 자료에서 자동 작업이 깨지던 것

- **밤 그래프 계산이 실패하고 자동 계산이 멈추던 셋**
  - 객체는 있는데 선이 0개 — NetworKit 의 모듈성이 예외를 냈다. GPU 판처럼 무리는 「없음」, 다리 역할은 0.
  - 이어지는 관계의 선이 모두 고리 안(A → B · B → A) — 맨 위가 없어 IndexError. 그 관계만 「비슷한 것」 을
    건너뛰고 까닭을 남긴다.
  - `GRAPH_CALC_WHOLE_RELATIONS` 에 지금은 없는 이름 — **결정을 바꿨다**(ADR 0067 은 「모르는 이름이면 계산이
    실패하고 아는 이름을 말한다」). 빼고 짓고 판의 「건너뜀」 에 그 이름과 쓸 수 있는 이름을 적는다. 모두
    없으면 무리 · 다리 역할만 건너뛴다(전부로 짓지 않는다 — 무리의 뜻이 바뀐다). 관계 하나를 지웠다고 이
    설정과 상관없는 기대는 수 · 비슷한 것까지 밤마다 멈추는 것이 더 나빴다. 관계 종류 · 속성을 지우는 계획이
    그 이름이 설정에 있으면 알린다.
- **10건 이하인 데이터 소스는 바깥이 한 번 빈 응답을 주면 전부 사용 중지 · 끊김 · 「내려감」** — 대량 실종
  문턱의 바닥(10)에 걸렸다. **가진 것이 전부 안 왔으면** 작은 소스여도 멈춘다(`too_many_gone`). 정말 다
  지워진 것이면 사람이 화면에서 처리한다.
- **뜻으로 찾기의 고른 칸이 모두 지워지면 그 타입의 조각이 하루 안에 오류 없이 다 사라졌다.** 그 타입은
  맞추기를 건너뛰고(조각을 지킨다) 까닭을 남긴다. 속성 삭제 계획이 그 칸이 뜻으로 찾기에 쓰인다고 알린다.
- 대신 세울 시스템 관리자를 고를 때 정지 · 삭제된 계정을 빼지 않던 곳(데이터 소스 동기화 · 선 굵기 셈 ·
  지표 훑기 · 관리자 알림)을 고쳤다.

### 4. 파일스토어

개발 환경의 첨부 16개가 원본 파일 없이 기록만 남아 있었다. 까닭을 확정하지는 못했지만 길이 둘 보였다.

- **한 줄로 돌린 pytest 가 개발 환경의 파일스토어 · 로그를 시험 DB 와 함께 썼다** — 병렬(`-n`)일 때만 임시
  폴더로 옮겼다. 언제나 옮긴다.
- **파일스토어가 어느 DB 의 것인지 묶는 표지가 없다** — 다른 DB 에 붙은 워커가 같은 폴더를 보면 그 DB 가
  모르는 파일이 전부 고아로 보여 하루 지난 것이 다 지워진다. 표지 파일은 누가 먼저 쓰느냐가 다시 같은 문제라
  두지 않고, **자동 정리가 저장소 대부분(전부, 또는 20개 넘게 절반 넘게)을 지우려 하면 멈춘다**(데이터 소스의
  대량 실종 막기와 같은 무늬). 「지금 정리」 는 계획에 그 경고를 싣고, 사람이 읽고 적용하면 지운다.
- 첨부 행은 있는데 원본이 없으면 403 이 아니라 404 다(FILES-6 그대로) — 403 이면 권한 문제로 찾는다.

### 5. 그 밖

- 다른 타입으로 **두 번 이상** 옮긴 객체(A → B → C)의 A 주소도 C 를 안내하고, 이력은 A 의 키로 적힌 기록을
  두 단계의 칸 대응을 이어 C 의 키로 읽는다(전에는 마지막 한 단계만).
- 옮기기가 대상에 새로 만드는 칸의 키를 검사하지 않았다(`status` · 모양이 틀린 키 · 49자면 DB 오류). 새
  속성과 같은 규칙으로 막는다. 원 타입에 **정의 없이 남은 옛 값**(지운 속성의 저장값)이 대상 칸과 같은 키면
  막는다 — 옮기면 그 칸의 값으로 살아난다. `mapping` 에 `{"키": null}` 로 버린다. 식별자 범위가 부서 → 전사로
  넓어지면 부서끼리 같은 식별자 · 대상의 유일 칸에 옮길 것끼리 같은 값을 막는다.
- slug · 키 변경의 LIKE 가 `_` 를 가리지 않아 `a_1` 을 바꿀 때 `a11` 의 알림 링크 · 검토 결정까지 바뀌었다.
- 정의 제안: 값만 고쳐 다시 낸 제안이 옛 제안으로 돌아왔다(지문이 값을 안 담는다) — 정의 본문까지 견준다.
  계획의 지문은 경고 속 **지금 수**를 지운다(쓰기가 잦은 타입의 제안이 매번 「바뀌었다」 로 막혔다). 적용 ·
  거절 · 철회 · 복원은 행을 잠그고 다시 읽는다.
- 원 표 객체(부서)의 화면이 타입을 알기 전에 언급 · 이력을 물어 404 를 냈다.

### 6. 의존성

- 백엔드: Pillow 12.3.0 → 13.0.0(알려진 취약점 42건 — 올린 그림을 여는 곳이라 실제로 닿는다), PyJWT 2.13.0 →
  2.15.1(15건 — 포털 로그인 검증), certifi 2026.7.22 → 2026.10.18. MCP · 키트의 의존성은 알려진 것 없음.
- 프론트: 취약점 22건이 모두 빌드 · 시험 도구(shadcn CLI · vite · vitest · happy-dom)였다 — 화면에 실려 나가지
  않는다. 같은 큰 판 안은 그대로 올리고, vitest 3 → 4 · happy-dom 20 → 21 로 올려 0건(시험 885개 통과).

## 대안 — 버린 것

- **파일스토어에 DB 표지 파일** — 표지가 없는 저장소를 누가 먼저 「내 것」 으로 적느냐가 같은 문제다(시험 DB 가
  먼저 적으면 개발 DB 의 정리가 영영 멈춘다). 대량 삭제 멈춤이 그 경우를 그대로 잡는다.
- **모르는 그래프 이름이면 지금처럼 실패** — 관계 하나를 지우는 흔한 일이 밤 계산 전체와 자동 계산을 멈춘다.
- **작은 소스는 비율로만** — 전부 안 온 것과 몇 건 빠진 것을 가르지 못한다.
- **slug `plan` 을 지표 slug 의 예약어로** — 읽기 POST 를 그 주소 하나로 좁히면 다른 경로에서도 같은 틀이 안 생긴다.

## 결과

- DB 마이그레이션 없음. 새 `.env` 값 없음. 새 오류 코드 JOBS-31 · SLIDES-40 · SLIDES-41. FILES-6 은 404 로.
- **열린 정의 제안은 한 번 「다시 셈」** — 지문의 계산이 바뀌어 올리기 전에 낸 제안은 「제안 뒤 정의가 바뀌었다」
  로 보인다.
- 키트 쪽(1의 앞 셋 · 개인 정보 검사)은 키트를 새로 받아야 쓰인다.
- MCP 안내서 2026-11-26b(묶음의 문서 · 부서 자료 옮기기 적용 · SPARQL 창구의 토큰 POST).

## 보강(2026-11-27, [ADR 0101](0101-재점검-고침-묶음.md))

이 묶음의 규칙 여럿이 드문 모양에서 비켜 갔다 — RA 의 「전부 안 오면 멈춤」 은 이미 내려간 행을 빼고 세고,
파일 정리의 멈춤은 하루 지난 파일과 견주며(바닥 3) 멈추면 관리자에게 알리고, 정의 제안의 지문은 잃는 값의
수를 다시 넣고, 사람만 적용하는 계획은 작업 종류로도 가리고, 장표의 「쓰인 장표」 는 빈 목록 · 볼 수 없는 주제의
제목은 가린다.
