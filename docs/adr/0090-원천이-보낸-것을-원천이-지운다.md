# 0090. 원천이 보낸 것을 원천이 지운다 — 삭제 표식의 「삭제」 · 원천 잠금 해제

- 상태: 채택(2026-11-24 구현 · 시험)
  - 삭제 표식: `bundles/schemas.py`(`ObjectTombstoneIn.action`) · `bundles/tombstones.py`(`_delete_rows` ·
    `_delete_refusal`) · `bundles/undo.py`(`blockers` — 함께 쓰는 잣대)
  - 잠금 해제: `ontology/routes.py`(`POST /api/ontology/{types|relation-types|interfaces}/{slug}/unlock`,
    `DefinitionUnlockOut`)
  - 원천 이름으로 정의 삭제(보강): `ontology/managed.py`(`require_definition_deletable`) · 정의 삭제 · 미리 보기의
    `source` · MCP `ontology_delete(source=)`
  - 화면: 「작업」 의 묶음 결과에 삭제 표식(`jobs/TombstonePlanView`) · 정의 화면 셋의 「<원천> 관리 · 잠금 해제」
    (`ontology/ManagedBadge`)
  - 시험: `tests/api/test_tombstone_delete.py` · `TombstonePlanView.test.tsx` · `ManagedBadge.test.tsx`
- 날짜: 2026-11-24
- 관련: [ADR 0087](0087-원천-잠금-안내와-원천-정보.md)(원천 잠금) · [ADR 0008](0008-지운-객체-영구-삭제.md)(삭제 ·
  영구 삭제) · datarelay 의 요청서 「원천이 보낸 것을 원천이 지우게」(2026-11-23)

## 배경

datarelay 가 SP 에 넣은 객체는 **지울 길이 없었다.** 시험으로 보낸 것도, 잘못 보낸 것도 그렇다.
datarelay 는 「보낸 것 걷어내기」 를 만들어 삭제 표식(`tombstones`)만 담은 묶음을 올리지만, SP 는 이렇게 받았다.

| 하려는 일 | 막는 곳 | 까닭 |
| --- | --- | --- |
| 잠긴 타입의 객체를 화면에서 지우기 | `delete_object` → `managed.require_objects_editable`(OBJECTS-87) | 정본은 원천이다 |
| 원천이 삭제 표식으로 지우기 | `tombstones.py` — 객체는 `deprecated` 만 | 「받는 쪽은 지우지 않는다」 |
| 잠긴 타입을 지우기 | `_type_deletion` → `require_definition_editable` | 정의도 원천의 것이다 |

네 줄 각각은 맞다. 그러나 겹치면 시험 데이터를 영영 못 치운다. 그리고 「작업」 화면은 묶음의 객체 · 관계 단계만
그렸다. 삭제 표식만 담은 걷어내기 묶음은 빈 표로 보였다.

## 결정

### 1. 삭제 표식에 `action: "delete"`

- `ObjectTombstoneIn.action` 은 `"deprecate"`(기본 — 지금과 같다) · `"delete"` 다. `delete` 는 화면의 삭제와 같다
  (`lifecycle._soft_delete` — `deleted_at`, 별칭을 비운다, 감사 기록 `object.delete`).
- **그 타입을 잠근 원천의 묶음만** 쓴다(`managed_by == source`, 비어 있지 않다). 남이 잠근 타입 · 사람이 만든
  타입은 그 줄을 오류로 둔다. 사용 중지는 그대로 된다.
- 이미 사용 중지된 객체에도 된다. 예전에 걷어낸 것을 나중에 지운다.
- `merged_into` 와 함께 적으면 그 줄을 오류로 둔다. 무엇을 하라는지 모른다.

### 2. 가리키는 것이 있으면 막는다 — 같은 묶음은 빼고 센다

- 화면의 `mode=block` 과 같다. 참조를 비우는 `detach` 는 두지 않는다 — 남의 객체를 고치는 일이다(datarelay 도 막기로
  충분하다고 했다).
- 잣대는 묶음 되돌리기(`undo.blockers`)와 같다. 그 객체에 남은 선 · 원 표의 선 · 그 객체를 담은 참조 칸 중
  **같은 묶음이 끊는 선(`cut`)과 함께 지우는 객체(`doomed`)는 뺀다.** 그래서 지우는 줄은 선 삭제 표식 **뒤에**
  계획한다. 표의 줄 차례는 보낸 차례 그대로다.
- **함께 지우는 것 중 하나가 밖에서 막히면 다시 센다.** 막힌 것은 빠지고, 그것이 가리키는 것도 막힌다 —
  하나만 남았는데 나머지가 지워져 남은 것이 지운 것을 가리키는 일이 없게(고정점).
- 묶음은 「전부 아니면 무」 라, 한 줄이라도 막히면 아무것도 지우지 않는다.

### 3. 계획에서 따로 센다

- 줄의 동작은 `delete` 다. `counts.delete` · 묶음 결과의 `tombstones_delete` 로 `deprecate` 와 따로 선다.
- 「작업」 화면이 묶음 결과의 삭제 표식을 그린다 — 「삭제 표식 — 삭제 N · 사용 중지 N · 관계 해제 N」 과 줄마다의 말.
  삭제가 있으면 「목록에서 제외되고 복원할 수 없습니다」 를 붉게 적는다. 작업 목록의 요약 줄에도 붙인다.

### 4. 원천 잠금 해제 — 화면(가)

- datarelay 의 두 안 중 **가) 화면의 「잠금 해제」** 다. 시스템 관리자만, 확인 창, 감사 기록
  (`ontology.type.unlock` · `ontology.relation_type.unlock` · `ontology.interface.unlock`, 앞뒤 `managed_by`)을 갖춘다.
- 타입만이 아니라 **관계 종류 · 인터페이스도** 연다. 시험 타입을 치우면 그 원천이 잠근 관계 종류도 함께 남기 때문이다.
- `managed_by` 를 비운다. 그 뒤로는 사람이 평소처럼 고치고 지운다(객체의 화면 삭제 · 타입 삭제 · ADR 0008 의
  영구 삭제 확인).
- **원천이 같은 정의를 다시 보내면 다시 잠긴다** — 가져오기의 규칙 그대로다(`if source: managed_by = source`).
  확인 창이 「아직 보내는 중이면 다음 적재가 다시 잠그고 덮어씁니다」 를 먼저 말한다.
- 이미 풀려 있으면 아무것도 안 바꾼다(`was` 가 빈 값).
- 정의 화면의 배지는 「허브 관리」 대신 잠근 원천의 이름(「datarelay 관리」)을 적는다. datarelay 인지 허브인지
  보여야 풀지 말지 정한다.

## 대안 — 버린 것

- **나) 원천 묶음으로 타입 지우기** — 정의를 없애는 일은 SP 의 사람이 정하는 편이 맞다(datarelay 도 가를 권했다).
  원천을 끊을 때도 같은 잠금 해제가 필요하다. *(묶음은 그대로 버린다. 정의 삭제 경로가 원천 이름을 받는 것은
  아래 보강으로 열었다 — 삭제 미리 보기 · 막는 것 · 스냅샷을 그대로 거친다.)*
- **`detach` 를 고르게 하기** — 원천이 SP 의 다른 객체(사람이 만든 것)의 칸을 비우게 된다.
- **사용 중지된 것을 타입 삭제가 「없는 것」 으로 세기** — 사용 중지는 지운 것이 아니다. 지울 것은 지운다.
- **지운 것을 판 되돌리기로 되살리기** — 화면의 삭제도 되살리는 길이 없다. 같은 식별자를 다시 보내면 새 객체가
  생긴다(식별자의 고유성은 살아 있는 객체 사이에서만 본다).

## 결과

- 옛 SP(0.4.100 까지)는 모르는 칸 `action` 을 버려 사용 중지한다. datarelay 는 `/api/health` 의 판으로 보고,
  안 되는 SP 에는 「사용 중지만 됩니다」 라고 말한다.
- DB 마이그레이션 없음.
- 시험: `test_tombstone_delete.py`
  - 원천의 삭제 표식으로 지움(셋을 함께, 서로 가리키는 것 · 닿는 선 포함) — 계획은 따로 센다, 미리 보기는 그대로.
  - 감사 기록의 까닭.
  - 막기 — 기업만 지우면 참조 칸 2건. 셋을 지우되 선을 안 끊으면, 툴은 선에 막히고 기업은 툴에 막힌다(다시 셈).
  - 남이 잠근 타입 · 사람이 만든 타입은 줄 오류(사용 중지는 됨), 병합과 함께면 오류, 사용 중지된 것을 나중에 지움.
  - 잠금 해제 — 시스템 관리자만, 감사 기록, 두 번째는 아무것도 안 바꿈, 푼 뒤 화면의 막기 · `detach` 삭제,
    관계 종류 잠금 해제, 원천이 다시 보내면 다시 잠김.
- 화면 시험: 삭제 표식의 셈 · 「복원할 수 없다」 · 요약 줄, 배지의 원천 이름 · 잠금 해제는 시스템 관리자만 ·
  누른 것이 표의 줄로 안 올라감.

## 보강 — 정의 삭제가 원천 이름을 받는다(2026-11-24)

사용자 요청: 「`ontology_delete` 가 `source` 를 받게 해서, 그 원천 이름으로 부르면 잠긴 타입도 지울 수 있게」. 위의
길은 사람이 화면에서 「잠금 해제」 를 누른 뒤 지우는 것뿐이라, 시험으로 보낸 타입을 MCP 로 치우던 중에도 화면에 가야
했다. 고치기는 원천이 다시 보내면 되지만 **지우기는 보내서 할 길이 없다** — 그래서 지우는 경로만 연다.

- 정의 삭제 다섯(`DELETE /api/ontology/types/{slug}` · `relation-types/{slug}` · `interfaces/{slug}` ·
  `types/{slug}/properties/{key}` · `interfaces/{slug}/properties/{key}`)과 미리 보기(`GET /delete-plan`)가 `source`
  를 받는다. 잣대는 `managed.require_definition_deletable` 이다 — `managed_by` 가 비었거나 `source` 와 **같으면**
  통과. 다르면 지금과 같은 ONTOLOGY-82 로 막고, 말이 「…가 원천 이름(source)을 적어 삭제하거나 시스템 관리자가
  「잠금 해제」 한 뒤」 를 안내한다. 속성은 주인 타입 · 인터페이스의 잠금을 본다. 묶음(`group`)에는 잠금이 없다.
- **다른 막는 것은 그대로다.** 살아 있는 객체 · 맺힌 관계 · 데이터 소스 · 지표 · 외부 공개(코어) · 가리키는 지운
  객체 · 영구 삭제 확인(`purge_deleted`). 원천은 객체를 삭제 표식 `action: "delete"` 로 먼저 지우고(결정 1), 선을 선
  삭제 표식으로 해제한 뒤 정의를 지운다. 스냅샷(「삭제 직전: …」)도 그대로 남는다.
- 감사 기록: 잠근 원천의 이름으로 지웠으면 `reason` 에 「원천(<이름>)의 이름으로 삭제」(타입은 영구 삭제의 까닭과
  「 · 」 로 함께). 잠금이 없는 정의에 `source` 를 적은 것은 평소의 삭제와 같다.
- 미리 보기가 `managed_by` 를 싣는다 — 기계가 사람에게 「datarelay 가 잠근 정의를 datarelay 의 이름으로 지운다」 를
  보일 자리다.
- MCP `ontology_delete(…, source=)` 가 미리 보기 · 적용 모두에 싣는다. 안내서(`GUIDE.md` 「원천의 이름으로 지우기」)는
  **잠금을 넘으려고 원천 이름을 빌리지 않는다**고 적는다 — 원천 이름은 묶음 가져오기와 같이 스스로 대는 이름이고 인증이
  아니다(시스템 관리자만 지운다는 것은 그대로). 아직 보내는 원천이면 다음 적재가 정의를 다시 만들고 잠근다.
- 화면은 그대로다 — 사람은 「잠금 해제」 로 푼다. 화면이 원천 이름을 대신 대면 잠금이 있는 까닭이 없어진다.
- 시험: `test_tombstone_delete.py`(원천의 이름으로 타입 · 관계 종류 · 속성 지우기, 다른 이름은 막기, 감사 기록) ·
  `test_mcp_tools.py` · `mcp_server/tests/test_server.py`(`source` 가 계획 · 적용에 실린다, 묶음에는 안 실린다).
