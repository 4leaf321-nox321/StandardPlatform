# 0052. 뜻으로 찾기 — 축 타입을 일괄로 대상 지정하고, 통합 검색에 「뜻이 가까운 것」 을 더한다

- 상태: 채택(2026-11-06 구현 — `modules/semantic`(`semantic_targets` · `object_embeddings`, 마이그레이션 0094),
  작업 종류 `semantic_sync`, 워커의 5분 차례(`semantic.schedule`), `GET /api/search?meaning=true`, 서버 화면의
  「뜻으로 찾기」 칸, `deploy.sh` 의 `require_vector`)
- 날짜: 2026-11-06
- 관련: [ADR 0050](0050-뜻으로-찾기의-바탕.md)(바탕 — pgvector · 서버 안의 bge-m3), [ADR 0011](0011-축과-기록.md)(축 · 기록),
  [ADR 0010](0010-규모-참조-색인.md)(글자 찾기 — pg_trgm), [ADR 0034](0034-조회는-전원에게.md)(보는 범위)

> 번호 0051 은 협업자의 `ext/jvhub` 브랜치에 있는 제안(자주검증 포스트모텀 입력)이 쓰고 있어 건너뛴다.

## 배경

0.4.70 · 0.4.71 로 pgvector 와 서버 안의 임베딩 모델(bge-m3)이 운영 서버까지 깔렸지만 쓰는 곳이 없었다(ADR 0050
「다음」). 「다음」 은 넷이었다 — 고르는 칸 · 담는 표 · 워커 작업 · 쓰는 곳. 사용자와 정한 순서(2026-11-06):

1. **축 타입부터, 일괄로.** 축 · 기준정보는 수가 적다 — 개발 DB 의 축 274개(부품 112 · 판매 모델 84 · 불량 코드 32
   · 서비스 센터 24 · 기본 모델 14 · 국가 8)는 약 4MB, 개발 PC 에서 7초. 칸을 하나하나 고르지 않고 타입 단위로 켠다.
2. **쓰는 곳은 통합 검색 하나** — 효과를 먼저 본다. 기록(시장 서비스 13.6만 건의 고객 증상 · 수리 내역)은 칸을
   골라 켜고 용량 · 시간을 미리 보는 다음 판의 몫이다.

개발 DB 의 축 객체는 글이 이름 정도다(이름 평균 3 ~ 20자 · 설명 0건 · 선택 칸 1 ~ 2개). 그래서 축에서의 효과는
「이름의 다른 표현」 — 「뒷면 커버」 → 후면 커버 · 「battery」 → 배터리 · 「폴더블」 → 폴드 — 이고, 긴 글의 뜻이
힘을 내는 것은 기록 쪽이다.

## 결정

### 1. 대상은 설치의 운영 선택 — 온톨로지 정의에 두지 않는다

`semantic_targets`(타입 하나에 한 줄)에 둔다. 같은 정의를 쓰는 다른 설치(형제 SP)는 서버 · 용량이 달라 다르게
고르고, 정의에 두면 묶음 내보내기 · 가져오기가 그 선택까지 옮긴다. 시스템 관리자가 서버 화면 「뜻으로 찾기」 에서
고른다(`PUT /api/semantic/targets` — 통째로). 고르면 감사 기록(`semantic.targets`)이 남는다.

**이 판은 축 타입만** — 기록 · 원 표(부서 · 계정) 타입은 서버가 거절한다(`SEMANTIC-0002`). 줄의 `fields` 칸은
비워 둔다(None = 기본 글) — 기록을 칸으로 켜는 다음 판의 자리다.

### 2. 「기본 글」 — 객체 하나를 한 줄로

타입 이름 · 이름 · 사람이 붙인 다른 이름 · 설명 · 글 · 긴 글 · 선택 칸의 값 · 참조 칸이 가리키는 것의 이름. 예:
「부품: N12 카메라 · 부품군: 카메라 · 모델: N12」. 넣지 않는 것:

- 숫자 · 날짜 · 주소 · 파일 — 뜻이 없는 값이다.
- 식별자 · 외부 시스템의 코드(`source:` 별칭) — 글자 찾기가 이미 잘 찾고, 뜻의 자리를 흐린다.

4,000자에서 자른다(bge-m3 은 8,192 토큰까지 받지만 긴 글은 뜻이 흐려진다).

### 3. 담는 표 — 객체 하나에 자리 하나, 해시로 바뀐 것만

`object_embeddings`(객체 id 가 열쇠 · 타입 · 글의 해시 · 모델 · 맞춰 본 때 · `extensions.vector(1024)`), HNSW
(코사인) 색인. 해시는 **모델 이름 + 기본 글**의 sha256 — 같으면 Ollama 를 부르지 않고, 모델을 바꾸면 전부 다르다.
객체를 영구 삭제하면 함께 사라진다(CASCADE). 지운(휴지통) 객체 · 대상에서 뺀 타입의 자리는 워커가 지운다.

파이썬 pgvector 패키지는 쓰지 않는다 — 폐쇄망 번들에 의존성이 하나 늘고, 하는 일은 글 `[0.1,…]` 로 바꾸고 읽는
것뿐이다(`vectors.Vector` — 넣을 때 `CAST(… AS extensions.vector)`).

### 4. 워커 — 켜면 곧장, 5분마다 바뀐 것, 하루 한 번 전부

- 대상을 바꾸면 곧장 계산을 넣는다(대상의 것은 채우고 뺀 것은 지운다). 서버 화면의 「재계산」 은 전부를 해시로.
- 워커가 5분마다 차례를 본다(`schedule`, 자문 잠금) — 새것 · 고친 것(객체의 `updated_at` 이 맞춰 본 때보다
  나중) · 모델이 바뀐 것 · 지울 자리가 있으면 「바뀐 것만」.
- **하루 한 번은 전부를 해시로** — 다른 이름 · 가리키는 것의 이름이 바뀌어도 객체의 `updated_at` 은 안 바뀐다.
  「전부」 의 차례는 **마지막으로 성공한 때**로 센다 — 처음 차례가 실패했으면 다시 넣을 때도 전부다.
- 실패(Ollama 에 닿지 않음 …)하면 그 말이 작업에 남고, **한 시간은 다시 넣지 않는다** — 꺼진 서버에서 5분마다
  실패를 쌓지 않게. `EMBEDDING_BACKEND=off` 면 아무것도 안 넣는다.
- 묶음(500개)마다 커밋한다 — 멈추면(취소 · 재시작) 거기까지는 남고 다음 차례가 이어 간다. Ollama 에는 32개씩.

### 5. 찾기 — 통합 검색의 첫 쪽에 「뜻이 가까운 것」 을 따로

`GET /api/search?meaning=true` — 검색 화면만 묻는다(별칭 후보 창 같은 다른 부르는 곳은 글자만). 찾을 말을 뜻의
자리로 바꿔(한 번, 5초 상한) 대상 타입에서 가까운 것을 여덟까지:

- **유사도 0.45 이상만.** 개발 DB 의 축으로 잰 값(2026-11-06) — 맞는 짝: 「뒷면 커버」 → 후면 커버 0.66 ·
  「폴더블」 → 폴드 0.64 · 「충전 단자」 → 충전 보드 0.59 · 「battery」 → 배터리 0.55 · 「물에 빠짐」 → 침수 0.47.
  상관없는 말(「날씨」 「회의록」 「점심 메뉴」)의 맨 위가 0.41 ~ 0.43 이었다.
- **볼 수 있는 것만**(`visible_owner_clause`), 지운 것 · **글자로 이미 찾은 줄은 뺀다** — 같은 것을 두 번 세우지
  않는다.
- 글자로 찾은 줄에 **섞지 않고 따로 선다** — 섞으면 「왜 이게 나왔나」 를 말할 수 없다(글자 찾기는 이름 · 식별자 ·
  별칭이라고 말한다).
- 타입으로 좁히면 그 타입(인터페이스면 구현 타입)에서만. 쪽을 넘기면 묻지 않는다.
- 뜻으로 못 바꾸면(Ollama 가 꺼졌다 …) `meaning_state = unavailable` — 화면이 그렇다고 말하고 글자로 찾은 것은
  그대로 낸다. 찾기 전체는 멈추지 않는다.
- pgvector 0.6 은 걸러 찾을 때 색인을 이어 훑지 못한다 — 부서 · 타입으로 걸러지면 덜 나올 수 있어 이 질의에서만
  `hnsw.ef_search` 를 200 으로 올린다(ADR 0050 「다음」).

### 6. 배포 — 이 판부터 확장이 없으면 멈춘다(내리기 전에)

ADR 0050 이 이 판에 넘긴 것이다. `require_vector` — install · reset 은 마이그레이션 앞에서, update 는 **서비스를
내리기 전에** `ensure_vector` 를 부르고 못 갖추면 멈춘다(옛 판이 그대로 돈다). 내린 뒤 마이그레이션에서 멈추면
서비스가 꺼진 채 남는다. DB 가 다른 서버라 이 서버에서 모르면(`ensure_vector` 가 2) 지나간다 — 없으면 마이그레이션
(0094)이 할 일을 말하며 멈춘다(superuser 면 만든다). 대기 서버는 패키지만 깔면 된다(확장은 주에서 복제로 온다).
prepare 는 경고하고 이어 간다(뒤의 apptainer).

0.4.70 이후로 올린 서버에는 확장이 이미 있다 — 이 판의 갱신은 확인만 하고 지나간다.

## 대안 — 버린 것

- **기록까지 일괄로 켜기** — 시장 서비스 13.6만 건이면 약 1.9GB · 개발 PC(GPU) 26분, GPU 없는 서버는 훨씬 길다.
  칸을 골라 켜고 용량 · 시간을 먼저 보는 다음 판으로.
- **대상을 온톨로지 정의(타입의 칸)에** — 1 의 까닭.
- **글자로 찾은 줄과 한 목록으로 섞기(점수를 합쳐)** — 왜 나왔는지 말할 수 없고, 두 점수의 눈금이 달라 섞는 비가
  임의다. 먼저 따로 세워 효과를 본다.
- **검색할 때마다 늘 뜻으로(헤더의 칸 · 별칭 후보 창까지)** — 부를 때마다 모델을 한 번 더 부른다. 검색 화면만.
- **바뀔 때마다 곧장(트리거 · 요청 안에서)** — 요청이 모델을 기다리게 되고, 일괄 입력 수천 건이 수천 번 부른다.
  5분 차례로 모아서.
