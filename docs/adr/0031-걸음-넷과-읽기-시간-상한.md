# 0031. 걸음 넷과 읽기 시간 상한 — 걸음 수가 아니라 시간으로 막는다

- 상태: 채택(2026-10-15 구현 — 주소 걸음 셋 → 넷, 목록 · 통계 시간 상한 60초, 관계 걸음을 uuid 로 잇기)
- 날짜: 2026-10-15
- 관련: [ADR 0013](0013-지표.md)(주소 · 3걸음), [ADR 0017](0017-들어오는-참조.md)(나를 가리키는 것),
  [ADR 0026](0026-느린-요청-감시.md)(느린 요청), `objects/paths.py` · `shared/querycap.py`

## 배경

사용자가 「기록이 2,000만 건이면 SPARQL 이 막힌다」 를 물었다. SPARQL 은 질의마다 그래프를 메모리에 세우므로
5만 객체에서 막고(`rdf/export.MAX_OBJECTS`), 트리플 스토어(2,000만 건이면 약 7.5억 트리플 — 실측 DB 의 객체당
속성 값 평균 32.6개)는 동기화 · 부서 가림 재구현 · 폐쇄망 설치의 비용에 비해 메우는 빈틈(4걸음 이상 · 깊이 모를
반복 경로의 집계 · 자유 패턴 조인)이 좁아 **보류**했다. 대신 지금 길(통계 · 조건 · 지표의 주소)의 걸음 상한 3을
4로 올리기로 했다.

상한 3의 이유는 「넷부터는 조건을 화면에서 읽을 수 없고 질의 비용을 짐작할 수 없다」 였다. 사용자는 「2,000만이
있어도 실제로 연결된 것은 적을 수 있지 않나」 를 물었고, 2,000만 건 실측 DB 에서 재 보니 **비용은 걸음 수가 아니라
그 길로 지나가는 줄 수**였다. PostgreSQL 은 좁은 끝(색인이 있는 이름 조건)에서 출발한다.

재다가 두 가지가 더 드러났다.

- **관계 걸음이 객체 표 전부를 훑었다.** 선(`Resolver.edges`)이 저쪽 id 를 글자로 내서 `objects.id::text = other`
  로 이었는데, 그 조인은 색인을 못 타 2,000만 건을 해시하고 행 수 어림도 2.5억으로 틀어졌다 — 모델 6천 개 안에서만
  도는 네 걸음 통계가 21초. 걸음 수와 무관하게 v0.4.54 에도 있는 문제다.
- **조인이 12개를 넘으면 계획기가 순서를 어림으로 고른다**(PostgreSQL 기본 `join_collapse_limit` 8 · `geqo_threshold`
  12). 네 걸음 기준 + 세 걸음 세부 기준 + 조건이면 조인 17개 — 100초 걸려 끊겼다.

## 결정

1. **주소의 걸음은 넷까지**(`paths.MAX_HOPS = 4`). 다섯부터는 사람이 주소를 읽어 뜻을 확인하기 어렵다. 화면의
   고르개는 그대로 두 걸음(`PICKER_HOPS`) — 넷은 AI(MCP) · 직접 적은 주소 · 지표의 기준이 쓴다.
2. **목록 · 통계 · 추이에 시간 상한**(`READ_QUERY_SECONDS`, 기본 60초, 0 이면 끔). `objects/routes._filtered` 가
   요청의 트랜잭션에 `SET LOCAL statement_timeout` 을 건다 — 목록 · 통계 · 추이 · 그 내보내기(동기) · 0건 진단이 다
   여기를 지난다. **작업(내보내기 · 지표 계산)에는 안 건다**(`cap=False`) — 사람이 기다리지 않고 큰 CSV 는 원래
   몇 분이다. 지표 계획의 어림은 이미 따로 상한이 있다.
3. **넘으면 504 `APP-COMMON-0504`** — 「질의가 N초를 넘겨 멈췄습니다 … 끝이 좁은 조건을 먼저 걸거나, 자주 보는
   물음이면 지표로」. 500 이면 사람은 고장으로 읽고 다시 누른다. **503 이 아닌 까닭**: 이중화 nginx 는 503 이면
   같은 요청을 다른 서버에 다시 보낸다(`proxy_next_upstream … http_503`) — 무거운 질의가 한 번 더 돈다.
   상한이 없을 때는 600초 뒤 nginx 의 `timeout` 으로 같은 일이 났다.
4. **MCP 의 읽기 대기는 90초**(`_READ_WAIT_SECONDS`) — 백엔드 상한보다 길어야 AI 가 맨 시간 초과 대신 504 의
   안내를 받는다.
5. **상한을 거는 읽기는 계획기도 넓힌다**(`join_collapse_limit` · `from_collapse_limit` · `geqo_threshold` = 20,
   `querycap.PLANNER_JOINS`). 조인이 8개 아래인 보통 질의에는 차이가 없고, 계획에 드는 시간도 상한 안이다.
6. **관계 걸음은 uuid 로 잇는다**(`paths.reaches`). 읽을 선이 하나면(방향 있는 관계의 저쪽이 객체 타입뿐, 또는 원
   표뿐) uuid 그대로 낸다. **여럿을 합칠 때만**(방향 없는 관계 · 객체와 원 표가 섞인 끝) 예전처럼 글자로 합친다 —
   uuid 를 `UNION ALL` 로 합친 선 위에서 묶으면 PostgreSQL 16.15 가 `could not find pathkey item to sort` 내부
   오류를 냈다(실측). 사람이 준 값과 견주는 조건 · 막대의 키는 그 자리에서 글자로 바꾼다 — id 가 아닌 글자를
   줘도 오류가 아니라 「안 맞음」.
7. **트리플 스토어는 보류.** 다시 볼 신호: 실제 업무 질문이 4걸음 넘는 사슬 · 반복 경로의 집계 · 기록끼리의 패턴
   조인에 거듭 걸릴 때, 또는 다른 시스템이 표준 SPARQL 창구를 요구할 때.
8. **DB 설정은 두 층으로, 개발 PC 와 운영이 같은 것을 쓴다**(2026-10-15 추가). PostgreSQL 은 설치 기본값(공유
   버퍼 128MB · 작업 메모리 4MB · 디스크 비용은 회전 디스크 기준)으로 돌았고 배포는 그것을 안 건드렸다.
   - **요청마다**: 상한을 거는 읽기가 `work_mem`(`READ_WORK_MEM`, 기본 64MB)과 `max_parallel_workers_per_gather`
     (`READ_PARALLEL_WORKERS`, 기본 4)도 그 트랜잭션에만 건다 — 계획기 · 시간 상한과 함께 **한 번 왕복**
     (`set_config(…, true)`). `.env` 라 개발 서버(로컬 실행)와 운영이 같은 값이다. 틀린 값은 걸지 않고 서버
     설정을 따른다(기동을 막지 않는다).
   - **서버 전체**: `deploy/pg-tune.sh`(운영은 `sudo ./deploy.sh pg-tune`, 개발 PC 는 `--url <DATABASE_URL>`)가
     메모리 · CPU 로 공유 버퍼 · 캐시 어림 · 유지보수 메모리 · 디스크 비용 · 병렬 작업자를 권장하고 지금 값과 견준다.
     **기본은 보여 주기만**, `--apply` 면 `ALTER SYSTEM` + 다시 읽기. 재시작은 하지 않고 무엇이 남았는지 말한다.
9. **SPARQL 은 `types` 를 안 주면 기록 타입을 뺀다**(2026-10-15 추가). 기록(`usage="log"`)은 수백만 ~ 수천만
   건이라 늘 5만 객체 상한(`RDF-0005`)에 걸렸고, 그래서 모델 · 과제 · 프로젝트를 건너뛰는 코어의 물음까지
   막혔다. 기본 범위는 기록이 아닌 타입 전부이고, 빠진 것은 답의 `left_out` 이 말한다. **질의가 빠진 기록
   타입을 부르면**(그 타입 · 그 칸 · 그 개체의 IRI — 파싱한 질의 나무에서, 접두어 표기와 무관하게) `RDF-0006`
   으로 거절한다 — 0건이면 「없다」 로 읽힌다. 그래서 질의를 **그래프를 세우기 전에** 푼다(접두어만 묶은
   빈 그래프로). 좁혀서 물을 때 범위 밖 객체의 IRI 는 **범위 안이 실제로 가리키는 것만** 읽는다 — 예전에는
   범위 밖 객체 전부(기록 2,000만 건)를 읽어 좁혀도 무거웠다.
10. **끊긴 질문을 남긴다**(2026-10-16 추가, `cut_questions`). 시간 상한(504)에 걸린 목록 · 통계(오류 처리기가)와
    SPARQL 의 거절(그래프가 큼 `RDF-0005` · 추론이 큼 `RDF-0003` · 빠진 기록 타입 `RDF-0006`, 그 경로가)을
    **모양만** 남긴다 — 타입 · 기준 · 세부 기준 · 조건의 **칸과 연산**(값과 검색어는 안 남긴다 — 요청 시간
    기록이 물음표 뒤를 안 남기는 것과 같은 까닭), SPARQL 은 범위와 질의문(앞 2,000자). 관리 › 서버 「느린 요청 ·
    큰 응답」 과 MCP `server_status(performance="cut")` 가 같은 모양끼리 묶어 몇 번 · 몇 명 · 마지막을 보이고,
    최근 24시간에 있으면 시스템 관리자의 홈 「남은 일」 에 뜬다. **무엇을 지표로 미리 세어 둘지, 트리플 스토어가
    정말 필요한지를 짐작이 아니라 실제 물음으로 가르려는 것이다.** 따로 세션으로 넣고(요청의 트랜잭션은 거절과
    함께 버려진다), 넣다가 실패해도 사람이 받을 안내는 그대로 나간다. 보관 기간은 요청 시간 기록과 같다.

## 결과

2,000만 건 실측 DB(`standardplatform_big_scale` — 기록 2,020만 · 모델 6천 · 과제 5천 · 프로젝트 120 · 부품 300,
PostgreSQL 16.15, 개발 PC · WSL, 캐시에 따라 흔들린다). 「전」 은 v0.4.54 코드에 이 측정에서만 걸음 상한을 4로
넓힌 것.

| 질의 | 걸음 | 지나가는 줄 | 전 | 후 |
| --- | --- | --- | --- | --- |
| ① 「그 부품이 교체된 기록이 있는 프로젝트」(조건, 끝이 좁음) | 4 | 수천~수만 | 1.7~41초(부품마다) | 2.7~4.6초 |
| ② 모델 › 기본 모델 › 형제 모델 › 과제 › 프로젝트별(통계, 축끼리) | 4 | 6천 | 21초 | **0.4초** |
| ③ 기록 중 「형제 모델의 과제 = 과제 1」(조건) | 4 | 1만 | 2.7초 | **0.2초** |
| ④ 좁은 조건 + 4걸음 기준 + 3걸음 세부 기준(조인 17개) | 4 · 3 | 6.7만 | 94초에 끊김(상한을 건 채로) | **13~20초** |
| ⑤ 프로젝트별 교체 부품(통계, 기록 전부를 지남) | 4 | 2,000만 | 181초 | 60초에 504 |
| ⑥ 기록 전부를 프로젝트별로(통계) | 3 | 2,000만 | 20~38초 | 20~37초 |
| 「프로젝트 1」 에 속한 기록(조건) | 3 | 16만 | 26초(두 번째) ~ 70초(처음) | — |

- 상한은 **질의 하나**에 건다 — 통계 한 번은 질의 서넛(전체 수 · 막대 · 세부 기준)이라 요청 전체는 그보다 길 수
  있다(④ 는 관계 걸음만 고친 판에서 질의 하나하나는 60초 안이었지만 합쳐 87초였다). 요청 전체를 묶는 `transaction_timeout` 은 PostgreSQL 17 부터다.
- 시험: `tests/api/test_query_cap.py`(상한과 계획기 설정이 그 트랜잭션에만 · 넘으면 504 와 안내 · 그 뒤 같은
  연결이 멀쩡 · 내보내기 작업은 상한을 안 건다), `test_linked_fields`(네 걸음 통계 · 조건, 다섯은 422),
  `test_system_types`(원 표로 가는 관계 걸음으로 묶고 거르기 · id 아닌 글자는 「안 맞음」). 방향 없는 관계(글자로
  합치는 길)는 기존 시험이 덮는다.
- 안내서 `GUIDE_VERSION 2026-10-15c` — 「걸리는 시간은 걸음 수가 아니라 지나가는 기록 수」 와 504 를 받았을 때 할 일.
- **요청마다 거는 DB 설정**(결정 8, ⑥ 「기록 전부를 프로젝트별로」, 조합마다 두 번 — 같은 PC 에서 다른 프로젝트의
  시험이 같이 돌아 흔들린다): 기본 27~34초 · 작업 메모리 64MB + 작업자 4(기본값으로 정한 것) 22~23초 · 128MB + 8
  21초 · 디스크 비용 1.1 + 캐시 어림 20GB 만 23~28초 · 작업자 8만 23~24초. 효과는 작업 메모리와 병렬 작업자에서
  온다. 좁은 조건(「프로젝트 7」 기록 17만 건)은 설정보다 캐시가 좌우한다 — 처음 17~28초, 두 번째부터 3~4초.
  2,000만 건을 다 지나가는 네 걸음 통계(⑤)는 설정을 바꿔도 96~130초라 시간 상한에 걸린다 — 지표의 자리다.
- 끊긴 질문(결정 10): `tests/api/test_cut_questions.py` — 504 가 모양만 남기고 같은 모양은 한 줄(조건의 값 ·
  검색어가 응답 어디에도 없다), SPARQL 의 두 거절이 질의문과 함께, 시스템 관리자만 · 홈 「남은 일」 · 보관 기간 뒤
  정리. 화면 시험(`Performance.test.tsx`), MCP 경로 시험.
