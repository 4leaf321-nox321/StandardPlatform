# 0007. 속성 종류를 바꾼다 — 저장된 값을 함께, 계획 먼저

- 상태: 채택
- 날짜: 2026-10-01
- 관련: [ADR 0005](0005-온톨로지-메타모델.md)(온톨로지 메타모델 — 속성 정의가 화면을 만든다),
  [ADR 0006](0006-인터페이스.md)(인터페이스 — 「키 · 종류 바꾸기 도구가 생기면 그 길로 간다」 의 종류 쪽).
  화면과 라우트의 「종류는 만들 때만 정한다」(ONTOLOGY-35)를 고친다

## 배경

지금은 속성 종류(`data_type`)를 어디서도 못 바꾼다 — 화면 · 라우트(ONTOLOGY-35) · 정의 가져오기가 모두
거절하고, 유일한 예외가 코드표 승격(고를 값 → 참조)이다. 거절한 이유는 맞았다: 종류만 바꾸면 이미 저장된
값이 새 종류에 안 맞는데 **화면은 그것을 말해 주지 못한다.** 하지만 그 대가가 셋으로 드러났다.

1. **인터페이스를 기존 데이터에 못 쓴다.** 개발 DB 실측 — `nw_supplier.country` 는 글, `sim_company.country`
   는 고를 값이라 두 타입이 같은 「거래처」 인터페이스를 구현하지 못한다(ADR 0006 결정 5 가 그렇게 막는다).
   맞추려면 새 속성을 만들어 값을 손으로 옮기는 수밖에 없었다.
2. **표 추론의 약속을 못 지킨다.** 표에서 타입을 만들 때 「애매한 열은 글자로 둔다 — 나중에 좁히는 것은
   쉽다」 고 했는데, 좁힐 길이 없었다.
3. **종류가 바뀐 뒤의 스냅샷 복원이 통째로 실패한다.** 복원은 정의 가져오기와 같은 길을 타고, 그 길이 종류
   변경을 거절한다 — 코드표 승격 직전 스냅샷이 이미 그렇다.

Palantir Foundry 비교(2026-09-30) §11 의 두 번째 줄 「속성 종류 바꾸기 — 계획 먼저」 가 이것이다.

## 결정

**종류 변경을 둔다 — 속성 종류를 바꾸면서 저장된 값도 새 종류로 변환한다. 계획을 먼저 보고 적용한다.**

    종류 변경      POST …/properties/{key}/retype — 계획(apply=false) → 적용(apply=true)
    변환           저장값을 정해진 글자로 읽은 뒤 새 종류로 해석한다
    대체 값        변환할 수 없는 값 대신 넣을 값(또는 값 삭제) — 값마다 사람이 정한다

1. **글자로 읽어 새 종류로 해석한다.** 저장값(여러 값이면 원소마다)을 정해진 글자로 읽은 뒤 새 종류의
   규칙으로 해석한다 — 글 · 긴 글 · 주소 · 숫자 · 날짜 · 시각 · 참/거짓 · 고를 값 사이의 어느 쌍이든 같은
   규칙이다. 쌍마다 규칙을 따로 두면 한 쌍만 고쳐지고, 그때 같은 값이 길에 따라 다르게 변환된다.
   참조 · 파일은 양쪽 다 제외한다(고를 값 → 참조는 코드표 승격이 한다).
2. **변환할 수 없는 값이 하나라도 있으면 적용하지 않는다.** 계획이 값마다(「12 kg」 37건, 견본 객체) 보여 주고,
   사람이 값마다 대체 값을 적거나 값 삭제를 고른다. **조용히 비우거나 짐작으로 맞추지 않는다** — 비운 값은
   다시 오지 않고, 짐작한 값은 맞는 값처럼 쓰인다. 빈 글자는 값이 없는 것이라 실패가 아니다(키를 지운다).
3. **PATCH 로는 종류를 바꾸지 않는다.** 속성 수정은 계획도 대체 값도 없다 — 종류 변경은 따로 된 동작이고,
   ONTOLOGY-35 가 그 길을 가리킨다.
4. **화면 · 정의 가져오기 · 허브 묶음 · 스냅샷 복원이 같은 함수로 변환한다.** 두 벌이면 한쪽만 고쳐진다.
   가져오기에는 대체 값을 적을 자리가 없으니 변환할 수 없는 값은 계획 오류다(화면에서 정하고 다시).
   예외 하나 — **허브가 관리하는 타입**(쌍둥이 쪽)은 그 허브의 묶음으로 바뀔 때 변환할 수 없는 값을 비우고
   경고로 목록을 적는다. 쌍둥이는 그 객체를 못 고치므로 「고치고 다시」 가 불가능하고, 허브가 변환한 값은
   같은 묶음의 객체 단계가 다시 보낸다.
5. **인터페이스의 공통 속성은 구현 타입 전부를 한 번에 바꾼다** — 한 타입이라도 변환할 수 없는 값이 있으면
   아무것도 안 바뀐다. 묶인 타입 속성은 타입 쪽에서 바꾸지 않는다(ADR 0006 결정 4).
6. **딸린 것을 같이 말한다.** 공개 타입이면 수신 시스템 확인을 받는다(종류가 계약의 일부다). 목록의 롤업이
   숫자 아닌 칸을 가리키게 되면 걷어낸다(남기면 다음 타입 수정이 거절된다). 저장된 뷰 · 홈 위젯이 새로
   깨지면 경고한다 — 사람의 것이라 고치지 않는다. 유일 속성에 변환으로 새 겹침이 생기면 오류다.
7. **되돌리기는 정의 스냅샷 + 객체 이력이다**(코드표 승격과 같은 수준). 적용 직전에 정의 스냅샷을 남기고,
   객체마다 이력에 전→후가 남는다. 복원하면 값도 다시 변환된다 — 원래 표기(「1,234」)는 이력에만 남는다.

## 대안

### PATCH 에서 종류를 받는다

가장 싸다. 하지만 계획이 없으니 무엇이 변환되고 무엇이 안 되는지 누르기 전에 모르고, 대체 값을 적을 자리도
없다. 화면의 저장 본문은 늘 종류를 보내므로, 실수 한 번이 수천 개 값을 바꾼다.

### 새 속성을 만들어 옮기는 것만 돕는다

키가 바뀐다 — 목록 · 폼 · 저장된 뷰 · 코어 API · RDF 주소가 전부 옛 키를 들고 있다. 키 바꾸기를 먼저
만들어야 하고, 그것은 이 결정보다 훨씬 넓다.

### 변환할 수 없는 값은 비우고 경고한다

빠르지만 값을 잃는다. 경고는 한 번 지나가면 아무도 다시 안 읽는다.

### 화면 전용(가져오기 · 묶음은 지금처럼 거절)

범위는 작지만, 허브에서 바꾼 종류가 쌍둥이로 전해지지 않고 종류가 바뀐 뒤의 스냅샷 복원이 계속 막힌다.

## 결과

- 표 추론이 글자로 둔 칸을 나중에 좁힐 수 있고, 인터페이스를 구현하기 전에 모양을 맞출 수 있다.
- 종류가 바뀐 뒤에도 그 전 스냅샷을 복원할 수 있다(참조 ↔ 고를 값은 여전히 안 된다 — 승격의 반대는 이
  결정 밖이다).
- 관계 종류의 속성은 아직 바꾸지 않는다 — 값이 객체가 아니라 관계 줄에 있다.
- **속성 키 바꾸기는 이 결정의 범위가 아니다.** 저장값의 칸 이름 · 목록 · 폼 · 저장된 뷰 · 이어진 칸 주소 ·
  RDF · 코어 약속 · 허브 묶음(키로 맞춘다)에 닿아 따로 결정한다.
- 절차와 단계별 할 일은 [온톨로지-메타모델-설계.md](../온톨로지-메타모델-설계.md) §9 의 7단계가 정본이다.
