# 0071. SPARQL 사본 — 흘려 싣기와 바뀐 것만 고치기(지문으로 고른다)

- 상태: 채택(2026-11-11 구현)
  - 앱: `app/modules/rdf/copycli.py`(통째로 — 내보내는 자식 → 파이프 → `bulk_load`, 바뀐 것만 · 언제 통째로) ·
    `copystate.py`(지문 · 견주기 · 다시 낼 줄 · DB 가 말하는 개수) · `copyapply.py`(체크포인트 · 지우기 · 넣기 · 사본의
    개수 — pyoxigraph, 밤 작업만) · `copyexport.py`(정의에서 한 번 읽는 `Shape`, 거르기를 받는 부분 내보내기)
  - 설정: `RDF_COPY_CHANGES`(기본 켬) · `RDF_COPY_FULL_WEEKDAY`(기본 `sun`)
  - 시험: `tests/api/test_rdf_copy_changes.py`(바뀌는 꼴마다 고친 사본 = 통째로 내보낸 것, 끊긴 내보내기)
- 날짜: 2026-11-11
- 관련: [ADR 0070](0070-SPARQL-사본-디스크에-세운-RDF-저장소.md)(SPARQL 사본 — 「다음」 의 두 가지),
  [ADR 0069](0069-그래프-사본-설치마다-Neo4j.md)(그래프 사본 — 여기서는 통째로 그대로, 아래 「고르지 않은 것」)

## 배경

SPARQL 사본은 밤마다 통째로 실었다 — 2,000만 객체에서 내보내기 26분이 임시 파일 90GB 를 다 쓴 뒤에 싣기 27분이
시작됐다(모두 53분, 싣는 동안 디스크 약 260GB). 1억 객체면 4 ~ 5시간으로 어림했다. 사용자 결정(2026-11-11): **흘려
싣기**(임시 파일 없이) · **바뀐 것만 고치기**(주 1회 통째로, 그 사이 바뀐 것만) — 「부작용이 없을지 잘 검토하고」.

## 결정

### 1. 흘려 싣기 — 내보내는 자식 → 파이프 → 싣기

- 이 프로세스가 내보내는 **자식 프로세스**(한 트랜잭션, REPEATABLE READ)를 띄우고, 자식이 정의 · 데이터 N-Triples 를
  파이프로 흘리면 받는 대로 쉬는 쪽 폴더에 싣는다(`bulk_load`). 임시 파일이 없다.
- 한 프로세스의 두 스레드로 하지 않는다 — 싣기가 파이썬 쪽에서 읽는 동안 GIL 을 쥐면 내보내는 스레드가 못 돌아
  파이프가 막힌다.
- **실패는 자식의 종료 코드로만 판다.** 파이프가 줄 끝에서 끊기면 싣기는 「다 받았다」 로 끝날 수 있다(시험이 두
  꼴을 다 본다 — 줄 끝에서 끊김 · 줄 가운데서 끊김). 실패하면 실은 폴더를 버리고 `active` 는 그대로다.
- 자식은 다 흘린 뒤 **같은 트랜잭션에서** 지문을 짓는다(아래 2) — 그 사이 이쪽은 다진다(`optimize`).

### 2. 바뀐 것은 시각이 아니라 지문으로 고른다

**`updated_at` 으로 고르면 빠진다** — 사본에 실리는 것이 바뀌어도 시각이 안 바뀌는 길이 있다(조사 2026-11-11):

| 길 | 사본에서 바뀌는 것 | `updated_at` |
| --- | --- | --- |
| 선을 다시 고정(`lineage._write_pin`) · 허브에서 실어 온 선의 판정 옮기기 | 구체화한 진술의 `pinnedRevision` · `pinnedAt` | **일부러 그대로**(`onupdate` 를 막는다) |
| 관계 종류의 계보 끝 · 타입의 개정 칸을 바꿀 때 트리거 | 같은 것 | 안 바뀜 |
| 기간이 있는 선 — **날짜만 지나** 유효해지거나 끝남 | 선이 생기거나 사라짐 | 안 바뀜(DB 는 그대로) |
| 별칭 | `skos:altLabel` | 객체를 `_touch` 한다(코어 API 가 기댄다) — 괜찮음 |
| 끊은 선 | 선이 사라짐 | 무덤(`object_relation_tombstones`, ORM 만) |

그래서 **사본에 실리는 칸 그대로에서 지문**(`md5`, DB 가 계산)을 짓고 지난 판의 지문과 견준다 — 무엇이 그 칸을
고쳤든 다르면 다르다. 시각 · 무덤 · 트랜잭션 시작 시각(코어 API 의 `watermark`)에 기대지 않는다.

- **객체**: 타입 · 식별자 · 이름 · 설명 · 값(`properties::text` — jsonb 는 키 차례를 맞춘 글이라 같은 값은 같은 글) ·
  사람이 붙인 별칭. 참조 색인(`object_refs`)은 값 · 타입 · 삭제에서 트리거가 만들므로 값에 이미 들어 있다. 살아 있는
  것(지움 · 합침이 아닌 것)만 — 사라지면 「사라짐」 으로 잡힌다.
- **관계**: 오늘 유효하고 두 끝이 살아 있는 선만 — 종류 · 두 끝 · 기간 · 고정. 날짜가 지나 유효해진 선은 「새로
  생김」, 끝난 선은 「사라짐」 으로 저절로 잡힌다.
- **정의**: 타입 · 칸 · 인터페이스 · 관계 종류 표의 행 전부 + 지문의 판 + SP 판. 다르면 그날은 통째로. 화면 배치 ·
  시각 칸(`list_view` · `form_view` · `detail_view` · `created_at` · `updated_at`)은 뺀다 — 목록 칸 배치를 고칠 때마다
  통째로가 되지 않게. 사본이 그 칸을 안 읽는 것은 시험이 지킨다.
- 지문 · IRI 는 사본 곁의 `state.sqlite`(폴더마다 — 사본과 함께 바꿔 끼우고 함께 버린다)에 둔다. **사본을 내보낸 그
  트랜잭션에서** 짓는다 — 다른 때에 지으면 그 사이 바뀐 것이 사본에는 없는데 지문에는 있어, 다음 밤에 「안 바뀜」
  으로 보고 영영 빠진다.
- 지문은 `COPY (…) TO STDOUT` 으로 받는다 — 서버 쪽 커서는 병렬 질의를 끈다(2,020만 객체: 커서 580초 → `COPY` 91초).
  정렬이 디스크로 쏟아지지 않게 그 트랜잭션만 `work_mem` 256MB.

### 3. 고치기 — 체크포인트 위에, 지우고 다시 낸다

1. 지금 판을 **체크포인트**로 뜬다(읽기 전용으로 열고 `backup` — 같은 디스크에서 하드 링크, 몇 초). 쓰는 동안 웹은
   지금 판을 그대로 읽는다.
2. **지운다**(옛 IRI 로 — 지문 파일에 있다): 바뀐 객체가 주어인 줄(관계 술어는 빼고). IRI 가 달라진 객체(생김 ·
   사라짐 · 식별자 · 타입)는 그것을 가리키는 줄(들어오는 참조 · 관계 · 구체화한 진술)과 나가는 관계까지. 바뀐 선은
   **열쇠(출발 · 종류 · 도착)마다** 그 줄과 같은 몸통의 구체화한 진술 전부 — 같은 열쇠의 선 여럿이 사본의 줄 하나를
   함께 쓴다.
3. **다시 낸다** — 통째로 내보내기와 **같은 함수 · 같은 거르기**(`copyexport` 의 부분 내보내기)로, 지운 것의 지금
   모습: 바뀐 객체의 줄 · 별칭 · 나가는 참조, IRI 가 달라진 객체에 들어오는 참조 · 닿는 관계, 바뀐 열쇠의 오늘 유효한
   선 전부(같은 열쇠의 안 바뀐 선까지). 같은 선을 두 번 내지 않는다(구체화한 진술이 둘이 된다).
4. **견준다** — 타입 · 인터페이스마다 객체 수, 관계 종류마다 (출발, 도착) 짝 수, 참조 칸마다 줄 수, 구체화한 진술 수,
   별칭 수를 DB 가 말하는 것과. 다르면 그 판을 버리고 **그 밤에 통째로**.
5. 지문 파일을 바뀐 줄만 고쳐 이번 판으로 — `active` 를 바꿔 끼운다.

**빈 노드는 이름으로 못 찾는다** — `bulk_load` 가 이름을 새로 짓는다(`_:r<선 id>` 가 남지 않는다, 실측). 그래서
2 의 구체화한 진술은 몸통으로 찾는다.

**IRI 를 함께 쓰는 객체**(v0.4.82 CI 에서 드러남) — IRI 는 타입과 식별자로 짓는다. 식별자를 부서마다 따로 쓰는
타입(`key_scope=workspace`)에서는 두 부서의 「M-1」 이 사본에서 IRI 하나다(예전부터 — 메모리 그래프도 같다). 그
IRI 의 줄을 지우면 안 바뀐 쪽의 줄까지 지워진다. 그래서 바뀐 것이 닿는 IRI(바뀐 객체의 옛 · 새 IRI, 바뀐 선의 두
끝)마다 그 IRI 를 지금 쓰는 객체를 DB 에서 찾아(식별자 색인) 둘 이상이면 **모두** IRI 가 바뀐 것처럼 지우고 다시
낸다(`copystate.widen`). 4 의 개수도 그런 타입에 닿는 줄은 서로 다른 IRI 로 센다.

**개수 견주기는 그물이지 보증이 아니다** — 값 줄 하나가 빠져도 수는 그대로일 수 있다(위의 함께 쓰는 IRI 를 고치기
전에, 다른 부서 객체의 이름 · 값이 사라졌는데 개수는 맞았다 — 시험이 견주어 잡았다). 그래서 바뀌는 꼴마다 「고친
사본 = 통째로 내보낸 것」 을 줄 단위로 견주는 시험이 본 보증이고, 주 1회 통째로가 남은 것을 바로잡는다.

### 4. 언제 통째로

`--full` · 지난 판이나 지문이 없음 · 지문 판 · SP 판 · 정의가 다름 · **주 1회**(`RDF_COPY_FULL_WEEKDAY`, 기본
일요일 — 그날 이미 통째로 했으면 안 한다) · 통째로 한 지 7일(그 요일의 싣기가 실패했거나 요일을 비웠을 때) · 바뀐
것이 지난 판의 10% 넘음(그쯤이면 통째로가 빠르고 깨끗하다) · 고친 뒤 개수가 어긋남 · 고치다 오류. 끄기
`RDF_COPY_CHANGES=false`(늘 통째로 — 예전과 같다).

통째로 하는 날은 지금처럼 다진다(`optimize`). 바뀐 것만 고친 판은 다지지 않는다 — 85GB 를 다시 쓰는 일이라 고치기
보다 크다. RocksDB 가 스스로 합치고, 주 1회 통째로가 다진다.

## 부작용 검토(2026-11-11)

| 무엇 | 어떻게 되나 |
| --- | --- |
| 쓰는 길이 `updated_at` 을 안 올림 · 트리거 · 날짜 경계 · 무덤 없는 삭제 | 지문으로 고르므로 상관없다(위 2) |
| 정본(SP) | 읽기만 한다. 객체 · 선의 `updated_at` 뜻을 바꾸지 않는다(계보의 낡음 판정이 기댄다) |
| 정말 지우는 길(타입 삭제의 영구 삭제 · 초기화) | 정의가 바뀌므로 그날 통째로 |
| DB 의 짐 | 밤에 지문 질의 둘(병렬 `COPY` — 2,000만 객체 약 1.5분) + 개수 질의. 반복 읽기 트랜잭션은 통째로의 26분보다 짧다 |
| 웹 · 질의 | `active` 만 읽는다 — 바꿔 끼우기는 이름 바꾸기 한 번. 앞 판은 다음 밤까지 둔다(지금과 같다) |
| 디스크 | 체크포인트는 하드 링크 — 두 폴더가 파일 대부분을 함께 쓴다(합치기가 다시 쓰는 만큼 벌어진다). 지문 파일이 폴더마다 하나(아래 결과) |
| 사본이 어긋남 | 고친 뒤 개수 견주기 → 그 밤 통째로(개수로 안 보이는 어긋남도 있다 — 위 3). 주 1회 통째로가 나머지를 바로잡는다 |
| 같은 IRI 를 두 객체가 씀(부서마다 같은 식별자) | 함께 지우고 함께 다시 낸다(위 3). 두 객체가 사본에서 하나로 보이는 것 자체는 예전부터의 이름 짓는 법이다 — 이번에 바꾸지 않았다 |
| 이중화 | 서버마다 제 사본 · 제 지문 — 나눠 쓰는 것이 없다 |
| 판 올리기 | SP 판이 지문에 들어 있어 `update` 뒤 첫 싣기는 통째로 |
| 밤 작업 자리표 | 바뀐 것만 고치는 밤은 자리를 짧게 쥔다 — 같은 서버의 다른 설치가 덜 기다린다 |
| 화면 · API | 그대로. `copied_at` 은 그 판을 지은 때. 판 기록(`manifest.json`)에 `mode`(`full` · `changes`) · `reason` · 바뀐 수가 더해진다 |

## 결과

개발 PC(32코어 · 31GB), 운영 모양 DB(객체 2,020만 · 트리플 7억 3,125만), 합성 자료.

| | 예전(파일로 쓰고 싣기, ADR 0070) | 통째로 — 흘려 싣기 | 바뀐 것만(하루 10만 객체 가정) |
| --- | --- | --- | --- |
| 모두 | 53분 | **42분 39초** | **7분 18초** |
| 나눠 보면 | 내보내기 26분 → 싣기 · 다지기 27분 | 내보내기 26분 47초 · 받으며 싣기 32분(내보내기와 겹친다) · 다지기 약 10분 · 지문 짓기 2분 39초(다지기와 겹친다) | 지문 견주기 117초 · 고치기 240초(줄 362만 지우고 다시 넣기) · 개수 견주기 81초 |
| 임시 파일 | 90GB | **없다** | 없다 |
| 최대 메모리 | 20.5GB | **2.1GB** | 1.7GB |
| 사본(한 벌) | 84.5GB | 97GB + 지문 1.9GB | 앞 판과 하드 링크로 나눠 쓰고, 이 판만의 것 4.0GB |
| 질의(전부의 타입별 수 · 참조 칸 하나의 수 · 하나에서 출발) | 6.4초 · — · 0.09초 | 5.6초 · 5.1초 · 0.02초 | 6.3초 · 5.5초 · 0.01초(다지지 않은 판) |

- **흘려 실은 사본이 14% 크다**(같은 트리플 · 같은 다지기 — 다시 다져도 그대로다). 파일로 실을 때는 Oxigraph 가 파일을
  나눠 여러 코어로 큰 덩이를 지었고(메모리 20GB), 흐름에서는 한 줄로 작은 덩이씩 짓는다(2GB). 대신 임시 90GB ·
  메모리 18GB · 10분이 준다.
- **바뀐 것이 두 배면**(같은 IRI 찾기를 더한 뒤, 객체 20만 · IRI 200 · 선 200) — 12분 2초(지문 견주기 158초 · 고치기
  478초 · 개수 견주기 85초). 고치기는 바뀐 양에 비례하고, 같은 IRI 찾기는 20만 개에 40초쯤 더한다.
- **바뀐 것만**은 실제로 DB 를 고치지 않고 지문 파일을 비틀어 쟀다(값 10만 · IRI 100 · 선 100이 「바뀐」 것으로 보이게)
  — 지우기 · 다시 내기 · 넣기 · 개수 견주기가 실제와 같은 만큼 돈다. 개수가 맞아 바꿔 끼웠다.
- **디스크(설치 하나)** — 바뀐 것만 고치는 밤에는 두 폴더가 파일 대부분을 함께 써서 평소 약 100 ~ 110GB(예전 두 벌
  170GB). 통째로 하는 날(일요일)은 싣는 동안 최대 약 240GB(앞 판 + 짓는 판이 다지는 동안 잠깐 142GB), 다음 밤까지 약
  200GB.

## 고르지 않은 것

- **`updated_at` · 무덤으로 고르기**(코어 API 의 방식) — 위 2 의 표. 코어 API 는 고정(`pinned_*`)을 내지 않아서 그
  길이 맞지만, 사본은 그것을 싣는다. 앞으로 생길 쓰는 길도 같은 함정에 빠진다.
- **매일 통째로 내보내고 줄마다 해시로 견주기** — 내보내기(26분)가 그대로 남는다.
- **지문을 PostgreSQL 표에 두기** — 사본 폴더와 따로 놀 틈이 생기고(바꿔 끼우기와 표 쓰기가 한 번에 안 된다), 운영
  DB 에 2,000만 줄을 밤마다 쓴다(WAL · 백업).
- **Neo4j 사본도 바뀐 것만**(계획에는 있었다) — 2,020만 객체 실측이 통째로 내보내기 4분 34초 · 싣기 3분 18초(CSV
  11GB · 저장소 17GB)라 얻을 것이 작다. 떠 있는 사본에 바로 써야 해서(무료판은 DB 하나) 고치는 동안 반쯤 고친 상태가
  보이고, 중간에 실패하면 어긋난 채 남는다. 1억 객체쯤에서 다시 본다. CSV 를 gzip 으로 줄이는 것도 하지 않는다 —
  임시 11GB 가 3분쯤 있다 사라지는데, 압축이 한 줄로 도는 내보내기를 늦춘다.
