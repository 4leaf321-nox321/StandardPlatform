# 0054. 뜻으로 찾기의 조각 — 기록은 칸을 골라, 문서는 절마다

- 상태: 채택(2026-11-06 구현 — `object_embeddings` 의 `part` · `heading` · `anchor` · 글 해시 색인, `semantic_marks`,
  마이그레이션 0096, `semantic_targets.fields`, `services.sections` · `pieces_of` · 같은 글 옮겨 쓰기, 검색의 절 ·
  같은 내용 수, 관리 칸의 칸 고르기 · 시간 어림)
- 날짜: 2026-11-06
- 관련: [ADR 0052](0052-뜻으로-찾기-축-타입과-통합-검색.md)(축 타입 · 통합 검색), [ADR 0053](0053-문서-속성-마크다운과-판.md)
  (문서 속성), [ADR 0050](0050-뜻으로-찾기의-바탕.md)(바탕 · 용량 실측)

## 배경

ADR 0052 는 축 타입을 일괄로만 켰다 — 객체 하나에 자리 하나(「기본 글」). 남은 둘(2026-11-06):

1. **기록도 일부 칸만.** 시장 서비스 13.6만 건의 「고객 증상」 · 「수리 내역」 처럼 사람마다 다르게 적는 글이 뜻으로
   찾기가 힘을 내는 곳이다. 전부(자동)는 이름 · 코드 칸까지 섞여 뜻이 흐리고, GPU 없는 서버에서 끝나지 않는다.
2. **문서의 절**(ADR 0053 의 ②). 백서 한 편(20만 자)을 자리 하나로 바꾸면 그 안의 한 가지 이야기가 묻히고,
   bge-m3 의 8,192 토큰도 넘는다. 찾은 줄이 「백서 X › 3.1 모서리 찍힘」 처럼 절을 가리켜야 한다.

## 결정

### 1. 조각 — 객체 하나에 자리 여럿

`object_embeddings` 의 열쇠를 (객체, `part`)로. `part = ""` 는 기본 글, `part = "doc:<칸>:<번호>"` 는 문서의 절.
절에는 경로(`heading` — 「3. 결과 › 3.1 모서리 찍힘」)와 제목 id(`anchor`)를 둔다. 있던 자리는 그대로 기본 글
조각이 된다(0096).

### 2. 대상의 칸 — 축은 자동, 기록은 고른다

`semantic_targets.fields` — None 이면 **자동**(축만: 이름 · 다른 이름 · 설명 · 글 · 선택 · 참조 칸 전부 + 문서 전부).
목록이면 **고른 칸만** — 고를 수 있는 것은 글 · 여러 줄 글 · 선택 · 참조 · 문서와 이름(`label`). 기록은 반드시
고른다(`SEMANTIC-0004`), 없는 칸 · 숫자 · 날짜 같은 칸은 거절(`SEMANTIC-0005`). 고른 칸의 기본 글에는 이름이 들지
않는다(기록의 이름은 대개 번호다 — 「SR2302-000003 · …」) — 고르면 든다.

칸을 바꾼 타입은 맞춰 본 때를 지워 **전부 다시** 맞춘다(글이 같은 조각은 해시로 그대로 남는다).

### 3. 맞춰 본 때 — `semantic_marks`

객체마다 마지막으로 맞춰 본 때 · 모델. 0052 는 자리 줄의 `embedded_at` 으로 그 일을 했지만, 조각이 하나도 없는
객체(고른 칸이 다 빈 기록)는 그 줄이 없어 5분마다 다시 보게 된다. 객체의 `updated_at` 이 이보다 나중이거나 모델이
바뀌었으면 다시 볼 차례다(문서를 고치면 객체의 `updated_at` 이 오른다 — ADR 0053).

### 4. 문서를 절로 — 화면과 같은 제목 id

제목 h1 ~ h3 로 나눈다(h4 이하는 절 안의 글). 코드 울타리(```` ``` ```` · `~~~`) 안의 「#」 은 제목이 아니다. 절이
1,500자를 넘으면 문단(빈 줄) 단위로 더 나눈다. 조각의 글은 「객체 이름 › 절의 경로」 + 절의 글.

제목 id 는 **화면(`MarkdownView` 의 `slugOf`)과 같은 규칙** — 링크 · 굵게 · 코드 표시를 뺀 제목 글을 소문자로,
글자 · 숫자 말고는 「-」, 같은 id 가 또 나오면 「-2」(h1 ~ h3 전부를 차례로 센다). 찾은 줄이
`/o/<타입>/<id>#<제목 id>` 로 그 절에 바로 간다(문서 칸이 주소의 `#` 를 보고 옮긴다).

### 5. 같은 글은 한 번만 — 해시로 자리를 옮겨 쓴다

조각의 글 해시(모델 이름 + 글)가 이미 있는 조각과 같으면 Ollama 를 부르지 않고 그 자리를 복사한다(글 해시 색인).
개발 DB 의 시장 서비스는 13.6만 건인데 (고객 증상, 수리 내역) 쌍이 1,103개뿐이다 — 3,000건 실측에서 569번만
계산하고 2,431개를 옮겨 썼다(24.9초).

### 6. 찾기 — 객체마다 한 줄, 같은 글은 하나만

가까운 조각을 넉넉히(`EF_SEARCH` 400) 받아 **객체마다 가장 가까운 조각 하나**, **글이 똑같은 것은 하나만** 세운다.
같은 글의 다른 객체 수(볼 수 있는 것만)를 「같은 내용 N건 더」 로 함께 말한다 — 그대로 늘어놓으면 같은 증상의
기록이 첫 쪽을 다 차지했다(실측). 문서의 절이면 그 절의 경로와 id 를 싣는다.

### 7. 관리 칸 — 칸 고르기와 시간 어림

줄마다 대상 · 칸(자동 / 고른 칸, 연필 단추로 고르기) · 객체 · 계산 완료 · 조각 · 대기 · **예상**(조각 수 · 용량 ·
시간). 시간은 **이 서버의 지난 계산 속도**(조각 100개 이상을 새로 바꾼 계산의 초당 조각 수)로 어림한다 — GPU
유무가 몇십 배를 가른다. 처음에는 「첫 계산 뒤에 어림」. 같은 글을 옮겨 쓰므로 실제는 대개 어림보다 짧다. 기록의
대상 칸을 누르면 칸 고르기가 먼저 열린다.

## 대안 — 버린 것

- **기록도 자동(전부)** — 번호 · 코드 칸이 섞여 뜻이 흐리고 서버가 감당하지 못한다.
- **문서 전체를 자리 하나로** — 긴 글의 한 이야기가 묻히고 토큰 상한을 넘는다.
- **조각마다 맞춰 본 때(`embedded_at`)** — 조각 없는 객체를 영영 다시 본다(3).
- **같은 글을 묶어 한 줄로만 담기(글 표 + 객체 표)** — 표가 하나 더 늘고 찾기가 한 번 더 잇는다. 해시로 복사하면
  자리는 늘지만(조각마다 14KB) 질의가 단순하다. 늘어나는 자리가 문제가 되면 다시 본다.

## 결과

시험(`tests/api/test_semantic.py`): 기록은 칸을 골라야 대상(자동 거절 · 숫자 칸 거절 · 고른 칸이 그대로) · 절은
제목으로 나뉘고 id 는 화면과 같음(울타리 · h4 · 같은 제목 「-2」 · 1,500자 나눔) · 기록은 고른 칸만, 문서는 절마다
조각 · 고른 칸이 빈 기록도 맞춘 것으로 · 칸을 바꾸면 전부 다시 · 같은 글은 한 번만 계산하고 검색에는 하나만(같은
내용 수) · 검색이 문서의 절을 가리킴. 프론트: 관리 칸(기록의 칸 고르기 · 축 일괄 · 어림 · 시간) · 검색(절의 경로 ·
`#` 링크 · 같은 내용 수).

실측(개발 DB · RTX 3070 · 실제 bge-m3, 롤백): 예시 백서 1편 → 조각 7(기본 글 + 절 6), 「모서리 찍힘 시험 결과」 →
「3.1 모서리 찍힘」 0.64 · 「온습도 시험 조건」 → 「2. 시험 조건」 0.57.
