# 0018. RA 보고서를 기록으로 — 조직 하나의 발행 보고서를 쌍둥이에 쌓는다

- 상태: 채택 · 구현 중
- 날짜: 2026-10-04
- 관련: [ADR 0009](0009-기록을-축에-잇는다.md)(기록이 참조 칸으로 축을 가리킨다),
  [ADR 0017](0017-들어오는-참조.md)(축에서 기록으로 내려가는 걸음), ReportArchive
  `docs/[미구현] 기준정보_교환_설계.md` §7(발행 보고서 피드)

## 배경

조직 하나(예: CAE 그룹)의 쌍둥이에 그 조직의 **발행 보고서**를 기록으로 쌓아, 에이전트(Claude + SP
MCP)가 보고서와 개발모델 · 과제 · 부서를 **한 온톨로지로** 묻게 하려 한다. 보고서의 정본은 ReportArchive
(RA)다. RA 는 읽기 전용 피드 `GET /api/feeds/published-reports` 를 낸다 — 조직(게시판)과 그 하위, 단계,
증분 커서 `(changed_at, id)`, 축 태그(`entities`)를 준다.

정해진 것(사용자, 2026-10-04):

1. **본문을 쌍둥이에 둔다** — 에이전트가 내용으로 답하고, RA 에서 사라져도 남는다.
2. **발행본만**(`phase=finalized`). 바꿀 수 있게 둔다.
3. 쌍둥이를 연계할 때 **RA 조직 하나를 고르면 그 하위 전부**를 받는다.
4. 운영의 데이터는 개발 서버에서 볼 수 없다 — **「보고서를 기록으로」 하는 SP 의 지원 기능**을 만들고,
   운영(CAE 그룹 Datahub)에서는 화면 설정만 한다.
5. **원본에서 내려간 보고서는 표시한다** — 지우지 않는다.

## 결정

1. **데이터 소스의 새 종류 `ra_reports`.** 일반 REST 에 기능 다섯(두 값 커서 · 목록에서 골라 꺼내기 · 행마다
   부서 · …)을 덧대는 대신 RA 피드 전용으로 둔다 — 칸 대응을 사람이 적지 않고, 화면은 「RA 조직 고르기」
   하나가 된다. 나머지 파이프라인(다시 찾기 · 계획 → 적용 · 감사 · 별칭 `source:<slug>`)은 그대로다.
2. **보고서 기록 타입의 틀.** 「보고서 기록 타입 만들기」 가 표준 칸과 고른 축의 참조 칸을 한 번에 짓는다
   (정의 가져오기 — 화면 · MCP 와 같은 함수). 칸 키가 약속이다: `ra_id · url · report_date · phase ·
   report_type · revision · ra_workspace · boards · author · tags · ra_tags · body · origin_state ·
   removed_on`, 축 참조는 `ref_<SP 타입 slug>`. 식별자는 `RA-<id>`, 이름은 제목, 본문은 목록 검색 칸.
3. **쌓기 — 증분과 하루 한 번의 전량.** 증분은 저장한 커서에서 **5분 겹쳐** 읽는다(RA 의 커밋 순서 · 시계
   때문에 경계의 한두 건이 늦을 수 있다 — 고치기는 멱등이다). 커서는 끝까지 받고 적용에 성공했을 때만
   옮긴다. 전량은 본문 없이 받아 태그만 바뀐 것(RA 는 이때 `updated_at` 을 안 움직인다)을 메우고 대조한다.
4. **원본 상태.** 전량 대조에서 안 온 기록은 `origin_state = 원본에서 내려감` · `removed_on = 그날`, 다시 오면
   `게시 중` 으로 돌리고 날짜를 지운다. **지우지도 사용 중지하지도 않는다**(「이번에 안 온 것을 사용 중지」
   는 이 종류에서 켤 수 없다). 사유(삭제 · 게시취소 · 발행취소 · 범위 밖 이동 · 계정 권한)는 피드에서 가를
   수 없어 「원본에서 볼 수 없음」 하나로 말한다.
5. **축 태그.** RA 가 SP 에서 받은 축이면 피드가 `sp: {type, key}` 를 준다 — 그 타입의 참조 칸
   (`ref_<type>`)에 식별자로 건다. 칸이 없거나 못 찾으면 비우고 기록하고(동기화를 멈추지 않는다), RA 전용
   축은 `ra_tags`(「종류: 값」)로 남긴다.
6. **소유 부서.** RA 작성 부서와 slug 가 같은 SP 부서가 있으면 그 부서 — SP 부서를 RA 「부서 정보
   내보내기」 로 만들었다면 같다. 없으면 소스의 기본 부서. 일괄 입력은 소유 부서를 호출마다 하나 받으므로
   행을 부서끼리 모아 넘긴다.
7. **긴 본문.** 본문은 긴 글 칸(`text_long`)이다. 감사 기록은 다른 칸처럼 **통째로** 남긴다 — 이력의
   되돌리기가 이전 값을 읽으므로 잘라 두면 되돌릴 수 없다(본문은 고쳐질 때만 다시 실린다). 보여 주는
   쪽이 자른다: 미리보기는 300자, MCP 는 긴 칸을 잘라 주고 이어 읽는 길을 둔다.

## 대안

### 일반 REST 소스에 기능을 덧댄다

다른 REST 에도 쓰일 일반 기능(두 값 커서 · `entities[type=model].code` 같은 경로)이 되지만, 운영자가 칸
대응 열몇 줄과 커서 경로를 손으로 적어야 하고 「원본 상태」 같은 이 용도의 규칙은 어차피 따로다.

### RA 가 SP 로 보낸다(push)

RA 에 송신 · 스케줄 · 비밀 · 「이 보고서 = 저쪽 몇 번」 표가 새로 든다(RA 설계 §7-1).

### 본문 없이 색인만

RA 설계의 처음 결정이었다. 에이전트가 내용으로 답하지 못하고, RA 에서 사라지면 주소도 죽는다.
