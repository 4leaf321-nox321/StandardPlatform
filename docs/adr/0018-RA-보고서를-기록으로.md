# 0018. RA 보고서를 기록으로 — 조직 하나의 게시 보고서를 쌍둥이에 쌓는다

- 상태: 채택(2026-10-04 구현 — 소스 종류 · 화면 · MCP · 0063, RA a478675 와 맞춤)
- 날짜: 2026-10-04
- 관련: [ADR 0009](0009-기록을-축에-잇는다.md)(기록이 참조 칸으로 축을 가리킨다),
  [ADR 0017](0017-들어오는-참조.md)(축에서 기록으로 내려가는 걸음), ReportArchive
  `docs/[미구현] 기준정보_교환_설계.md` §7(발행 보고서 피드)

## 배경

조직 하나(예: CAE 그룹)의 쌍둥이에 그 조직에 **게시된 보고서**를 기록으로 쌓아, 에이전트(Claude + SP
MCP)가 보고서와 개발모델 · 과제 · 부서를 **한 온톨로지로** 묻게 하려 한다. 보고서의 정본은 ReportArchive
(RA)다. RA 는 읽기 전용 피드 `GET /api/feeds/published-reports` 를 낸다 — 조직(게시판)과 그 하위, 단계,
증분 커서 `(changed_at, id)`, 축 태그(`entities`)를 준다.

정해진 것(사용자, 2026-10-04):

1. **본문을 쌍둥이에 둔다** — 에이전트가 내용으로 답하고, RA 에서 사라져도 남는다.
2. ~~발행본만(`phase=finalized`)~~ → **게시된 것 전부**(`phase=published` — 검토 중 · 발행)가 기본, 발행본만으로
   좁힐 수 있다(소스마다). 같은 날 바꿨다 — RA 회신: 발행은 편집 잠금을 겸해 드물고(전사 13건), 조직에
   내놓았다는 신호는 사실상 게시다. 화면은 단계를 늘 적어 둔다(기본이 바뀌어도 저장된 소스가 그대로).
3. 쌍둥이를 연계할 때 **RA 조직 하나를 고르면 그 하위 전부**를 받는다.
4. 운영의 데이터는 개발 서버에서 볼 수 없다 — **「보고서를 기록으로」 하는 SP 의 지원 기능**을 만들고,
   운영(CAE 그룹 Datahub)에서는 화면 설정만 한다.
5. **원본에서 내려간 보고서는 표시한다** — 지우지 않는다.

## 결정

1. **데이터 소스의 새 종류 `ra_reports`.** 일반 REST 에 기능 다섯(두 값 커서 · 목록에서 골라 꺼내기 · 행마다
   부서 · …)을 덧대는 대신 RA 피드 전용으로 둔다 — 칸 대응을 사람이 적지 않고, 화면은 「RA 조직 고르기」
   하나가 된다. 나머지 파이프라인(다시 찾기 · 계획 → 적용 · 감사 · 별칭 `source:<slug>`)은 그대로다.
2. **보고서 기록 타입의 틀.** 「보고서 기록 타입 만들기」 가 표준 칸과 고른 축의 참조 칸을 한 번에 짓는다
   (정의 가져오기 — 화면 · MCP 와 같은 함수). 칸 키가 약속이다: `ra_id · url · report_date · phase ·
   report_type · revision · ra_workspace · boards · author · tags · ra_tags · body · origin_state ·
   removed_on`, 축 참조는 `ref_<SP 타입 slug>`. 식별자는 `RA-<id>`, 이름은 제목, 본문은 목록 검색 칸.
3. **쌓기 — 증분과 하루 한 번의 전량.** 증분은 저장한 커서에서 **5분 겹쳐** 읽는다(RA 의 커밋 순서 · 시계
   때문에 경계의 한두 건이 늦을 수 있다 — 고치기는 멱등이다). 커서는 끝까지 받고 적용에 성공했을 때만
   옮긴다. 전량은 본문 없이 받아 태그만 바뀐 것(RA 는 이때 `updated_at` 을 안 움직인다)을 메우고 대조한다.
4. **원본 상태.** 전량 대조에서 안 온 기록은 `origin_state = 원본에서 내려감` · `removed_on = 그날`, 다시 오면
   `게시 중` 으로 돌리고 날짜를 지운다. **지우지도 사용 중지하지도 않는다**(「이번에 안 온 것을 사용 중지」
   는 이 종류에서 켤 수 없다). 사유(삭제 · 게시취소 · 발행취소 · 범위 밖 이동 · 계정 권한)는 피드에서 가를
   수 없어 「원본에서 볼 수 없음」 하나로 말한다.
5. **축 태그.** RA 가 SP 에서 받은 축이면 피드가 `sp: {type, key}` 를 준다 — 그 타입의 참조 칸
   (`ref_<type>`)에 식별자로 건다. 칸이 없거나 못 찾으면 비우고 기록하고(동기화를 멈추지 않는다), RA 전용
   축은 `ra_tags`(「종류: 값」)로 남긴다. **피드가 비워 보낸 여럿 값 칸**(태그 · 게시판 · 축 참조 · RA
   태그)은 우리도 비운다(`\null`) — 일괄 입력은 빈 값을 「안 건드림」 으로 읽어서, RA 에서 태그를 다 뺀
   보고서가 옛 태그로 남는다.
6. **소유 부서.** RA 작성 부서와 slug 가 같은 SP 부서가 있으면 그 부서 — SP 부서를 RA 「부서 정보
   내보내기」 로 만들었다면 같다. 없으면 소스의 기본 부서. 일괄 입력은 소유 부서를 호출마다 하나 받으므로
   행을 부서끼리 모아 넘긴다.
7. **긴 본문.** 본문은 긴 글 칸(`text_long`)이다. 감사 기록은 다른 칸처럼 **통째로** 남긴다 — 이력의
   되돌리기가 이전 값을 읽으므로 잘라 두면 되돌릴 수 없다(본문은 고쳐질 때만 다시 실린다). 보여 주는
   쪽이 자른다: 미리보기는 300자, MCP 는 긴 칸을 잘라 주고 이어 읽는 길을 둔다.

8. **태깅은 RA 에서 한다**(사용자, 2026-10-04). SP(에이전트 · 사람)는 보고서의 축 태그를 보태지 않는다.
   RA 가 채우는 칸은 동기화가 RA 값으로 다시 쓰고(액세스 토큰으로 고친 칸은 「사람이 고친 칸」 보호도
   받지 않는다), 보탤 칸을 따로 두면 출처가 둘이 되어 꼬인다. 빠진 태그는 SP 에서 찾아(축 참조 칸의
   `empty` · `ra_tags` 글로만 남은 것) RA 에서 고친다 — 정본이 좋아져야 모든 받는 쪽이 같이 좋아진다.

## 대안

### 일반 REST 소스에 기능을 덧댄다

다른 REST 에도 쓰일 일반 기능(두 값 커서 · `entities[type=model].code` 같은 경로)이 되지만, 운영자가 칸
대응 열몇 줄과 커서 경로를 손으로 적어야 하고 「원본 상태」 같은 이 용도의 규칙은 어차피 따로다.

### RA 가 SP 로 보낸다(push)

RA 에 송신 · 스케줄 · 비밀 · 「이 보고서 = 저쪽 몇 번」 표가 새로 든다(RA 설계 §7-1).

### SP 에서 태깅을 보탠다

축마다 「SP 태깅」 칸을 두고 동기화가 RA 태그와 합집합으로 쓰는 길. 에이전트가 본문을 읽어 빠진 태그를
채울 수 있지만, 같은 축의 태그가 두 곳에서 오고(누가 단 것인지 · 누가 지울 것인지), RA 의 태깅이 나아질
동기가 사라진다. 결정 8.

### 본문 없이 색인만

RA 설계의 처음 결정이었다. 에이전트가 내용으로 답하지 못하고, RA 에서 사라지면 주소도 죽는다.

## 결과

- **화면** — 데이터 소스의 종류 「ReportArchive 보고서」: RA 주소 · 액세스 토큰 · 「보고서 기록 타입 생성」 ·
  「저장 후 RA 조직 조회」(경로로 찾는 고르개) · 하위 조직 포함 · 본문 포함 · 단계. 칸 대응 · 인증 방식 ·
  경로는 그리지 않는다. 실행 기록에 원본에서 내려감 · 다시 게시 · 내려감 보류 · 전량 대조가 선다.
- **MCP** — 긴 글 칸은 목록에서 300자, `object_get` 에서 6,000자씩(`clipped` · `text_from`). 안내서 주제
  `reports` 가 묻는 길과 전할 때의 규칙(출처 · 「원본에서 내려감」 은 사유를 짓지 않고 · 범위를 함께)을 쥔다.
- **RA 와 맞춘 것**(RA a478675, 2026-10-04 회신):
  - `include_text` 면 `text`(없으면 null) · `text_truncated`(한 건 1MB) — 잘린 본문은 끝에 잘렸다고 적는다.
    쪽 누적 8MB 에서 RA 가 쪽을 끊고 `has_more` 를 주지만, 커서를 따라가므로 이쪽에 할 일은 없다.
  - RA 의 `APP_BASE_URL` 이 비면 원문 주소가 `/w/…` 상대 경로로 온다 — 소스의 RA 루트를 붙인다.
  - 본문은 RA 의 검색용 평문(`search_text`)이라 **첨부 파일 이름이 섞여 있다** — 칸 설명(`help`)과 MCP
    안내서에 적었다. 백필은 필요 없다(RA 실측: 게시분 7,139건 중 빈 것 0).
  - `entities[].sp` 는 지금 전부 null 이다 — RA 운영에서 `sp_core` 수신과 태깅 백필이 끝나야 찬다. 그 전에는
    축 태그가 `ra_tags` 글로 쌓이고, 찬 뒤의 전량 대조(태그만 바뀐 것은 증분에 안 잡힌다)가 참조 칸으로
    옮긴다(결정 5 의 비우기가 옛 글 태그를 치운다).
  - **발행본은 아직 적다** — 전사 13건(2026-10). 그래서 기본을 「게시된 것 전부」 로 바꿨고(결정 2), 목록을
    단계로 거른다. 「발행본만」 으로 좁힌 소스가 0건이면 동기화 창이 이유와 넓히는 길을 말한다.
- **넣을 타입은 보고서 기록 타입이어야 한다**(0.4.40, 2026-10-05). 화면의 「넣을 타입」 에는 첫 타입
  (「프로젝트」)이 기본으로 서 있어, 「보고서 기록 타입 생성」 을 안 누르고 저장하면 보고서 수천 건이
  프로젝트 객체로 설 수 있었다(틀에 없는 칸은 건너뛰므로 막는 것이 없었다). RA 번호 칸(`ra_id`)이 없는
  타입은 저장(만들기 · 고치기)이 거절하고(DATASOURCES-0060), 이미 저장된 소스는 동기화가 RA 를 부르기
  전에 실패로 적는다. 손으로 만든 타입도 `ra_id` 만 있으면 받는다(다른 틀 칸은 없어도 된다).

  비밀 · 삭제 · 보고서 타입이 아님), 단위 2, 화면 5, MCP 1.
