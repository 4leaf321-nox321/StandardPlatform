## 배경

SPARQL(`rdf_query`)은 질의마다 그 범위의 객체를 메모리 그래프(rdflib)로 세워 물었다 — 객체 5만 개에서 거절하고,
기록 타입은 기본 범위에서 뺐다. 견주기(2026-11-11)에서 메모리 방식은 548만 트리플에 156초 · 6.6GB 였고 무거운 질의는
10분을 넘겼다. 사용자 결정: **메모리 방식은 더 안 늘린다**, 디스크 저장소는 「미리 세워 충분히 빠르면 도입」.
Oxigraph(디스크 · RocksDB) 실측은 같은 548만 트리플에 싣기 33초 · 0.75GB · 질의 0.006 ~ 9.8초였고, 사용자가 **바깥
시스템이 SPARQL 로 물을 수요가 있다**고 해 들인다(2026-11-11).

엮어 묻기는 Neo4j 사본(ADR 0069)이 맡는다 — 같은 자료의 세 번째 길(SP · Cypher · SPARQL)이라 **언제 무엇을 쓰나**를
가이드에 박는다(아래 4).

## 결정

### 1. 사본 — 밤에 통째로, 두 벌 바꿔 끼우기, 서비스는 없다

- 밤(05:45, 대기 서버 06:15)에 PostgreSQL 에서 N-Triples 를 흘려 쓰고(REPEATABLE READ 한 번) **쉬는 쪽 폴더**에
  Oxigraph `bulk_load` → 다지기(`optimize`) → `manifest.json` → `active` 를 이름 바꾸기 한 번으로 바꿔 끼운다.
- **서비스가 없다** — 사본은 폴더이고, 웹이 질의마다 `active` 를 다시 읽는다(Neo4j 와 달리 다시 띄울 것이 없다).
  웹 유닛은 그 폴더를 **읽기 전용**으로 건다(RocksDB 읽기 전용 열기는 읽기 전용 폴더에서 된다 — 실측). 싣기는 운영
  계정의 oneshot 유닛이다(root 가 필요 없다).
- 앞 판은 다음 밤까지 둔다 — 바꿔 끼운 순간 돌던 질의가 그것을 읽는다. 백업하지 않는다(다시 싣는다).

### 2. 같은 트리플 — 메모리 그래프와 사본이 같은 답을 낸다

- 사본은 메모리 그래프(`export.data_graph`)와 **같은 IRI · 같은 모양**이다: 타입 · 인터페이스(직접 `rdf:type`),
  `rdfs:label`@ko · `dcterms:identifier` · `rdfs:comment` · `skos:altLabel`, 값(형마다), 참조 칸, **오늘 유효한 관계**,
  기간 · 고정이 있는 선은 구체화한 진술. 정의(OWL)는 `schema_graph` 그대로. 시험이 같은 세계를 둘로 만들어 견준다
  (`tests/api/test_rdf_copy.py`). 견주기 DB 에서 트리플 수가 메모리 그래프와 같다(5,478,299).
- 다른 점: 사본은 **전부**(부서 구분 없음 · 기록 포함 · 객체 상한 없음), 못 읽는 숫자는 형 없는 글자, 지수꼴 소수는
  소수꼴로 편다.
- **IRI 의 바탕** — 메모리 그래프는 요청이 들어온 주소로 IRI 를 짓는다. 사본은 고정된 바탕(`https://sp-copy.invalid/`)으로
  짓고 묻고 답할 때 요청의 바탕과 서로 바꾼다 — 쓰는 쪽에는 같은 IRI 다.
- 내보내기는 줄마다 rdflib 개체 · ORM 개체를 만들지 않는다(서버 쪽 커서 · 튜플 · 글자) — 견주기 84만 객체에서
  54초 → 26초.

### 3. 묻기 — 따로 도는 프로세스에서 상한을 걸고

- Oxigraph 의 질의에는 시간 상한이 없다. 그래서 질의마다 **따로 도는 프로세스**(`storeq.py` — 앱을 import 하지 않는다)
  를 띄워 시간(`RDF_QUERY_SECONDS` 60초) · 메모리(`RDF_QUERY_MEMORY_MB` 4GB, `RLIMIT_DATA`)를 넘으면 끊는다. 웹 프로세스
  하나가 동시에 `RDF_CONCURRENCY`(2)개.
- `rdf_query`: 사본이 있고 · `infer` 가 아니고 · 모든 부서를 보는 사람이면 **사본**(`source=copy` · `copied_at`), 아니면
  지금처럼 메모리. 추론은 사본에 없다(속성 경로 `+` · `^` 로 묻고, 인터페이스는 직접 실려 있다).
- 쓰기 · 바깥 호출(SERVICE)은 메모리 길과 같은 검사로 먼저 막는다(파싱한 모양까지).
- **쓰는 차례에 민감하다** — 출발점에서 걷는 길을 부분 질의로 먼저 쓰면 0.007초, 한 덩어리로 쓰면 23초(견주기 —
  Oxigraph 가 타입 쪽에서 출발해 모델마다 길을 다시 걷는다). 가이드 · 도구 설명이 그 꼴을 가르친다.

### 4. 바깥 창구 · 쓰는 순서

- `GET|POST /api/rdf/sparql` — SPARQL 1.1 Protocol(`?query=` · 폼 · `application/sparql-query`), 답은
  `application/sparql-results+json`, 토큰(Bearer) 인증, 사본에만(없으면 503), 머리 `X-SP-Copied-At` · `X-SP-Truncated`.
  부서로 좁힌 설치에서는 모든 부서를 보는 사람만(403).
- 가이드의 순서: ① SP 도구(지금 값) → ② 관계를 엮는 물음은 `graph_query`(Cypher) → ③ SPARQL 은 사람 · 바깥 시스템이
  원할 때 · 온톨로지를 따라 묻기 · 추론 · 표준 RDF 어휘.

## 결과

| | 객체 84만(견주기 DB) | 객체 2,020만(운영 모양 DB) |
| --- | --- | --- |
| 트리플 | 5,478,299(메모리 그래프와 같다) | 731,248,153(객체당 36) |
| 내보내기 | 26초(처음 54초 — 줄마다 개체를 안 만들게 고친 뒤) | 1,565초(26분) · 메모리 0.3GB · 임시 90GB |
| 싣기 · 다지기 | 12.7초 | 1,637초(27분) · 최대 메모리 20.5GB |
| 사본 | 0.74GB | 84.45GB(트리플당 124바이트) |
| 질의(따로 도는 프로세스 포함) | Q2 0.09 · Q9 10.4초 · Q1 23초 → 부분 질의 먼저 0.007초 | 하나에서 출발 0.09초 · 두 걸음 0.09초 · 전부의 타입별 수 6.4초 · 축끼리 묶기 1.2초 |

견주기 Q1 · Q2 · Q9 는 정답과 같다. 설치 하나의 디스크는 사본 두 벌 + 싣는 동안 임시 파일(2,000만 객체: 평소 약
170GB · 싣는 동안 약 260GB). 1억 객체면 한 벌 약 420GB · 밤 싣기 4 ~ 5시간으로 어림한다 — 그때는 아래 「다음」 의
흘려 싣기 · 바뀐 것만이 필요해진다. 개발 PC(32코어 · 31GB)에서 잰 것이다.

**설치가 여럿이면** — 밤의 무거운 일(그래프 사본 · SPARQL 사본)은 서버 하나의 **밤 작업 자리표**(`nightly-slot.sh` —
잠금 파일 N개, 기본 2)를 거친다. 빈 자리를 잡은 것만 돌고 나머지는 기다린다 — 시각을 나눠 두면 데이터가 커지는 날
겹친다(사용자 결정 2026-11-11 — 시각이 아니라 끝났는지를 보고).

## 고르지 않은 것

- **메모리 방식을 늘리기** — 사용자 결정(배경). 548만 트리플에 6.6GB · 156초.
- **Oxigraph 서버(따로 도는 HTTP 서비스)** — 포트 · 유닛이 하나 더 늘고, 질의 시간 상한은 여전히 없다. 폴더 + 질의
  프로세스가 더 단순하다.
- **웹 프로세스 안에서 바로 묻기** — 시간 상한이 없어 잘못 쓴 질의가 웹 프로세스를 붙잡는다.
- **바뀐 것만 고치기** — 사본이 어긋날 틈이 생긴다(ADR 0069 와 같은 까닭).
- **사본에서 추론하기** — 실체화한 추론(상속 · 역관계 · 이행)은 트리플이 몇 배로 늘고, 이행 관계의 닫힘은 BOM 에서
  폭발한다. 속성 경로로 묻는다.
