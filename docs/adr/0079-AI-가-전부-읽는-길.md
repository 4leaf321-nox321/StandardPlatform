# 0079. AI 가 전부 읽는 길 — 커서 쪽넘김 · 토큰의 쪽 상한 · 전수 집계 · 세부 기준의 쪽

## 배경

AI 가 2,000만 건 표를 다룰 때 막힌 자리가 넷이었다.

1. **목록 쪽넘김이 `offset` 하나**였다 — 100만 번째 줄부터의 한 쪽은 앞 100만 줄을 읽고 버린 뒤에 나오고, 쪽마다
   전체 수(`total`)를 다시 셌다. 끝까지 받는 AI 는 쪽이 갈수록 느려지다 시간 상한(60초)에 걸렸다.
2. **쪽 상한 200** 이 백엔드(`pagination.MAX_LIMIT`)와 MCP 설명 여러 곳에 박혀 있었다 — 200줄씩이면 2,000만 건은 10만 번.
3. **통계는 그림이다** — 막대 30개에서 「그 밖에」 로 접고, 쪽으로 넘겨도 한 쪽 500 이다. 「시장 165곳 각각」 · 「모델
   3천 개마다」 같은 표가 답인 물음에서 AI 는 쪽을 넘기다 끝을 놓치거나 원본을 받아 직접 셌다. 받은 막대를 더해 전체와
   같은지도 몰랐다.
4. **세부 기준은 열둘에서 말없이 잘렸다**(`MAX_SPLITS`) — 열둘 밖 값의 조각이 빠져 조각의 합이 막대보다 작았다. MCP
   에는 이 상한이 없어 AI 는 백엔드 상수를 짐작해야 했다.

화면은 사정이 반대다. 홈의 위젯 · 목록과 통계를 한꺼번에 부르고, 하나하나가 커지면 화면이 멈춘다 — 검토함이 종류
여덟을 한 번에 받다 열리지 않은 일이 있었다(ADR 0073 · 0075). **화면의 상한은 그대로 두고 기계의 길만 넓힌다.**

## 결정

1. **화면과 기계를 가른다** — API 토큰(PAT)으로 들어온 요청만 기계다(`request.state.token_scopes` — 인증이 정하고,
   사람의 세션에는 없다). 머리 · 인자로는 못 바꾼다. 기계의 목록 쪽은 **2,000** 까지(코어 API 와 같다), 화면은 200 그대로.
   세부 기준 쪽도 기계 200 · 화면 12(그림의 색 여덟을 돌려 쓰는 상한).
2. **커서 쪽넘김**(`cursor`) — 처음은 `cursor=start`, 다음은 응답의 `next_cursor`. 차례는 **id**(목록 화면의 정렬을 안
   따른다 — 이름순으로 끊으면 이름이 같은 줄 · 고쳐서 이름이 바뀐 줄이 쪽 사이에서 빠지거나 겹친다), 다음 쪽은 `id > 마지막
   id` 로 기본 키 색인에서 바로 이어진다. 맞는 줄이 적으면(1만 이하) id 를 먼저 모아 그 안에서 고른다(`page_rows` 와 같은
   생각 — 드문 조건에서 표 끝까지 걷지 않게). **전체 수는 첫 쪽에서만** 세어 커서에 싣고, 응답의 `offset` 은 앞 쪽들에서
   준 줄 수다. 커서에 **조건의 지문**을 실어 조건을 바꾼 옛 커서는 422(`OBJECTS-0155`). 다른 표를 비추는 타입은 커서를
   안 받는다(`OBJECTS-0156`). 화면은 커서를 안 쓴다(`offset` · 화면 정렬 그대로).
3. **전수 집계**(`GET /api/objects/{slug}/census`) — 거르기 · 기준 · 셈은 통계와 같고(`summary._grouped`), 묶음을 **전부**
   돌려준다. 묶음 수와 묶음 건수의 합은 창 함수로 같은 질의 한 번에 센다. 응답의 **`check`** 가 「묶음 합 = `total`
   인가」 와 그 판정 글이다 — 여러 값 기준이면 합이 더 클 수 있다(겹침), 작으면 어느 묶음에도 안 든 기록이 있다.
   - 묶음이 **5,000 이하면** 그 자리에서 전부(`complete`). 넘으면 수 · 검증값만 주고 작업 `objects_census` 를 넣는다 —
     워커가 묶음을 덩어리마다 읽어 줄마다 JSON 한 줄로 결과 파일에 쓰고, `GET .../census/rows?cursor=` 가 나눠 준다
     (한 쪽 1,000 · 5,000 까지). 그 자리의 집계가 시간 상한에 걸리는 물음은 `POST .../census/job` 으로 처음부터 작업으로.
   - 작업 넣기는 **읽기다**(`/api/objects/*/census/job` — 읽기 토큰으로 된다, 내보내기와 같다).
4. **세부 기준의 쪽과 「그 밖에」** — `split_limit` · `split_offset` 으로 넘기고, 이 쪽에 없는 값은 막대마다
   `other_part`(「그 밖에 N종류」)로 묶어 **조각 합이 막대와 맞는다**. 그 조각의 값은 합 · 최솟값 · 최댓값만(평균은
   조각마다의 평균에서 다시 낼 수 없어 비운다). `split_total` 이 값의 전체 수.

## 대안

- **목록 화면의 정렬로 커서를 짓는다**(이름 · 날짜 · 칸 값 + id) — 버렸다. 칸 값 정렬은 숫자 · 글자 · 빈 값이 섞여 비교식이
  커지고, 이름을 고치면 줄이 쪽 사이를 건너간다. 전부 읽기에 차례는 뜻이 없다.
- **쪽 상한을 모두에게 올린다** — 버렸다. 화면이 「전부 보기」 를 큰 수로 구현하는 순간 멈춘다(그 버그가 있었다).
- **통계의 상한(30 · 500)을 올린다** — 버렸다. 통계는 그림이 쓰는 응답이고, 표가 답인 물음은 검증값까지 필요하다.
  길을 하나 더 두는 편이 둘 다 지킨다.
- **전수 집계를 늘 작업으로** — 버렸다. 대부분의 표(시장 165 · 공장 30)는 그 자리에서 1초 안이다. 큰 것만 작업이 된다.

## 실측(2,000만 건 DB `standardplatform_big_scale`, 2026-11-17 — 같은 PC 에 다른 작업이 돌아 세기 시간은 두세 배 흔들렸다)

| 무엇 | 전 | 후 |
| --- | --- | --- |
| 목록 쪽 200줄 — 앞(offset 0) | 3 ~ 9초(쪽마다 2,000만 건 세기) | 커서 다음 쪽 0.05초(세지 않음) · 첫 쪽만 세기 |
| 목록 쪽 200줄 — 100만 번째 뒤 | offset 12 ~ 41초 | 커서 0.07초(1,000만 번째 뒤도 같다) |
| 목록 쪽 200줄 — 1,000만 번째 뒤 | offset 14 ~ 37초 | 커서 0.07초 |
| 줄 하나 크기 | **23KB**(아래) | 1.2KB |
| 쪽 크기(커서 다음 쪽) | — | 200줄 0.07초 · 0.25MB / 2,000줄 0.73초 · 2.5MB / 10,000줄 2.8초 · 12.3MB |
| 전수 집계 | — | 증상 40묶음 15초 · 모델 5,701묶음 23초, 둘 다 합 = 전체(19,997,260) |

- **줄마다 쪽 전체의 참조 이름이 실리던 것을 고쳤다**(`routes._own_ref_labels`) — 목록은 쪽의 참조 이름을 한 번에
  읽고 그 사전을 줄마다 통째로 넘겼다. 200줄 쪽이면 줄마다 이름 800개 남짓, 줄 하나가 23KB · 쪽 4.3MB 였고, 줄 수 x
  이름 수로 커져 2,000줄 쪽이면 수백 MB 였다. 이제 줄마다 자기 칸의 값만 싣는다(화면은 줄마다 그 줄의 것만 읽고, 조건
  칩은 줄들의 것을 합쳐 쓴다 — 다른 줄의 이름에 기대는 곳이 없다). 화면의 200줄 쪽도 4.3MB → 0.25MB.
- **쪽 상한 2,000 의 근거** — 한 쪽 0.73초 · 2.5MB. 10,000 으로 올려도 줄당 시간이 0.36 → 0.28ms 로 2할 남짓 줄 뿐이고
  (줄마다의 일 — 이름 · 별칭 · 첨부 칸 — 이 대부분), 응답은 12MB · 자리를 쥐는 시간이 네 배다. 2,000만 건 전부는 2,000줄
  쪽으로 1만 번 · 약 2시간이다 — 통째로는 내보내기 작업(파일)이 맞다. AI 에게는 2.5MB 도 대화에 넣기에 크다(줄을 받지 말고
  통계 · 전수 집계로 세게 한다).

## 결과

- 끝까지 읽는 AI 의 쪽마다 비용이 같다 — 전체 수를 쪽마다 다시 세지 않는다.
- 전수 집계는 큰 결과에서 그룹 질의를 두 번 돈다(그 자리의 시도 + 작업). 그 자리의 시도가 묶음 수 · 검증값을 바로 주는
  값이다.
- 결과 파일은 작업 파일의 보관 기간(`JOB_FILE_TTL_DAYS`)이 지나면 지워진다 — 그 뒤의 커서는 410(`OBJECTS-0159`).
