# 0073. 검토함의 종류마다 시간 상한 — 한 종류가 느려도 화면이 선다

- 상태: 채택(2026-11-16 구현 · 200만 건 DB 실측). 「남은 것」 ① 은 [ADR 0074](0074-별칭-후보의-이것-아닐까-미리-셈.md)
  (「이것 아닐까」 미리 셈)로 했다 — 이 시간 상한은 아직 안 셈한 줄의 길로 남는다.
  - 앱: `app/modules/review/services.py`(`collect` — 종류마다 시간 · `_within` 끊기 · `late_notes`) ·
    `registry.py`(`Filters.deadline` · `Collected.cut`) · `objects/review.py`(`collect_candidates` — 셈한 데까지) ·
    `objects/misses.py`(`page` 의 시간 · `Axes` 범위마다 한 번 · 같은 점수의 차례)
  - 창구 · 화면 · AI: `GET /api/review/items` 의 `kinds[].late` · `seconds`, 검토함의 「시간 안에 다 읽지 못한 종류」
    알림 · 칩의 시계 표, MCP `review_list` 설명 · GUIDE 2026-11-16a
  - 실측: `scripts/scale_rehearsal.py measure --only review`
- 날짜: 2026-11-16
- 관련: [ADR 0027](0027-검토함.md)(검토함 — 원래 자리에서 읽는다), [ADR 0025](0025-채울-곳과-별칭-후보.md)(못 찾은 말 · 「이것 아닐까」),
  [ADR 0048](0048-오래-도는-읽기의-안전장치.md)(`readguard` — 도는 질의를 끊는 길)

## 배경

운영에서 별칭 후보(못 찾은 말)가 몇만 건이 되자 **검토함이 열리지 않았다** — `GET /api/review/items` 가 60초를 넘겨
504(2026-11-16 사용자). 검토함은 종류 여덟을 **차례로 원래 자리에서 읽어** 한 응답으로 낸다(ADR 0027). 그래서 하나가
끝나지 않으면 나머지 일곱도 못 본다.

### 별칭 후보가 느린 까닭 — 줄마다 「이것 아닐까」 질의가 붙는다

별칭 후보는 많이 찾은 것부터 200줄(`CANDIDATE_CAP`)을 읽고, **줄마다** 그 범위의 축 객체 · 별칭에서 이름이 비슷한
것(pg_trgm `similarity` · `word_similarity` ≥ 0.3)을 찾는다(`misses.similar` — 이름 · 식별자 한 번, 별칭 한 번). 그
질의가 **인덱스를 못 탄다**: 문턱 0.3 이 낮아 한 말에 축 객체의 절반 넘게 걸린다(모델 코드처럼 앞이 같은 이름 —
「sm-x01234_kr」 하나에 1.3만 건 중 8천 건). 계획기는 trigram GIN 대신 타입 인덱스로 다 훑고 줄마다 비슷함을 셈한다.
`%` · `%>` 연산자로 바꿔 GIN 을 쓰게 해도 같은 계획이었다(아래 실측).

200만 건 DB(`standardplatform_scale` — 축 객체 1.34만: 모델 6천 · 과제 5천 · 기본 모델 2천 · 부품 300 · 프로젝트
120)에 대기 3만 건(세 번 이상 2.4만)을 롤백 안에서 심고 쟀다:

| | 별칭 없음 | 별칭 13.4만(축 객체마다 외부 식별자 10개 — 동기화의 `source:` 별칭 모양) |
| --- | --- | --- |
| 「이것 아닐까」 한 줄(205말의 중앙) | 84ms(이름 · 식별자 45ms + 별칭) | **466ms**(별칭을 다 훑는다 — 병렬 3) |
| 별칭 후보 200줄 모으기 | **19.5초**(질의 805번 중 비슷함 400번이 18.1초) | 약 **94초**(205말 합 96초) |
| 나머지 일곱 종류 합 | 1.4초 | 1.4초 |

대기 수(몇만)는 그 자체로는 비싸지 않다(세기 · 차례 0.01초). **200줄을 늘 다 채우게 되는 것**이 문제다 — 대기가 200
아래이던 때는 줄 수만큼만 셈했다. 한 줄의 값은 축 객체 · 별칭 수에 비례하고, 운영은 데이터 소스 동기화가 외부 식별자를
별칭으로 남긴다(`source:<slug>`, ADR 0025) — 별칭 표가 클수록 줄마다 그만큼 훑는다. (ADR 0027 의 「별칭 후보 200줄
0.55초」 는 축 타입이 작던 때의 값이다.)

같은 계산이 데이터 품질의 **별칭 후보 창**(50줄)에도 있다 — 운영 모양이면 25초 남짓.

## 결정

### 1. 종류마다 시간 — 여럿이면 하나에 8초, 다 합쳐 15초

`services.collect` 가 종류마다 시간을 준다: 여러 종류를 함께 보면 하나에 `KIND_SECONDS`(8초), 다 합쳐
`COLLECT_SECONDS`(15초). **종류 하나만 보면**(`kind`) 그 종류가 15초를 다 쓴다. 15초인 까닭: 「추천대로 모두」 ·
「거른 전부」 의 미리 보기는 목록을 읽고(이 시간까지) 고른 항목을 한 번 더 읽어(대개 비슷한 시간) 이것의 두 배
남짓이 든다 — 프록시의 60초 안에 넉넉히 둔다.

시간 안에 다 못 읽은 종류는 `late` 다 — **「없다」 가 아니다.** 까닭은 그 종류의 `notes`, 든 시간은 `seconds`(어느
종류가 느린지 보인다). 서버 로그에도 종류와 시간을 한 줄 남긴다(`검토함: 「별칭 후보」(alias_candidate)는 8.4초에
18건만 읽음`).

### 2. 두 길로 멈춘다 — 스스로 멈추는 종류는 거기까지, 못 멈추는 종류는 끊는다

- **스스로 멈춘다**(`Filters.deadline`): 줄마다 일하는 종류는 시간이 되면 하던 줄을 마치고 거기까지 낸다
  (`Collected.cut`). 별칭 후보가 그렇다(결정 3).
- **끊는다**(`_within`): 그러지 못하는 종류(큰 질의 하나 · 멈출 자리를 보지 않는 되풀이)는 `KIND_GRACE`(4초) 뒤에
  끊고 건너뛴다. 끊는 길은 ADR 0048 의 `readguard` 그대로다 — 타이머가 도는 질의에 취소를 보내고(DB 에서도 멈춘다),
  그 종류의 다음 질의는 보내지 않는다(모든 엔진의 `before_cursor_execute`). **세이브포인트 안에서** 돌려 끊겨도 요청의
  트랜잭션이 살아 다음 종류가 읽는다. 끝난 뒤에는 취소를 보내지 않는다(잠금 — 다음 종류의 질의가 맞지 않게).

`statement_timeout` 만으로는 안 된다 — 별칭 후보는 **짧은 질의 400번**이라 하나하나는 상한에 안 걸린다.

### 3. 별칭 후보는 많이 찾은 것부터 셈한 데까지

시간이 다 되면 「이것 아닐까」 를 셈한 줄까지만 낸다 — 많이 찾은 것이 먼저다(목록의 차례 그대로). 「많이 찾은 것부터
N건만 표시합니다(대기 M건) — 처리하면 다음 것이 표시됩니다」. 셈한 줄은 추천 · 확신도가 온전하다. 셈하지 않은 줄을
추천 없이 싣지 않는다 — 후보가 없는 줄은 「무시」 밖에 못 하고, 그 줄이 목록을 덮는다. (ADR 0074 뒤로는 미리 셈한
줄은 시간과 상관없이 내고, 시간이 다 되면 **안 셈한 줄만** 건너뛴다.)

- **결정할 항목을 다시 읽을 때**(미리 보기 · 적용의 `item_ids`)는 시간으로 자르지 않는다 — 고른 것은 다 본다(잘리면
  「이미 처리했거나 볼 수 없는 항목」 으로 막혀 미리 본 것과 달라진다).
- 「추천대로 모두」 · 「거른 전부」 의 미리 보기는 늦은 종류에서 **보인 것만** 골랐다고 말한다(`late_notes`).
- 같은 범위(타입)의 축 타입 · 그 객체 수를 줄마다 다시 묻지 않는다(`misses.Axes` — 200줄이면 질의 400번, 0.6초).
- 같은 점수는 이름 · id 차례로 고른다 — 별칭 질의에 차례가 없어 같은 점수의 둘 중 어느 것이 오는지가 질의마다 달랐다
  (미리 보기와 적용의 추천이 갈리면 지문이 어긋나 409).

### 4. 별칭 후보 창도 10초

데이터 품질의 별칭 후보 창(`GET /api/objects/alias-candidates`, 50줄)도 10초(`misses.PAGE_SUGGEST_SECONDS`)가 지나면
나머지 줄의 「이것 아닐까」 를 셈하지 않고 그 줄에 적는다 — 「다른 객체 선택」 으로 고르거나, 후보 하나를 열면
(`GET …/alias-candidates/{id}`) 그 줄만 셈한다.

### 5. 화면 · AI 는 「없다」 고 읽지 않는다

- 화면: 늦은 종류의 칩에 시계 표(건너뛴 종류는 수 대신 「?」), 위에 「시간 안에 다 읽지 못한 종류」 알림 — 「N건만
  읽었습니다」 / 「건너뛰었습니다」 · **「없는 것이 아닙니다」** · 「이 종류만 보기」(그 종류가 시간을 다 쓴다) ·
  건너뛴 종류는 원래 화면 링크. 항목이 0건이어도 늦은 종류가 있으면 「검토할 항목이 없습니다」 대신 「시간 안에 다
  읽지 못했습니다」.
- MCP `review_list` · GUIDE: `kinds[].late` 면 「없다」 고 말하지 말고 `notes` 를 전하고 `kind=` 로 다시 부른다.

## 대안

- **trigram 인덱스를 타게 고친다**(`label % q OR label %> q`, 문턱을 `pg_trgm.*_threshold` 로) — 결과는 205말 모두
  같았지만 **계획이 그대로**였다(한 말에 8천 건이 걸려 계획기가 GIN 을 버린다): 별칭 없이 20.5 → 20.4초, 별칭 13.4만이면
  96 → 56초(최대 한 말 0.96초). 문턱을 0.5 로 올리면 인덱스가 타서 별칭 13.4만에 한 말 중앙 103ms(4배)지만, 축 전체
  범위에서 **맨 위 추천이 205말 중 49말 달라진다** — 먼 오타를 못 잡는다. 둘 다 시간을 「줄 수 × 한 말」 에서 못 벗어난다.
- **화면이 종류마다 따로 부른다**(먼저 끝난 종류부터 그리기) — 느린 종류가 화면을 막지 않는 다른 길이지만, 「전체」 의 쪽
  넘김 · 타입 · 부서 칩 · 「거른 전부」 가 종류를 가로지르는 지금 모양을 바꿔야 한다. 서버 시간 상한은 MCP 와 미리 보기
  (「추천대로 모두」 는 서버가 다시 모은다)까지 한 번에 지킨다. 아래 「남은 것」 에 둔다.
- **종류마다 스레드로 나란히** — 세션을 따로 열어야 하고(세션은 스레드끼리 못 나눈다), 시간이 넘은 스레드의 질의는
  여전히 돈다. 끊는 길(결정 2)이 필요한 것은 같다.
- **「이것 아닐까」 를 미리 셈해 둔다** — 근본 처방이다(아래 「남은 것」 ①). 표 · 워커 작업 · 낡음 규칙을 정해야 해서
  이번에는 시간 상한으로 화면을 먼저 세웠다 → 같은 날 ADR 0074 로 했다.

## 남은 것 — 검토함의 수가 많을 때

시간 상한은 **화면을 세울 뿐** 일을 줄이지 않는다 — 운영 모양이면 별칭 후보는 한 번에 18 ~ 33줄씩 보이고, 열 때마다
8 ~ 15초를 다시 쓴다. 다음 처방(효과 큰 차례):

1. ~~**「이것 아닐까」 를 미리 셈해 둔다**~~ → [ADR 0074](0074-별칭-후보의-이것-아닐까-미리-셈.md)(2026-11-16 — 검토함
   전체 9.4 → 1.25초 · 별칭 후보만 15 → 0.04초 · 미리 보기 21 → 0.43초). 처음 적은 생각: 못 찾은 말 줄(`search_misses`)에 제안(객체 id · 점수 · 어디가 비슷했나)과
   셈한 시각을 두고, 워커가 많이 찾은 것부터 채운다(새로 세 번을 넘은 줄 · 하루 넘은 줄 · 축 객체 · 별칭이 바뀐 범위).
   검토함 · 창은 읽기만 해서 200줄이 질의 몇 번이 되고, 미리 보기 · 적용이 같은 값을 읽어 지문도 흔들리지 않는다.
   항목은 여전히 원래 자리에서 읽는다(ADR 0027 의 「새 표에 복사하지 않는다」 그대로 — 셈한 짐작만 그 줄에 얹는다).
   가리키던 객체가 지워졌으면 읽을 때 빼고, 붙이기는 원래 기능이 다시 검사한다. 낡음의 값: 셈한 뒤 생긴 더 비슷한
   객체를 그 주기만큼 늦게 본다.
