# 0048. 오래 도는 읽기의 안전장치 — 떠나면 멈추고, 시간 · 동시 개수 · 임시 파일에 상한

- 상태: 채택(2026-11-02 구현 — `shared/readguard.py` · 정적 그리기 `GET /api/graph/whole` · 영향 범위
  `GET /api/graph/reach` · 탐색 그림 `GET /api/graph/subgraph` · `GET /api/graph/neighborhood` · 참조 수 세기
  `refedges.degree_counts` · `querycap` 의 `temp_file_limit` · 화면 그래프 요청의 `signal` · `deploy.sh` 의
  `grant_temp_limit` · `pg-tune.sh` 의 `temp_file_limit`)
- 날짜: 2026-11-02
- 관련: [ADR 0031](0031-걸음-넷과-읽기-시간-상한.md)(질의 하나의 시간 상한 — 이것은 요청 하나의 상한),
  [ADR 0045](0045-지식-그래프의-정적-그리기.md)(정적 그리기), [ADR 0047](0047-들어오는-선-방향과-영향-범위.md)
  (영향 범위), [ADR 0026](0026-느린-요청-감시.md)(느린 요청)

## 배경

운영에서 지식 그래프 전체 보기(정적 그리기)가 오래 걸려 화면을 닫았다. 그런데 서버는 계속 돌면서 디스크를
잡아먹다가 멈췄다(2026-11-02 사용자 보고). 코드에서 확인한 구멍은 다섯이다.

| 구멍 | 그 결과 |
| --- | --- |
| 화면이 결과만 버리고 **요청을 끊지 않았다** | 단계 · 씨앗을 바꾸거나 정적 그리기를 꺼도 앞 요청이 서버에서 끝까지 돈다. 단계를 1 → 2 → 3 으로 바꾸면 셋이 함께 돈다 |
| FastAPI 의 `def` 라우트는 **연결이 끊겨도 끝까지 돈다** | 탭을 닫아도 스레드와 DB 질의는 남는다 |
| 시간 상한이 **질의마다**다(60초, ADR 0031) | 정적 그리기는 단계마다 여섯 번 넘게 묻는다. 요청 하나가 몇 분이다 |
| 동시 개수에 상한이 없다 | 닫고 다시 열 때마다 하나씩 쌓인다 |
| 임시 파일에 상한이 없다(`temp_file_limit = -1`) | 정렬 · 해시가 디스크로 넘어가면, 질의 하나가 디스크를 다 채울 수 있다 |

**정적 그리기는 임시 파일을 쓰지 않았다.** 개발 PC의 2,000만 건 DB에서 아홉 가지(타입 씨앗 10만 ~ 20만,
1 ~ 3단계, 기록 포함 · 제외)를 관리자로 돌렸다. 가장 오래 걸린 것이 47초(찬 캐시)였고, 임시 파일은 하나도
생기지 않았다(`pg_stat_database.temp_bytes` 차이 0). 기본 조회 범위(`VIEW_SCOPE=all`)에서는 일반 사용자의 계획도
같다.

**임시 파일을 쓴 것은 정적 그리기를 끈 「타입 전체 표시」(`/graph/subgraph`)였다.** 같은 DB 에서 그림 노드 2만으로
모델 6천 개를 그리면 28초에 임시 파일 1,533개 · 1.79GB, 타입 여덟 개를 함께 고르면 60초에 3,066개 · 3.53GB 였다.
- 원인은 노드마다 붙는 「+N」 의 근거인 **나를 가리키는 참조 수 세기**(`refedges.degree_counts`)다.
- 이 질의는 지운 것 · 안 보이는 것을 거르려고 참조 표(5,000만 줄)를 객체 표(2,000만 줄)와 해시로 이었다. 해시가
  256조각으로 디스크에 넘쳤다(그 질의 하나가 20초 · 1.7GB).
- 이 경로에는 질의 시간 상한도 없었다. 그래서 닫아도 끝까지 돌고, 다시 누를 때마다 하나씩 더 쌓였다.

운영에서 디스크를 채운 것이 이것인지는 운영 기록으로 확인하지 않았다. 그래서 이 질의를 고치는 것과 함께, **무엇이
차든 막는 장치**를 둔다. 운영에서 확인할 길은 맨 아래 「운영에서 볼 것」 에 적었다.

## 결정

### 0. 참조 수는 색인만으로 센다 · 총수는 계수표로

- 참조 색인에는 **살아 있는 출발점만** 있다(`refindex` 트리거 — 지운 객체의 줄은 지운다). 그래서 모두를 보는
  사람(`sees_every_department` — 기본 `VIEW_SCOPE=all` · 시스템 관리자)은 객체 표를 거치지 않고 `(dst_id, key)`
  색인만으로 센다. 정적 그리기의 넓히기가 이미 그렇게 한다.
- 부서로 좁힌 설치는 보이는 것만 세야 하므로 지금처럼 잇는다. 그 대신 아래 상한이 걸린다.
- 기록 수 세기(`log_counts`)도 같은 기준으로 맞췄다. 전에는 「시스템 관리자일 때만」 건너뛰었다.
- 「타입 전체 표시」 의 총수(「2,000만 개 중 300개」)는 이름으로 좁히지 않았으면 계수표(ADR 0038)에서 읽는다.
  기록 타입을 통째로 세는 데만 10초를 넘게 썼다.

### 1. 화면이 끊는다

그래프 요청(정적 그리기 · 이웃 · 타입 전체 표시)의 물음에 `signal`(`AbortSignal`)을 싣는다 —
`api.get(path, { signal })`. 씨앗 · 단계 · 거르기를 바꾸거나, 정적 그리기를 끄거나, 화면을 떠나면 앞 요청을
끊는다(`GraphPage` 의 effect 정리). 탭을 닫으면 브라우저가 끊는다.

### 2. 서버가 끊김을 보고 멈춘다(`readguard.run`)

- 라우트는 `async def` 로, 몸(동기)은 스레드에서 돈다. 라우트는 0.5초마다 요청한 쪽의 연결을 본다
  (`request.is_disconnected()`).
- 끊겼으면 **지금 도는 질의를 취소한다**. psycopg `cancel_safe()` 로 DB 에 취소를 요청하고, 일이 끝날 때까지
  0.5초마다 다시 보낸다.
- **그 요청의 다음 질의는 보내지 않는다.** 모든 엔진의 `before_cursor_execute` 에서 그 요청의 표시(contextvar)를
  보고 `Stopped` 를 낸다. 취소는 「지금 도는 질의」 만 끊으므로, 질의 사이에 닿으면 이것이 멈춘다.
- 응답은 499 이고 로그에 `요청한 쪽이 떠나 멈췄습니다(정적 그리기)` 가 남는다. 받는 사람은 없다.

### 3. 요청 하나의 시간 상한 — `LONG_READ_SECONDS`(기본 120초)

질의 여러 번을 합친 시간이다. 넘으면 2와 같은 길로 멈추고 504 로 좁히는 길을 말한다. 정적 그리기의 안내는
「단계를 줄이거나 관계 · 이웃 타입으로 거르거나, 전부는 전체 지도에서」 다. 질의 하나의 상한(60초)도 그대로 걸린다.

### 4. 동시 개수 — `WHOLE_SLOTS`(기본 2, 설치 전체)

- 자문 잠금 `graph_whole:0` · `graph_whole:1` 중 하나를 트랜잭션 동안 쥔다. DB 하나에 걸린 잠금이라 이중화의 두
  서버 · 서버마다 워커 넷을 다 합쳐 센다.
- 자리가 없으면 5초 동안 다시 본다(`SLOT_WAIT`). 화면이 단계를 바꾸면 앞 요청을 끊고 곧바로 새로 묻는데, 그
  사이에 앞 요청이 아직 취소되는 중일 수 있어서다. 그래도 없으면 429 「앞의 것이 끝나면 다시」 다.
- 상태 코드는 503 이 아니다. 이중화의 nginx 는 503 · 시간 초과면 같은 요청을 다른 서버에 다시 보낸다.

### 5. 임시 파일 상한 — 요청마다(`READ_TEMP_LIMIT`, 기본 5GB) · 서버 전체(`pg-tune`)

- **읽기 요청마다**: `querycap.cap` 을 쓰는 읽기(목록 · 통계 · 추이 · 정적 그리기 …)에 `SET LOCAL
  temp_file_limit` 를 건다.
  - 넘으면 그 질의만 끊고 507 「범위를 좁혀」 로 답한다.
  - 이 설정은 superuser 만 바꿀 수 있다. 그래서 `deploy.sh` 의 `prepare` · `update` 가 앱 계정에
    `GRANT SET ON PARAMETER temp_file_limit` 를 준다(PostgreSQL 15부터). 대기 서버는 복제로 받으므로 건너뛴다.
  - 권한이 없으면 걸면 요청이 통째로 실패한다. 그래서 프로세스마다 한 번 **걸어 보고**, 된 때만 건다
    (`temp_limit_allowed`). 확실한 「못 건다」(권한 없음 42501 · 틀린 값 22023)만 기억한다. 기동 직후 DB 가
    잠깐 안 닿은 것을 기억하면 그 프로세스는 재시작까지 상한 없이 돈다.
  - `remove` 는 역할을 지우기 전에 그 권한을 거둔다. 권한이 남은 역할은 `DROP ROLE` 이 거절한다.
- **서버 전체**: `pg-tune` 이 `temp_file_limit` 를 데이터 디스크의 1/5(100GB까지)로 권한다.
  - 작업 · 마이그레이션까지 모든 프로세스에 걸리는 마지막 안전망이다.
  - 넘으면 그 질의 · 작업만 실패한다. 디스크가 차서 DB 가 통째로 멈추는 것보다 낫다.
  - 다시 읽히기(`pg_reload_conf`)만으로 바뀐다. 재시작은 필요 없다.

## 대안 — 버린 것

- **모든 GET 에 미들웨어로** — 끊김을 보려면 미들웨어가 앱과 함께 `receive` 를 읽어야 하고, 본문을 읽는 라우트 ·
  스트리밍 응답과 겹친다. 오래 도는 것이 확인된 두 라우트에만 건다. 다른 읽기가 오래 돌면 `readguard.run`
  한 줄로 넓힌다.
- **질의마다 `statement_timeout` 을 남은 시간으로 다시 걸기** — 시간 상한은 되지만 끊김은 못 본다. 취소 길 하나로
  둘을 같이 한다.
- **같은 사람의 새 요청이 앞 요청을 취소** — 서버 사이 · 워커 사이에 「앞 요청」 을 찾아 끊는 신호가 필요하다.
  화면이 앞 요청을 끊으니 서버는 끊김만 보면 된다.
- **디스크 남은 공간을 보고 거절** — DB 가 다른 서버(이중화 · VIP)에 있으면 앱이 그 디스크를 못 본다.
  `temp_file_limit` 는 DB 가 스스로 지킨다.

507 응답만 시험했고, 실제로 상한을 넘겨 끊기는 것은 권한을 받은 설치에서 본다.

### 함정

- **「+N」 하나가 디스크를 썼다** — 노드 옆의 작은 수를 세려고 객체 표 전체를 해시로 이었다. 색인이 이미 지킨
  규칙(살아 있는 것만)을 질의가 한 번 더 확인한 값이었다.
- **연결 하나에 건 이벤트는 세션이 연결을 바꾸면 놓친다** — `rollback` 뒤 같은 세션의 다음 질의는 새 연결로
  갔다. 모든 엔진(`Engine` 클래스)에 걸고, 요청은 contextvar 로 가른다.
- **취소가 질의 사이에 닿으면 아무 일도 없다** — DB 의 취소는 「지금 도는 질의」 만 끊는다. 다음 질의를 막는
  자리와 0.5초마다의 다시 취소가 함께 있어야 멈춘다.
- **`temp_file_limit` 는 superuser 만 바꾼다** — 권한 없이 `SET LOCAL` 하면 그 요청의 트랜잭션이 통째로
  실패한다(목록 · 통계가 다 멈춘다). 기동 뒤 처음 읽을 때 따로 걸어 보고, 실패하면 안 건다.
- **매개변수 권한이 남은 역할은 지우지 못한다** — `remove` 가 `REVOKE SET ON PARAMETER` 를 먼저 한다.

## 운영에서 볼 것

디스크가 다시 차면, 어디가 찼는지부터 본다.

- DB 임시 파일: `SELECT temp_files, pg_size_pretty(temp_bytes) FROM pg_stat_database WHERE datname = '<DB>'`
  (누적) · `du -sh /var/lib/postgresql/16/main/base/pgsql_tmp`(지금).
- 앱 로그 · 저널: `du -sh <설치 경로>/logs`(컨테이너 안의 `/data/logs`) · `journalctl --disk-usage`.
