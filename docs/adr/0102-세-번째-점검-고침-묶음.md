## 배경

0.4.108 을 낸 뒤 세 번째로 점검했다. 돌려 본 쪽은 깨끗했다 — 개발 DB 사본에 띄운 서버의 GET API 전부에서
5xx 0, 화면 86개 중 깨진 것은 원래 알던 첨부 원본 16개 자리뿐, 의존성 감사 0. 코드는 여섯 갈래로 나눠 읽고
굵은 것은 다시 확인했다(화면은 브라우저로 재현, MCP 경로는 httpx 로, 예약은 개발 DB 의 작업 기록으로).

이번 결함은 새 코드보다 **오래된 길의 드문 모양**에 있었다. 결과 모양을 칸 하나로 짐작하는 화면, 적용한
뒤에야 끊김을 보는 동기화, 덤프를 보기 전에 운영 DB 를 지우는 복구, 「지난번 이후」 를 `updated_at` 으로 묻는
쪽 넷이 못 보는 일괄 SQL, 문자열로 이어 붙인 주소가 그것이다.

## 결정

### 1. 「작업」 화면 — 모르는 결과 모양에 깨지지 않는다

**문제:** 「작업」 화면이 결과 모양을 칸 하나만 보고 짐작했다. 「온톨로지 전체 내보내기」(`objects: 3400` — 수)나
「검토함 일괄 확인」(`rows` 에 계획 줄이 아닌 결정)을 펼치면 화면 전체가 「이 화면을 그리지 못했습니다」 로
바뀌었다(브라우저로 재현). 검토함 자동 확인은 밤마다 돌아 「내가 시킨 것만」 에도 뜬다.

**바뀐 것:**
- 그 모양에만 있는 칸까지 보고 고른다. 모르는 모양은 값만 적는다.
- 검토함 결과는 결정마다 종류 · 질문 · 선택 · 결과를 보이고, 목록 줄은 「적용 — 처리 2건 · 그 사이 막힘 1건」 처럼
  쓴다(전에는 「새로 0 · 고침 0 · 그대로 0」).
- 2만 건이 넘어 작업으로 세운 옮기기 · 키 변경 계획도 읽고 적용한다. 판정은 서버와 같다(`errors` 없음, 공개 타입이면
  `accept_core`).

**적용 상태:** `applied_status` 로 「적용 대기 중 · 적용 중 · 적용함」 을 가른다. 전에는 적용 작업이 워커를 기다리는
동안에도 「적용했습니다」 였다. 적용 작업 번호를 클릭하면 그 작업이 맨 위에 펼쳐진다.

**고아 파일 정리:**
- 전에는 계획이 「남길 결과가 없는 작업입니다」 로만 보였고, 옆의 「적용」 이 확인 없이 파일을 삭제했다.
- 이제 삭제할 것 · 앞 20개 목록 · 「다른 DB 의 저장소일 수 있음」 경고를 보인다.
- 적용은 확인 창을 거친다. 경고가 있으면 「이 설치의 저장소가 맞습니다」 를 선택해야 「삭제」 가 눌린다.
- 선택 적용에서는 뺀다. 서버 요약도 용어집 말로 바꿨다(「삭제할 것 · 탐색한 파일」).

**링크:** `?job=` 링크가 첫 쪽에 없을 뿐인 작업에도 「목록에 없습니다」 라고 했다. 이제는 따로 읽어 맨 위에 펼치고,
서버가 404 일 때만 「찾을 수 없습니다」 라고 한다.

### 2. 데이터 소스 — 적용하기 전에 끊김을 본다, 대조는 커서를 끝으로 옮기지 않는다

**끊겨 온 선 소스:**
- 한 행이 선 하나인 소스(BOM 등)가 「파일대로 맞춤」 일 때, 5만 행이나 쪽 상한에서 끊겨도 맞춤을 먼저 커밋했다.
  끊김은 그 뒤에 봤다.
- 예: P-100 의 선 둘 중 하나가 5만 행 뒤에 있으면 「표에 없는 선」 으로 끊겼고, 실행은 「실패」 로만 남았다.
- 이제는 객체 · RA 쪽과 같이 끊겨 오면 계획만 세운다(끊을 셈은 보인다). 아무것도 바뀌지 않는다.
- 「더하기」 도 끊기면 하나도 안 넣는다. 전에는 앞 5만 줄을 넣었다 — 규칙을 하나로 맞췄다.

**RA 전량 대조의 커서(ADR 0018 보강):**
- 대조는 본문 없이 전량을 읽고 커서를 그 끝으로 옮겼다.
- 예: 09:00 에 증분을 받고, 10:00 에 RA-2 의 본문을 고치고, 11:00 에 대조가 돌았다. 대조는 본문 없이 받고 커서를
  11:00 쪽 끝으로 옮겼다. 다음 증분은 10:55 이후만 읽으므로 RA-2 의 새 본문은 영영 안 왔다.
- 간격이 하루 이상인 소스는 차례마다 대조라, 새 보고서의 본문이 한 번도 안 왔다.
- 이제 대조 차례는 전량(본문 없이) 다음에 저장한 커서에서 본문까지 한 번 더 읽고, 커서는 그 끝으로만 옮긴다.
  처음 받기와 본문을 안 받는 소스는 전처럼 한 번 읽는다.

### 3. 복구 스크립트 — 검사가 먼저, 임시 DB 에 풀고, 옛 DB 는 남긴다

**문제:**
- `restore.sh` 는 덤프를 보기 전에 운영 DB 를 지웠다. `pg_restore` 실패는 `|| true` 로 넘겼고, 검사는 「표 1개 이상」
  뿐이었다.
- 예: 뒤쪽이 잘린 덤프에 `-f` 를 주면 운영이 지워지고, 행이 0 인 DB 가 「복구 완료」 됐다(실측).
- 표준 배포의 앱 계정에는 CREATEDB 가 없다. 그래서 지운 뒤 만들기에서 멈춰 운영이 아예 없었을 것이다.
- 확인용 이름에 `-i` 를 붙이면 `-f` 없이 운영 첨부 폴더에 `rsync --delete` 를 했다.

**바뀐 것 — 차례:**
1. 덤프 검사: `pg_restore -l` 이 0 으로 끝나고 `TABLE DATA` 가 있어야 한다. 그 전에는 어느 DB 도 안 건드린다.
2. 임시 DB `<db>__restoring` 에 푼다.
3. 검사: 중간에 멈추지 않았나, 무해한 것(스키마 · 주석 · 확장) 밖의 오류가 없나, 표가 있나, `alembic_version` 에
   행이 있나. 하나라도 걸리면 임시 DB 만 지운다.
4. 한 트랜잭션으로 이름을 바꾼다. 옛 DB 는 `<db>__before_restore_<시각>` 으로 남기고, 지우는 명령과 되돌리는 명령을
   찍는다.

**누가 하나:**
- **DB 서버에서 `sudo ./restore.sh`** 로 돌리면 DB 만들기 · 이름 바꾸기 · pgvector 는 그 서버의 postgres 계정이 한다.
  앱 계정에 CREATEDB 를 주지 않는다.
- 같은 클러스터인지는 앱 접속과 postgres 접속의 시작 시각 + system_identifier 를 견줘 가린다. 이중화 주 서버는 앱이
  DB VIP 로 붙으므로 주소 이름만으로는 못 가린다.
- 대기 서버, 다른 클러스터, 주인이 앱 계정이 아닌 DB 는 거절한다.
- sudo 없이, 또는 DB 가 다른 서버면 앱 계정으로 한다. CREATEDB 가 없으면 아무것도 안 바꾸고 할 일을 적은 뒤 멈춘다.

**첨부와 접속:**
- 비어 있지 않은 첨부 폴더는 DB 이름과 상관없이 `-f` 가 있어야 한다.
- 첨부 복구는 `--delete` 를 뺐다 — 남긴 옛 DB 가 가리키는 파일을 지우면 되돌아갈 수 없다.
- 접속이 남아 있으면 거절한다(누가 붙었는지 적는다). 끊지는 않는다. 계정이 있는 접속만 센다(`usename IS NOT NULL`)
  — autovacuum 작업자까지 세면 서비스를 다 멈춘 직후의 정상 복구도 거절됐다. 이름 바꾸기가 autovacuum 을 내보낸다.

**정렬(원래부터 있던 것):**
- 정렬(locale)은 덤프에 안 실린다. 그래서 예전에는 서버 기본(template1)으로 만들어, C.UTF-8 로 다시 만든 운영 DB 도 복구
  한 번에 en_US 로 돌아갔다. 이름의 차례와 색인 비교가 함께 바뀐다.
- 이제는 지금 DB 의 정렬(LC_COLLATE · LC_CTYPE · ICU 로캘)로 `TEMPLATE template0` 에서 임시 DB 를 만든다. 만든 뒤 다시
  읽어 다르면 멈춘다.
- 지금 DB 가 없으면(확인용 이름) 서버 기본대로 만들고 무엇이 됐는지 적는다.

### 4. 타입 옮기기의 뒤 — 「지난번 이후」 를 묻는 쪽이 따라온다(ADR 0094 §1 을 바꾼다)

**문제:**
- 「협력사」 300건을 「공급사」 로 옮겨도 객체의 `updated_at` 은 그대로였다(ADR 0094 §1).
- 그래서 `type_id + updated_at` 으로 「지난번 이후」 를 묻는 쪽이 모두 그 300건을 못 봤다.
  - 공급사의 수신 시스템 · 코어 구독은 300건을 영영 못 받았다.
  - 협력사의 수신 측은 떠난 300건을 살아 있는 것으로 들었다. 처음부터 받으면 0건이라 「전부 안 오면 멈춤」 에 걸렸다.
  - 지표는 최대 7일 동안 협력사에서 300건을 계속 셌고, 공급사에는 안 더했다.
- 계획의 「수신 시스템에서 사라집니다 / 새 객체를 받습니다」 는 거짓이었다.

**`updated_at` 결정:**
- `_MOVE` 가 같은 문장에서 `updated_at = now()` 로 올린다. 타입 · 칸의 키가 바뀐 것은 받는 쪽에는 바뀐 것이다.
- 읽는 곳을 모두 훑었다(이력 · 정렬 · `datasource_seen_at` · 계보 · ETag · 묶음 되돌리기). 그대로 두는 데 기대는 곳은
  계보 「낡음」 판정 하나였다. 그래서 대상에 개정 칸이 없으면, 옮기기 전에 낡지 않던 선의 `pinned_at` 도 함께 올려
  판정을 지킨다(`_KEEP_PINS`).
- 이 때문에 「최근 수정」 정렬에서 옮긴 객체가 위로 온다. 묶음 되돌리기는 옮긴 객체를 「그 뒤에 고쳐져 안 지웁니다」
  로 남긴다 — 더 안전한 쪽이다.

**원 타입 쪽:**
- 원 타입의 카탈로그 · 쪽에 `moved_at`(옮긴 때) · `moved_to`(간 **공개** 타입, 비공개 대상이면 `null`)를 싣는다.
  판(`revision`)에도 든다 — 옮긴 적 없는 타입의 판은 그대로다.
- 코어 연동 키트(2026-11-28 판)와 형제 SP 의 코어 구독은 간 곳을 먼저 받는다. 간 곳에 같은 `key` 가 온 것만 원 타입
  쪽을 비활성 · 사용 중지한다(지우지 않는다). 선의 끝 타입도 옮긴다.
- 옛 판 키트는 판이 바뀌어 처음부터 다시 받고, 원 타입이 비어 와서 **지우지 않고** 「확인 필요」 로 멈춘다.

**지표와 병합:**
- 지표 증분은 그 지표가 읽는 타입(원천 · 참조 너머 · 하위 트리)에서 · 으로 옮기기가 있었으면 전량으로 센다.
- 원래 있던 버그도 고쳤다. 옮기며 같은 식별자로 병합된 진 쪽의 무덤이 나가면, 받는 쪽이 이긴 쪽 행을 비활성으로
  만들었다. 이제 그 무덤은 **빼기만** 하고, 이긴 쪽이 같은 흐름에 따로 오지 않을 때만 그 자리에 이긴 쪽 행을 한 번
  둔다(`_without_same_key_graves`). 처음 고침은 이긴 쪽을 두 번 보내, 형제 SP 가 「같은 식별자」 로 조각을 거절하고
  시계가 멈췄다(검토에서 실측).
- 받는 쪽도 막아 둔다. 키트는 한 번 받기 안에서 같은 key 의 산 행이 이기고(`alive_wins`), 형제 SP 는 한 차례에 같은
  key 의 산 행을 마지막 것만 받는다(`fetchers.last_alive_per_key`).

**원 타입은 id 로 맞춘다:**
- 옮기기 감사 기록(`ontology.type.move`)의 `changes` 에 원 타입 id(`from_id`)를 남기고, `Trail` 은 그것으로 맞춘다.
- `from_id` 가 없는 옛 기록은 slug 동안으로 맞추되, 그 slug 를 다른 타입이 지우거나 바꿔 내놓은 차례 뒤로만 맞춘다.
  그래서 옮긴 원 타입을 지우고 같은 slug 로 새 타입을 만들어도 옛 `moved_to` 를 물려받지 않는다.
- 구독은 원 타입과 간 곳이 이 설치의 같은 타입으로 이어져 있으면 아무것도 사용 중지하지 않는다.

### 5. MCP 의 경로 — 한 자리에서 막고, 인자는 마디 하나로 인용한다

**문제:**
- 도구 인자를 주소에 그대로 넣었다. httpx 는 `..` 를 접고, `#` 뒤를 버리고, `?` 뒤를 쿼리로 읽는다.
- 그래서 `relation_proposal_decide(proposal_id="../part/<id>?mode=detach", decision="withdraw")` 가
  `DELETE /api/objects/part/<id>?mode=detach`(= `objects_delete`)가 됐다.
- 위험 도구는 시스템 관리자만이라는 규칙(ADR 0030)을 비켜 갔다. 문서에 심은 글(프롬프트 주입)로도 닿는 길이었다.
  서버의 권한 검사는 그대로라, 사용자 자신의 권한 밖까지 가지는 않았다.

**바뀐 것:**
- 모든 요청이 한 자리(`_GuardedClient.build_request`)를 지난다. 다음 경로는 요청 없이 `unsafe_path` 오류로 돌려준다:
  - `/api/` 밖의 경로, `.` · `..` 마디
  - `?` · `#` · `\` · 제어 문자
  - `%2e` · `%2f` · `%5c`
- 인자는 `_seg`(`quote(…, safe="")`)로 마디 하나가 된다. 그래서 `<id>/merge` 같은 `/` 도 거절된다.
- 경로에 쿼리를 넣던 호출은 없었다(모두 `params=`). `extension_call` 은 `#` 도 거절한다.

### 6. 예약 — 같은 일을 5분마다 다시 하지 않고, 하루 한 번은 꼭 한다

**지도 덧붙임(ADR 0046):**
- 차례를 판의 생성 시각으로만 쟀다. 그런데 새 기준정보가 없는 덧붙임은 판을 안 만든다.
- 그래서 판이 30시간을 넘은 뒤로는 덧붙임이 끝나자마자 다시 들어갔다. 개발 DB 에서 11-08 이후 799번 돌았고, 그동안
  한 시간 집계는 한 번도 안 돌았다. 2천만 건에서는 한 번에 집계를 다시 센다(ADR 0046 실측 12초).
- 이제는 판의 때와 마지막으로 끝난 전체 배치 · 덧붙임 중 늦은 때로 잰다. 예: 이틀 된 판에서 방금 덧붙임이 끝나면,
  다음은 한 시간 뒤의 집계이고 덧붙임은 다음 밤이다.

**뜻 찾기의 하루 한 번 「전부」:**
- 「전부」 의 차례를 아무 계산이나 마지막으로 성공한 때로 쟀다. 하루에 한 번만 고쳐도 「바뀐 것만」 이 시계를 다시
  돌려, 바쁜 설치에서는 「전부」 가 영영 안 돌았다.
- 그래서 부품군 이름을 바꿔도 그 이름을 담은 다른 객체의 글이 다시 계산되지 않았다.
- 이제는 「전부」(`params.full`)의 성공으로만 잰다.

### 7. 토큰 범위 · 지켜보기 알림 · 경보

**토큰 범위:**
- `POST /api/graph/cypher` 가 범위 표에 없어 어떤 토큰으로도 AUTH-105 였다. 그래서 MCP `graph_query(action="query")`
  는 토큰으로 한 번도 안 됐다.
- `POST /api/objects/{타입}/similar` 는 읽기인데 `objects:write` 를 요구했다.
- 둘 다 읽기만 하는 것을 확인하고(Cypher 는 읽기 전용 세션 · 롤백, similar 는 select 만) 「POST 지만 읽기」 로
  열었다.

**관계 지켜보기 알림:**
- 알림 목록에 「관계가 …」 가 있었지만 한 번도 안 갔다. 선의 기록은 `object_relations` · `object_links` 에 남는데,
  객체 표의 일만 봤기 때문이다.
- 이제는 선의 양 끝을 지켜보는 사람에게 간다. 예: 「모터 — 관계가 추가됐습니다 · 부품 · 관리자 · 속함: 구동부」.
- 못 보는 끝은 「(볼 수 없는 객체)」 로 가린다. 한 번에 여럿이면 「(3건)」 한 통으로 묶는다. 객체를 지우며 끊긴 선은
  그 객체에 「삭제」 한 통만 보낸다.
- 묶음의 「파일대로 맞춤」 이 끊는 선의 기록에도 양 끝을 싣는다. 전에는 이유 한 줄뿐이라 알림도, 객체 이력의 그
  줄도 없었다.
- 만드는 곳이 없는 `object.restore` 는 목록에서 뺐다.

**경보 발생:**
- MCP `metric_alerts(slug)` 는 내 모든 경보의 최근 N개를 받아 지표로 걸렀다. 그래서 다른 지표가 자주 울리면 이
  지표의 발생이 밀려나 0건(「안 울렸다」)이 됐다.
- 이제 `GET /api/metrics/alerts/events?metric=<slug>` 가 그 지표의 것만 세어 N개를 준다(모르는 지표는 404).
  MCP 는 이것을 쓴다.

## 대안 — 버린 것

- **복구에서 앱 계정에 CREATEDB 를 준다:** 버렸다. 복구 한 번을 위해 늘 쓰는 계정의 권한을 늘린다. DB 서버의 postgres
  계정(sudo)이 하고, 아니면 할 일을 적고 멈춘다.
- **복구가 첨부를 `--delete` 로 맞춘다:** 버렸다. 옛 DB 를 남기는 뜻이 없어진다. DB 에 없는 파일이 남는 것은 무해하다
  (자동 정리가 하루 뒤 판단한다).
- **옮기기에서 `updated_at` 은 그대로 두고, 읽는 쪽마다 감사 기록을 읽는다:** 버렸다. 지표 · 코어 API · 구독 · 지도 넷이
  따로 해야 하고, 새로 생기는 「지난번 이후」 도 또 놓친다. 객체마다 기록을 남기는 것은 2천만 건에서 못 한다.
- **RA 대조는 커서를 안 옮기기만 한다:** 버렸다. 간격이 하루 이상인 소스는 차례마다 대조라 본문이 끝내 안 온다.
- **MCP 도구마다 인자를 검사한다:** 버렸다. 200개 가까운 호출처에서 하나만 빠져도 열린다. 보내는 한 자리에서 막고,
  인용은 그 위에 더했다.
- **끊겨 온 선 소스의 「더하기」 는 앞 5만 줄을 넣는다:** 버렸다. 해는 없지만 객체 · RA 와 규칙이 달라진다. 끊기면
  나눠 받으라는 같은 말을 한다.

## 결과

- **마이그레이션 · 설정:** DB 마이그레이션 없음. 새 `.env` 값 없음.
- **복구:** DB 가 있는 서버에서 `sudo ./restore.sh …` 로 돌린다.
  - 실제 복구는 앱 · 워커 · MCP · 타이머를 멈춘 뒤에 한다. 접속이 남으면 거절한다.
  - 옛 DB 가 남아 디스크를 한 벌 더 쓴다. 앱을 띄워 확인한 뒤 찍힌 `dropdb` 로 지운다.
  - 확인용에 `-i` · `-F` 를 쓰면 `-f` 가 필요하다. DB 이름은 영문 · 숫자 · `_` · `-` 만 받는다.
- **코어 연동 키트 2026-11-28 판:** 받는 곳에 새로 나눈다.
  - 이미 운영에서 타입을 옮긴 적이 있는 설치는 올리는 순간 그 원 타입에 `moved_to` 가 생기고 판이 한 번 바뀐다.
  - 그래서 키트가 처음부터 다시 받는다. 옛 키트는 그 원 타입에서 지우지 않고 멈춘다. 새 판으로 한 번 돌리거나
    `--full --allow-shrink` 로 맞춘다.
- **데이터 소스:**
  - 끊겨 온 선 소스는 「더하기」 여도 아무것도 안 넣는다 — `$filter` 로 나눈다.
  - 이미 놓친 RA 본문은 그 소스의 「수신 기준 시각」 을 비우면 다시 온다.
- **MCP:** 경로를 바꾸려는 인자는 `unsafe_path` 로 거절된다.
- **알림:** 관계 지켜보기 알림이 처음으로 나간다.
- **남은 것:**
  - 정제 키트(`pipeline/`)도 주소를 문자열로 잇는다. 사용자 PC 의 키트라 MCP 서버와 위험이 다르지만, 같은 거르기를
    볼 만하다.
  - 복구의 postgres 계정 길은 가짜 도구 시험으로만 봤다. 실제 sudo 로는 운영 서버에서 처음 돈다.
  - 형제 SP 는 두 차례에 걸쳐 정리된다(간 곳 다시 받기 → 다음 확인에서 원 타입 쪽 사용 중지).
  - 원 타입을 지우거나 공개를 해제하면 `moved_*` 도 사라진다. 삭제 미리 보기에 그 경고는 아직 없다.
  - 기존 객체 알림의 「지워졌습니다 · 값이 바뀌었습니다」 는 용어집(삭제 · 수정)과 어긋난다.
  - 점검 보고의 「그다음」 항목은 이 묶음에 들지 않았다: 객체 동시 수정의 잃음, 인라인 적용과 계획 지문, 큰 타입의
    종류 바꾸기, 지운 키의 값 되살아남, 웹훅 · 워커 정리 단계의 막힘, update 의 503 성공, 백업 첨부 사본 하나, 부서
    범위 설치의 이름 노출 등.
