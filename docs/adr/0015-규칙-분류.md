# 0015. 규칙 분류 — 조건 목록의 첫 일치로 값을 붙이는 기준

- 상태: 채택(2026-10-10 구현 — 규칙 기준 · 계획의 규칙별 수 · 규칙 판 · 정확한 건 보기(목록 조건의
  「제외」) · 구성비 보기 · MCP. 200만 건 실측, 수치는 「결과」)
- 날짜: 2026-10-03(제안) · 2026-10-10(채택)
- 관련: [ADR 0013](0013-지표.md)(지표 — 기준 · 건 보기), [ADR 0014](0014-분석.md)(분석 — 파레토 두 기간
  비교가 구성비 추이를 본다), [ADR 0016](0016-경보.md)(경보), [ADR 0024](0024-지표-증분과-홈-지표.md)(증분 —
  정의 지문 · 다른 객체 너머)

## 배경

열 가지 물음의 ⑧ 은 「성격(제품결함 · NTF · 고객과실 · SW)으로 분류한 뒤 그 **구성비 추이**」 다. 통계가
아니라 **분류**다 — 진단 코드 · 조치 코드 · 부품 교체 여부 같은 칸을 보고 사람이 정한 규칙으로 성격을
붙인다. 예:

| 차례 | 성격 | 조건(모두 맞으면) |
| --- | --- | --- |
| 1 | SW | 조치 코드가 `SW*` 로 시작 |
| 2 | 고객과실 | 진단 코드가 `C01` · `C02` · `C07` 중 하나 |
| 3 | NTF | 교체 부품이 비었고 조치 코드가 `N00` |
| 4 | 제품결함 | 교체 부품이 있다 |
| — | 기타 | 어느 규칙에도 안 맞음 |

지금은 이것을 AI 가 기록을 받아 분류하거나, 원천에서 성격 칸을 미리 채워 와야 한다. 앞의 것은 매번 다른
답이 나오고(ADR 0014 이 버린 길), 뒤의 것은 규칙이 원천 시스템의 코드 속에 숨어 아무도 못 본다. 규칙이
바뀌면(「C07 은 이제 고객과실이 아니다」) 지난 구성비를 다시 셀 길도 없다.

구성비 · 추이 자체는 이미 된다 — 성격이 **기준**이기만 하면 파레토의 몫 · 기간별 추이 · 두 기간 비교
(수정 잔차, ADR 0014)가 그대로 답한다. 빠진 것은 **규칙으로 값을 붙이는 기준** 하나다.

## 결정

1. **지표의 새 기준 종류 「규칙」.** 정의의 기준에 주소 대신 규칙 목록을 둔다(`metrics/spec.py`).

   ```json
   {"name": "nature", "label": "성격",
    "rules": [{"label": "SW", "when": [{"field": "action", "op": "starts", "value": "SW"}]},
              {"label": "고객과실", "when": [{"field": "diag", "op": "in", "value": "C01|C02|C07"}]}],
    "else": "기타"}
   ```

   계산 문장 안에서 `CASE WHEN <규칙 1> THEN '…' WHEN <규칙 2> … ELSE '기타' END` 로 지어 다른 기준처럼
   묶는다. **첫 일치**가 이긴다 — 차례가 뜻이다(「SW 이면서 부품 교체」 는 SW). 조건은 목록 조건과 같은
   모양 · 같은 연산(`conditions.clause` 를 공개하고 `conditions.matches` 로 묶는다 — 같음 · 다름 · 포함 ·
   시작 · 목록 중 하나 · 비었다 · 숫자 비교 · 걸음 셋까지의 참조 너머 칸). 이어진 것 너머의 칸은 EXISTS
   라 기록마다 한 번이고 행이 불지 않는다. 셀의 기준 값은 성격 이름 그대로다(`{"nature": "SW"}`).
   - **상한과 거절은 계획에서**: 규칙 스물 · 규칙마다 조건 열 · 이름 40자, 빈 규칙 목록 · 조건 없는 규칙
     (모두를 가져가 뒤가 다 막힌다) · 모르는 칸 · 안 맞는 연산 · 같은 칸 · 같은 연산 두 번 · 이름 겹침 ·
     「기타」 와 같은 이름 · 주소나 기간 단위를 함께 둔 것. 오류는 「규칙 3 「NTF」: …」 처럼 어느 규칙인지
     말한다.
   - **성격 이름은 규칙마다 하나다.** 같은 성격의 규칙을 여러 줄로 적게 하면(제안의 「열린 물음」) 한 셀이
     두 규칙의 합집합이라 건 보기를 AND · 제외로 정확히 못 적는다(아래 4). 한 칸 안의 「또는」 은 `in`,
     칸을 가로지르는 「또는」 은 **차례**로 푼다 — 개발 DB 시연에서 「제품결함 = 불량 코드가 있다」 를 맨
     뒤에 두니 앞의 셋(SW · 고객과실 · NTF)을 뺀 나머지가 됐다(「결과」).
   - 기준 이름 · 보여 줄 이름(`label`)은 다른 기준과 같다. 여러 기준 · 거르기 · 분모 · 코호트와 함께 돈다.
     분모와는 **같은 규칙(지문)** 끼리만 짝짓는다(이름이 같아도 규칙이 다르면 같은 값이 아니다).
2. **규칙은 데이터다 — 지표 정의 안(JSON)에.** 고치는 사람은 지표 정의를 고치는 사람(시스템 관리자)이다.
   코드표 같은 축 타입(「성격 규칙」)으로 옮기는 것은 현업이 자주 고치게 될 때의 다음 걸음이다.
   **계획**(「계획 보기」 · `POST /api/metrics/plan` 의 `rules[]`)이 규칙마다 **맞는 기록**(`matched` — 앞
   규칙과 상관없이) · **붙인 기록**(`won` — 첫 일치) · 앞 규칙이 가져간 것(`taken_by`), **막힌 규칙**
   (`blocked` — 맞는데 한 건도 안 남음), **맞는 기록이 없는 규칙**, 「기타」 의 수와 몫(20% 넘으면 경고)을
   낸다. 원천을 한 번 훑으며 규칙마다 맞나(참 · 거짓)를 묶고 첫 일치는 파이썬에서 가른다. 20만 건을 넘으면
   셀 어림과 같은 무작위 표본에서 세고 그렇다고 말한다.
3. **규칙이 바뀌면 다시 센다 · 규칙 판을 남긴다.** 규칙(차례 포함)은 정의 JSON 이라 바뀌면 정의 지문
   (`spec_hash`)이 달라 다음 계산은 전량이다 — 지난 기간도 새 규칙으로. 증분(ADR 0024)은 규칙 조건의
   칸도 「다른 객체 너머」 로 따진다(`_foreign_addresses`) — 너머 칸을 보는 규칙은 그 객체가 바뀌면 기록의
   시각이 안 올라도 전량이다. 정의를 저장할 때 감사에 `rules: {기준: {from, to}}`(규칙 판의 지문)를 남기고,
   계산마다 `metric_runs.stats.rules`(→ `MetricRunOut.rules`)에 **그 계산이 쓴 규칙 판** — 지문 · 규칙 수 ·
   그 판을 저장한 때 · 사람 — 을 적는다. 「계산 기록」 탭의 「규칙 판」 열 · MCP `metric_runs` 가 그것을
   보인다. 보여 줄 이름만 바꾸면 같은 판이다.
4. **건 보기는 정확하게 — 목록 조건에 「제외」.** 규칙 k 의 셀은 「규칙 k 의 조건 AND NOT(규칙 1) AND … AND
   NOT(규칙 k-1)」, 기타는 「NOT(모든 규칙)」 이다. 목록 조건에 **제외 묶음**을 더했다:
   `nf<번호>.<칸>.<연산>=<값>` — 같은 번호끼리 AND 로 묶어 그 묶음에 맞는 것을 뺀다(`NOT coalesce(묶음,
   false)` — 칸이 비어 비교가 NULL 인 기록은 「안 맞음」 이라 남는다. `CASE WHEN` 이 NULL 을 「안 맞음」 으로
   넘기는 것과 같은 뜻이고, 맨 `NOT` 이면 그 기록이 양쪽 다에서 빠졌다).
   - **모양을 고른 까닭**: 조건 하나의 꼴(`칸.연산=값`)은 그대로 두고 앞머리만 달리하면 옛 주소 · 옛 저장된
     뷰 · 옛 클라이언트가 하나도 안 깨진다. 트리(`not(and(...))`)를 JSON 으로 받는 길은 주소에 붙여 넣을 수
     없고 화면의 칩으로 못 그린다. 저장된 뷰 · API 의 조건에는 `exclude`(묶음 번호, 0 은 보통 조건) 한 칸이
     붙고, MCP `objects_list` 의 조건도 `exclude` 를 받는다. 0건 진단은 묶음 하나를 한 조건으로 뺀다.
   - 화면의 조건 줄은 묶음을 테두리 안의 칩들(「제외 …」)로 세우고, 「조건 추가」 의 「넣을 곳」 에서 새 묶음 ·
     걸린 묶음을 고른다. 지표의 거르기 · 규칙의 조건에는 제외가 없다(규칙 안에 또 부정을 두면 건 보기가
     부정의 부정이 된다).
   - 건 보기의 목록 조건은 `{키: 값}` 이라 같은 칸 · 같은 연산이 둘이면 하나가 덮였다 — 규칙의 `diag in …`
     과 정의의 거르기 `diag in …` 이 같은 키면 덮인 쪽만큼 목록이 셀보다 많아진다. 이제 **둘 다 맞는 하나로
     합친다**(`query._Conds`): 범위는 좁은 쪽, `in` 은 겹치는 값, `다름` 둘은 제외 묶음 하나(`nf.<칸>.in=A|B`).
     합칠 수 없는 것(여러 값 칸 · 이어진 것 너머 · 「포함」 둘)은 `partial` — 「≈」 라고 말한다. 같은 덮임이
     기간 범위와 거르기 사이에도 있었다(거르기의 `received gte 2026-01-15` 를 기간 셀의 `gte 2026-01-01` 이
     덮어 1월 1~14일이 섞였다) — 같은 합치기로 고쳤다.
5. **구성비 보기.** 표(`GET …/values?composition=<기준>`)는 셀마다 그 기준의 값들 사이의 몫(%)을 —
   나머지 칸(기간 · 코호트 · 다른 기준)이 같은 셀끼리 합 100. 추이(`…/series?split=<기준>&composition=true`)
   는 점마다 그 기간의 선들 사이의 몫(그린 선이 상한에서 잘려도 모든 값의 합으로). 화면은 표 탭의
   「구성비(%)」 고르개(여러 기준이면 어느 기준의 몫인지)와 추이 탭의 「구성비(%) — 기간마다 100%」(100% 쌓은
   영역 그림 + 기간 x 값의 표, 칸마다 그 기록으로).
   - **뜻**: 건수 · 합계(· 조건 비율의 조건 건수)의 몫이다. 평균 · 최소 · 최대는 더할 수 없어 몫이 뜻이
     없다 — 422. 비율(분모로 나눈 값)의 몫은 내지 않는다: 분모가 그 기준과 짝이면 값마다 분모가 달라 비율끼리의
     몫은 뜻이 없고, 짝이 아니면 분모가 같아 분자의 몫과 같다. 그래서 화면은 구성비를 켜면 「비율로 보기」 를
     잠근다. 여러 값 기준이면 몫은 「나온 횟수」 의 몫이다(겹침 — 머리가 말한다).
6. **분석 · 경보 · MCP 는 기준 이름으로.** 규칙 기준은 보통 기준과 같은 `Dim`(값 종류 `rule`)이라 파레토(두
   기간 비교의 수정 잔차) · 변화점 값마다 훑기 · 경보(`d.nature=SW` · `by=nature`)가 그대로 걸리고 근거
   (`drill`)는 위 4 의 조건이다. MCP `metric_define` 이 규칙 기준을 받고 계획의 `rules[]` 를 돌려주며,
   `metric_query` 는 `composition` 을 받는다. 안내(GUIDE `metrics` · `find`, README)에 ⑧ 의 예를 적었다.
7. **이번에 안 하는 것.** 규칙을 기계가 배우는 분류(모형 학습), 기록마다 성격 칸을 써 넣기(셀 위에서만
   붙인다 — 원천을 고치지 않는다), 코드표 축 타입으로 옮기기, 칸을 가로지르는 「또는」(같은 성격 여러 줄).

## 대안

### 원천에서 성격 칸을 채워 온다

규칙이 원천 시스템의 코드에 숨고, 규칙이 바뀐 날 지난 기록은 옛 규칙의 값으로 남는다. 「이 구성비가 왜
지난달과 다르냐」 에 규칙이 바뀌어서인지 실제로 바뀌어서인지 가를 수 없다.

### AI 가 기록을 받아 분류한다

ADR 0014 이 버린 길과 같다 — 같은 물음에 매번 다른 분류, 200만 건을 토큰으로.

### 성격을 객체의 칸으로 저장하고 일괄 고치기로 채운다

일괄 고치기(`bulk_edit`)로 한 번은 된다. 그러나 새 기록이 들어올 때마다 다시 돌려야 하고, 규칙이
바뀌면 누가 언제 무엇으로 바꿨는지가 기록마다 흩어진다.

### 건 보기를 「≈(partial)」 로 넘긴다(제안의 4)

목록 조건이 AND 뿐이라 「앞 규칙에 안 맞음」 을 못 적으니, 겹칠 수 있으면 「목록이 더 많을 수 있다」 고만
말하는 길이었다. 규칙은 거의 늘 겹친다(SW 이면서 부품 교체) — 그러면 거의 모든 셀이 「≈」 이고, 사람은
「N건 보기」 를 믿지 않게 된다. 사용자가 정확한 쪽을 골랐다(2026-10-10).

### 건 보기를 「지표 규칙 k 에 든다」 같은 특수 조건으로

`rule.<지표>.<기준>=SW` 처럼 계산과 같은 `CASE` 를 목록에서 다시 짓는 조건이면 겹침 · 같은 성격 여러 줄도
정확하다. 하지만 목록의 조건 줄에 「무엇으로 걸렀는지」 가 안 보이고(규칙을 고치면 같은 주소가 다른 목록이
된다), 지표를 지우면 저장된 뷰가 깨진다. 제외 묶음은 조건이 그대로 보인다.

## 정한 것(제안의 「열린 물음」)

- 규칙을 고치는 사람 — **지표 정의를 고칠 수 있는 사람(시스템 관리자), 정의 안(JSON)에.** 축 타입은 나중.
- 규칙 판을 보일 자리 — 「계산 기록」 의 「규칙 판」 열(지문 · 수정한 때 · 사람)과 감사의 `rules`.
- 성격 하나에 조건 묶음이 여럿(OR) — **같은 성격 여러 줄은 막는다**(정확한 건 보기). 한 칸 안은 `in`,
  칸을 가로지르면 차례로.
