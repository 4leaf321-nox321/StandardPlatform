# 0015. 규칙 분류 — 조건 목록의 첫 일치로 값을 붙이는 기준

- 상태: 제안(초안 — 구현 전에 사람이 규칙의 자리와 고치는 사람을 정한다)
- 날짜: 2026-10-03
- 관련: [ADR 0013](0013-지표.md)(지표 — 기준 · 건 보기), [ADR 0014](0014-분석.md)(분석 — 파레토 두 기간
  비교가 구성비 추이를 본다)

## 배경

열 가지 물음의 ⑧ 은 「성격(제품결함 · NTF · 고객과실 · SW)으로 분류한 뒤 그 **구성비 추이**」 다. 통계가
아니라 **분류**다 — 진단 코드 · 조치 코드 · 부품 교체 여부 같은 칸을 보고 사람이 정한 규칙으로 성격을
붙인다. 예:

| 차례 | 성격 | 조건(모두 맞으면) |
| --- | --- | --- |
| 1 | SW | 조치 코드가 `SW*` 로 시작 |
| 2 | 고객과실 | 진단 코드가 `C01` · `C02` · `C07` 중 하나 |
| 3 | NTF | 교체 부품이 비었고 조치 코드가 `N00` |
| 4 | 제품결함 | 교체 부품이 있다 |
| — | 기타 | 어느 규칙에도 안 맞음 |

지금은 이것을 AI 가 기록을 받아 분류하거나, 원천에서 성격 칸을 미리 채워 와야 한다. 앞의 것은 매번 다른
답이 나오고(ADR 0014 이 버린 길), 뒤의 것은 규칙이 원천 시스템의 코드 속에 숨어 아무도 못 본다. 규칙이
바뀌면(「C07 은 이제 고객과실이 아니다」) 지난 구성비를 다시 셀 길도 없다.

구성비 · 추이 자체는 이미 된다 — 성격이 **기준**이기만 하면 파레토의 몫 · 기간별 추이 · 두 기간 비교
(수정 잔차, ADR 0014)가 그대로 답한다. 빠진 것은 **규칙으로 값을 붙이는 기준** 하나다.

## 결정(제안)

1. **지표의 새 기준 종류 「규칙」.** 정의의 기준에 주소 대신 규칙 목록을 둔다.

   ```json
   {"name": "nature",
    "rules": [{"label": "SW", "when": [{"field": "properties.action", "op": "starts", "value": "SW"}]},
              {"label": "고객과실", "when": [{"field": "properties.diag", "op": "in", "value": "C01|C02|C07"}]}],
    "else": "기타"}
   ```

   계산 문장 안에서 `CASE WHEN <규칙 1> THEN '…' WHEN <규칙 2> … ELSE '기타' END` 로 지어 다른 기준처럼
   묶는다. **첫 일치**가 이긴다 — 차례가 뜻이다(「SW 이면서 부품 교체」 는 SW). 조건은 목록 조건과 같은
   모양(`conditions._clause` 를 공개해 쓴다) — 칸 · 연산 · 값을 따로 배우지 않는다.
2. **규칙은 데이터다.** 규칙을 지표 정의 안(JSON)에 두는 것이 첫걸음이다 — 계획(「계획 보기」)이 규칙마다
   맞는 기록 수 · 겹침(앞 규칙에 먹혀 한 건도 안 남는 규칙) · 기타의 몫을 말한다. 규칙을 현업이 자주
   고치면 다음 걸음으로 **코드표 같은 축 타입**(「성격 규칙」 — 차례 · 성격 · 조건)에 두고 지표가 그것을
   읽는다(감사 이력 · 권한이 그대로 붙는다). 어느 쪽으로 갈지는 고치는 사람이 정한다(아래 「열린 물음」).
3. **규칙이 바뀌면 다시 센다.** 정의가 바뀌면 지금처럼 전부 다시 센다(ADR 0013) — 지난 기간도 새
   규칙으로. 실행(`metric_runs.stats`)에 규칙의 지문(해시)을 남겨 「이 구성비는 어느 규칙으로 셌나」 를
   답한다.
4. **건 보기.** 규칙 k 의 셀은 「규칙 k 의 조건 + 앞 규칙들에 안 맞음」 이다. 목록 조건은 AND 뿐이라
   「앞 규칙에 안 맞음(NOT (A AND B))」 을 못 적는다 — 앞 규칙과 겹치지 않는 규칙이면 그 조건만으로
   정확하고, 겹칠 수 있으면 `partial` 을 붙여 「목록이 더 많을 수 있다」 고 말한다(지금의 「≈」 와 같다).
   기타는 늘 `partial`.
5. **이번에 안 하는 것.** 규칙을 기계가 배우는 분류(모형 학습), 기록마다 성격 칸을 써 넣기(셀 위에서만
   붙인다 — 원천을 고치지 않는다).

## 대안

### 원천에서 성격 칸을 채워 온다

규칙이 원천 시스템의 코드에 숨고, 규칙이 바뀐 날 지난 기록은 옛 규칙의 값으로 남는다. 「이 구성비가 왜
지난달과 다르냐」 에 규칙이 바뀌어서인지 실제로 바뀌어서인지 가를 수 없다.

### AI 가 기록을 받아 분류한다

ADR 0014 이 버린 길과 같다 — 같은 물음에 매번 다른 분류, 200만 건을 토큰으로.

### 성격을 객체의 칸으로 저장하고 일괄 고치기로 채운다

일괄 고치기(`bulk_edit`)로 한 번은 된다. 그러나 새 기록이 들어올 때마다 다시 돌려야 하고, 규칙이
바뀌면 누가 언제 무엇으로 바꿨는지가 기록마다 흩어진다.

## 열린 물음(구현 전에 정할 것)

- 규칙을 고치는 사람이 시스템 관리자뿐인가, 품질 부서인가 — 정의 안(JSON) 대 축 타입.
- 규칙의 차례가 바뀌면 지난 구성비도 바뀐다 — 「규칙 판」 을 사람에게 보여 줄 자리(지표 상세의 「계산
  기록」 에 지문).
- 성격 하나에 조건 묶음이 여럿(OR)이면 — 같은 성격의 규칙을 여러 줄로 적는다(첫 일치라 OR 이 된다).
