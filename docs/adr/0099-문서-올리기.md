# 0099. 문서 올리기 — 로컬 마크다운 · 그림을 파일 그대로, 대조는 sha256 으로

- 상태: 채택(2026-11-27 구현 · 시험) · 보강 [ADR 0100](0100-키트의-적용은-대화의-확인-뒤에.md)(묶음 적용 · 되돌리기도

    `document_check`,
    `docx_extract` 의 다음 할 일, `AGENTS.md` 「Word 문서를 문서 속성으로」

## 배경

운영에 Word 569건(약 270만 자)을 문서 속성으로 넣어야 한다. 그림은 `attachment_upload_prepare` 가 돌려주는
`curl` 로 올라가 바이트가 모델을 안 거치는데, 본문은 MCP `document_write` 의 **도구 인자**다 — 모델이
본문을 글자 그대로 적어야 해서 토큰이 많이 들고 옮기다 틀린다. 쓴 것을 대조하려면 `document_read` 로
본문 전체를 다시 받아야 했다.

## 결정

### 1. 키트가 파일을 묶어 올리고, 사람이 「좋다」 하면 AI 가 적용한다

키트의 `document_push(work, …)` 가 마크다운과 그 그림을 **파일 그대로** zip 하나(목록 `manifest.json` ·
마크다운 · 그림)로 묶어 플랫폼 작업 「문서 올리기」(`documents_push`)로 올린다. 플랫폼이 **계획**을 세운다
(문서마다 새로 · 고침 · 그대로 · 오류, 판 · 글자 수 · 그림 수 — 아무것도 안 바꾼다). AI 가 그 계획을
사람에게 보이고, **사람이 대화에서 「좋다 · 적용해」 라고 하면** 키트의 `document_apply(work)` 가 작업마다
적용하고 곧바로 대조한다(2). 화면에서 보고 싶으면 그 플랫폼 「작업」 의 「적용」 도 된다(그때는
`document_check`).

- **처음에는 키트의 도구 가운데 적용하는 것이 이것뿐이었다**(2026-11-27 사용자 결정) — 문서는 판이 남아 사람이
  옛 판으로 되돌릴 수 있고, 569건을 화면에서 한 건씩 누를 일도 아니다. 같은 날 묶음 적용 · 되돌리기도 같은
  규칙이 됐다(ADR 0100). 사람의 말 없이 · 짐작으로 · 오류가 있는 계획에 부르지 않는다(도구 설명 ·
  지시서). 적용은 그 계획을 세운 토큰의 주인으로 가고(계획을 본 사람이 적용한다 — JOBS-12), 같은 계획을 두 번
  넣지 않는다(JOBS-22 — 화면에서 먼저 적용한 작업은 `already` 로 건너뛴다).
- 한 건이면 `type_slug` · `object_id` · `key` · `path` · `base_revision`, 여러 건이면 목록 파일
  (`manifest` — 작업 폴더의 JSON). 크면(400MB · 1000건) 키트가 나눠 작업 여럿으로 올린다.
- **그림** — 본문의 `![캡션](media/image3.png?w=60)` 이 가리키는 파일을 함께 싣는다(내용 주소
  `img/<sha256>` 로 한 번씩). 적용하면 그 문서 칸에 붙이고 그림 줄을 `photo:<첨부 id>` 로 바꿔 쓴다.
  **같은 그림(sha256)이 그 문서 칸에 이미 붙어 있으면 그것을 쓴다** — 다시 올려도 첨부가 늘지 않는다.
  새 그림은 적용할 때 붙는다(계획은 아무것도 바꾸지 않는다).
- **판** — `base_revision` 은 읽고 고친 판. 비우면 올릴 때의 지금 판이고, 그 사이 오르면 적용이
  거절한다(지문). 적힌 판과 지금 판이 다르면 그 줄이 오류다.
- **한 줄이라도 오류면 적용하지 않는다**(일괄 입력 · 묶음과 같다). 사진 일괄 업로드는 「붙는 것은
  붙는다」 인데, 문서는 판이 남고 사람이 쓴 것을 덮을 수 있어서 계획 전체가 깨끗할 때만 쓴다 — 오류 줄은
  목록에서 빼거나 고쳐 다시 올린다.
- 키트가 먼저 막는 것(플랫폼에 아무것도 안 보낸다): 없는 파일 · 작업 폴더 밖 · 100만 자 넘음 · **개인
  정보 꼴**(묶음의 문서 본문과 같은 검사, ADR 0097) · 없는 그림 · 같은 칸 둘. 플랫폼이 다시 보는 것:
  없는 객체 · 문서 칸 아님 · 권한 · 원천 잠금 · 판 · 이미지 아님 · 같은 칸 둘(키트를 안 거친 zip 도 믿지
  않는다).
- 판의 「어디서」 는 「문서 올리기」 — 화면 · MCP 의 쓰기와 가른다.

### 2. 대조는 본문 없이 — sha256

- 문서의 답에 **`sha256`**(본문의 UTF-8 · 줄바꿈 `\n`)을 싣고, **`GET …/documents/{key}?body=false`**
  (MCP `document_read(body=False)`)는 본문 없이 판 · 글자 수 · sha256 만 준다. `document_write` 의 답에도
  sha256 이 온다.
- 적용한 작업의 결과에 문서마다 새 판 · 글자 수 · sha256 · 그림마다 붙은 첨부 id 가 남는다.
- 키트의 **`document_check(work)`** 는 서버의 판 · sha256 과 그 문서 칸의 그림(sha256 → 첨부 id)만 받아, 로컬
  초안을 플랫폼이 쓰는 꼴(그림 줄 → `photo:<id>`)로 바꾼 것의 sha256 과 견준다 — `same` · `different`(적용
  전 · 그 뒤 누가 고침 · 그림이 안 붙음) · `not_written` · `local_changed`(올린 뒤 로컬 파일이 바뀜).

## 대안 — 버린 것

- **사람이 화면에서만 적용**(키트의 다른 도구처럼) — 처음에는 이렇게 지었다. 사용자가 「대화에서 좋다 하면 AI
  가 바로 쓰게」 로 정했다(2026-11-27) — 화면 단추는 남는다.
- **플랫폼의 한 번 쓰는 업로드 표**(`document_upload_prepare` → `curl` 이 본문을 PUT) — 그림과 같은 길이라
  키트가 없어도 되지만, 미리 보기 · 사람의 확정이 없는 쓰기다(그림은 붙여도 본문에 안 보이지만 본문은
  바로 판이 된다). 그림 줄을 `photo:<id>` 로 바꾸는 일도 모델에게 남는다. 키트가 있는 곳(정제 작업을 하는
  PC)이 곧 파일이 있는 곳이라 키트의 길로 한다. 키트가 없는 클라이언트는 지금처럼 `document_write` 로
  한 편씩(짧은 본문) — 필요해지면 그때 둔다.
- **묶음의 문서 본문(`_documents`, ADR 0097)에 그림을 더하기** — 묶음은 JSON 이라 그림 바이트를 못 싣고,
  식별자(`key`)로 객체를 찾는다(식별자 없는 타입 · 객체 id 로 아는 경우가 막힌다). 실행 폴더 · 정의 확정을
  거치지 않는 「문서만」 일에는 무겁다. 행과 함께 본문을 넣을 때는 그대로 묶음의 길이다.
- **올릴 때 그림을 먼저 붙이기** — 미리 보기가 무언가를 바꾸게 된다(적용하지 않으면 안 쓰인 첨부가
  남는다). 그림은 zip 안에서 기다렸다가 적용할 때 붙는다.
