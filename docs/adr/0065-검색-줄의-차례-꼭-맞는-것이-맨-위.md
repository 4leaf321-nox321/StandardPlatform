# 0065. 검색 줄의 차례 — 꼭 맞는 것이 맨 위

- 상태: 채택(2026-11-09 구현)
  - 차례 식: `objects.services.relevance_order`, 같은 판정의 파이썬 쪽 `is_exact`
  - 통합 검색: `search.services.search`(기록 타입으로 좁힌 찾기는 이름 순 그대로), 응답 줄의 `exact`
    (`SearchHitOut.exact`), 화면의 「꼭 맞음」 표
  - 이름 풀이의 「포함」 후보: `resolve.by_name`(기록 타입이면 이름 순 그대로)
  - MCP `search` 설명
- 날짜: 2026-11-09
- 관련: [ADR 0057](0057-검색어는-낱말로-나눠-찾는다.md)(낱말로 나눠 찾기), [ADR 0010](0010-규모-참조-색인.md)(찾기의 색인)

## 배경

통합 검색은 찾은 줄을 **이름 가나다 순**으로 세웠다. 그래서 「BT-2041」 을 친 사람의 그 줄이 「BT-20411」 ·
「BT-20412」 … 사이에 묻혔다. 사람은 눈으로 찾으면 되지만, 바깥 AI 가 쓰는 MCP `search` 는 기본 20줄만 받는다
— 꼭 맞는 줄이 20줄 밖이면 AI 는 「없다」 고 답한다. 이름 풀이의 「포함」 후보도 이름 순으로 200개를 받아 앞 20개만
보였다.

NVIDIA Auto Ontology 와 견준 조사(2026-11-07, SP 개선 목록 「다음」)에서 나왔다. AO 는 찾은 줄을 「이름이 모든
낱말을 담음 → 동의어 → 짧은 이름」 순으로 세우고, 상한으로 자르기 전에 DB 에서 같은 순서로 정렬한다.

## 결정

1. **네 자리로 세운다** — 0 꼭 맞음(이름 · 식별자는 대소문자 무시, 별칭은 비교키) → 1 이름 · 식별자가 그 말로
   시작 → 2 이름에 낱말이 모두 듦 → 3 식별자 · 별칭에만 듦. 같은 자리 안에서는 **짧은 이름부터**, 그다음
   이름 · id(쪽을 넘겨도 차례가 같다 — 꼭 맞는 줄을 첫 쪽에만 따로 얹지 않는 까닭).
2. **꼭 맞는 줄은 표시한다** — 응답 줄의 `exact`, 화면의 「꼭 맞음」. 차례 식과 표시가 같은 판정(`is_exact`)을
   쓴다 — 따로 정하면 맨 위의 줄에 표시가 없거나 표시가 중간에 선다.
3. **걸러진 줄에만 계산한다** — `containing_ids` 로 좁힌 뒤의 줄마다 식 몇 개다. 별칭은 그 객체의 것만 객체 id
   색인으로 짚는다. 식별자는 비교키 식(NFKC · 공백 정리) 대신 대소문자만 무시한다 — 차례를 매기는 데는 그것으로
   족하고, 비교키 식은 줄마다 비싸다(아래 결과).
4. **기록 타입으로 좁힌 찾기 · 풀이는 이름 순 그대로** — 걸린 줄이 수백만일 수 있어, 줄마다 식을 계산하는 값을
   재 보기 전에는 바꾸지 않는다(꼭 맞음 표시는 한다). 섞어 찾을 때는 기록이 줄에 안 섞이므로 해당 없다.

## 결과

2,000만 건 실측 DB(`standardplatform_big_scale` — 기록 2,000만 + 축 객체 약 1.3만)에서 고치기 전(이름 순)과 후를
같은 질의로 견줬다(5번의 가운데 값, ms).

| 찾은 말 | 범위 | 걸린 줄 | 전 | 후 | 맨 위(후) |
| --- | --- | ---: | ---: | ---: | --- |
| SM-X00879 | 섞어 | 2 | 68 | 68 | **SM-X00879**(꼭 맞음) · SM-X00879_KOR_01 |
| 과제 30 | 섞어 | 199 | 26 | 28 | **과제 30**(꼭 맞음) · 과제 300 · 과제 301 |
| 과제 | 섞어 | 5,000 | 80 | 75 | 과제 1 · 과제 2 · 과제 3(전에는 과제 1 · 과제 10 · 과제 100) |
| SM-X02 | 판매 모델 | 1,000 | 31 | 33 | |
| KOR | 판매 모델 | 6,000 | 58 | 72 | |
| 풀이 KOR_01 | 판매 모델 | 200 후보 | 44 | 61 | |

- 늘어난 몫은 걸린 줄 수에 비례한다 — 6,000줄에 약 14ms. 식별자를 비교키 식으로 견주면 같은 질의가 약 25ms 더
  들었다(그래서 3).
- 「SM-X」(8,001줄) 3.6초 · 「C0000」 1.2초는 **고치기 전에도 같았다** — 차례가 아니라 찾기 자체(기록까지 훑는
  포함 조건)의 몫이다. 따로 볼 일이다.

## 남은 것

- 기록 타입으로 좁힌 찾기에도 차례를 줄지 — 걸린 줄이 많은 질의로 재 본 뒤.
- 같은 자리 · 같은 길이의 줄은 이름 차례라 DB 의 정렬 규칙을 따른다(en_US 면 한글 차례가 흐트러진다 — 운영 DB 의
  정렬 규칙은 아직 모른다, 2026-11-08 논의).
