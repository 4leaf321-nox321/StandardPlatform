## 배경

AI 가 문서마다 정의를 만들면 같은 개념이 두 타입에 갈린다 — `협력사` 300건과 `공급사` 1,200건. 객체 합치기는
같은 타입끼리만 되고(OBJECTS-52 — 다른 타입이면 그 객체를 가리키던 칸의 정의와 어긋난다), 다른 타입으로 옮기는
길이 없었다. 내보내서 다시 넣고 지우면 관계 · 별칭 · 이력 · 참조가 끊긴다.

## 결정

### 1. 객체 id 를 그대로 둔 채 타입을 바꾼다

참조 칸 · 관계 · 첨부 · 문서 · 이력은 객체 id 로 이어져 있어 그대로 따라온다. 바꾸는 것은 타입을 따로 쥔 자리뿐이다:
객체(`type_id` · 값의 키 · 사람이 수정한 칸 표시), 별칭(`type_id` — 타입 안에서 유일하다), 원 표와 맺은 관계의 끝
(`object_links` 의 타입 slug), 뜻으로 찾기(조각 · 표시를 지워 다시 계산), 못 찾은 말(대상 범위로). 참조 색인 ·
타입별 수는 트리거가 `type_id` 변경을 따라간다. 지운 객체까지 옮긴다 — 원 타입이 비어야 영구 삭제 없이 지워진다.
객체의 `updated_at` 은 그대로다.

### 2. 칸 대응 — 사람이 줄마다 본다

원 타입의 속성마다 `same`(대상의 같은 키) · `map`(대상의 다른 키 — 같은 이름이면 고른다) · `create`(대상에 정의를
베껴 새로) · `drop`(버림). 적지 않으면 같은 키 → 같은 이름(모양이 같을 때) → 새로 만들기 차례다. **버림은 사람이
`mapping` 에 null 을 적을 때만**이다. 모양이 다르면(종류 · 단위 · 값 하나/여러 값 · 가리키는 타입) 막는다 — 값을
바꾸는 일은 종류 변경(ADR 0007)이 계획 · 대체 값과 함께 한다. 선택 값이면 원 타입에서 쓴 값이 대상의 선택 값에
다 있어야 한다. 문서 · 파일 속성은 같은 키로만(첨부 · 판 표가 키를 쥔다). 두 원 칸이 같은 대상 칸으로 가면 막는다.

### 3. 겹치는 객체는 병합으로

대상에 같은 식별자(대상의 식별자 범위 — 전사 · 부서)의 객체가 있으면 막는다. 같은 것이면 `merge_duplicates` —
옮긴 뒤(이제 같은 타입이다) 대상의 객체로 **병합**한다(객체 병합과 같은 함수: 참조 · 관계 · 별칭이 따라가고
옮긴 쪽은 `merged_into` 로 남는다). 병합할 짝끼리 겹치는 별칭은 옮길 쪽을 버린다. 서로 다른 객체가 같은 별칭을
쓰거나, 대상의 유일 칸에 같은 값이 있거나, 대상의 식별자 정책(필수 · 없음)에 안 맞으면 막는다.

### 4. 정의를 함께 맞춘다 · 남는 것은 알린다

- 바꾼다: 대상의 새 속성, 이 타입을 가리키던 참조 속성의 대상(→ 대상 타입), 관계 종류의 끝(대상을 더한다 —
  원 타입은 남겨 둔다).
- 알린다: 원 타입에 걸린 저장된 뷰 · 지표 · 장표 틀 · 뜻으로 찾기 대상 · 웹훅(원 타입에 남는다), 대상의 필수
  칸이 빌 객체, 개정 칸이 다른 계보, 공개 타입(원 타입이면 `accept_core`).
- 막는다: 키 변경과 같은 것(원천 잠금 · 원 표 · 확장이 쓰는 타입 · 그 타입을 쥔 작업 — 두 타입 모두), 원 타입에
  넣는 데이터 소스(다음 동기화가 다시 만든다).
- 원 타입은 **빈 채로** 남는다 — 정리는 삭제 미리 보기로. 한 번에 지우지 않는 까닭은 뷰 · 지표 같은 남은 것을
  사람이 먼저 보게 하려는 것이다.

### 5. 이력 · 큰 타입

- 감사 기록 하나(`ontology.type.move`, `from` · `to` · `keys`)를 대상 타입에 남긴다. 이력은 옮기기 전 기록(감사
  기록의 이름표가 `<원 타입>:…`)을 그 대응으로 대상의 키로 읽는다 — 키 변경(ADR 0093)의 번역과 겹쳐 쓴다.
- 옮길 객체가 2만 건을 넘으면 ONTOLOGY-106 — 작업으로 계획하고 지문이 같을 때만 적용한다. 5천 건씩 id 차례로.

### 6. 보강(v0.4.105) — 옮긴 객체의 옛 주소

`/o/<원 타입>/<id>` 는 「객체를 찾을 수 없습니다」 로 끊겼다 — 즐겨찾기 · 알림 · 문서에 붙인 링크가 깨진다. 그 타입에서
옮긴 일이 있고(감사 기록) 볼 수 있는 객체면 404 에 어디로 갔는지(`moved_to` · `object_id`, OBJECTS-160)를 싣고, 화면은
새 주소로 간다(객체는 id 로 하나뿐이다 — 병합과 같다). 옮긴 뒤 병합됐으면 이긴 쪽으로. 타입을 잘못 적은 주소까지 넘기지는
않는다.

## 대안 — 버린 것

- **값 변환까지(모양이 다른 칸)** — 종류 변경이 대체 값 · 변환할 수 없는 값을 사람과 정한다. 두 길을 한 창에
  섞으면 계획이 너무 커진다. 먼저 맞추게 한다.
- **원 타입을 지우기까지** — 원 타입에 걸린 뷰 · 지표 · 데이터 소스를 사람이 먼저 보게 한다. 삭제는 기존 미리
  보기로.
- **일부 객체만 옮기기** — 같은 개념의 두 타입을 합치는 것이 먼저다. 조건으로 골라 옮기기는 필요가 생기면.
