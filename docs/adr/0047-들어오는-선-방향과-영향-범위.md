## 배경

「재귀 질의 · 질의 언어 · 받은 엣지 따라가기가 되나」 를 물었을 때(2026-10-30) 받은 선을 따라가는 길을
표로 정리했다. 비어 있던 곳:

| 길 | 받은 선 | 깊이 | 한계 |
| --- | --- | --- | --- |
| `object_references` | 나를 가리키는 참조 칸 · 관계 | 한 걸음 | |
| 트리 「위 전부」 | 부모 쪽 | 20단 | 트리로 정한 관계만 |
| BOM 「어디에 쓰였나」 | 수량 관계 거꾸로 | 끝까지 | 수량 관계만 |
| 계보 「위(원천) 사슬」 | 원천 쪽 | 20단 | 계보 관계만 |
| `graph_neighbors` | 들어오는 선 · 나가는 선 **함께** | 몇 단계 | 받은 것만 고르지 못함 |
| SPARQL `^관계+` | 거꾸로 | 끝까지 | 객체 5만 개 안에서만 |

**아무 관계 종류를 골라 「이것에 기대는 것 전부」 를 끝까지 거꾸로 따라가는 일**이 큰 자료에서는 안 됐다.
그때 둘을 제안했다 — ① `graph_neighbors` 에 방향, ② 「거꾸로 전부(영향 범위)」 도구. 사용자 답(2026-11-02):
「제안 주고 답 못받은거는, 적용하는게 부작용없이 할만하다 싶으면 적용해줘」. 둘 다 **읽기만** 하고 기존
응답의 기본값을 바꾸지 않으므로 넣었다.

## 결정

### 1. 이웃의 방향(`direction` — `both` · `in` · `out`)

- 이웃 API(`GET /api/graph/neighborhood`) · MCP `graph_neighbors` · 화면 탐색 칸의 「방향」(양쪽 · 들어오는
  선만 · 나가는 선만, 주소 `dir=`). 기본은 `both` — 이전과 같다.
- **단계마다 그 노드에서 본 방향**이다. 관계(`object_relations`) · 원 표 링크(`object_links`) · 참조 칸
  (`object_refs`) 세 갈래에 같은 뜻으로 건다. 참조 칸은 칸을 가진 객체 → 가리키는 객체가 나가는 선이다.
- **방향 없는 관계 종류**(`directed=false`)는 어느 쪽으로 보든 잇는다 — 「이웃함」 에 들어오고 나가는 쪽이
  없다.
- 이미 실린 노드끼리의 선(`induced_edges`)은 방향과 상관없이 긋는다 — 그림에 있는 두 노드 사이의 선을
  숨기면 「관계없음」 으로 읽힌다.
- 나를 가리키는 기록의 수(`log_counts`)는 들어오는 선이라 `out` 에서는 싣지 않는다. 노드의 「더 있음」
  (`truncated`)은 관계 · 타입 거르기처럼 다른 방향의 선도 센다 — 사람이 고른 거르기를 잊고 「이웃이 하나뿐」
  으로 읽지 않게.

### 2. 영향 범위(`GET /api/graph/reach` · MCP `graph_reach`)

- 고른 선의 종류(`relations` — 관계 slug · `ref:<타입>.<칸>`, 꼭)를 한 방향(`in` 기본 · `out`)으로
  **20단까지**. 없는 종류는 422 와 `details.unknown`.
- **고리** — 한 번 닿은 객체는 다시 펼치지 않는다. 노드마다 처음 닿은 단계(`depth` — 가장 가까운 것)와 그
  길 하나(`parent` · `via`)를 적는다. 다이아몬드(같은 부품을 두 어셈블리가 씀)는 길 하나만 남는다.
- 응답은 노드와 **타입별 수(`by_type`) · 단계별 수(`levels`)**. 선 전부는 싣지 않는다 — 큰 범위에서는
  수가 답이고, 길은 `parent` 사슬로 읽는다.
- **상한** — 닿은 객체 `limit`(기본 2천, 최대 2만; MCP 는 기본 300 — AI 의 맥락), 한 단계에 읽는 선은 남은
  자리만큼(최대 6만). 닿으면 `truncated` — 「이게 전부」 가 아니다. 더 갈 곳이 없어 멈추면 `exhausted`.
- **보이지 않거나 지운 객체에서는 멈춘다** — 이웃 그림과 같은 규칙. 그 너머를 따라가면 안 보이는 객체가
  길로 드러난다. 시작점이 안 보이면 404(없는 것과 같은 말).
- **기준일**(`as_of`, 비우면 오늘) — 관계는 그날 살아 있는 선만(`edges.alive`). 참조 칸은 기간이 없다.
- 원 표(부서 · 계정)와 잇는 관계는 따라가지 않는다 — 그 끝은 객체가 아니다.
- **질의는 닿은 객체마다 색인을 찾게 묶는다**(`unnest` + LATERAL, 객체 500개씩). 관계는 (끝, 관계) 색인,
  참조 칸은 (도착, 칸) 색인 · 나가는 쪽은 기본 키(출발, 칸, 도착)다.

## 대안 — 버린 것

- **재귀 CTE 한 질의** — 관계와 참조 칸을 `UNION` 한 선 위에서 돌리면 질의는 하나지만, 고리 막기(들른 id
  배열)와 상한(닿은 수 · 단계마다 읽는 수)을 SQL 안에서 같이 걸기가 어렵다. 인기 모델은 기록 100만 건이
  가리켜 상한 없는 한 단계가 곧 사고다. 단계마다 파이썬에서 상한을 거는 쪽이 「잘렸다고 말한다」 를 지키기
  쉽다. 20단이면 질의는 최대 20 × 종류 갈래 수다.
- **트리 「위 전부」 를 아무 관계에나 열기** — 트리 함수는 관계 하나 · 부모 끝 하나를 전제로 롤업 · 계층
  축이 함께 쓴다. 고리가 있는 관계를 거기 넣으면 그 전제가 깨진다.
- **SPARQL 로 안내** — `^관계+` 는 객체 5만 개 안에서만 돈다(기록 타입은 기본으로 빠진다).
- **화면에 영향 범위 판** — 이번에는 API · MCP 만. 화면은 탐색의 「방향」 으로 한 단계씩 본다. 끝까지의 결과를
  그림으로 보이려면 정적 그리기(ADR 0045)에 「한 방향으로」 를 더하는 쪽이 맞아 보인다(다음).

## 결과 — 실측(2026-11-02, `standardplatform_big_scale` 2,000만 건)

처음 읽는 모델(기록 3,333건 — 캐시가 식은 쪽):

| 물음 | 첫 번째 | 두 번째 |
| --- | --- | --- |
| ← 서비스 기록, 상한 2천(잘림) | 0.69초 | 0.18초 |
| ← 서비스 기록, 상한 2만(전부 — 끝까지) | 1.1초 | 0.06초 |

기록 100만 건이 가리키는 모델(고치기 전 측정으로 캐시가 데워진 뒤):

| 물음 | 시간 |
| --- | --- |
| ← 서비스 기록, 상한 2천 / 2만(잘림) | 0.15 ~ 0.26초 / 0.6초 |
| ← 기준정보 종류만(0건) | 0.007 ~ 0.013초 |
| 경로 전체(응답까지) — 2천 / 2만 | 0.15 ~ 0.35초 / 1.5 ~ 1.7초(응답 0.5 / 5.2MB) |
| 이웃의 방향 `both` · `in` · `out` | 3 ~ 7ms |

시험 — `tests/api/test_graph_reach.py`(사슬 · 나가는 쪽 · 고리 · 방향 없는 종류 · 참조 칸 · 깊이와 상한 ·
기준일 · 없는 종류 · 남의 부서에서 멈춤 · 이웃의 방향 세 갈래), MCP `test_영향_범위와_이웃의_방향이_그대로_건너간다`,
화면 `방향이 주소에서 이웃 요청으로 실리고…`.

### 실측으로 드러난 함정

- **상한 2천에 질의마다 6만 줄을 읽었다** — 처음 짠 것은 선 상한(6만)만 걸어, 기록 100만 건 모델에서 상한
  2천을 물어도 6만 줄 · 6만 객체 행을 읽었다(처음 21초 · 데워진 뒤 1.3초). 단계마다 **남은 자리만큼**만 읽는다
  (방향 없는 종류는 온 길로 돌아오는 선이 노드마다 하나 섞여 프런티어 수만큼 더) → 데워진 뒤 0.15초.
- **(타입, 칸) 짝을 OR 로만 주면 색인의 칸을 못 쓴다** — 그 모델을 가리키는 기준정보 칸(모델의 기본 모델 ·
  과제 …)만 물었는데 그 모델의 참조 100만 줄을 다 읽었다(처음 47초 · 데워진 뒤 3.7초, 답은 0건). 칸을
  `key IN (…)` 로 따로도 주자 (도착, 칸) 색인으로 0.013초. 이웃 그림의 `refedges._incoming` 도 같은 꼴이지만
  거기는 대상마다 `fanout` 으로 잘라 읽고 기록 칸을 기본으로 빼서 이번 실측에서 느리지 않았다.
- **닿은 객체를 통째로 읽으면 무겁다** — 응답을 만들 때 속성(JSONB)까지 읽지 않고 이름 · 식별자 · 타입 ·
  상태 · 부서만.

## 다음

- **정적 그리기에 「한 방향으로」** — 영향 범위를 그림으로. 정적 그리기의 단계 · 상한을 그대로 쓰고 선만 한
  방향으로 고른다.
- **부서로 좁힌 설치에서 「안 보여 멈춘 곳 N개」** — 지우기 확인 창(「그중 볼 수 없는 부서의 것 N」)처럼
  수만 말할지. 지금은 이웃 그림처럼 아무 말 없이 멈춘다.
- **수량 · 가중** — 영향 범위는 닿았는지만 본다. 「몇 개가 영향받나(수량 곱)」 는 BOM 전개(ADR 0040)다.
