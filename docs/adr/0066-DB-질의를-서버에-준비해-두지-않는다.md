# 0066. DB 질의를 서버에 준비해 두지 않는다 — 일반 계획이 글자 찾기를 48초로 만든다

- 상태: 채택(2026-11-09 구현)
  - `app/database.py` 의 엔진: `connect_args={"prepare_threshold": None}`
- 날짜: 2026-11-09
- 관련: [ADR 0065](0065-검색-줄의-차례-꼭-맞는-것이-맨-위.md)(검색 줄의 차례 — 그 실측에서 드러났다),
  [ADR 0048](0048-오래-도는-읽기의-안전장치.md)(오래 도는 읽기의 안전장치), [ADR 0026](0026-느린-요청-감시.md)(느린 요청)

## 배경

DB 드라이버(psycopg 3)는 기본으로 **같은 글의 질의를 다섯 번 넘게 보내면 서버에 준비해 둔다**(prepared
statement). 준비된 질의가 몇 번 더 쓰이면 Postgres 는 값을 보지 않고 미리 짜 둔 **일반 계획**(generic plan)이 싸
보일 때 그것으로 바꾼다(`plan_cache_mode=auto`). 값이 계획을 크게 가르는 질의 — 글자로 찾기(`ILIKE '%…%'` ·
trigram · 두 글자 조각 색인), 볼 수 있는 범위 조건 — 에는 그 일반 계획이 재앙이다.

ADR 0065 의 실측(2,000만 건 DB)에서 드러났다. 관리자와 일반 사용자의 통합 검색은 **같은 글**이고 값만 다르다:

| 차례 | 관리자 「과제 30」 7번 → 일반 사용자 같은 말 7번 | 일반 사용자 |
| --- | --- | --- |
| 고치기 전 | 0.03초 안팎 | 0.03 · 0.03 · 0.03 · **419초** · 46 · 46 · 47초 |
| 고친 뒤 | 0.05초 안팎 | 0.04 ~ 0.05초(일곱 번 모두) |

일반 사용자만 일곱 번 돌리면 모두 빨랐다 — 같은 글이 열 번쯤 쌓인 뒤에야 바뀐다. 운영 앱은 오래 떠 있으며 같은
모양의 질의를 계속 되풀이하므로 이 조건이 쉽게 선다. 운영에서 실제로 그랬는지는 아직 모른다 — 서버 화면의
「느린 요청 · 큰 응답」(ADR 0026, 요청마다 걸린 시간)에서 `/api/search` 의 최대 · p95 가 수십 초면 이것이다.

## 결정

**질의를 서버에 준비해 두지 않는다**(`prepare_threshold=None`). 질의마다 값을 보고 계획을 짠다 — 처음 다섯 번이 늘
하던 일이다. 앱의 연결은 `app/database.py` 한 곳뿐이다(시험도 같은 엔진을 쓴다).

견준 것:

- `plan_cache_mode=force_custom_plan`(서버 쪽 설정) — 준비는 하되 늘 값을 보고 짠다. 효과는 같지만 연결 문자열의
  서버 설정에 기대고, 준비해 두는 이득(구문 분석 한 번)이 작다. 드라이버 쪽 한 줄이 더 단순하다.
- 검색 같은 자리에서만 끄기 — 같은 위험이 목록의 글 검색 · 이름 풀이 · 별칭 후보 · 볼 수 있는 범위 조건 어디에나
  있어 자리를 다 셀 수 없다.

## 결과

200만 건 실측 DB(`standardplatform_scale`)에서 고치기 전(기본)과 후를 작업 트리 둘로 나눠 **번갈아** 쟀다 — 읽기
점검 25개는 한 프로세스에서 12번씩(준비 질의가 생길 만큼 — 오래 떠 있는 서버와 같은 조건), 쓰기 쪽(가져오기 계획
10만 행 · 표 추론 · 제안)은 실측 스크립트 그대로, 두 바퀴. 결과(초, 바퀴마다의 가운데 값):

- **읽기는 전후 범위가 겹쳤다** — 느려진 것이 없다. 한 바퀴에서 느려 보인 「개발모델 상세(뜨거움)」 0.18 →
  0.22 는 20번씩 세 바퀴로 다시 재 0.18 · 0.19 · 0.18 → 0.16 · 0.19 · 0.19 로 같았다. 검색 영역도 20번씩 세 바퀴로
  같았다(0.04 ~ 0.10).
- **쓰기는 빨라졌다** — 작은 질의를 많이 되풀이하는 일에서 준비해 둔 질의가 오히려 일반 계획으로 느려졌던 것으로
  보인다:

  | 무엇 | 전 | 후 |
  | --- | ---: | ---: |
  | 여러 건 제안 500줄(줄마다 검사 · savepoint) | 4.29 · 5.83 | 3.48 · 3.99 |
  | 확정 100건 × 3(감사 포함) | 1.45 · 2.03 | 1.11 · 1.25 |
  | 검토함 모으기 · 부서 관리자 · 타입 거르기 | 1.06 · 1.08 | 0.61 · 0.92 |
  | 일괄 입력 계획 100,000행 | 11.36 · 12.47 | 10.29 · 11.23 |

- 백엔드 시험 2,028개 통과.

## 남은 것

- 운영 서버의 「느린 요청 · 큰 응답」 에서 이 판 앞뒤의 `/api/search` · 목록 글 검색의 최대 · p95 를 견준다 — 앞에서
  수십 초가 있었다면 이 일이었다.
