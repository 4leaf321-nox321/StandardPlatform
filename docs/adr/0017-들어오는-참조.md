# 0017. 들어오는 참조도 걸음으로 — 축에서 기록으로 내려가는 거르기 · 통계

- 상태: 채택(2026-10-04 구현 — 걸음 · 객체마다 한 번 세기 · 가시성 · 참조 색인 통계 0062)
- 날짜: 2026-10-04
- 관련: [ADR 0009](0009-기록을-축에-잇는다.md)(기록이 참조 칸으로 축을 가리킨다),
  [ADR 0010](0010-규모-참조-색인.md)(참조 색인), [ADR 0011](0011-축과-기록.md)(축과 기록)

## 배경

조건 · 통계의 걸음은 셋이었다 — 참조 칸(`ref.<칸>`, 내가 가리키는 것), 관계의 두 방향(`out.` · `in.`).
기록은 참조 칸으로 축을 가리키므로(ADR 0009) **기록에서 축으로는** 간다(「서비스 기록 → 개발모델 →
과제」). 그런데 **축에서 기록으로는** 못 간다 — 개발모델 목록에서 「서비스 기록이 있는 모델」, 「증상이
S07 인 기록이 있는 모델」, 「증상별 모델 수」 를 묻지 못했다. 참조 칸은 그래프 · 관련 객체에서는 이미
양방향 선이지만(`refedges`), 조건 · 통계의 걸음에는 들어오는 쪽이 없었다.

## 결정

1. **주소는 `in.<가리키는 타입>:<참조 칸>`.** 「들어오는 것」 이라는 뜻이 들어오는 관계(`in.<관계>`)와
   같아 같은 걸음 종류에 둔다. 관계 slug 에는 `:` 가 못 들어가 겹치지 않는다. 그 너머의 칸은 다른
   걸음처럼 잇는다 — `in.svc_case:model.symptom`(이 모델을 가리키는 서비스 기록의 증상), 걸음 둘이면
   `in.plm_model:base.in.svc_case:model.symptom`(기본 모델 ← 개발모델 ← 서비스 기록의 증상).
2. **언제나 여럿이다.** 한 축 객체를 수만 건의 기록이 가리킨다. 조건은 다른 여럿 걸음처럼 「그중
   하나라도」(`EXISTS`)이고, 걸음 자체로는 있음/없음(「기록이 없는 모델」)과 특정 기록만 묻는다 —
   그 걸음 자체를 통계 기준으로 두지 않는다(기록마다 막대 하나가 된다).
3. **통계는 객체마다 한 번 센다.** 여럿으로 이어지는 기준은 지금까지 이어진 줄마다 셌다 — 같은 증상의
   기록이 300건인 모델은 그 막대에서 300 이었다. 「증상별 모델 수」 가 되게 **(객체, 막대)를 한 번씩**
   센다. 이것은 이미 있던 여럿 걸음(같은 공급사의 부품 둘을 단 기록)에도 맞는 셈이다 — 합계 ·
   평균도 객체마다 한 번.
4. **가리키는 기록은 보이는 것만.** 기록은 부서의 것이다 — 남의 부서 기록이 있다는 사실이 「기록이
   있는 모델」 로 새지 않게, 들어오는 참조 걸음은 보는 사람이 볼 수 있는 기록만 잇는다. 나가는 걸음
   (축을 가리키는 쪽)은 지금처럼 상대의 부서를 보지 않는다 — 축은 대개 전역이고, 지표가 그 규칙으로
   세어 왔다.
5. **지표의 기준으로는 안 받는다.** 지표는 기록을 센다 — 기록에서 거꾸로 가는 걸음은 한 기록을 여럿으로
   불린다. 정의에 적으면 이유와 함께 거절한다.
6. **고르개.** 「가리키는 것 · 서비스 기록(개발모델)」 제목 아래 그 기록 타입의 칸이 선다(`objects/paths.py` 의
   두 걸음 고르개와 같은 규칙 — 되짚는 걸음은 뺀다: 개발모델 → 서비스 기록 → 개발모델).

## 대안

### 축 타입에 「기록 수」 칸을 채워 둔다

적재 때마다 다시 세야 하고, 「증상 S07 인 기록」 처럼 조건이 붙으면 칸이 조건마다 하나씩 는다.

### 지표로 묻게 한다

「증상별 모델 수」 는 지표로도 되지만 정의 · 계산을 거쳐야 하고, 목록에서 바로 거르는 물음(「기록이
없는 모델」)은 지표의 모양이 아니다.

## 결과

- 걸음 종류는 그대로 셋(`ref` · `out` · `in`) — 들어오는 참조는 `in.<타입>:<참조 칸>` 으로 선다. 조건 ·
  통계 · 분포 · 고르개 · 진단이 같은 걸음을 쓴다. 지표의 기준으로는 거절한다(거르기로는 된다 —
  `EXISTS` 라 불어나지 않는다).
- **참조 색인에 확장 통계(0062).** 플래너가 「타입 = 개발모델 · 칸 = base」 를 11줄로 어림했다(실제
  6,000줄) — 두 칸을 따로 어림해 곱한 탓이다. 그 어림으로 200만 건을 한 줄씩 찾아가 두 걸음 거꾸로
  세기가 28초였다. `(src_type_id, key)` · `(dst_id, key)` 를 함께 어림하게 하니 6.2초.
- 규모(기록 200만 · 개발모델 6,000 · 기본 모델 2,001):

  | 물음 | 시간 |
  | --- | --- |
  | 증상 S07 기록이 있는 개발모델(거르기) | 2.4초 |
  | 기록이 없는 개발모델(거르기) | 2.9초 |
  | 최근 한 달 기록이 있는 개발모델(날짜 거르기) | 6.9초 |
  | 증상별 개발모델 수(통계) | 5.4초 |
  | 시리즈별 개발모델 수를 기록의 증상으로 나눔 | 4.6초 |
  | 증상별 기본 모델 수(두 걸음 거꾸로, 통계) | 5.6초(통계 전 27.5초) |
  | 증상 S07 기록이 있는 기본 모델(두 걸음 거꾸로, 거르기) | 8.2초(통계 전 54.6초) |

- 「객체마다 한 번」 은 이미 있던 여럿 걸음의 셈도 바로잡는다 — 같은 값으로 여럿 이어진 객체가 같은
  막대에서 두 번 세던 것.
