## 배경

키트 0.4.69 로 일한 쪽이 요청 아홉을 보냈다(키트 여섯 · 플랫폼 셋). 그중 하나(업무 공통 틀의 `work` · `organization`
에 `key_policy` 가 없어 식별자가 있는 행이 거절됨)는 0.4.102 에서 이미 고쳤다 — 여섯 타입이 식별자 필수다. 나머지
여덟을 코드에서 확인했다.

## 결정

### 1. 문서 본문을 묶음에 싣는다

묶음에는 객체 · 관계 행만 실려 문서 칸(ADR 0053)에는 목록 정보만 들어갔다.

- 키트: 실행 폴더의 `documents/*.md` 를 행의 `"_documents": {"<문서 칸 키>": "documents/<파일>.md"}` 로 붙인다(식별자가
  있는 행만, 실행 폴더 안 · 마크다운 · 100만 자까지). 보낼 때 읽어 묶음의 `documents` 에 싣는다 — 본문이 지문에 들어가
  미리 본 뒤 고치면 「바뀜」 이다.
- 플랫폼: `documents: [{type_slug, key, property, body, note}]` 를 객체 · 관계 단계 뒤에 쓴다(같은 묶음이 만든 객체에도).
  객체는 식별자로 찾고, 문서 칸(`data_type: document`)만 받으며, 권한은 화면의 문서 수정과 같다. 미리 보기도 쓴다(바깥이
  롤백 — 적용과 같은 판정), 가벼운 미리 보기는 이 묶음이 만들 객체를 `pending` 으로. 같은 본문이면 판을 안 올린다.
  쓰기는 화면과 같은 함수(`write_body` — 판 · 언급 · 감사)이고, 판의 「어디서」 는 「묶음 가져오기」 다(작업이 쓰고, 사람이
  화면에서 적용하기도 한다 — 누가 적용했는지는 묶음의 판). 묶음 되돌리기는 문서를 되돌리지 않는다 — 문서의 판으로.
- **이름 · 전화 검사**(키트 검사): 전화번호 · 메일 · 주민등록번호 꼴은 **오류**(문서는 판으로 남아 나중에 지워도 옛 판에
  남는다), 직함이 붙은 이름 · 「담당: 홍길동」 꼴은 **경고**(짐작이라 「다소 과장」 도 걸린다). 보고서는 가린 값만 적는다.

### 2. 플랫폼 칸과 겹치는 속성 키

객체 행에서 `id` · `key` · `label` · `description` · `aliases` · `status` · `valid_from_year` · `valid_to_year` ·
`renamed_from` · `previous_keys` 는 속성이 아니라 객체의 칸으로 읽힌다. `status` 로 업무 상태 칸을 만들자 검사는 오류 0
으로 통과하고 미리 보기에서 463행이 막혔다(값이 수명 `active` · `deprecated` 가 아니라서).

- 키트 검사: 정의의 그 키 · 수명이 아닌 `status` 값 · 연도가 아닌 `valid_*_year` 를 오류로.
- 플랫폼: 새 타입 · 공통 속성의 키로 받지 않는다(ONTOLOGY-113, 가져오기는 계획의 오류) — 이미 있는 속성은 그대로(지우거나
  「키 변경」 으로). 목록은 일괄 입력의 고정 열과 같다(시험이 견준다).

### 3. 이름이 빈 행

검사가 `label` 도 `key` 도 없을 때만 막았다. 이제 **새로 만드는 객체**의 빈 이름을 오류로 — 플랫폼에 묻는 검사
(`ask_platform`)는 이미 있는 식별자면 고치는 행이라 통과시킨다(플랫폼과 같은 규칙: 새 행만 이름이 필요하다).

### 4. 다시 미리 본 실행 · 닫기

`preview.json` 이 마지막 잡만 남아, 앞 잡으로 화면에서 이미 적용한 실행이 「적용 전」 으로 남고 다음 잡의 적용 링크가
또 떴다. 이제 미리 보기마다 앞 잡을 `previews.json` 에 남기고, 상태가 **잡 전부**에 묻는다 — 적용한 것이 보이면
`applied.json`(`via: screen`)을 적어 다시 묻지 않는다. 적용한 실행은 다시 미리 보지 않는다(새 실행으로). **같은 묶음
(지문)을 이미 적용한 다른 실행**은 「또 넣지 않는다」 로 알린다. 쓰지 않을 실행은 `run_close(reason=)` — 할 일에서
빠지고 다시 미리 보지 않는다(지우지 않는다).

### 5. 실행 이름

`run_init` 이 날짜로 시작하는 이름에 날짜를 또 붙였고, 검사 · 미리 보기는 `runs/` 를 붙여야 받았다. 이제 날짜가 있으면
안 붙이고, `runs/<이름>` · `<이름>` · 날짜를 뺀 이름(하나뿐일 때) 모두 받는다 — 여럿과 맞으면 후보를 말한다.

### 6. 관계의 칸을 RDF 로

관계 속성(수량 · 옵션)이 `rdf_query` 에 없어 적용 뒤 값 대조가 안 됐다. 칸 값이 있는 선은 구체화한 진술(`rdf:Statement`)
에 `sp:rel.<관계>-<칸 키>` 로 싣는다 — 메모리 그래프와 사본(Oxigraph)이 같은 글을 낸다. 사본의 바뀐 것만 고치기는 선의
지문에 칸을 넣고, 「진술 수」 검증도 칸이 있는 선을 센다. 이름에 점을 하나만 쓰는 까닭: `rel.<관계>.<키>` 는 키가
`inverse` 인 칸이 역방향 이름과 겹치고, **점이 둘인 접두어 이름(`sp:a.b.c`)을 Oxigraph 0.5 가 질의에서 못 읽는다**
(실측 — 그래서 사본에서는 `rel.x.inverse` 도 IRI 를 다 적어야 한다, 안내서에 적었다). 참조 종류의 칸은 아직 안 낸다.

### 7. 작업 상태의 크기

`job_status` 가 계획을 통째로(목록마다 500줄) 돌려줘 36만 ~ 145만 자였다. `GET /api/jobs/{id}?rows=N`(0 ~ 500, 문제 줄
먼저 · 뺀 수는 `rows_omitted`)을 두고 MCP 는 기본 20줄로 받는다(`job_status(rows=)`, 작업을 기다리는 도구 전부).

### 8. SPARQL 의 0건

「`VALUES` 가 WHERE 맨 앞이면 0건」 은 재현되지 않았다 — 자리를 바꿔도 같다. 0건의 실제 까닭은 둘이었다.

- **글자 꼬리표** — 이름 · 설명 · 글 칸은 `"…"@ko` 라 꼬리표 없는 `"볼트"` 와 안 맞는다. 0건이면 답의 `notes` 가 꼬리표
  없는 글자로 견준 자리(삼중 패턴 · `VALUES` · 변수와의 `=`)와, 그래프에 없는 술어 · 타입(이 설치의 것)을 짐작해 적는다.
- **메모리 그래프의 `xsd:string`** — rdflib 은 `"A"^^xsd:string` 과 `"A"` 를 다르게 맞춰 고를 값 질의가 메모리에서만
  0건이었다(사본은 RDF 1.1 대로 같게 본다). 고를 값 · 파일 칸을 형 없는 글자로 낸다(사본도 같은 글).

## 대안 — 버린 것

- **문서 본문을 행의 칸으로** — 문서 칸은 값이 `properties` 에 없다(판 · 언급 표). 행에 실으면 일괄 입력의 모든 길이 그
  칸을 따로 다뤄야 한다. 묶음의 따로 된 절로 둔다.
- **이름 · 전화를 모두 오류로** — 직함 패턴은 짐작이라 막으면 멀쩡한 글이 막힌다. 확실한 꼴만 오류.
- **플랫폼이 `status` 속성을 자동으로 다른 이름으로** — 짐작으로 키를 바꾸면 정의와 행이 갈린다. 막고 말한다.
- **`VALUES` 를 질의 뒤로 옮겨 주기** — 자리는 까닭이 아니었다.
