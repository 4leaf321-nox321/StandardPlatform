# 0010. 기록 200만 건을 견딘다 — 참조 색인 표와 찾기 인덱스

- 상태: 채택
- 날짜: 2026-10-03
- 관련: [ADR 0005](0005-온톨로지-메타모델.md)(객체는 한 표 `objects` 의 JSONB 에 산다 · 승격 경로),
  [ADR 0009](0009-기록을-축에-잇는다.md)(기록을 축에 잇는다 — 이 결정이 그 전제다)

## 배경

운영에서는 **한 기록 타입이 최대 200만 건**이다(시장 서비스 건 · 시험 결과 …). 기록은 축(개발모델 ·
과제 · 부서)을 참조 칸으로 가리킨다. 개발 서버에는 기록이 없어 드러나지 않았으므로 실험용 DB 를 따로
만들어 쟀다(`backend/scripts/scale_rehearsal.py` — 축 1.1만 + 기록 200만, 속성 31칸, 5% 는 한 인기
모델을 가리킴, 개발 PC 의 Postgres 기본 설정).

참조 칸은 상대의 id 를 `properties-><칸>`(글자 하나 또는 목록)에 담는다. 그래서 **「이것을 가리키는
것」 을 물을 때마다 가리키는 타입을 통째로 읽었다** — 질의가 `properties->>'model' = id` 꼴이라
`properties` 의 GIN 인덱스를 못 탄다(같은 물음을 포함 꼴 `@>` 로 물으면 297ms → 0.14ms).

| 무엇 | 고치기 전 | 참조 색인 뒤 | 검색 · 통계 뒤 |
| --- | --- | --- | --- |
| 목록 첫 쪽 · 건수 · 고를 값 조건 | 0.2 ~ 0.3초 | 그대로 | 그대로 |
| 목록 — 참조 조건(보통 모델) | 1.26초 | 0.03초 | 0.03초 |
| 목록 — 참조 너머 칸(모델 시리즈) | **2분 넘어 끊김** | 1.61초 | 1.46초 |
| 목록 — 글 검색 | 2.35초 | 2.79초 | 0.03초 |
| 개발모델 상세(보통 / 인기) — 관련 객체 | 1.50초 / **오류** | 0.04초 / 0.24초 | 0.03초 / 0.19초 |
| 그래프 이웃(보통 / 인기) | 3.0초 / **오류** | 0.09초 / 0.42초 | 0.06초 / 0.34초 |
| 그래프 개요 | 2.87초 | 1.40초 | 1.13초 |
| 통계 — 증상별 | 2.04초 | 2.81초 | 1.13초 |
| 통계 — 모델 시리즈별(참조 너머) | **2분 넘어 끊김** | 5.97초 | 2.77초 |
| 통합 검색 | 2.48초 | 2.74초 | 0.03초 |
| 이름 풀이(MCP `object_resolve`) | **107초** | 2.05초 | 0.02초 |
| 품질 보고 | 10.3초 | 1.56초 | 1.45초 |
| 일괄 입력 10만 행 계획 | **실패**(바인드 한도) | 13.6초 | 11.7초 |

「오류」 는 인기 모델을 가리키는 10만 건을 `IN (...)` 으로 넘기다 Postgres 한 문장의 바인드 변수 한도
(65,535)에 걸린 것이다 — 일괄 입력 10만 행도 같은 자리에서 실패했다.

## 결정

1. **참조 색인 표 `object_refs(src_id, key, dst_id, src_type_id)`** — 참조 칸의 값을 원소마다 한 줄로
   둔다. 인덱스는 `(dst_id, key)`(가리키는 것 찾기)와 `(src_type_id, key)`(타입 · 칸 전부). 값의 정본은
   여전히 `objects.properties` 이고 이 표는 **사본**이다.
2. **DB 트리거가 유지한다**(`objects/refindex.py`). 객체를 쓰는 길이 열 곳이 넘는다(화면 · 일괄 입력 ·
   묶음 · 데이터 소스 · 종류 변경 · 병합 · 이력 되돌리기 · 코드표 승격 · 영구 삭제 …) — 코드로 맞추면
   언젠가 한 길이 빠지고, 빠진 길로 쓴 값은 「관련 객체」 에서 **조용히** 사라진다.
   - 객체 넣기 · 고치기(문장 단위, 값 · 타입 · 지움이 바뀐 행만), 행 삭제는 FK CASCADE.
   - 지운 객체(`deleted_at`)는 줄이 없다 — 살아 있는 것만 「가리킨다」.
   - 속성 정의가 참조가 되거나 아니게 되면 그 타입 · 칸을 통째로 다시 쓴다(순서 무관).
   - 상대(dst)는 FK 가 없다 — 원 표(부서 · 계정)의 id 도, 지운 상대를 가리키는 줄도 들어야 한다.
3. **읽는 쪽은 색인으로 묻는다** — 관련 객체 · 그래프 이웃 · 차수 · 개요 · 트리 · 「가리키는 것」(삭제 ·
   병합 전 확인) · 참조 칸 조건 · 참조 너머 칸 조건과 통계 · 품질의 끊긴 참조 · 묶음 되돌리기 · 영구 삭제.
   관계 쪽이 이미 쓰던 `(나 → 상대)` 모양에 참조가 그대로 얹힌다.
4. **찾기 인덱스** — `objects(key, type_id)`, 비교키(`compare_key` 와 같은 식 — NFKC · 공백 · 소문자)
   식 인덱스, `(type_id, lower(label))`. 이름 풀이는 키 있는 행을 전부 파이썬으로 읽던 것을 그 인덱스로
   좁힌 뒤 같은 규칙으로 견준다.
5. **긴 목록은 나눠 묻는다**(`shared/batches.chunks`, 1만 개씩) — 바인드 한도를 넘는 `IN` 을 만들지
   않는다. 보여 주는 자리는 상한을 두고 수로 말한다(「가리키는 것」 칸마다 200 + `more_property_refs`,
   관련 객체 · 그래프 이웃은 대상마다 fanout).
6. **두 벌인 SQL** — 시험은 모델로 표를 세우므로(`create_all`) 메타데이터 이벤트가 트리거를 걸고, 운영은
   마이그레이션(0049)이 그날의 사본으로 건다. 고칠 때는 둘 다(새 마이그레이션).
7. **「들어간 것」 찾기는 trigram 으로**(0051, `pg_trgm`) — 이름 · 식별자 · 별칭. 그리고 셋을 **따로 묻고
   합친다**(`containing_ids`) — 한 `OR` 에 별칭 부분 질의를 묶으면 Postgres 가 인덱스를 버리고 표 전체를
   읽었다(627ms → 9ms). 두 글자 검색은 결정 11.
8. **통계는 한 번에 센다** — 그룹 수 · 합을 창 함수로 같은 질의에서(예전에는 같은 조인을 두 번 돌았다).
9. **RDF 그래프는 세우기 전에 센다** — 올릴 객체가 5만 건을 넘으면 거절하고 `types` 로 좁히라고 한다.
   그래프는 메모리에 서므로, 세운 뒤에 거절하면 이미 늦다.
10. **`properties` 통째 GIN 인덱스를 뺀다**(0052). 거르기는 칸 하나씩(`properties->>'k'`)이라 그것을
    못 타고, 「값 있음」(`?`)은 늘 타입으로 먼저 좁힌다 — 실측 사용이 개발 DB 6회 · 실험 DB 7회였다. 그런데
    속성을 고칠 때마다 행의 **모든 칸**을 다시 넣는다: 기록 200만 건 종류 변경에서 덩어리 하나(5천 행)
    2.93초 중 2.5초가 이 인덱스였고, 크기는 1.3GB 였다. 빼고 재니 「값 있음」 은 큰 타입에서 그대로
    (0.42초), 작은 타입에서 2ms → 29ms, 타입 없이 물을 때만 느려진다(그렇게 묻는 코드는 없다).
    칸 하나를 자주 포함 꼴로 거르게 되면 그 칸의 식 인덱스를 따로 둔다. 뺀 뒤 위 표의 측정을 다시 돌리니
    그대로였다(목록 0.21초 · 통계 1.09 ~ 2.65초 · 품질 1.31초 · 일괄 입력 계획 11.6초). 200만 건을 여러 번
    고친 뒤에는 죽은 행으로 표가 부풀어 전반이 1.5 ~ 2배 느렸다 — 자동 청소가 따라오면 돌아온다(`VACUUM
    FULL` 로 확인).
11. **두 글자 검색은 두 글자 조각 인덱스로**(0054). trigram 은 세 글자부터라 「과제」 · 「소음」 처럼 흔한
    한글 두 글자 낱말이 표 전체를 읽었다(3.1초). 글자를 두 글자 조각 배열로 만드는 SQL 함수(`sp_bigrams`,
    확장 없음)에 GIN 인덱스를 걸고, 두 글자로 찾을 때 `sp_bigrams(label) @> ARRAY['과제']` 로 거른 뒤
    `ILIKE` 가 다시 본다 — 0.04초. 다만 **흔한 조각이면 안 건다**: 「C0」 처럼 200만 건 전부에 든 조각은
    어차피 표를 다 읽는데, 거기에 행마다 조각을 만드는 값이 더해져 두 배로 느려졌다. 그 비율은 Postgres 가
    그 인덱스에 모아 둔 통계(`pg_stats` 의 자주 나오는 원소)로 알고, 2% 를 넘으면 예전 길로 간다
    (`objects.services.bigram_plan`).
12. **큰 참조 대상은 넣을 값만 묻는다.** 참조 풀이(`bulk.Refs`)는 대상 타입의 식별자 · 이름을 통째로
    읽었다 — 기록이 기록(200만 건)을 가리키면 그것을 다 메모리에 든다. 대상이 10만 건을 넘으면 넣을 값을
    모아 덩어리째(1만 개씩) 묻는다(식별자 · 이름 · 별칭 · id). 판정 규칙은 같다. 일괄 입력 · 종류 변경 ·
    참조 후보가 미리 모아 묻는다 — 기록 200만 건을 가리키는 1만 행 계획이 1.7초 · 177MB, 표 추론 0.36초.
13. **가리키는 것을 전부 고치는 일은 덩어리로, 크면 작업으로.** 병합(참조를 이긴 쪽으로) · 참조 비우고
    지우기는 가리키는 객체를 하나씩 실어 고치고 속성 전체를 이력에 두 번 담았다. 이제 종류 변경과 같은
    길(`objects.rewrite` — 덩어리마다 문장 하나로 그 칸만, 이력은 바뀐 칸만)이다. 인기 모델(기록 10만 건)의
    병합이 31초 · 152MB 라, 가리키는 것이 2만 건을 넘으면 요청이 OBJECTS-96 으로 작업 주소를 주고
    (`…/merge/job` · `…/detach/job`) 화면 · MCP 가 그리로 간다(작업 25.7초). 여럿 지우기에서는 그 줄에
    작업 주소를 적는다. **내보내기**는 타입 전체를 객체로 싣고 파일을 한 번에 만들었다 — 이제 덩어리마다
    읽어 쓰고(`yield_per`), 10만 행이 넘으면 zip 으로 낸다. 작업이 만드는 결과 파일의 상한은 올리는 파일과
    따로 512MB 다(`JOB_OUTPUT_MAX_BYTES`) — 기록 200만 건이 zip 으로 134MB(265초)였다.
14. **일괄 입력의 새 줄은 COPY 로 넣는다**(`shared/copyin.py`, 2026-10-09). 개발 DB 의 서비스 기록
    5만 줄(전부 새로) 적용이 39초였고 그중 flush 가 24초 — ORM 이 새 행을 1,000줄짜리
    `INSERT … VALUES … RETURNING` 으로 묶는데, psycopg 는 4KB 넘는 문장을 캐시하지 않아 덩어리마다
    문장을 다시 쪼갰다. 줄씩 보내는 executemany 는 참조 색인 트리거(문장 단위)가 줄마다 돌아 더
    느렸다(객체 5만: ORM 15.7초 · executemany 20.9초 · COPY 9.6초 / 감사 5만: 8.2 · 2.6 · 0.9초). 그래서
    새 객체 · 새 선과 그 감사 기록 · 되돌릴 기록을 5천 줄씩 모았다가 COPY 한다. **감사는 줄마다 그대로
    남고 바깥 알림도 줄마다 나간다**(`audit.Batch` — `record_rows` 는 알림을 안 내 뜻이 다르다). 함께
    고친 것: 적용이 계획을 다시 세우며 같은 줄을 세 번 읽던 것(칸 값 · 참조 풀이 · 검증)을 한 번으로,
    계획이 별칭 칸 없는 줄마다 표식 글자를 별칭으로 묻던 것, 긴 목록을 배열 바인드 하나로
    (`batches.any_of` — 관계 파일은 출발점 2만 개쯤에서 끝점 질의가 바인드 한도에 걸려 **계획부터
    죽었다**). cProfile 끄고 두 번씩:

    | 5만 줄 | 전 | 뒤 |
    | --- | --- | --- |
    | 객체 새로 — 적용(계획 다시 세우기 포함) | 38.8 · 39.1초 | 17.4 · 16.6초 |
    | 객체 새로 — 계획(미리 보기) | 7.2 · 7.6초 | 4.5 · 4.5초 |
    | 객체 그대로 다시 적용 / 한 칸씩 고침 | 11.8 · 11.7초 / 51.7 · 53.2초 | 7.9 · 8.0초 / 36.6 · 39.0초 |
    | 관계 새로 — 적용 | **실패**(1만 5천 줄 7.4 · 7.0초) | 7.1 · 6.9초(1만 5천 줄 2.2 · 2.1초) |

    남은 시간의 대부분은 DB 안이다 — 객체 5만 줄 INSERT 8.1초 중 참조 색인 트리거가 3.4초(object_refs
    23만 줄), 나머지는 색인 15개 · 외래키다. 고치는 줄은 여전히 ORM 이 줄마다 UPDATE 하는데,
    `updated_at` 이 색인 칸이라 HOT 갱신이 안 돼 매번 색인 15개(GIN 넷)를 다 새로 쓴다 — 같은 5만 줄을
    덩어리 UPDATE 로 바꿔 재 봐도 GIN 대기 목록 정리에 따라 11 ~ 81초로 흔들려 이번에는 손대지 않았다.

    **고치는 줄도 덩어리로, 트리거는 달라진 줄만**(2026-10-10, 마이그레이션 0075). 흔들림은 GIN 이
    아니었다. 고치기 트리거(`object_refs_updated`)의 SQL 은 plpgsql 이 **연결마다 첫 호출에서 계획을
    굳혀** 다시 쓰고, 전이 표의 크기도 그때 것으로 어림한다. 한 줄짜리 갱신을 한 연결이 5천 줄 덩어리를
    고치면 한 줄짜리 계획(옛 행 x 새 행 중첩 반복)으로 5천 x 5천을 돌아 **덩어리 하나가 40초**였다
    (계획을 새로 세우면 1.5초). 계획은 다른 연결의 자동 청소가 표 통계를 고칠 때에야 다시 서므로 몇
    덩어리째에 풀릴지가 우연이었다 — 그것이 11 ~ 81초다. GIN 은 따로 재 봤다(새 트리거, 5만 줄): 대기 목록
    한도 기본 4MB 7.5 ~ 8.6초 · 64MB 8.0 · 8.3초 · 64kB 11.5 · 12.0초(정리가 잦아 덩어리 최악 2.4초),
    `fastupdate=off` 는 1만 줄에서 기본의 2.3배(3.8 · 4.2초 / 1.6 · 1.9초) — 기본값 그대로 둔다. 바꾼 것:

    - **트리거는 참조가 달라진 행의 달라진 줄만** 지우고 넣는다 — 타입 · 지움이 바뀌었거나 그 타입의
      참조 칸 값이 다른 행만 고르고, 값이 바뀐 칸만 줄로 풀어 옛 쪽 · 새 쪽을 `EXCEPT` 로 뺀다. 예전에는
      속성이 바뀐 행이면 그 행의 줄을 통째로 지우고 다시 넣었다(비용 칸 하나를 고친 5만 줄에 23만 줄 +
      외래키 검사). **64줄이 넘는 문장은 그때그때 계획한다**(`EXECUTE`), 작은 문장은 정적 SQL 그대로
      (계획을 매번 세우는 값이 한 줄 고치기에는 그 일보다 크다). 남는 색인은 같다 — 옛 트리거와 새
      트리거를 같은 갱신들(참조 칸 · 목록 · 비움 · 지움 · 되살림 · 같은 칸 이름의 타입으로 바꿈)에
      돌려 견주는 시험이 있다(`test_object_refs.py`).
    - **고친 줄은 5천 줄씩 `UPDATE … FROM unnest(…)` 한 문장으로**(`copyin.update_rows`) — 바뀐 칸을
      flush 와 같은 판정으로 고르고(같은 값을 다시 넣은 칸 · 그런 칸뿐인 줄은 안 쓴다), 바뀐 칸이 같은
      줄끼리 묶는다. 별칭 맞추기가 끝에서 flush 하므로 그 앞에서 모아 둔 것을 먼저 쓴다. 감사 · 알림 ·
      되돌릴 기록과 그 차례는 그대로다 — 같은 파일을 예전 길(flush)과 새 길로 넣어 남는 것을 견주는
      시험이 있다(`test_bulk_writes.py`).
    - 적용이 계획이 검증한 속성을 다시 검증하던 것(사람이 고친 칸을 비켜 가지 않고 그 객체를 앞줄이
      고치지 않았을 때만 그대로 쓴다), 관계 근거 고치기가 **속성 정의 없는 종류**에서 줄마다 정의를
      다시 묻던 것(빈 목록을 `or` 로 「없음」 으로 읽었다 — 2만 줄 14.4초 중 9초 남짓).

    개발 DB, 같은 트랜잭션에서 새로 → 그대로 → 한 칸 고침(롤백), cProfile 끄고 전후를 번갈아 세 번씩
    (전 = 그 전 코드 + 0049 트리거). 같은 서버에서 다른 DB 의 큰 갱신이 함께 돌던 때다:

    | 5만 줄(서비스 기록) | 전 — 중앙값 / 최악 (세 번) | 뒤 — 중앙값 / 최악 (세 번) |
    | --- | --- | --- |
    | 새로 — 적용 | 19.0 / 20.0초 (16.7 · 19.0 · 20.0) | 20.0 / 20.0초 (18.6 · 20.0 · 20.0) |
    | 그대로 다시 적용 | 8.5 / 9.5초 (8.2 · 9.5 · 8.5) | 8.8 / 8.9초 (8.7 · 8.8 · 8.9) |
    | 한 칸(비용)씩 고침 — 적용 | **44.2 / 45.4초** (40.3 · 44.2 · 45.4) | **22.9 / 24.2초** (22.9 · 24.2 · 22.0) |
    | 　그중 객체 UPDATE | 27.2 / 27.3초 (줄마다 5만 문장) | 9.2 / 10.4초 (11문장) |
    | 관계 2만 줄 근거 고침 — 적용 | **14.4 / 14.6초** (14.4 · 14.6 · 14.4) | **4.4 / 4.4초** (4.4 · 4.4 · 4.2) |
    | 관계 2만 줄 새로 · 그대로 | 3.4 · 1.7초 | 3.4 · 1.8초 |

    앞서 한 번 더 번갈아 잰 것도 같았다(고침 전 44.5 · 41.2 · 39.8 / 뒤 23.8 · 25.2 · 23.2초). 트리거만
    떼어(이미 있는 5만 줄을 5천 줄씩 덩어리 UPDATE, 롤백):

    | 5만 줄 덩어리 UPDATE | 0049 트리거 | 0075 트리거 |
    | --- | --- | --- |
    | 비용 칸 고침(참조 그대로) | 16.5 · 16.5초 | 8.8 · 9.3초 (트리거 빈 함수 7.4 · 7.8초) |
    | 참조 칸(sku) 고침 | 15.9 · 16.0초 | 11.3 · 11.8초 |
    | 같은 연결이 앞서 한 줄을 고쳤을 때 | 53.8 · 54.2초 (첫 덩어리 40초) | 8.8 · 11.2초 (덩어리 최악 1.3초) |

    고친 뒤 남은 것: 5만 줄 고치기 23초 중 계획(그대로 다시와 같은 일 — 칸 값 읽기 · 미리 읽기 · 판정)이
    8초 남짓, 객체 UPDATE 9 ~ 10초(HOT 이 안 돼 색인 15개를 다 쓴다 — `updated_at` 색인을 빼지 않는 한
    그대로), 감사 COPY 2초 남짓. 넣기 트리거(`object_refs_inserted`)는 그대로다 — 새 객체 5만 줄(참조
    22.8만 줄)에서 줄 뽑기 1.1초 · 넣기 1.3 ~ 1.8초(그중 `ON CONFLICT` 0.4 ~ 0.7초) · 외래키 검사 1.0초로,
    줄 뽑기를 고쳐 써 봐도 20% 안팎이었고 외래키는 영구 삭제의 CASCADE 가 기대어 남긴다.

## 대안

### 질의만 포함 꼴(`@>`)로 고쳐 쓴다

하나를 가리키는 찾기(상세 · 삭제 전 확인 · 참조 조건)는 GIN 으로 빨라진다. 하지만 **잇기와 묶기**(참조
너머 칸으로 거르기 · 묶기, 그래프 개요 · 차수, 끊긴 참조)는 여전히 타입을 통째로 읽는다 — 포함은 등가
조인이 아니라서다. 그 기능들을 큰 타입에서 막아야 했다.

### 큰 기록 타입을 전용 표로 승격한다

`docs/승격-경로.md` 의 길이다. 하지만 기록마다 배포 · 마이그레이션이 필요해지고(정의를 고치면 화면이
생기는 길에서 빠진다), 사용자가 피하려는 「기록마다 따로 개발」 그 자체다. 참조 문제는 승격해도 같다.

### 색인을 앱 코드가 쓴다

트리거 없이 쓰는 자리마다 맞춘다. 길이 열 곳이 넘고 앞으로도 는다 — 하나가 빠지는 순간 색인과 값이
갈리고, 그 어긋남은 아무 데도 안 뜬다.

## 결과

- 쓰기마다 트리거가 돈다 — 일괄 입력 10만 행 계획이 13.6초(적용은 작업으로 돈다). 갱신은 값 · 타입 ·
  지움이 바뀐 행만 다시 쓴다.
- 마이그레이션 0049 가 기존 값을 채운다 — 200만 건에서 약 2분, 0050 의 인덱스 셋은 8.5초(실측).
- 목록 · 상세 · 그래프 · 검색 · 이름 풀이는 화면 목표선(1초) 안, 묶기(통계 · 개요 · 품질)는 3초 안이다.
  개발 PC 기본 설정(work_mem 4MB)이라 운영 서버에서는 더 빠를 수 있으나, **질의의 모양**은 같다.
- `pg_trgm` 확장이 필요하다 — Postgres 13 부터 신뢰된 확장이라 DB 소유자가 만들 수 있고, contrib 에
  들어 있어 폐쇄망에도 새로 깔 것이 없다.
- 병합 · 참조 해제 삭제 · 내보내기는 결정 13.
