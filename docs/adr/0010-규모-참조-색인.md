# 0010. 기록 200만 건을 견딘다 — 참조 색인 표와 찾기 인덱스

- 상태: 채택
- 날짜: 2026-10-03
- 관련: [ADR 0005](0005-온톨로지-메타모델.md)(객체는 한 표 `objects` 의 JSONB 에 산다 · 승격 경로),
  ADR 0009(기록을 축에 잇는다 — 다음 단계, 이 결정이 그 전제다)

## 배경

운영에서는 **한 기록 타입이 최대 200만 건**이다(시장 서비스 건 · 시험 결과 …). 기록은 축(개발모델 ·
과제 · 부서)을 참조 칸으로 가리킨다. 개발 서버에는 기록이 없어 드러나지 않았으므로 실험용 DB 를 따로
만들어 쟀다(`backend/scripts/scale_rehearsal.py` — 축 1.1만 + 기록 200만, 속성 31칸, 5% 는 한 인기
모델을 가리킴, 개발 PC 의 Postgres 기본 설정).

참조 칸은 상대의 id 를 `properties-><칸>`(글자 하나 또는 목록)에 담는다. 그래서 **「이것을 가리키는
것」 을 물을 때마다 가리키는 타입을 통째로 읽었다** — 질의가 `properties->>'model' = id` 꼴이라
`properties` 의 GIN 인덱스를 못 탄다(같은 물음을 포함 꼴 `@>` 로 물으면 297ms → 0.14ms).

| 무엇 | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 목록 첫 쪽 · 건수 · 고를 값 조건 | 0.2 ~ 0.3초 | 그대로 |
| 목록 — 참조 조건(보통 모델) | 1.26초 | 0.03초 |
| 목록 — 참조 너머 칸(모델 시리즈) | **2분 넘어 끊김** | 1.61초 |
| 개발모델 상세(보통 / 인기) — 관련 객체 | 1.50초 / **오류** | 0.04초 / 0.24초 |
| 그래프 이웃(보통 / 인기) | 3.0초 / **오류** | 0.09초 / 0.42초 |
| 그래프 개요 | 2.87초 | 1.40초 |
| 통계 — 모델 시리즈별(참조 너머) | **2분 넘어 끊김** | 5.97초 |
| 이름 풀이(MCP `object_resolve`) | **107초** | 2.05초 |
| 품질 보고 | 10.3초 | 1.56초 |
| 일괄 입력 10만 행 계획 | **실패**(바인드 한도) | 13.6초 |

「오류」 는 인기 모델을 가리키는 10만 건을 `IN (...)` 으로 넘기다 Postgres 한 문장의 바인드 변수 한도
(65,535)에 걸린 것이다 — 일괄 입력 10만 행도 같은 자리에서 실패했다.

## 결정

1. **참조 색인 표 `object_refs(src_id, key, dst_id, src_type_id)`** — 참조 칸의 값을 원소마다 한 줄로
   둔다. 인덱스는 `(dst_id, key)`(가리키는 것 찾기)와 `(src_type_id, key)`(타입 · 칸 전부). 값의 정본은
   여전히 `objects.properties` 이고 이 표는 **사본**이다.
2. **DB 트리거가 유지한다**(`objects/refindex.py`). 객체를 쓰는 길이 열 곳이 넘는다(화면 · 일괄 입력 ·
   묶음 · 데이터 소스 · 종류 변경 · 병합 · 이력 되돌리기 · 코드표 승격 · 영구 삭제 …) — 코드로 맞추면
   언젠가 한 길이 빠지고, 빠진 길로 쓴 값은 「관련 객체」 에서 **조용히** 사라진다.
   - 객체 넣기 · 고치기(문장 단위, 값 · 타입 · 지움이 바뀐 행만), 행 삭제는 FK CASCADE.
   - 지운 객체(`deleted_at`)는 줄이 없다 — 살아 있는 것만 「가리킨다」.
   - 속성 정의가 참조가 되거나 아니게 되면 그 타입 · 칸을 통째로 다시 쓴다(순서 무관).
   - 상대(dst)는 FK 가 없다 — 원 표(부서 · 계정)의 id 도, 지운 상대를 가리키는 줄도 들어야 한다.
3. **읽는 쪽은 색인으로 묻는다** — 관련 객체 · 그래프 이웃 · 차수 · 개요 · 트리 · 「가리키는 것」(삭제 ·
   병합 전 확인) · 참조 칸 조건 · 참조 너머 칸 조건과 통계 · 품질의 끊긴 참조 · 묶음 되돌리기 · 영구 삭제.
   관계 쪽이 이미 쓰던 `(나 → 상대)` 모양에 참조가 그대로 얹힌다.
4. **찾기 인덱스** — `objects(key, type_id)`, 비교키(`compare_key` 와 같은 식 — NFKC · 공백 · 소문자)
   식 인덱스, `(type_id, lower(label))`. 이름 풀이는 키 있는 행을 전부 파이썬으로 읽던 것을 그 인덱스로
   좁힌 뒤 같은 규칙으로 견준다.
5. **긴 목록은 나눠 묻는다**(`shared/batches.chunks`, 1만 개씩) — 바인드 한도를 넘는 `IN` 을 만들지
   않는다. 보여 주는 자리는 상한을 두고 수로 말한다(「가리키는 것」 칸마다 200 + `more_property_refs`,
   관련 객체 · 그래프 이웃은 대상마다 fanout).
6. **두 벌인 SQL** — 시험은 모델로 표를 세우므로(`create_all`) 메타데이터 이벤트가 트리거를 걸고, 운영은
   마이그레이션(0049)이 그날의 사본으로 건다. 고칠 때는 둘 다(새 마이그레이션).

## 대안

### 질의만 포함 꼴(`@>`)로 고쳐 쓴다

하나를 가리키는 찾기(상세 · 삭제 전 확인 · 참조 조건)는 GIN 으로 빨라진다. 하지만 **잇기와 묶기**(참조
너머 칸으로 거르기 · 묶기, 그래프 개요 · 차수, 끊긴 참조)는 여전히 타입을 통째로 읽는다 — 포함은 등가
조인이 아니라서다. 그 기능들을 큰 타입에서 막아야 했다.

### 큰 기록 타입을 전용 표로 승격한다

`docs/승격-경로.md` 의 길이다. 하지만 기록마다 배포 · 마이그레이션이 필요해지고(정의를 고치면 화면이
생기는 길에서 빠진다), 사용자가 피하려는 「기록마다 따로 개발」 그 자체다. 참조 문제는 승격해도 같다.

### 색인을 앱 코드가 쓴다

트리거 없이 쓰는 자리마다 맞춘다. 길이 열 곳이 넘고 앞으로도 는다 — 하나가 빠지는 순간 색인과 값이
갈리고, 그 어긋남은 아무 데도 안 뜬다.

## 결과

- 쓰기마다 트리거가 돈다 — 일괄 입력 10만 행 계획이 13.6초(적용은 작업으로 돈다). 갱신은 값 · 타입 ·
  지움이 바뀐 행만 다시 쓴다.
- 마이그레이션 0049 가 기존 값을 채운다 — 200만 건에서 약 2분, 0050 의 인덱스 셋은 8.5초(실측).
- **아직 목표선(화면 1초 · 묶기 3초)을 넘는 것** — 통계의 참조 너머 칸(6초), 검색 · 목록 글 검색
  (2.7초, `ILIKE '%q%'`), 이름 풀이의 「포함」 단계(2초). 검색은 `pg_trgm` 으로, 나머지는 실측과 함께
  다음 단계에서 다룬다. 개발 PC 기본 설정(work_mem 4MB)이라 운영 서버에서는 더 빠를 수 있으나,
  **질의의 모양**은 같다.
- 병합 · 참조 해제 삭제처럼 가리키는 것을 **전부 고치는** 일은 여전히 요청 안에서 돈다 — 인기 모델을
  병합하면 10만 건을 고친다. 그 일이 실제로 필요해지면 작업으로 옮긴다.
