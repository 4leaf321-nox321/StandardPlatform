## 배경

AI 여럿이 도구를 나란히 부르거나 화면 여럿이 위젯을 한꺼번에 부르면, 요청은 DB 연결 풀(워커마다 15)을 기다리다 30초
뒤 `QueuePool limit … timed out` 으로 끝났다 — 그 예외는 처리하는 곳이 없어 **500 「서버 오류」** 였다. 사람은 고장으로
읽고, AI 는 같은 요청을 곧바로 다시 보내 몰림을 키웠다. 그 사이 무거운 목록 · 통계는 DB 를 함께 붙들었다.

정적 그리기에는 이미 설치 전체의 자리(자문 잠금)가 있었다(ADR 0048) — 넘으면 몇 초 기다렸다가 429.

## 결정

1. **목록 · 통계 · 0건 진단 · 전수 집계에 같은 자리를 건다**(`readguard.take`) — 요청의 트랜잭션에서 자문 잠금
   `<이름>:<번호>` 하나를 쥐고(끝나면 풀린다), 없으면 5초 동안 다시 보고 **429 와 `Retry-After: 3`**.
2. **화면과 API 토큰은 자리가 따로다** — `read_screen`(`LIST_SLOTS`, 기본 16) · `read_token`(`LIST_SLOTS_TOKEN`, 기본 6).
   AI 가 한꺼번에 부르는 몰림이 사람의 화면 자리를 다 쥐지 않게, 화면이 위젯마다 함께 부르는 것이 AI 의 자리를 다
   쥐지 않게. 화면 쪽을 넉넉히 둔다 — 화면은 원래 여럿을 함께 부른다.
3. **DB 연결 대기 시간 초과는 503 과 `Retry-After: 5`** — 「요청이 몰려 연결을 내주지 못했다 · 바뀐 것은 없다」.
   이중화의 nginx 는 503 을 다른 서버에 다시 보낸다(그쪽이 한가하면 답이 된다).
4. **읽기는 부르는 쪽이 기다려 다시 부른다** — 화면의 API 클라이언트와 MCP 가 같은 규칙: GET 이고 `Retry-After` 가
   15초 이하면 그만큼(+ 흩뜨림 1초 안) 기다려 **두 번까지**. 쓰기는 다시 보내지 않는다(한 번 들어갔을 수 있다). 끊으면
   (화면의 `signal`) 기다리던 것도 멈춘다. 그래도 거절이면 화면은 서버의 말을, MCP 는 그 말과 `retry_after` 를 전한다
   — GUIDE 는 「하나씩, 나란히 부르지 않는다」 를 말한다.

## 대안

- **연결 풀을 키운다** — 버렸다(이번에는). 몰림을 DB 로 옮길 뿐이고, 풀 크기는 서버 사양마다 다르다. 자리가 「동시에
  무거운 읽기 몇 개」 를 정한다.
- **한 자리를 함께 쓴다** — 버렸다. AI 몇이 나란히 부르면 사람의 화면이 429 를 받는다.
- **화면은 자리를 안 쓴다** — 버렸다. 화면의 한꺼번에 부르기가 몰림의 다른 절반이다. 넉넉히 두고 기다려 다시 부르게
  해서 사람에게는 「조금 늦게 뜸」 으로 보이게 한다.

## 결과

- 몰림의 끝이 500 이 아니라 「몇 초 뒤」 다 — 화면은 대개 기다려 다시 받아 오류를 안 보인다.
- 자리를 쥐는 질의가 요청마다 하나 는다(자문 잠금, 1ms 안팎).
- 작업 · 내보내기 · 쓰기는 자리를 안 쓴다(사람이 기다리지 않거나 짧다).
