# 0026. 느린 요청 · 큰 응답 — 요청마다 걸린 시간과 크기를 남긴다

- 상태: 채택(2026-10-10 구현 — 표 `request_timings`(마이그레이션 `0073_access_timing`) · 미들웨어 ·
  API 셋 · 서버 화면 탭 · 홈 「남은 일」 두 줄. 300만 건 실측, 수치는 「결과」)
- 날짜: 2026-10-10
- 관련: `shared/access_log.py`(접근 로그 미들웨어), `shared/request_timing.py`(모아 넣기),
  `modules/server/performance.py`(집계 · 문턱 · 정리), [ADR 0002](0002-확장-지점-레지스트리.md)(「남은 일」
  레지스트리), `docs/작업-워커-설계.md`(작업의 소요 · 대기)

## 배경

사용자가 「작업에서 적용을 누르면 화면이 너무 느리다」 고 말하고 나서야, 작업 목록 API 가 한 번에 **93MB ·
4.4초**였던 것을 알았다(2026-10-09). 작업 결과에 파일의 모든 줄의 계획이 들어 있었고, 화면은 도는 작업이 있으면
그 목록을 3초마다 다시 받았다(고친 것은 `sp_job_brief`, 마이그레이션 0072).

그 수치는 그 전부터 요청마다 났다. **남는 곳이 없었다.** 접근 로그(`access_logs`)는 누가 · 어디를 · 어떤 상태로
불렀는지만 남기고 걸린 시간 · 응답 크기는 안 남긴다. 게다가 **조회(GET)는 아예 안 남긴다** — 접근 로그는 사용자
지원용이라 「무엇을 했는가」 만 적는다. 93MB 였던 것이 바로 조회였다.

운영 서버의 실제 수치로 다음 성능 문제를 사람보다 먼저 보는 자리가 필요했다.

## 결정

1. **요청마다 한 줄 — 접근 로그와 표를 가른다**(`request_timings`). 조회까지 전부 남기고, 폴링 · 헬스체크
   (`access_log._SKIP`)와 `OPTIONS` 만 뺀다. 접근 로그에 칸만 더하지 않은 까닭: 조회를 거기 넣으면 그 표가 조회로
   가득 차 정작 「누가 무엇을 했나」 를 못 찾고, 보관 기간도 다르다. 칸은 가볍게 — 받은 시각 · 메서드 ·
   **경로 틀** · 원 경로 · 상태 · 걸린 시간(ms) · 보낸 바이트 · 응답 종류 · 누가 · 요청 ID. 계정에 외래키를
   걸지 않는다(계정을 지울 때 이 표 전체를 훑게 된다).

2. **걸린 시간은 응답의 마지막 바이트를 보낼 때까지.** 미들웨어가 `http.response.body` 의 마지막 조각
   (`more_body` 가 거짓)을 **보내고 난 뒤** 잰다 — 첫 바이트까지만 재면 93MB 짜리 응답 · 스트리밍 · 내려받기가
   빠른 요청으로 보인다. 응답 뒤에 도는 백그라운드 일은 넣지 않는다. 처리 못 한 예외가 미들웨어를 지나가도
   500 으로 남긴다 — 느려서 터진 요청이 가장 보고 싶은 줄이다.

3. **경로 틀로 묶는다.** 원 경로는 객체마다 달라 묶을 수 없다. 라우터가 맞춘 라우트(`scope["route"]`)의
   `path_format` 은 **자기 라우터 안의 경로**라(FastAPI 0.141 은 포함한 라우터를 펴지 않는다 — `/api` 접두어가
   빠진다), 실제 경로에서 그 라우트가 맞춘 꼬리(틀에 값을 다시 끼운 것)를 떼고 앞을 붙인다. 맞는 라우트가 없던
   요청(SPA 받아내기 포함)은 「(없는 경로)」 하나로 모은다 — 아무 주소나 두드리는 요청이 묶음을 늘리지 않게.

4. **기록이 요청을 늦추지 않는다 — 모아서 넣는다**(`shared/request_timing.py`). 접근 로그처럼 요청마다 커밋하면
   그 DB 왕복이 이벤트 루프를 막는다(미들웨어는 루프 위에서 돈다). 줄은 메모리에 모으고, 따로 도는 스레드가
   3초마다(또는 500건이 모이면) 한 번에 넣는다. **잃어도 되는 기록이다** — 앱이 죽으면 마지막 몇 초가 사라지고,
   5만 건이 밀리면 그 뒤는 버리고 로그에 남긴다.

5. **집계는 SQL 이 한다**(`percentile_cont`). 경로 틀 · 메서드마다 호출 수 · p50 · p95 · 최대 · 평균/최대 크기,
   기간은 최근 1시간 · 24시간 · 7일. 평균 대신 p50 · p95 를 쓰는 까닭: 평균은 가끔 몹시 느린 몇 번을 묻는다.
   - **상한 100만 건**(`performance.MAX_ROWS`) — 기간의 기록이 그보다 많으면 최근 100만 건만 세고
     `capped` 로 말한다. 화면이 「최근 기록만 셌습니다」 라고 적는다.
   - 경로 틀 칸은 **글자 정렬 규칙을 C 로** 둔다 — 묶느라 통째로 정렬하는 칸이다.
   - 색인: `created_at`(기간 · 정리 · 상한 찾기), `(route, method, created_at)`(최악 사례).

6. **최악 사례** — 줄을 클릭하면 그 경로 틀의 최근 요청 가운데 가장 오래 걸린(큰 순으로 보고 있으면 가장 큰)
   20건: 누가 · 언제 · 상태 · 걸린 시간 · 크기 · 원 경로 · **요청 ID**(app.log 의 그 요청 줄로 가는 끈).

7. **작업 종류별 소요 · 대기** — 같은 화면에. `jobs` 의 `created_at → started_at`(대기) · `started_at →
   finished_at`(소요)의 p50 · p95 · 최대와 끝난 수, 그리고 **아직 대기인 것 중 가장 오래 기다린 것** — 집힌 것만
   세는 대기 시간은 워커가 멎었을 때(아무것도 안 집힐 때)를 못 본다. 오래 걸리는 일을 작업으로 옮긴 뒤 거기서
   느려지면 다시 아무도 모르게 된다.

8. **문턱을 넘으면 홈 「남은 일」**(`performance.maintenance`, `main.py` 에서 등록) — 최근 24시간에 p95 가
   `SLOW_REQUEST_P95_SECONDS`(기본 3)를 넘은 경로는 「느린 요청」, `LARGE_RESPONSE_MB`(기본 5)보다 큰 응답을
   낸 경로는 「큰 응답」, 각각 경로 수로. **시스템 관리자에게만**(고칠 수 있는 사람), `info` 로(느린 것은 고장이
   아니다 — 경고색은 멎은 것의 색이다). 잡음이 되지 않게 둘을 뺀다:
   - **파일 응답** — 대부분이 JSON 이 아닌 경로(내려받기 · 사진). 크고, 받는 쪽 회선 속도를 타는 것이 정상이다.
     화면에는 「파일」 표시와 함께 나온다.
   - **몇 번 안 불린 경로의 p95** — 24시간에 `SLOW_REQUEST_MIN_CALLS`(기본 5)번 미만이면 p95 를 안 본다.
     기동 직후 찬 캐시의 한두 번이 하루 내내 홈에 떠 있으면 그 줄은 아무도 안 읽게 된다.
   판정은 프로세스마다 5분 기억한다 — 시스템 관리자가 홈을 열 때마다 24시간을 다시 묶지 않게.

9. **보관 — `log_retention_days`(기본 30일)**. 워커가 한 시간마다(다른 정리와 함께) 지운다. 한 번에 5만 줄씩,
   한 시간에 백만 줄까지 — 보관 기간을 줄인 날 수백만 줄을 한 문장으로 지우면 워커 바퀴(박동)가 그동안 멎는다.

10. **시스템 관리자만** — 세 API 모두(`GET /api/server/performance/requests` · `…/requests/cases` · `…/jobs`).
    누가 언제 무엇을 불렀나가 함께 나간다(접근 로그와 같은 무게).

## 대안

- **접근 로그에 칸을 더한다.** 가장 적게 바뀌지만 조회가 안 남는다 — 93MB 였던 것이 조회였다. 조회까지
  남기면 접근 로그가 그것으로 찬다.
- **첫 바이트까지 잰다**(흔한 미들웨어 · 로그 형식이 그렇다). 큰 응답이 빠르게 보인다 — 이 일의 발단을 못 잡는다.
- **시간마다 미리 묶어 둔다**(경로 × 시간의 수 · 합 · 최대 · 히스토그램). 집계가 가장 싸지만 백분위는 합칠 수
  없어 어림이 되고, 최악 사례(누가 · 요청 ID)를 잃는다. 하루 10만 요청 · 7일이 0.6초라 아직 필요 없다 —
  상한(100만)에 자주 닿는 설치가 생기면 다시 본다.
- **바깥 도구(APM · Prometheus)**. 사내 설치마다 따로 깔고 지켜야 하고, 운영자가 그 화면을 따로 열어야 한다 —
  홈 「남은 일」 에 뜨지 않으면 아무도 안 본다(백업 · 동기화 실패가 같은 이유로 홈에 있다).
- **경로 틀을 해시로 묶는다 · `work_mem` 을 늘린다** — 실측에서 빨라지지 않았다(아래).

## 결과

- 개발 PC 실측(2026-10-10, 따로 만든 DB, 300만 건 · 30일 · 경로 틀 600개, 색인 포함 699MB ≈ 줄당 233바이트):
  | 기간 | 세는 줄 | 상한 찾기 | 집계(정렬 · 백분위) |
  | --- | --- | --- | --- |
  | 1시간 | 4천 | 1ms | 5ms |
  | 24시간 | 10만 | 8ms | 74ms |
  | 7일 | 70만 | 44ms | 0.59 ~ 0.78초 |
  | (상한) | 100만 | 50ms | 0.55초 |
  최악 사례(가장 많이 불린 경로, 7일 4만 줄) 70ms. 경로 틀을 C 정렬로 두니 70만 줄 묶기가 0.64 → 0.36초(JSON 판정
  없이 잰 값). `work_mem` 64 · 128MB, 해시로 묶기는 차이가 없었다 — 정렬보다 묶음마다의 백분위가 무겁다.
- 하루 10만 요청 · 30일이면 표가 약 0.7GB. 「쌓인 것」 에는 안 띄운다(셀 때마다 표를 훑는다).
- 접근 로그(`access_logs`)는 여전히 지우는 주기가 없다 — 이번에 손대지 않았다(운영 자료를 지우는 결정이라 따로).
