## 배경

0.4.107 을 낸 뒤 같은 방법으로 다시 점검했다(개발 DB 사본에 띄운 서버 · GET API 276개 · 화면 86개 · 의존성
감사 · 코드는 나눠 읽고 굵은 것은 재현). 돌아가는 쪽은 깨끗했고(5xx 0 · 깨진 화면 0 · 취약점 0), 결함은
**전날 넣은 코드**(ADR 0098 · 0099 · 0100)에 몰려 있었다 — 새 규칙이 드문 모양(대기열 · 이미 내려간 행 ·
작은 저장소 · 부서 범위)에서 비켜 가거나, 새 입구(문서 zip · 키트의 적용)가 크기 · 모양을 덜 봤다.

## 결정

### 1. 키트의 적용 — 끝난 것만 「적용함」, 대기는 거절이 아니다

- **대기열에 있는 적용을 「거절됨」 으로 적었다.** 워커가 밤 계산으로 바빠 2분을 넘기면 키트가 기다리기를
  멈추고 `apply_failed.json` 을 썼다 — 사람은 실패로 알아듣고 다시 미리 보는 사이 앞의 적용이 들어간다.
  이제 받아들여졌는데 끝을 못 본 적용은 `waiting` 이고 `applying.json` 에 적용 작업 번호를 남긴다.
  `work_status` · 다음 적용이 그 작업에 다시 물어 `applied.json`(끝남) 또는 `apply_failed.json`(실패)로
  옮긴다. 기다리는 동안 다시 미리 보기 · 닫기는 막는다. 화면 말은 「적용 대기 중」. 그 사이 **등록한 주소가
  바뀌었으면**(설치기를 다시 돌려 포털 주소로) 같은 이름의 지금 등록으로 묻는다 — 옛 주소로만 물으면 영영 대기였다.
  그 플랫폼이 등록에서 빠졌으면 실행을 닫을 수 있다. **같은 묶음(지문)이 다른 실행에서 대기 중**이어도 또 넣지
  않는다(백필의 가벼운 미리 보기는 지문이 없어 플랫폼도 못 막는다).
- **대기 중인 적용을 보고 실행을 「적용함」 으로 굳혔다.** 플랫폼은 대기 · 도는 중인 적용도 「적용한 것」
  으로 센다(`counts_as_apply` — JOBS-22 의 `applied_by`). 그것만 보고 `applied.json` 을 쓰면 그 적용이
  실패해도 실행이 영영 잠겼다. 이제 적용 작업이 **끝나 들어갔을 때만** 쓴다(화면에서 적용한 것도 같다).
  시스템 관리자가 남의 전역 계획을 화면에서 적용하면 그 적용 작업은 토큰에 안 보여(404) 키트가 「적용함」 으로
  쳤다 — 플랫폼이 계획 작업에 **그 적용의 상태**(`applied_status` — `queued` · `running` · `done`)를 싣고, 키트는
  그것으로 가른다(없는 옛 플랫폼만 예전처럼).
- **실행이 싣는 정의를 보지 않았다.** `before_apply` 는 `02-정의/ontology.json` 의 지문만 확정과 견줘, v1 을
  확정해 변환한 실행을 v2 를 확정한 뒤 넣을 수 있었다. 이제 **실행의 `ontology.json`**(보내는 것)의 내용이
  지금 확정한 정의와 같아야 한다 — 다르면 「정의가 확정된 뒤 다시 변환하세요」. 확정이 있는데 정의 파일이
  없어졌거나, 「새 정의 없음」 을 확정했는데 실행이 정의를 실으면 막는다. 허브에서 받은 실행(`source`)은 허브의
  정의라 견주지 않는다.
- **미리 본 뒤 넣을 곳을 바꾸면 옛 곳에 넣었다.** `work_platform` 으로 바꾼 뒤 「좋다」 하면 미리 본 플랫폼에
  들어갔다 — 이제 멈추고 다시 미리 보게 한다.
- **번호 · 경로를 덜 봤다.** `run_undo` 의 판 번호를 꾸미면(`<uuid>/undo?apply=true#`) 계획만 세워야 할
  도구가 되돌리기를 넣었다 — 작업 · 판 번호는 uuid 꼴만 주소에 넣는다(대문자도 받는다, `job_uuid`).
  `document_apply` 는 작업 폴더의 아무 파일이나 기록으로 받아 문서와 상관없는 계획을 적용할 수 있었다 —
  `docs/.push/<때>/push.json` 만, 작업 종류 `documents_push` · 끝난 계획 · 오류 없음을 적용 전에 본다. 대응
  파일의 `ontology` · `@keys` 경로는 작업 폴더 안만.
- **포털 로그인 화면(HTML)이 오면 날것의 오류가 났다**(「Expecting value」). 2xx 인데 JSON 이 아니면 「포털
  로그인이 끝났을 수 있다」 로 멈춘다.
- **가벼운(백필) 미리 보기에는 지문이 없다** — 안내가 있다고 적고 있었다. 안내를 고쳤다(적용 때 다시
  판정한다). 온전한 미리 보기 뒤 참조 대상이 지워지면 플랫폼의 다시 판정 · 지문(JOBS-20)이 막는 것을 시험으로
  확인했다.

### 2. 문서 올리기 — 크기 · 모양의 상한을 양쪽에서

- **그림을 찾는 정규식이 본문 길이의 제곱으로 느렸다**(`![](` 되풀이 8만 자에 31초 — 상한 100만 자면 80분).
  캡션 · 경로에서 괄호를 빼 한 번에 끝나게 했다 — 플랫폼과 키트가 같은 식이다.
- **키트가 zip 크기 · 문서 수로만 작업을 나눴다** — 플랫폼은 zip 항목을 2,000개까지 받는다. 항목 수(1,900)로도
  나눈다.
- **여러 작업으로 나뉜 올리기가 일부만 적용됐다.** 적용 전에 작업 전부의 계획을 함께 보고 하나라도 나쁘면
  아무것도 넣지 않는다. 그 뒤에도 플랫폼이 거절하면(그 사이 누가 바꿈) 어디까지 들어갔는지 말한다.
- **빈 본문이 있던 본문을 경고 없이 덮었다**(사용자 결정 2026-11-27): 키트가 막고, 정말 비우려면 그 문서에
  `allow_empty` 를 밝힌다 — 사람이 비우라고 했을 때만. 플랫폼 계획도 경고를 낸다.
- **본문의 NUL 은 적용 묶음 전체를 DB 오류로 깨뜨렸다** — 키트 · 플랫폼 모두 계획 때 오류로.
- **정규식에 안 걸리는 그림 줄**(제목 · 경로의 빈칸 · 네 자리 `?w=` · 캡션의 `]` · `/` 로 시작)이 그림 없이
  들어가는데 대조는 「같음」 이라 했다 — 키트는 올리기 전에 오류, 플랫폼은 경고. **같은 그림**(`./img/a.png` ·
  `img/a.png`, 같은 바이트)은 한 번만 붙인다. 참조식 그림(`![logo][1]`) 뒤의 링크는 그림 자리로 보지 않는다.

- **압축 폭탄이 통했다.** 목록(manifest.json)과 마크다운을 크기 상한 없이 읽어, 1MB zip 안의 1GB 목록 하나로
  워커가 메모리를 다 썼다(다시 도는 작업이라 세 번). 항목마다 적힌 크기를 먼저 보고 읽을 때도 묶는다 — 목록
  4MB, 마크다운 100만 자 × 4바이트. 넘으면 작업이 실패로 끝나거나(목록 — 다시 돌지 않는다) 그 줄이 오류다.
  본문은 계획 내내 들고 있지 않고 적용 때 zip 에서 다시 읽는다.
- **계획 줄의 경고가 키트 · 화면에서 잘렸다.** 500줄로 자를 때 오류 줄만 앞세웠다 — 경고 줄도 앞에 둔다(사진
  일괄 업로드의 「너무 큼」 도). 화면 「작업」 이 줄 아래에 경고를 적고 「확인할 것 N」 을 단다. 끝난 문서 올리기
  계획을 펼치면 「작업」 화면이 멈추던 것(결과에 `errors` 가 없음)도 고쳤다.

### 2-1. 장표 · 객체의 주소

- **장표 목록이 볼 수 없는 주제의 이름을 드러냈다**(사용자 결정): 주제 칸은 가렸지만(ADR 0098) 저장된 기본
  제목(「N12 카메라 품질 보고」)에 이름이 그대로였다. 목록에 두고 제목을 「(볼 수 없는 주제) 품질 보고」 로
  가린다(기본 꼴이 아니면 「(볼 수 없는 주제)」). 검색 `q` 도 가린 제목으로만 맞춘다(합쳐진 주제의 이긴 쪽이 또
  합쳐졌으면 질의는 못 보는 것으로 친다 — 목록은 끝까지 따라가 가리는데 검색이 한 걸음만 봐 옛 이름으로 걸렸다). 자기가 만든 장표가 목록에서
  사라지지 않는다. 후보 고르기 · 저장도 주제를 못 보면 403 이고, 저장은 쓰기 전에 거절한다.
- **부서 · 계정 화면의 「쓰인 장표」 가 404 였다**(ADR 0098 의 회귀 — 이 둘은 `objects` 에 행이 없는 시스템
  타입이다). 없는 객체 · 볼 수 없는 객체 모두 빈 목록을 준다(있는지 알리지 않는다).
- **옮긴 뒤 대상 타입의 slug 를 바꾸면 옛 주소 안내가 끊겼다.** 옮기기 기록을 slug 글자로만 이어서다. 대상은
  타입 id 로, 원 타입은 그 타입의 slug 이력(`ontology.type.rename`)과 맞춰 따라간다(감사 차례 `seq` 로 —
  개발 PC 의 시계가 뒤로 뛴 것을 실측했다). 이력 화면의 여러 단계 옮기기(`_moves`)도 가운데 타입의 slug 를
  바꾼 뒤 이어지게 타입 id 로도 잇는다.
- 메시지 「부서은 다른 표를…」 의 조사를 「은(는)」 으로.

### 3. 자동 작업의 멈춤 — 드문 모양에서 비켜 가지 않게

- **RA 소스의 「전부 안 오면 멈춤」 이 거의 늘 비켜 갔다.** 이미 「원본에서 내려감」 인 행까지 「가진 수」 로
  세어, 8건 중 1건이 내려간 소스에서 빈 응답 한 번에 나머지 7건이 내려갔다. 살아 있는 행만 센다.
- **파일 정리의 「남의 저장소 같으면 멈춤」 이 작은 저장소에서 비켜 갔다.** 훑은 수에 오늘 올린 파일 ·
  가리키는 파일이 들어 있고 바닥이 20 이라, 하루 지난 고아 16개 + 오늘 올린 1개면 16개를 지웠다(11-26 의
  개발 사고와 같은 규모). 이제 **이 DB 가 모르는 파일**(하루 지난 고아 + 오늘 올린 고아 — 남의 저장소면 오늘
  올린 것까지 모른다)을 훑은 전부와 견준다: 전부를 모르거나, 하루 지난 고아가 3개 이상이고 모르는 것이 절반을
  넘으면 멈춘다. 하루 지난 파일만과 견주면 사진 일괄 「교체」 다음 날(옛 100장이 고아, 새 100장은 아직 하루가
  안 됨) 정상 저장소가 멈췄다. 멈추면 **시스템 관리자에게
  알린다**(사용자 결정 — 「첨부 저장소의 자동 정리를 멈췄습니다」, 20시간에 한 번). 임시 파일(`_incoming`)
  정리도 함께 미루고 그것을 알림에 적는다.
- **코어 연동 키트의 정리 문턱이 옛 규칙이었다** — 10건 이하인 표는 빈 응답 한 번에 전부 비활성. 플랫폼과
  같이 「전부 안 오면 멈춤」(키트 판 2026-11-27).

### 4. 정의 — 범위 · 크기를 보는 검사

- **옮기기가 정상인 경우를 막았다.** 「옮길 것끼리 겹침」 이 값만 묶어, 대상의 키가 부서마다 유일한데도 부서
  A · B 의 「S1」 을 오류로 냈다. 대상의 범위가 부서면 부서까지 묶고, 같은 대상 객체로 병합되는 짝은 겹침에서
  뺀다(부서 → 전사 식별자의 겹침도 같다). 빈 값은 보지 않는다.
- **코어 구독이 플랫폼 칸 키 하나로 그 차례 전체를 검토 대기로 뒀다**(사용자 결정): 허브 정의에 새 `status`
  같은 속성이 있으면 **그 속성만** 정의 검토 대기로 남기고 나머지는 자동으로 들어간다(그 타입의 화면 설정도
  이번에는 그대로). 묶음 · `?source=` 의 길은 그대로 엄격하다.
- **정의 제안의 지문이 손실의 크기를 못 봤다.** ADR 0098 이 경고 속 숫자를 전부 빼 「비우는 값 1개」 가
  12,000개가 돼도 같은 계획으로 적용됐다(사용자 결정): **잃는 값의 수만** 다시 지문에 넣는다. 잃는 값이 있는
  열린 제안은 「다시 셈」 을 한 번 더 눌러야 적용된다.
- **판을 올리기 전에 세운 부서 자료 옮기기 계획은 토큰으로도 적용됐다**(표지가 없어서). 작업 종류
  (`workspace_reassign`)로도 사람만 적용하게 한다.
- LIKE 의 `_` 를 가리지 않아 이웃 slug 의 문서 · 이력을 셌다 — 가린다. 키 변경의 `.env` 알림이 이름 앞부분만
  맞아도 걸렸다 — 이름이 같을 때만.

## 대안 — 버린 것

- **대기 중인 적용을 기다리기를 늘려서 끝을 보기** — 밤 계산은 수십 분 걸린다. 도구 하나가 그만큼 잡혀
  있을 수 없고, 못 닿는 경우는 늘려도 같다. 받아들여진 것을 기록하고 다음에 묻는다.
- **장표에서 볼 수 없는 주제의 장표를 목록에서 감추기** — 자기가 만든 장표가 사라진 것처럼 보인다. 제목만
  가린다.
- **코어 구독의 그 차례 전체를 검토 대기로 두기**(지금까지) — 새 칸 하나 때문에 다른 타입이 몇 날이고 안
  들어온다. 그 속성만 남긴다.
- **파일 정리의 바닥(20)을 그대로 두기** — 하루 지난 고아 16개뿐인 저장소는 여전히 지운다. 바닥을 낮추고(3)
  오늘 올린 고아도 「모르는 것」 으로 센다.
- **하루 지난 파일만과 견주기**(처음 고친 모양) — 사진을 통째로 바꾼 다음 날 정상 저장소가 멈추고 관리자에게
  거짓 알림이 간다.

## 결과

- DB 마이그레이션 없음. 새 `.env` 값 없음. 작업 API 에 칸 하나(`applied_status`)가 늘었다.
- **잃는 값이 있는 열린 정의 제안은 「다시 셈」 을 한 번 더 누른 뒤 적용한다**(지문이 바뀐다).
- 키트는 화면 「내 정보」 에서 새로 받아야 쓰인다(도구 25개 그대로). 코어 연동 키트는 2026-11-27 판 — 받는
  쪽에 새로 나눠야 쓰인다.
