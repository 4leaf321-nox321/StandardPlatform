# 파일럿 그룹 정리 — 온톨로지를 시작하기 전에 채우는 것

이 문서를 그룹 담당자가 채우면, AI 가 이것과 [모델링 규약](../../mcp_server/guide/GUIDE.md)
(`get_guide(topic="modeling")`)을 읽고 정의 초안을 만든다. **길게 쓸 필요 없다** — 항목마다
몇 줄이면 된다. 모르는 칸은 비워 둔다.

> 채운 파일은 그룹의 작업 폴더(저장소 밖)에 둔다. 사내 정보가 git 에 섞이지 않게.

---

## 1. 그룹이 하는 일

**업무 단위로 3~7개.** 「무엇을 받아서 → 무엇을 하고 → 무엇을 내놓나」.

| 업무 이름 | 받는 것(입력) | 하는 일 | 내놓는 것(산출물) | 주기 |
| --- | --- | --- | --- | --- |
| 예: 구조 해석 의뢰 처리 | 설계팀 해석 의뢰서 | 모델링 · 해석 · 검토 | 해석 보고서(PPT), 결과 요약(엑셀) | 비정기, 월 10건 |
| | | | | |

## 2. 사람들이 자주 묻는 질문 — **가장 중요하다**

온톨로지는 **이 질문들에 답하려고** 만든다. 질문에 없는 것은 만들지 않는다. 10개 안팎,
실제로 받는 말투 그대로.

1. 예: 「작년에 ○○ 부품으로 해석한 과제가 뭐가 있었지?」
2. 예: 「이 해석 툴은 어느 과제에서 쓰고 있어?」
3. 예: 「△△ 고객사 관련 보고서 전부 보여 줘」
4.
5.

## 3. 다루는 「것들」 — 명사 목록

업무와 질문에 반복해 나오는 명사. 이것이 타입 후보다. **이미 쓰는 번호 체계가 있으면 꼭 적는다**
(식별자가 된다).

| 이름 | 무엇인가 | 번호 · 식별 체계 | 대략 몇 개 | 예시 2~3개 |
| --- | --- | --- | --- | --- |
| 예: 과제 | 해석 의뢰 한 건 | 과제번호 CAE-2026-001 | 연 120 | CAE-2026-014 |
| 예: 해석 툴 | 사용하는 소프트웨어 | 없음(이름) | 15 | Abaqus, Fluent |
| | | | | |

그리고 **그것들 사이의 연결** — 「과제는 고객사가 의뢰한다」 「보고서는 과제의 산출물이다」.

- 예: 과제 —(의뢰)→ 고객사
- 예: 과제 —(산출)→ 보고서
-

## 4. 원천 데이터 목록

**파일 종류마다 한 줄.** 샘플은 1~2개만 따로 전달한다(전체는 나중에).

| 원천 | 형식 | 대략 개수 · 크기 | 어디 있나 | 갱신 | 누가 만드나 | 샘플 |
| --- | --- | --- | --- | --- | --- | --- |
| 예: 과제 관리 대장 | 엑셀(시트 3개) | 1개, 2천 행 | 팀 공유 폴더 | 매주 | 팀장 | 대장_2026.xlsx |
| 예: 해석 보고서 | PPT | 연 120개 | 과제별 폴더 | 과제 끝날 때 | 담당자 | 보고서_CAE-2026-014.pptx |
| 예: 해석 기준서 | Word · PDF | 30개 | 문서 시스템 | 연 1회 | 품질팀 | 기준서_구조.pdf |
| | | | | | | |

엑셀이면 **시트마다 한 행이 무엇인지**(과제 한 건? 부품 하나?)와 열 이름을, 문서면 **어느 부분에
필요한 정보가 있는지**(표지의 과제번호, 3장의 결론 등)를 한 줄 덧붙인다.

## 5. 정의를 확정하고 데이터를 검토하는 사람

| 역할 | 누구 | 하는 일 |
| --- | --- | --- |
| 온톨로지 담당 | | 새 타입 · 속성 · 관계를 확정한다(미리 보기의 정의 변경을 본다) |
| 데이터 검토 | | 미해결 목록에 답하고, 미리 보기의 객체 · 관계를 확인한다 |

## 6. 민감한 것

넣으면 안 되는 정보(개인정보 · 계약 금액 · 고객 기밀)와, 볼 수 있는 사람이 제한되는 원천.
