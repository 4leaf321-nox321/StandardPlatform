# 사내 AI 지시문 — 그룹 데이터를 온톨로지로 불러올 형태로 만들기

사내 AI(대화형 · 파일 첨부)에게 그룹 원천을 맡길 때 **단계마다 붙여 넣는 지시문**이다. 도구 없이
대화만 되는 AI 를 기준으로 썼다 — 옮기는 일은 사람이 PC 에서 도구로 한다.

> **Claude Desktop · Gemini CLI 에 로컬 MCP(`sp-pipeline`)를 붙였으면 이 문서는 필요 없다.**
> AI 가 `pipeline_guide` 로 같은 절차를 받고, 조사 · 변환 · 검증을 직접 돌린다
> ([README](../README.md) 「Claude Desktop · Gemini CLI 에 붙이기」). 이 문서는 MCP 를 못 쓰는
> 채팅 AI 를 위한 것이다.

> 채운 결과(조사 답 · 정의 · 대응 파일)는 그룹의 **작업 폴더(저장소 밖)** 에 둔다.

---

## 원칙 — AI 에게 데이터를 옮기게 하지 말고, 옮기는 규칙을 만들게 한다

| 원천 | 사내 AI 가 만드는 것 | 실제로 옮기는 것 |
| --- | --- | --- |
| **엑셀 · CSV** | **정의 초안 + 대응 파일**(규칙) | `sp_table.py` 가 규칙대로 전체 행을 |
| **PPT · PDF · Word** | **추출 결과 JSON**(행 + 원문 인용) | AI 가 뽑고, 사람이 `preview` 로 확인 |

표를 AI 가 통째로 옮기면 수천 행에서 **잘리거나 값을 지어내고**, 돌릴 때마다 결과가 달라진다.
규칙 파일은 몇십 줄이라 사람이 읽고 검토할 수 있고, 몇 번 돌려도 같은 결과가 나온다.

## 흐름

```
1 원천 조사 ─▶ 2 정의 초안 ─▶ (온톨로지 담당 확정) ─▶ 3 대응 파일 ─▶ 5 PC 에서 돌리기
                                                   └▶ 4 문서 추출 ──┘
```

| 자료 | 어디 | 왜 |
| --- | --- | --- |
| 실행 폴더 · 대응 파일 형식 | [`pipeline/AGENTS.md`](../AGENTS.md) | 출력 모양의 정본 |
| 모델링 규약 | `mcp_server/guide/GUIDE.md` 의 `<!--@ modeling -->` 부터 끝까지(또는 MCP `get_guide(topic="modeling")` 결과) — 사내 AI 는 MCP 를 못 쓰니 **텍스트로 붙인다** | 무엇을 타입 · 칸 · 관계로 만드나 |
| 공통 코어 정의 | 허브 플랫폼의 정의 JSON(프로젝트 · 과제 · 개발모델 …) | 그룹 데이터가 **붙을 곳** |


## 1단계 — 원천 조사

표마다 한 번. **답은 값이 아니라 건수 · 패턴으로** 받는다 — 작업 폴더 밖으로 옮겨 의논해도 된다.

```
첨부한 원천 표를 조사해 줘. 실제 값은 적지 말고 건수·비율·형식 패턴(A=영문, 9=숫자)으로만.

1. 행 단위: 전체 행 수, 열마다 고유값 수와 빈 칸 비율, 어떤 열 조합이 행을 유일하게 만드나
2. 몇 대 몇: 식별자 후보 열끼리 1:1 / N:1 / N:M 인지 (최소/최대/평균)
3. 같은 식별자인데 행마다 값이 갈리는 열 — 몇 건, 어떤 조합에서 갈리나
4. 형식: 코드 열마다 패턴 상위 5개, 이름 안에 조각이 박혀 있으면 조각 수 분포와 조각별 값 분포
5. 고를 값: 값 종류가 20개 이하인 열의 값과 건수
6. 날짜: 날짜 열의 형식 분포, 날짜가 아닌 값(-, Skip 등)의 종류와 건수
7. 코어 대조: 과제코드·개발모델명·부품번호로 보이는 열이 있나,
   첨부한 코어 정의의 식별자 형식과 그대로 맞는 비율, 줄여 쓴 형태(앞부분만 같음)의 비율,
   전혀 다른 형태의 대표 패턴
```

- **7번이 그룹 데이터에서 가장 중요하다.** 코어에 붙을 수 있는지가 여기서 갈린다.
- 답이 애매하면 한 번 더 파고든다 — 「갈리는 행의 공통점은?」 「그 조각은 다른 열 어디에 반영되나?」.
  한 번에 끝나지 않는 것이 보통이다.

## 2단계 — 정의 초안

```
조사 결과와 첨부한 모델링 규약·코어 정의·그룹 정리 문서를 읽고,
이 그룹 데이터의 온톨로지 정의 초안을 ontology.json 형식으로 만들어 줘.

규칙:
- 코어에 이미 있는 것(프로젝트·과제·개발모델 등)은 새로 만들지 말고 참조 칸(object_ref)으로 잇는다
- 그룹 전용 타입 slug·속성 key는 <그룹코드>_ 로 시작, 영어 소문자 snake_case, 단수
  (slug 32자, key 48자 이내, 영문 소문자로 시작)
- data_type 은 text, text_long, number, date, datetime, bool, enum, url, object_ref 중 하나
- 식별자가 있는 타입은 "key_policy": "required"
- 상대가 늘 하나면 참조 칸, 연결에 뜻·근거가 있거나 여럿과 이으면 관계(relation_types)
- 계산으로 나오는 값(주차, 합계, 경과일)은 만들지 않는다
- 행마다 값이 갈리는 열은 윗단계 타입이 아니라 행 쪽 타입의 칸으로 둔다
- 원천에 없어 채울 수 없는 연결은 정의만 두고, 짐작으로 채울 계획을 세우지 않는다

출력:
1. ontology.json — {"groups": [...], "types": [...], "relation_types": [...]}
   타입: slug, label, key_policy, description, properties[key, label, data_type, enum_options,
   ref_type_slug, multi, help]
   관계: slug, label, inverse_label, src_type_slugs, dst_type_slugs, cardinality
   (one_to_one | one_to_many | many_to_one | many_to_many)
2. 판단 표: 원천 열 → 어느 타입의 어느 칸 / 버림, 그리고 이유(조사 결과의 몇 번 근거)
3. 확신하지 못한 것 — 질문과 선택지로
```

**이 결과는 온톨로지 담당이 확정한다.** 판단 표를 보고 고친 뒤 3단계로. 정의가 흔들리면 뒤가 전부
다시 돈다.

## 3단계 — 대응 파일 (표 원천)

```
확정한 ontology.json 과 원천 열 목록으로, 첨부한 AGENTS.md 「표를 규칙으로 옮기기」 형식의
대응 파일(sp-table/1)을 만들어 줘.

- types 는 참조되는 타입이 먼저
- 이 표 안의 타입을 가리키는 참조 칸은 반드시 key_of 로 (같은 대문자·공백 규칙이 적용되게)
- 코어(허브에서 받은 PLM 과제·모델)를 가리키는 칸은 column 에 match 를 붙인다
  ({"keys": "plm_model", "prefix": true} — 못 맞춘 것은 비워 넣고 보고서에 남는다)
- 코어 식별자 열은 코어 정의의 형식에 맞게 upper 등을 적용
- 날짜 열은 date, 날짜 대신 들어가는 표시(-, Skip 등)는 blank 로 비우고, 그 뜻이 필요하면
  같은 열을 map 으로 다른 칸에
- 코드 안에 조각이 박힌 열은 parsers 로. 조각은 위치로 자리를 정하고 모양·사전으로 종류를 가른다.
  두 갈래로 읽힐 수 있는 규칙이면 어떤 경우인지 말해 줘
- 검증할 수 있는 규칙(조각이 다른 열의 끝과 같아야 함, 어떤 값이면 조각이 있어야 함)이 있으면 checks 로
- "ontology" 에는 정의 파일 이름, "workspace_slug" 에는 그룹 부서 slug

출력: JSON 하나, 그리고 각 규칙이 조사 결과의 어느 답에 근거하는지 한 줄씩.
```

## 4단계 — 문서 추출 (PPT · PDF · Word)

문서 몇 개씩 나눠 맡긴다 — 한 번에 많이 주면 뒤쪽 문서를 대충 읽는다.

```
첨부한 문서에서 AGENTS.md 형식의 실행 폴더 내용을 만들어 줘.

- 문서 자체를 document 객체 한 행으로 (식별자: 문서번호, 없으면 doc-<파일 sha256 앞 12자>)
- 코어 식별자(과제코드·개발모델명 등)는 표지·파일명·머리글·결재란에서 먼저 찾는다.
  원문 그대로 적고, 짐작해서 만들거나 고쳐 쓰지 않는다
- 여러 문서에 걸쳐 묻는 것(질문 목록에 나오는 것)만 행으로 뽑고, 나머지는 문서 description 에 요약
- 뽑은 사실은 objects/<type_slug>.json 의 행으로, 문서와는 evidence 관계로 relations/ 에
- 모든 행에 _source: {"file", "page" 또는 "slide", "quote": 원문 그대로 한두 문장}, _confidence
  (원문 그대로 0.9 이상, 표·그림에서 읽음 0.7~0.9)
- 확신도 0.7 미만은 행으로 만들지 말고 unresolved.json 에 {what, question, options, _source} 로
출력: objects/*.json, relations/*.json, unresolved.json 각각의 파일 이름과 내용
```

## 5단계 — PC 에서 돌리기

```bash
# 표
python sp_table.py <대응.table.json> <원천.csv> runs/<날짜>-<무엇>
# 표 · 문서 공통
python sp_pipeline.py validate runs/<날짜>-<무엇>
python sp_pipeline.py preview  runs/<날짜>-<무엇>
python sp_pipeline.py apply    runs/<날짜>-<무엇>     # preview 를 사람이 확인한 뒤
```

막히면 **출력을 그대로 사내 AI 에게 돌려준다**:

```
대응 파일로 돌린 결과다. 보고서(table-report.txt)와 validate/preview 출력을 보고
- 못 읽은 행 · 검증 위반 · 대응 없는 값의 원인이 규칙인지 원천인지 가르고
- 규칙이면 대응 파일의 고칠 곳을, 원천이면 사람에게 물을 질문을 적어 줘
```

`table-report.txt` 는 값을 가린 패턴만 담고 있다. `preview` 출력 · `unresolved.json` 에는 **원천 값이
들어 있으니** 사내 AI 밖으로 옮기지 않는다.

## 주의

- **코어 식별자를 AI 가 만들어 내지 않게 한다.** 그럴듯하게 지은 코드는 대개 `preview` 에서 「없는
  참조」 로 막히지만, 우연히 실제 코드와 겹치면 **엉뚱한 것에 조용히 붙는다.** 지시문마다 「원문 그대로」
  를 넣은 이유다.
- **미해결을 AI 가 대신 지우지 않게 한다.** 답은 사람이 하고, 정의나 대응을 고쳐 **새 실행 폴더로** 다시
  돌린다.
- **코어를 가리키는 칸에는 `match` 를 빠뜨리지 않는다.** 없이 보내면 허브에 없거나 줄여 쓴 코드 한
  줄이 `preview` 에서 오류가 되어 **묶음 전체가 막힌다.** `match` 가 있으면 못 맞춘 것은 비워 넣고
  보고서 `[참조 대조]` 에 건수 · 패턴이 남는다 — 비율이 낮으면 넣기 전에 사람에게 보인다.
